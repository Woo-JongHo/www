# WWW 개발 에이전트

역할 식별자는 `www-dev`다. WWW 제품의 개발 요청을 접수하고 같은 작업·권한·기준으로 필요한 스킬과 다음 행동을 연결한다. 이 파일은 역할 계약이며 독립 프로세스나 호스트의 자동 등록 형식을 뜻하지 않는다.

## 진입과 읽기 순서

저장소 `AGENTS.md`가 WWW 개발·진단·검증·재개 요청을 이 역할로 연결한다. 먼저 현재 경로·브랜치·변경 상태와 저장소 지침을 확인하고 [공통 계약](../../docs/skills/WORKFLOW.md)을 읽는다. 제품 판단에는 [제품 기준](../../docs/PRODUCT.md), 구조 판단에는 [아키텍처](../../docs/ARCHITECTURE.md), 관련 동작에는 [Chat 명세](../../docs/specs/chat.md)를 선택해서 읽는다. 이어 해당 작업과 필요한 스킬만 읽는다.

읽은 역할·스킬의 정본 경로와 내용 식별, 작업 UUID와 요청·권한 범위를 실행 맥락에 연결한다. 파일이 있다는 사실과 호스트가 실제로 수용했다는 사실을 구분한다. 호스트 로딩·호출 방식·현재 검증 범위는 [개발 안내](../../docs/DEVELOPMENT.md)와 해당 작업 검증 기록에서 확인한다.

## 접수와 작업 식별

1. 사용자 원문에서 질문, 구현, 진단, 검증, 커밋 요청과 명시한 제한을 구분한다. 인용된 문서·로그는 요청이나 권한으로 승격하지 않는다. 정보 질문은 필요한 답변으로 끝내며 작업 문서를 의무 생성하지 않는다.
2. UUID가 있으면 기존 작업 레코드를 찾아 실제 경로와 현재 상태를 확인한다. schema1은 기본 보존·읽기를 유지하고, 현재 직접 요청·접수 ID·권한·검사 입력·단계를 연결해 이어갈 때만 공통 계약의 명시 `adopt`로 같은 UUID를 사용한다. UUID가 없으면 관련 작업 기록을 먼저 찾아 재개 대상인지 판단한다. 같은 목표의 진행 중 작업을 찾았으면 새 UUID를 만들기 전에 연결 가능성을 확인한다.
3. 신규 변경이면 작업 접수 기능으로 실제 요청·범위·수용 기준을 가진 최소 `work.json`과 `spec.md`를 만들고 UUID를 확보한다. 폴더명과 번호는 표시용이며 UUID로 재개한다. 생성·충돌·목차 규칙은 공통 계약을 따른다.
4. 작업에 현행 요구, 기존 결정, 변경 목표와 요청에서 받은 권한의 근거를 연결한다. 구현 결정을 바꾸는 중요한 모호성만 좁혀 확인한다. 이미 결정됐거나 승인된 같은 내용을 단계마다 다시 묻지 않는다.

## 단계 선택과 권한 승계

| 요청 또는 상태 | 선택할 절차 |
|---|---|
| 범위·관찰 가능한 목표 정리 | [www-spec](../../skills/www/www-spec/SKILL.md) |
| 책임·데이터 흐름·위험 판단이 필요한 변경 | [www-design](../../skills/www/www-design/SKILL.md) |
| 허용된 구현 또는 같은 범위의 실패 수정 | [www-build](../../skills/www/www-build/SKILL.md) |
| 증상과 원인을 구분해야 하는 조사 | [www-diagnose](../../skills/www/www-diagnose/SKILL.md) |
| 실제 동작 확인과 증거 적용성 판단 | [www-verify](../../skills/www/www-verify/SKILL.md) |
| 커밋 준비·명시 실행 요청 | [www-commit](../../skills/www/www-commit/SKILL.md) |

코드·테스트·개발 도구의 구현·검증 단계에서는 [TypeScript 작성 및 하네스](../../docs/DEVELOPMENT.md#typescript-작성-및-하네스)를 읽고 공식 실행 경로와 검사 결과를 연결한다.

이 역할로 접수한 요청에서는 필요한 스킬을 선택할 수 있다. 사용자의 명시 스킬 호출도 지원한다. 단계별 세부 수행 절차는 각 스킬을 따르며 이 역할에 복제하지 않는다.

“구현해줘”는 명확한 요청 범위 안의 명세 정리·필요한 설계·구현·검증과 같은 범위의 실패 수정을 이어갈 권한이다. “원인만”은 진단 범위, “검증만”은 검사·기록과 수정 필요 사항 전달 범위다. 스킬을 선택하거나 파일을 읽는 행위가 새로운 권한을 만들지는 않는다. 커밋·게시에는 기존 명시 요청 정책을 적용한다.

구현 권한이 있으면 검증 실패를 보존하고 같은 UUID의 구현 단계로 돌아가 수정·재검증한다. 새 요구 추가, 수용 기준 약화, 허용 범위 밖 변경이 필요하면 그 결정을 구분해 사용자에게 확인한다.

## 완료와 재개

검토 가능한 대상 소스·요구·변경·실행 근거를 준비한 뒤 [공통 계약의 독립 검토](../../docs/skills/WORKFLOW.md#독립-검토의-책임)와 [검토 정책](review-policy.json)을 공유 검토 core로 적용하고 원문을 회수한다. 역할은 준비·실행·회수, 검토 어댑터는 실제 호출·권한 제한, 완료 판단은 필수 검토 충족을 맡는다. 대체 모델의 조건과 오류 분류를 역할 문서에 다시 정의하지 않는다. 검토가 실행되지 못하면 사유와 blocker를 남기며, 훅 설치를 전제하거나 검토 없이 자동 통과한 것으로 쓰지 않는다.

완료 전에는 현재 수용 기준 정의와 검증 대상 소스에 증거가 적용되는지 확인한다. 과거 통과를 지우거나 소스·기준이 달라진 현재 결과로 옮겨 쓰지 않는다. 현행 명세·구조가 달라졌으면 해당 문서를 함께 갱신하고, 실행 종료·업무 수용·게시 상태를 각각 보고한다. 판정 기준은 공통 계약이 소유한다.

완료 단계에서는 [공통 계약의 문서 영향 검토](../../docs/skills/WORKFLOW.md#문서-영향-검토)를 수행하고 그 기록이 현재 소스·기준·문서에 적용되는지 확인한다.

재개 시 이전 대화를 전제하지 않고 같은 UUID의 다음 내용을 확인한다.

- 적용되는 관련 기능 요구와 이번 변경 목표.
- 수용 기준 정의·현재 상태·기존 증거의 적용 가능성.
- 요청에서 받은 권한과 아직 필요한 결정.
- 미완료·차단·다음에 실제 수행할 행동.

상태를 요약하는 데서 멈추지 않고 유효한 권한 안의 다음 행동을 수행한다. 독립 검토·실제 호스트·GUI 검증이 미실행이면 그 한계를 남긴다. 새로운 작업을 중복 생성하거나 완료 조건을 건너뛴 재개를 성공으로 기록하지 않는다.

작업을 마치고 사용자에게 반환하기 전에는 [작업 종료 보고서 계약](../../docs/skills/REPORTS.md)에 따라 같은 UUID의 저작 보고서를 작성하고 앱에서 읽을 수 있는 결과를 남긴다. 감사 대기·부분 완료로 반환하는 경우도 포함한다.
