# 테스트 주도 개발

TDD는 빨강 → 초록 반복 과정입니다. 이 스킬은 그 반복 과정에서 보존할 가치가 있는 테스트를 만들기 위한 참고 자료입니다. 좋은 테스트란 무엇인지, 테스트를 어디에 두는지, 안티패턴은 무엇인지, 반복 과정의 규칙은 무엇인지 설명합니다. 모든 절은 매 주기마다 적용됩니다. 반복 과정이 끝난 뒤가 아니라 시작 전과 진행 중에 참고하세요.

코드베이스를 탐색할 때는 `GLOSSARY.md`가 있다면 읽어서 테스트 이름과 인터페이스 어휘를 프로젝트의 도메인 언어에 맞추고, 작업하는 영역의 ADR을 준수하세요.

## 좋은 테스트란 무엇인가

테스트는 구현 세부 사항이 아니라 공개 인터페이스를 통해 동작을 검증합니다. 코드는 완전히 바뀔 수 있지만 테스트는 그러면 안 됩니다. 좋은 테스트는 명세처럼 읽힙니다. "사용자는 유효한 장바구니로 결제할 수 있다"는 어떤 기능이 존재하는지 정확히 알려 주며, 내부 구조에 신경 쓰지 않으므로 리팩터링 후에도 유지됩니다.

예시는 [tests.md](tests.md)를, 모킹 지침은 [mocking.md](mocking.md)를 참조하세요.

## 심: 테스트를 두는 곳

**심(seam)**은 테스트가 이루어지는 공개 경계입니다. 내부에 접근하지 않고 동작을 관찰하는 인터페이스입니다. 테스트는 심에 두며, 내부 구현을 대상으로 두지 않습니다.

**사전에 합의한 심에서만 테스트하세요.** 테스트를 작성하기 전에 테스트할 심을 적고 사용자에게 확인받으세요. 확인되지 않은 심에는 테스트를 작성하지 않습니다. 모든 것을 테스트할 수는 없으므로, 심을 미리 합의해야 테스트 노력이 모든 극단적 사례가 아니라 핵심 경로와 복잡한 로직에 집중됩니다.

다음과 같이 질문하세요. "공개 인터페이스는 무엇이며 어떤 심을 테스트해야 합니까?" 제안하는 각 심에 무엇을 포착하고 무엇을 놓치는지 한 줄로 설명하세요.

그 인터페이스의 형태 자체가 쟁점일 때는(모듈이 얼마나 깊은지, 심이 어디에 속하는지, 인터페이스가 무엇을 노출해야 하는지) 어휘를 확인하기 위해 Skill 도구를 "codebase-design"으로 호출하세요. 이는 모듈, 인터페이스, 깊이, 심, 어댑터, 레버리지, 국소성 용어의 공유 출처이며, 실행할 세션이 아니라 참고할 자료입니다.

## 안티패턴

- **구현 결합**: 내부 협력자를 모킹하거나, 비공개 메서드를 테스트하거나, 우회 경로를 통해 검증합니다(인터페이스를 사용하는 대신 데이터베이스를 조회하는 경우). 징후는 동작이 바뀌지 않았는데 리팩터링하면 테스트가 깨지는 것입니다.
- **동어 반복**: 단언이 코드와 같은 방식으로 기댓값을 다시 계산하므로(`expect(add(a, b)).toBe(a + b)`, 같은 방식으로 직접 도출한 스냅샷, 자기 자신과 같다고 단언하는 상수), 구조상 통과하며 코드와 불일치할 수 없습니다. 기댓값은 정상임을 아는 리터럴, 풀이가 있는 예시, 명세처럼 독립된 진실의 출처에서 가져와야 합니다.
- **수평 분할**: 모든 테스트를 먼저 작성한 다음 모든 구현을 작성합니다. 대량의 테스트는 _상상한_ 동작을 검증합니다. 사용자 대면 동작이 아니라 사물의 _형태_를 테스트하고, 테스트는 실제 변경에 둔감해지며, 구현을 이해하기 전에 테스트 구조에 전념하게 됩니다. 대신 **수직 분할**로 작업하세요. 테스트 하나 → 구현 하나 → 반복의 순서로 진행하며, 각 테스트는 이전 주기에서 배운 내용에 반응하는 **예광탄**입니다.

## 반복 과정의 규칙

- **초록보다 빨강이 먼저입니다.** 실패하는 테스트를 먼저 작성한 다음, 통과하는 데 필요한 만큼의 코드만 작성하세요. 향후 테스트를 미리 예상하거나 추측성 기능을 추가하지 마세요.
- **한 번에 한 조각씩 진행하세요.** 주기마다 심 하나, 테스트 하나, 최소 구현 하나를 다룹니다.
- **리팩터링은 반복 과정의 일부가 아닙니다.** 리팩터링은 빨강 → 초록 구현 주기가 아니라 검토 단계에 속합니다(`code-review` 스킬 참조).
