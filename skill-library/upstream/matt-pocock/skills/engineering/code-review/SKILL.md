> 한국어 번역본: 고정 커밋 `4ae2317ddb22b046e26455e4f9c9b3aaaf62212d`의 원문을 한국어로 번역해 수정했습니다. 출처·원문 해시·라이선스는 `skill-library/sources.json`과 `skill-library/inventory.json`에 기록합니다.


`HEAD`와 사용자가 제공한 고정 지점 사이의 diff를 두 축으로 검토합니다.

- **표준**: 코드가 이 저장소에 문서화된 코딩 표준을 준수하는가?
- **명세**: 코드가 원래 이슈/명세를 충실히 구현하는가?

두 축은 서로의 맥락을 오염시키지 않도록 **병렬 하위 에이전트**로 실행한 다음, 이 스킬이 결과를 종합합니다. 모든 하위 에이전트는 새로운 컨텍스트 창으로 시작하세요.

이슈 트래커가 제공되어 있어야 합니다. 제공되지 않았다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 안내하세요.

## 절차

### 1. 고정 지점 확정

사용자가 말한 대상이 무엇이든 고정 지점입니다(커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5` 등). 지정하지 않았다면 물어보세요.

diff 명령을 한 번 기록하세요. `git diff <fixed-point>...HEAD`(점 세 개를 사용하여 병합 기준점과 비교). `git log <fixed-point>..HEAD --oneline`으로 커밋 목록도 기록하세요.

더 진행하기 전에 고정 지점이 해석되는지(`git rev-parse <fixed-point>`)와 diff가 비어 있지 않은지 확인하세요. 잘못된 참조나 빈 diff는 두 병렬 하위 에이전트 안이 아니라 여기서 실패해야 합니다.

### 2. 명세 출처 식별

다음 순서로 원래 명세를 찾으세요.

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등). 트래커 문서의 워크플로로 가져옵니다.
2. 사용자가 인자로 전달한 경로.
3. 브랜치 이름이나 기능과 일치하는 `docs/`, `specs/`, `.scratch/` 아래의 명세 파일.
4. 아무것도 찾지 못했다면 명세가 어디 있는지 사용자에게 물으세요. 명세가 없다고 하면 **명세** 하위 에이전트는 건너뛰고 "사용 가능한 명세 없음"이라고 보고합니다.

### 3. 표준 출처 식별

코드를 어떻게 작성해야 하는지 문서화한 모든 파일을 저장소에서 찾으세요. `CODING_STANDARDS.md` 또는 `CONTRIBUTING.md`가 있으면 반드시 목록에 포함해야 합니다.

저장소가 문서화한 내용에 더해, 표준 축에는 항상 아래의 **코드 냄새 기준선**이 적용됩니다. 저장소가 아무것도 문서화하지 않았을 때도 적용되는 Fowler의 고정된 코드 냄새 모음(_Refactoring_, 3장)입니다. 두 가지 규칙이 적용됩니다.

- **저장소가 우선합니다.** 문서화된 저장소 표준이 항상 우선합니다. 기준선이 지적할 내용을 저장소 표준이 승인한다면 해당 냄새를 억제하세요.
- **항상 판단의 문제입니다.** 각 냄새는 명확한 위반이 아니라 레이블이 붙은 휴리스틱(예: "Feature Envy 가능성")입니다. 여기의 다른 표준과 마찬가지로 도구가 이미 강제하는 내용은 건너뛰세요.

각 냄새는 *무엇인가* → *어떻게 고치는가* 순으로 설명합니다. diff와 대조하세요.

- **Mysterious Name**: 무엇을 하거나 담는지 이름으로 드러나지 않는 함수, 변수 또는 타입. → 이름을 바꾸세요. 정직한 이름을 지을 수 없다면 설계가 불분명한 것입니다.
- **Duplicated Code**: 변경의 둘 이상의 헝크나 파일에 동일한 형태의 로직이 나타남. → 공통 형태를 추출하고 양쪽에서 호출하세요.
- **Feature Envy**: 자기 데이터보다 다른 객체의 데이터에 더 많이 접근하는 메서드. → 메서드를 그 메서드가 탐내는 데이터 쪽으로 옮기세요.
- **Data Clumps**: 동일한 몇 개의 필드나 매개변수가 계속 함께 이동함(새 타입이 생겨나려는 상태). → 하나의 타입으로 묶어 전달하세요.
- **Primitive Obsession**: 자체 타입이 필요한 도메인 개념을 원시값이나 문자열이 대신함. → 개념에 작고 독립적인 타입을 부여하세요.
- **Repeated Switches**: 동일한 타입에 관한 같은 `switch`/`if` 연쇄가 변경 전반에서 반복됨. → 다형성이나 두 위치가 공유하는 하나의 맵으로 대체하세요.
- **Shotgun Surgery**: 하나의 논리적 변경 때문에 diff의 여러 파일을 흩어져 수정해야 함. → 함께 바뀌는 것을 하나의 모듈로 모으세요.
- **Divergent Change**: 하나의 파일이나 모듈이 서로 관련 없는 여러 이유로 수정됨. → 각 모듈이 한 가지 이유로 바뀌도록 분리하세요.
- **Speculative Generality**: 명세에 없는 필요를 위해 추상화, 매개변수 또는 훅을 추가함. → 삭제하세요. 실제 필요가 나타날 때까지 다시 인라인하세요.
- **Message Chains**: 호출자가 의존해서는 안 되는 긴 `a.b().c().d()` 탐색. → 첫 번째 객체의 메서드 하나 뒤로 탐색을 숨기세요.
- **Middle Man**: 대부분 다음 대상으로 위임하기만 하는 클래스나 함수. → 제거하고 실제 대상을 직접 호출하세요.
- **Refused Bequest**: 상속받은 내용 대부분을 무시하거나 재정의하는 하위 클래스 또는 구현체. → 상속을 없애고 합성을 사용하세요.

### 4. 두 하위 에이전트를 병렬로 생성

두 하위 에이전트 호출을 포그라운드에서 함께 실행하고, 반환된 보고서를 종합하세요.

**표준 하위 에이전트 프롬프트**에는 다음을 포함해야 합니다.

- 전체 diff 명령과 커밋 목록.
- 3단계에서 찾은 표준 출처 파일 목록과 **3단계의 코드 냄새 기준선 전문**(하위 에이전트는 달리 접근할 수 없음).
- 지시 사항: "관련된 경우 파일/헝크별로 (a) diff가 문서화된 표준을 위반한 모든 위치를 표준(파일 + 규칙)을 인용해 보고하고, (b) 발견한 모든 기준선 코드 냄새의 이름을 밝히고 헝크를 인용하세요. 명확한 위반과 판단 사항을 구분하세요. 문서화된 표준 위반은 명확할 수 있지만 기준선 코드 냄새는 항상 판단 사항이며, 문서화된 저장소 표준이 기준선보다 우선합니다. 도구가 강제하는 내용은 건너뛰세요. 400단어 이내."

**명세 하위 에이전트 프롬프트**에는 다음을 포함해야 합니다.

- diff 명령과 커밋 목록.
- 명세의 경로 또는 가져온 내용.
- 지시 사항: "(a) 명세가 요청했지만 누락되었거나 일부만 구현된 요구 사항, (b) diff에 있지만 요청되지 않은 동작(범위 확장), (c) 구현된 것으로 보이지만 구현이 잘못된 것 같은 요구 사항을 보고하세요. 각 발견 사항에 대해 명세의 줄을 인용하세요. 400단어 이내."

명세가 없으면 명세 하위 에이전트를 건너뛰고 최종 보고서에 이를 기록하세요.

### 5. 종합

두 보고서를 `## Standards` 및 `## Spec` 제목 아래에 그대로 또는 가볍게 정리하여 제시하세요. 두 축은 의도적으로 분리되어 있으므로 발견 사항을 합치거나 순위를 다시 매기지 **마세요**(_두 축을 사용하는 이유_ 참조).

축별 전체 발견 사항 수와 각 축에서 가장 심각한 문제(있는 경우)를 한 줄로 요약하며 끝내세요. 축을 가로질러 하나의 최우선 문제를 고르지 마세요. 그렇게 하면 분리한 결과의 순위를 다시 매기게 됩니다.

## 두 축을 사용하는 이유

변경은 한 축을 통과하고 다른 축에서는 실패할 수 있습니다.

- 모든 표준을 따르지만 잘못된 것을 구현한 코드 → **표준 통과, 명세 실패.**
- 이슈가 요청한 것을 정확히 수행하지만 프로젝트 관례를 어긴 코드 → **명세 통과, 표준 실패.**

따로 보고하면 한 축이 다른 축을 가리는 일을 막을 수 있습니다.
