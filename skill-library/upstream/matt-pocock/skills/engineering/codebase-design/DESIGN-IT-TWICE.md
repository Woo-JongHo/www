# 두 번 설계하기

사용자가 선택한 심화 후보에 대한 대안 인터페이스를 탐색하려 할 때 이 병렬 하위 에이전트 패턴을 사용하세요. "Design It Twice"(Ousterhout)를 바탕으로 합니다. 첫 번째 아이디어가 최선일 가능성은 낮습니다.

[SKILL.md](SKILL.md)의 어휘인 **모듈**, **인터페이스**, **심**, **어댑터**, **레버리지**를 사용합니다.

## 절차

### 1. 문제 공간의 틀 잡기

하위 에이전트를 생성하기 전에 선택한 후보의 문제 공간을 사용자에게 설명하는 글을 작성하세요.

- 모든 새 인터페이스가 충족해야 할 제약 조건
- 의존할 대상과 각 대상이 속하는 범주([DEEPENING.md](DEEPENING.md) 참조)
- 제약 조건에 구체성을 부여하기 위한 대략적인 예시 코드 스케치. 제안이 아니라 제약 조건을 구체적으로 만드는 수단일 뿐입니다

사용자에게 이를 보여준 다음 즉시 2단계로 진행하세요. 하위 에이전트가 병렬로 작업하는 동안 사용자는 읽고 생각합니다.

### 2. 하위 에이전트 생성

3개 이상의 하위 에이전트를 각각 새로운 컨텍스트 창에서 병렬로 생성하세요. 각 에이전트는 심화된 모듈에 대해 **근본적으로 다른** 인터페이스를 만들어야 합니다.

각 하위 에이전트에는 별도의 기술 개요(파일 경로, 결합 세부 사항, [DEEPENING.md](DEEPENING.md)의 의존성 범주, 심 뒤에 있는 내용)를 프롬프트로 제공하세요. 개요는 1단계에서 사용자에게 설명한 문제 공간과 독립적입니다. 에이전트마다 서로 다른 설계 제약을 부여하세요.

- 에이전트 1: "인터페이스를 최소화하세요. 진입점을 최대 1~3개로 제한하고 진입점당 레버리지를 극대화하세요."
- 에이전트 2: "유연성을 극대화하세요. 많은 사용 사례와 확장을 지원하세요."
- 에이전트 3: "가장 일반적인 호출자에 최적화하세요. 기본 사례를 아주 단순하게 만드세요."
- 에이전트 4(해당하는 경우): "심를 가로지르는 의존성을 포트와 어댑터 중심으로 설계하세요."

각 하위 에이전트가 아키텍처 언어와 프로젝트의 도메인 언어에 맞춰 일관되게 이름을 붙이도록 개요에 [SKILL.md](SKILL.md)의 어휘와 GLOSSARY.md의 어휘를 모두 포함하세요.

각 하위 에이전트는 다음을 출력합니다.

1. 인터페이스(타입, 메서드, 매개변수와 불변 조건, 순서, 오류 방식)
2. 호출자가 인터페이스를 사용하는 방법을 보여주는 사용 예시
3. 구현이 심 뒤에 숨기는 내용
4. 의존성 전략과 어댑터([DEEPENING.md](DEEPENING.md) 참조)
5. 절충점: 레버리지가 높은 곳과 약한 곳

### 3. 제시하고 비교하기

사용자가 각 설계를 이해할 수 있도록 차례로 제시한 다음 산문으로 비교하세요. **깊이**(인터페이스의 레버리지), **국소성**(변경이 집중되는 곳), **심 배치**를 기준으로 대조하세요.

비교한 뒤 어떤 설계가 가장 강력하다고 생각하는지와 그 이유를 직접 추천하세요. 서로 다른 설계의 요소를 결합하면 좋다면 혼합안을 제안하세요. 단호한 견해를 제시하세요. 사용자는 선택지가 나열된 메뉴가 아니라 강한 판단을 원합니다.
