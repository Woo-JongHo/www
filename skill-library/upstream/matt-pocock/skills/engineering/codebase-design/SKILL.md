# 코드베이스 설계

**깊은 모듈**을 설계하세요. 작은 인터페이스 뒤에 많은 동작을 두고, 깔끔한 심에 배치하며, 그 인터페이스를 통해 테스트할 수 있어야 합니다. 코드를 설계하거나 재구성하는 모든 곳에서 이 언어와 원칙을 사용하세요. 목표는 호출자에게 레버리지를, 유지보수자에게 국소성을, 모두에게 테스트 용이성을 제공하는 것입니다.

## 용어집

이 용어들을 정확히 사용하세요. "component", "service", "API", "boundary"로 바꾸지 마세요. 일관된 언어를 사용하는 것 자체가 핵심입니다.

**모듈(Module)**: 인터페이스와 구현이 있는 모든 것. 의도적으로 규모를 특정하지 않습니다. 함수, 클래스, 패키지 또는 여러 계층에 걸친 슬라이스일 수 있습니다. _피할 말_: unit, component, service.

**인터페이스(Interface)**: 호출자가 모듈을 올바르게 사용하기 위해 알아야 하는 모든 것. 타입 시그니처뿐 아니라 불변 조건, 순서 제약, 오류 양상, 필수 설정, 성능 특성도 포함합니다. _피할 말_: API, signature(너무 좁으며 타입 수준의 표면만 가리킵니다).

**구현(Implementation)**: 모듈 안에 있는 것, 즉 코드 본문입니다. **어댑터(Adapter)**와는 다릅니다. 어떤 것은 구현이 큰 작은 어댑터(Postgres 저장소)일 수도 있고, 구현이 작은 큰 어댑터(인메모리 페이크)일 수도 있습니다. 심이 주제라면 "adapter"를, 그 밖의 경우에는 "implementation"을 사용하세요.

**깊이(Depth)**: 인터페이스에서 얻는 레버리지. 호출자(또는 테스트)가 학습해야 하는 인터페이스 단위당 실행할 수 있는 동작의 양입니다. 작은 인터페이스 뒤에 많은 동작이 있으면 모듈이 **깊고(deep)**, 인터페이스가 구현만큼이나 복잡하면 **얕습니다(shallow)**.

**심(Seam)** _(Michael Feathers)_: 그 위치를 편집하지 않고도 동작을 바꿀 수 있는 곳으로, 모듈의 인터페이스가 존재하는 *위치*입니다. 심을 어디에 둘지는 그 뒤에 무엇을 둘지와 구별되는 독립적인 설계 결정입니다. _피할 말_: boundary(DDD의 bounded context 의미까지 겹쳐 있습니다).

**어댑터(Adapter)**: 심에서 인터페이스를 충족하는 구체적인 대상입니다. 실체(안에 무엇이 있는지)가 아니라 *역할*(어떤 자리를 채우는지)을 설명합니다.

**레버리지(Leverage)**: 호출자가 깊이로부터 얻는 것. 학습하는 인터페이스 단위당 더 많은 기능입니다. 하나의 구현이 N개의 호출 지점과 M개의 테스트 전반에서 보답합니다.

**국소성(Locality)**: 유지보수자가 깊이로부터 얻는 것. 변경, 버그, 지식, 검증이 호출자 전반에 퍼지지 않고 한곳에 집중됩니다. 한 번 고치면 모든 곳이 고쳐집니다.

## 깊음과 얕음

**깊은 모듈** = 작은 인터페이스 + 많은 구현:

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**얕은 모듈** = 큰 인터페이스 + 적은 구현(피할 것):

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

인터페이스를 설계할 때 다음을 물어보세요.

- 메서드 수를 줄일 수 있는가?
- 매개변수를 단순화할 수 있는가?
- 더 많은 복잡성을 내부에 숨길 수 있는가?

## 원칙

- **깊이는 구현이 아니라 인터페이스의 속성입니다.** 깊은 모듈의 내부는 작고 모킹 가능하며 교체 가능한 부분들로 구성될 수 있습니다. 단지 그 부분들이 인터페이스에 속하지 않을 뿐입니다. 모듈에는 인터페이스의 **외부 심**뿐 아니라 **내부 심**(구현 전용이며 자체 테스트에서 사용)도 있을 수 있습니다.
- **삭제 테스트.** 모듈을 삭제한다고 상상해 보세요. 복잡성이 사라진다면 그 모듈은 단순 통과 계층이었습니다. 복잡성이 N개의 호출자 전반에 다시 나타난다면 그 모듈은 제 몫을 하고 있었습니다.
- **인터페이스가 테스트 표면입니다.** 호출자와 테스트는 같은 심을 통과합니다. 인터페이스 *너머*를 테스트하고 싶다면 모듈의 형태가 잘못되었을 가능성이 큽니다.
- **어댑터가 하나면 가상의 심이고, 둘이면 실제 심입니다.** 심을 사이에 두고 실제로 무언가 달라지지 않는다면 심을 도입하지 마세요.

## 테스트 용이성을 위한 설계

좋은 인터페이스는 테스트를 자연스럽게 만듭니다.

1. **의존성을 생성하지 말고 받으세요.**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **부수 효과를 만들지 말고 결과를 반환하세요.**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **작은 표면적.** 메서드가 적을수록 필요한 테스트가 적습니다. 매개변수가 적을수록 테스트 설정이 단순합니다.

## 관계

- **모듈(Module)**에는 정확히 하나의 **인터페이스(Interface)**가 있습니다(호출자와 테스트에 제시하는 표면).
- **깊이(Depth)**는 **모듈(Module)**의 속성이며, 그 **인터페이스(Interface)**를 기준으로 측정합니다.
- **심(Seam)**은 **모듈(Module)**의 **인터페이스(Interface)**가 존재하는 곳입니다.
- **어댑터(Adapter)**는 **심(Seam)**에 위치하며 **인터페이스(Interface)**를 충족합니다.
- **깊이(Depth)**는 호출자에게 **레버리지(Leverage)**를, 유지보수자에게 **국소성(Locality)**을 만들어 줍니다.

## 채택하지 않은 관점

- **구현 줄 수와 인터페이스 줄 수의 비율로 보는 깊이**(Ousterhout): 구현을 불필요하게 늘리는 데 보상을 줍니다. 대신 깊이를 레버리지로 봅니다.
- **"Interface"를 TypeScript의 `interface` 키워드나 클래스의 public 메서드로 보는 관점**: 너무 좁습니다. 여기서 인터페이스는 호출자가 알아야 하는 모든 사실을 포함합니다.
- **"Boundary"**: DDD의 bounded context 의미까지 겹쳐 있습니다. **seam** 또는 **interface**라고 하세요.
