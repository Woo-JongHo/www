# 점진적 구현

## 개요

얇은 수직 단위로 만든다. 한 부분을 구현하고 테스트하고 검증한 뒤 확장한다. 전체 기능을 한 번에 구현하지 않는다. 각 증분은 시스템을 작동하고 테스트할 수 있는 상태로 남겨야 한다. 큰 기능을 다룰 수 있게 하는 실행 규율이다.

## 사용 시점

- 여러 파일에 걸친 변경을 구현할 때
- 작업 분해를 바탕으로 새 기능을 만들 때
- 기존 코드를 리팩터링할 때
- 테스트하기 전에 약 100줄 넘게 쓰고 싶어질 때

**사용하지 않을 때:** 범위가 이미 최소인 단일 파일, 단일 함수 변경.

## 증분 주기

```
┌──────────────────────────────────────┐
│                                      │
│   구현 ──→ 테스트 ──→ 검증 ─────┐    │
│     ▲                          │    │
│     └───── 커밋 ◄──────────────┘    │
│              │                       │
│              ▼                       │
│          다음 단위                   │
│                                      │
└──────────────────────────────────────┘
```

각 단위에 대해:

1. 완결된 가장 작은 기능을 **구현**한다
2. **테스트** — 테스트 모음을 실행한다(없으면 테스트를 작성한다)
3. **검증** — 예상대로 작동하는지 확인한다(테스트 통과, 빌드 성공, 수동 확인)
4. **커밋** -- 설명적인 메시지로 진행 상황을 저장한다(원자적 커밋 지침은 `git-workflow-and-versioning` 참조)
5. **다음 단위로 이동** — 이어서 진행하며 처음부터 다시 시작하지 않는다

## 분할 전략

### 수직 분할(권장)

스택 전체를 통과하는 완전한 경로 하나를 만든다:

```
단위 1: 작업 생성(DB + API + 기본 UI)
    → 테스트 통과, 사용자가 UI에서 작업을 만들 수 있음

단위 2: 작업 목록(쿼리 + API + UI)
    → 테스트 통과, 사용자가 자신의 작업을 볼 수 있음

단위 3: 작업 편집(갱신 + API + UI)
    → 테스트 통과, 사용자가 작업을 수정할 수 있음

단위 4: 작업 삭제(삭제 + API + UI + 확인)
    → 테스트 통과, 전체 CRUD 완성
```

각 단위는 전체 흐름에서 작동하는 기능을 전달한다.

### 계약 우선 분할

백엔드와 프런트엔드를 병렬로 개발해야 할 때:

```
단위 0: API 계약 정의(타입, 인터페이스, OpenAPI 명세)
단위 1a: 계약에 맞춰 백엔드 구현 + API 테스트
단위 1b: 계약에 맞는 모의 데이터로 프런트엔드 구현
단위 2: 통합 및 전체 흐름 테스트
```

### 위험 우선 분할

가장 위험하거나 불확실한 부분을 먼저 다룬다:

```
단위 1: WebSocket 연결이 작동함을 입증(가장 큰 위험)
단위 2: 입증된 연결 위에 실시간 작업 갱신 구현
단위 3: 오프라인 지원과 재연결 추가
```

단위 1이 실패하면 단위 2와 3에 투자하기 전에 알 수 있다.

## 구현 규칙

### 규칙 0: 단순함 우선

코드를 쓰기 전에 "작동할 수 있는 가장 단순한 것은 무엇인가?"라고 묻는다.

코드를 쓴 뒤 다음 기준으로 검토한다:
- 더 적은 줄로 할 수 있는가?
- 이 추상화는 그 복잡성을 감수할 가치가 있는가?
- 스태프 엔지니어가 보고 "왜 그냥 이렇게 하지 않았나요?"라고 하겠는가?
- 가상의 미래 요구사항을 만드는가, 현재 작업을 하는가?

```
단순함 점검:
✗ 알림 하나를 위한 미들웨어 파이프라인이 있는 범용 EventBus
✓ 단순한 함수 호출

✗ 비슷한 컴포넌트 둘을 위한 추상 팩터리 패턴
✓ 유틸리티를 공유하는 간단한 컴포넌트 둘

✗ 폼 세 개를 위한 설정 기반 폼 빌더
✓ 폼 컴포넌트 세 개
```

비슷한 코드 세 줄이 성급한 추상화보다 낫다. 먼저 단순하고 명백히 올바른 버전을 구현한다. 테스트로 정확성을 입증한 뒤에만 최적화한다.

### 규칙 0.5: 범위 규율

작업에 필요한 부분만 건드린다.

하지 말아야 할 일:
- 변경 주변 코드를 "정리"하기
- 수정하지 않는 파일의 import를 리팩터링하기
- 완전히 이해하지 못한 주석을 제거하기
- "유용해 보인다"며 명세에 없는 기능을 추가하기
- 읽기만 하는 파일의 문법을 현대화하기

작업 범위 밖에서 개선할 점을 발견하면 기록하고, 수정하지 않는다:

```
발견했지만 건드리지 않는 항목:
- src/utils/format.ts에 사용하지 않는 import가 있음(이 작업과 무관)
- 인증 미들웨어의 오류 메시지를 개선할 수 있음(별도 작업)
→ 이것들에 대한 작업을 만들까요?
```

### 규칙 1: 한 번에 한 가지

각 증분은 논리적인 한 가지를 바꾼다. 관심사를 섞지 않는다:

**나쁜 예:** 새 컴포넌트 추가, 기존 컴포넌트 리팩터링, 빌드 설정 갱신을 한 커밋에서 한다.

**좋은 예:** 변경마다 하나씩, 별도 커밋 세 개로 만든다.

### 규칙 2: 컴파일 가능한 상태 유지

각 증분 이후 프로젝트가 빌드되고 기존 테스트가 통과해야 한다. 단위 사이에 코드베이스를 깨진 상태로 두지 않는다.

### 규칙 3: 미완성 기능에는 기능 플래그

사용자에게 제공할 준비가 안 됐지만 증분을 병합해야 한다면:

```typescript
// Feature flag for work-in-progress
const ENABLE_TASK_SHARING = process.env.FEATURE_TASK_SHARING === 'true';

if (ENABLE_TASK_SHARING) {
  // New sharing UI
}
```

이렇게 하면 미완성 작업을 노출하지 않고 작은 증분을 메인 브랜치에 병합할 수 있다.

### 규칙 4: 안전한 기본값

새 코드는 기본적으로 안전하고 보수적으로 동작해야 한다:

```typescript
// Safe: disabled by default, opt-in
export function createTask(data: TaskInput, options?: { notify?: boolean }) {
  const shouldNotify = options?.notify ?? false;
  // ...
}
```

### 규칙 5: 되돌리기 쉽게

각 증분은 독립적으로 되돌릴 수 있어야 한다:

- 추가형 변경(새 파일, 새 함수)은 되돌리기 쉽다
- 기존 코드 수정은 최소화하고 초점을 유지한다
- 데이터베이스 마이그레이션에는 대응하는 롤백 마이그레이션이 있어야 한다
- 한 커밋에서 무언가를 삭제하고 대체하지 않는다. 분리한다

## 에이전트와 작업하기

에이전트에게 점진적으로 구현하도록 지시할 때:

```
"계획의 작업 3을 구현합시다.

데이터베이스 스키마 변경과 API 엔드포인트만으로 시작하세요.
UI는 아직 건드리지 마세요. 다음 증분에서 하겠습니다.

구현 후 저장소의 테스트와 빌드 명령을 실행해
깨진 것이 없는지 검증하세요."
```

각 증분의 범위에 포함되는 것과 포함되지 않는 것을 명확히 한다.

## 증분 체크리스트

각 증분 후 저장소 자체 명령으로 검증한다(test-driven-development 스킬의 스택을 먼저 파악하는 절 참조):

- [ ] 변경은 한 가지를 완결되게 수행한다
- [ ] 모든 기존 테스트가 계속 통과한다(저장소 테스트 명령: `npm test`, `./gradlew test`, `pytest`, ...)
- [ ] 빌드가 성공한다(저장소 빌드 명령)
- [ ] 해당 스택에 타입 검사가 있으면 통과한다(`npx tsc --noEmit`, `mypy`, ...)
- [ ] 린트가 통과한다(저장소 린트 명령)
- [ ] 새 기능이 예상대로 작동한다
- [ ] 설명적인 메시지로 변경을 커밋했다

**참고:** 각 검증 명령에 영향을 줄 수 있는 변경 후 해당 명령을 실행한다. 한 번 성공했다면 그 이후 코드가 바뀌지 않는 한 같은 명령을 반복하지 않는다. 바뀌지 않은 코드에서 재실행해도 정보가 늘지 않는다.

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "마지막에 전부 테스트하겠다" | 버그는 누적된다. 단위 1의 버그는 단위 2~5도 잘못되게 한다. 각 단위를 테스트한다. |
| "한 번에 다 하는 게 빠르다" | 무언가 깨져서 변경한 500줄 중 원인을 찾을 수 없게 되기 전까지만 빠르게 *느껴진다*. |
| "따로 커밋하기에는 변경이 너무 작다" | 작은 커밋은 비용이 들지 않는다. 큰 커밋은 버그를 숨기고 롤백을 어렵게 한다. |
| "기능 플래그는 나중에 추가하겠다" | 기능이 미완성이라면 사용자에게 보여서는 안 된다. 지금 플래그를 추가한다. |
| "이 리팩터링은 함께 넣어도 될 만큼 작다" | 리팩터링과 기능을 섞으면 둘 다 검토와 디버깅이 어려워진다. 분리한다. |
| "확실히 하려고 빌드 명령을 한 번 더 실행하겠다" | 성공한 뒤 코드가 바뀌지 않았다면 같은 명령을 반복해도 얻는 것이 없다. 안심하기 위해서가 아니라 후속 편집 후에 다시 실행한다. |

## 위험 신호

- 테스트를 실행하지 않고 코드를 100줄 넘게 작성하기
- 한 증분에서 관련 없는 변경 여러 개 만들기
- "이것도 금방 추가하자"는 범위 확대
- 속도를 위해 테스트/검증 단계 건너뛰기
- 증분 사이에 빌드나 테스트가 깨진 상태로 두기
- 커밋하지 않은 큰 변경을 쌓아 두기
- 세 번째 사용 사례가 요구하기 전에 추상화 만들기
- "온 김에" 작업 범위 밖 파일 건드리기
- 일회성 작업을 위한 새 유틸리티 파일 만들기
- 중간에 코드 변경 없이 같은 빌드/테스트 명령을 연속 두 번 실행하기

## 검증

작업의 모든 증분을 마친 뒤:

- [ ] 각 증분을 개별적으로 테스트하고 커밋했다
- [ ] 전체 테스트 모음이 통과한다
- [ ] 빌드가 깨끗하다
- [ ] 명세대로 기능의 전체 흐름이 작동한다
- [ ] 커밋하지 않은 변경이 남지 않았다
