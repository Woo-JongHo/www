# 코드 검토와 품질

## 개요

품질 게이트를 갖춘 다차원 코드 검토다. 모든 변경은 예외 없이 병합 전에 검토한다. 검토는 정확성, 가독성, 아키텍처, 보안, 성능의 다섯 축을 다룬다.

**승인 기준:** 완벽하지 않더라도 전반적인 코드 건전성을 확실히 높이는 변경은 승인한다. 완벽한 코드는 없으며 목표는 지속적인 개선이다. 자신이 작성했을 방식과 정확히 일치하지 않는다는 이유로 변경을 막지 않는다. 코드베이스를 개선하고 프로젝트 규칙을 따른다면 승인한다.

## 사용 시점

- PR이나 변경을 병합하기 전
- 기능 구현을 완료한 뒤
- 다른 에이전트나 모델이 만든 코드를 평가해야 할 때
- 기존 코드를 리팩터링할 때
- 버그를 수정한 뒤(수정과 회귀 테스트를 모두 검토)

## 다섯 축 검토

모든 검토는 다음 차원에서 코드를 평가한다.

### 1. 정확성

코드가 하겠다고 하는 일을 실제로 하는가?

- 명세나 작업 요구사항과 일치하는가?
- 경계 사례(null, 빈 값, 경곗값)를 처리하는가?
- 정상 경로뿐 아니라 오류 경로도 처리하는가?
- 모든 테스트를 통과하는가? 테스트가 실제로 올바른 대상을 검증하는가?
- 하나 차이 오류, 경쟁 조건, 상태 불일치가 있는가?

### 2. 가독성과 단순성

작성자의 설명 없이 다른 엔지니어나 에이전트가 이 코드를 이해할 수 있는가?

- 이름이 설명적이고 프로젝트 규칙과 일관적인가? (맥락 없이 `temp`, `data`, `result`를 사용하지 않음)
- 제어 흐름이 단순한가? (중첩 삼항식, 깊은 콜백을 피함)
- 코드가 논리적으로 구성되어 있는가? (관련 코드를 묶고 모듈 경계를 명확히 함)
- 단순화해야 할 “영리한” 기교가 있는가?
- **더 적은 줄로 구현할 수 있는가?** (100줄이면 충분한데 1000줄을 쓰는 것은 실패)
- **추상화가 복잡성만큼의 가치를 제공하는가?** (세 번째 사용 사례가 생기기 전에는 일반화하지 않음)
- 명백하지 않은 의도를 주석으로 설명하면 도움이 되는가? (명백한 코드를 주석으로 설명하지는 않음)
- 아무 일도 하지 않는 변수(`_unused`), 하위 호환 임시 코드, `// removed` 주석 같은 죽은 코드 흔적이 있는가?
- **관련 없는 흐름에 새 조건문을 덧붙였는가?** 이는 사소한 지적이 아닌 설계 문제다. 기존 경로를 얽히게 하지 말고 로직을 자체 헬퍼, 상태, 정책으로 옮긴다.
- **같은 형태를 대상으로 한 조건문이 반복되는가?** 모델이나 디스패처가 빠졌다는 신호다. “임시” 분기는 대개 영구적인 부채가 된다.

### 3. 아키텍처

변경이 시스템 설계에 맞는가?

- 기존 패턴을 따르는가, 새 패턴을 도입하는가? 새 패턴이라면 정당한 이유가 있는가?
- 모듈 경계를 명확하게 유지하는가?
- 공유해야 할 중복 코드가 있는가?
- 의존성이 올바른 방향으로 흐르는가? (순환 의존성이 없어야 함)
- 추상화 수준이 적절한가? (과도하게 설계되거나 결합되지 않아야 함)
- **이 리팩터링은 복잡성을 줄이는가, 위치만 바꾸는가?** 변경을 이해하는 독자가 기억해야 하는 개념 수를 센다. “더 깔끔한” 버전에서도 그 수가 같다면 더 깔끔해진 것이 아니다. 같은 로직을 다시 중앙으로 모으는 구조보다 분기, 모드, 계층 자체가 사라지는 구조를 선호한다. 추상화를 다듬기보다 삭제하는 편을 선호한다.
- **기능에 특화된 로직이 공용 또는 범용 모듈로 새어 나오는가?** 로직은 소유 계층에 두고, 거의 같은 헬퍼를 새로 만들지 말고 기존 정본 헬퍼를 재사용하며, 아키텍처 이탈을 정상으로 받아들이지 않는다.
- **타입 경계가 명시적인가?** 불명확한 불변식을 가리는 불필요한 `any`/`unknown`/선택적 타입/캐스트와 조용한 대체 동작을 의심한다. 경계를 명시하면 주변 제어 흐름도 단순해지는 경우가 많다.

### 4. 보안

상세한 보안 지침은 `security-and-hardening`을 참조한다. 변경이 취약점을 도입하는가?

- 사용자 입력을 검증하고 정제하는가?
- 비밀정보를 코드, 로그, 버전 관리에서 제외하는가?
- 필요한 곳에서 인증과 인가를 확인하는가?
- SQL 쿼리를 매개변수화하는가? (문자열 연결 금지)
- XSS를 막도록 출력을 인코딩하는가?
- 의존성이 알려진 취약점이 없는 신뢰할 수 있는 출처에서 왔는가?
- 외부 출처(API, 로그, 사용자 콘텐츠, 설정 파일)의 데이터를 신뢰하지 않는 데이터로 취급하는가?
- 외부 데이터 흐름을 로직이나 렌더링에 사용하기 전에 시스템 경계에서 검증하는가?

### 5. 성능

상세한 프로파일링과 최적화는 `performance-optimization`을 참조한다. 변경이 성능 문제를 도입하는가?

- N+1 쿼리 패턴이 있는가?
- 상한이 없는 루프나 제한 없는 데이터 가져오기가 있는가?
- 비동기로 해야 할 동기 작업이 있는가?
- UI 컴포넌트에서 불필요한 재렌더링이 발생하는가?
- 목록 엔드포인트에 페이지 나누기가 빠져 있는가?
- 자주 실행되는 경로에서 큰 객체를 생성하는가?

## 구조적 해결책

구조 문제를 지적할 때는 문제만 말하지 말고 어떤 이동이 필요한지 제안한다. “복잡하다”는 말만 하는 검토는 작성자가 해결책을 추측하게 만든다. 이름 붙일 수 있는 재구성 방식을 사용한다.

- **연속된 조건문을 교체한다.** 타입이 있는 모델이나 명시적인 디스패처를 사용한다.
- **중복 분기를 통합한다.** 하나의 더 명확한 흐름으로 만든다.
- **조정 로직과 비즈니스 로직을 분리한다.** 각각 독립적으로 읽을 수 있게 한다.
- **기능에 특화된 로직을 옮긴다.** 공용 모듈 밖으로, 그 개념을 소유하는 패키지에 둔다.
- **정본 헬퍼를 재사용한다.** 거의 같은 맞춤형 헬퍼를 새로 만들지 않는다.
- **타입 경계를 명시한다.** 이후의 분기가 사라지게 한다.
- **그대로 전달하는 래퍼를 삭제한다.** API를 명확히 하지 않으면서 간접 참조만 더한다면 제거한다.
- **헬퍼를 추출하거나 큰 파일을 나눈다.** 역할이 분명한 모듈로 분리한다.

같은 복잡성을 여러 곳으로 퍼뜨리는 해결책보다 움직이는 요소를 제거하는 해결책을 선호한다.

## 변경 크기

작고 집중된 변경은 검토하기 쉽고 병합이 빠르며 배포가 안전하다. 다음 크기를 목표로 한다.

```
변경 약 100줄   → 좋음. 한 번 앉아서 검토 가능.
변경 약 300줄   → 하나의 논리적 변경이라면 허용 가능.
변경 약 1000줄  → 너무 큼. 분할할 것.
```

**diff 크기뿐 아니라 파일 크기도 본다.** 작은 diff도 파일을 건전한 경계 밖으로 밀어낼 수 있다. 단일 파일의 *전체* 줄 수가 약 1000줄인 것은 흔한 점검 신호이며 엄격한 상한은 아니다. 위의 약 1000 *변경* 줄 기준과는 별개다. 이미 큰 파일을 실질적으로 더 키우는 변경이라면 더 쌓기 *전에* 헬퍼, 하위 컴포넌트, 모듈을 먼저 추출할지 묻는다. 분해한 뒤 추가한다.

**“하나의 변경”에 해당하는 것:** 하나의 문제를 해결하고 관련 테스트를 포함하며 제출 후에도 시스템이 동작하도록 유지하는 자체 완결적인 수정 하나다. 기능 전체가 아니라 기능의 일부다.

**변경이 너무 클 때의 분할 전략:**

| 전략 | 방법 | 사용 시점 |
|----------|-----|------|
| **쌓기** | 작은 변경을 제출하고 그 위에서 다음 변경을 시작 | 순차 의존성이 있을 때 |
| **파일 묶음별** | 서로 다른 검토자가 필요한 묶음을 별도 변경으로 분리 | 여러 영역에 걸친 관심사 |
| **수평 분할** | 공용 코드/스텁을 먼저 만들고 소비자를 나중에 작성 | 계층형 아키텍처 |
| **수직 분할** | 기능을 더 작은 전체 스택 조각으로 나눔 | 기능 작업 |

**큰 변경을 허용할 수 있는 경우:** 검토자가 모든 줄 대신 의도만 확인하면 되는 파일 전체 삭제와 자동 리팩터링.

**리팩터링과 기능 작업을 분리한다.** 기존 코드를 리팩터링하면서 새 동작도 추가하는 변경은 두 변경이므로 별도로 제출한다. 변수 이름 변경 같은 작은 정리는 검토자의 재량으로 포함할 수 있다.

## 변경 설명

모든 변경에는 버전 관리 이력에서 독립적으로 이해할 수 있는 설명이 필요하다.

**첫 줄:** 짧은 명령형 문장으로 독립적으로 이해할 수 있어야 한다. “FizzBuzz RPC를 삭제하는 중” 대신 “FizzBuzz RPC를 삭제하라”라고 쓴다. 이력을 검색하는 사람이 diff를 읽지 않고도 변경을 이해할 수 있을 만큼 유익해야 한다.

**본문:** 무엇을 왜 바꾸는지 쓴다. 코드 자체에서 보이지 않는 맥락, 결정, 근거를 포함한다. 관련된 버그 번호, 벤치마크 결과, 설계 문서에 연결한다. 접근에 단점이 있다면 인정한다.

**안티패턴:** “버그 수정”, “빌드 수정”, “패치 추가”, “A에서 B로 코드 이동”, “1단계”, “편의 함수 추가”.

## 검토 절차

### 1단계: 맥락 이해

코드를 보기 전에 의도를 이해한다.

```
- 이 변경은 무엇을 달성하려 하는가?
- 어떤 명세나 작업을 구현하는가?
- 기대하는 동작 변화는 무엇인가?
```

### 2단계: 테스트부터 검토

테스트는 의도와 검증 범위를 드러낸다.

```
- 변경에 대한 테스트가 있는가?
- 구현 세부사항이 아니라 동작을 테스트하는가?
- 경계 사례를 다루는가?
- 테스트 이름이 설명적인가?
- 코드가 바뀌면 테스트가 회귀를 잡아낼 수 있는가?
```

마지막 질문은 읽기만 하지 말고 실험으로 답한다. 변경에서 추가한 조건 하나를 뒤집고(부정을 제거하거나 `&&`를 `||`로 교체), 테스트 모음을 실행한 뒤 사본에서 파일을 복원한다. 변이 후에도 통과한다면 검토 결과로 기록하고 빠진 테스트 사례를 명시한다. 프로젝트 전체 변이 점수는 `constraint-driven-development`를 참조한다.

### 3단계: 구현 검토

다섯 축을 염두에 두고 코드를 따라간다.

```
변경된 각 파일에서:
1. 정확성: 테스트가 기대하는 일을 이 코드가 수행하는가?
2. 가독성: 도움 없이 이해할 수 있는가?
3. 아키텍처: 시스템에 맞는가?
4. 보안: 취약점이 있는가?
5. 성능: 병목이 있는가?
```

### 4단계: 발견 사항 분류

발견 사항을 보고하기 전에 변경 코드에 도달하는 호출자, 가드, 테스트와 대조하고, 이들이 문제 가능성을 배제한다면 제외한다. 기준 버전에 이미 존재하는 결함과 이번 변경이 도입한 회귀를 구분해 표시한다. 발견 사항이 없어도 유효한 결과이며 억지로 만들지 않는다.

작성자가 필수와 선택을 구별하도록 모든 의견에 심각도를 표시한다.

| 접두어 | 의미 | 작성자 조치 |
|--------|---------|---------------|
| *(접두어 없음)* | 필수 변경 | 병합 전에 해결해야 함 |
| **Critical:** | 병합 차단 | 보안 취약점, 데이터 손실, 기능 고장 |
| **Nit:** | 사소한 선택 사항 | 서식이나 스타일 취향 등으로 작성자가 무시할 수 있음 |
| **Optional:** / **Consider:** | 제안 | 고려할 가치가 있지만 필수는 아님 |
| **FYI** | 정보 전달만 | 조치가 필요 없으며 향후 참고할 맥락 |

이렇게 하면 작성자가 모든 피드백을 의무로 받아들여 선택 제안에 시간을 낭비하는 일을 막을 수 있다.

**중요한 것부터 말한다.** 효과가 큰 순서로 발견 사항을 나열한다. 정확성과 보안, 구조적 회귀와 놓친 단순화, 나머지 순서다. 실제 문제를 꾸미기 수준의 사소한 지적 아래 묻지 않는다. 긴 목록보다 확신할 수 있는 의견 몇 개가 낫다. 구조 문제 하나와 사소한 지적 열 개가 있다면 구조 문제가 바로 검토의 핵심이다.

### 5단계: 검증을 검증

작성자가 제시한 검증 근거를 확인한다.

```
- 어떤 테스트를 실행했는가?
- 빌드가 통과했는가?
- 수동으로 테스트했는가?
- UI 변경에 스크린샷이 있는가?
- 변경 전후 비교가 있는가?
```

## 다중 모델 검토 패턴

서로 다른 검토 관점에는 서로 다른 모델을 사용한다.

```
모델 A가 코드 작성
    │
    ▼
모델 B가 정확성과 아키텍처 검토
    │
    ▼
모델 A가 피드백 반영
    │
    ▼
인간이 최종 결정
```

모델마다 사각지대가 다르므로 단일 모델이 놓칠 수 있는 문제를 잡는다.

**검토 에이전트용 프롬프트 예시:**
```
이 코드 변경의 정확성, 보안, 프로젝트 규칙 준수 여부를 검토하라.
명세는 [X]를 요구하며 변경은 [Y]를 해야 한다.
문제에 Critical, Required, Optional, Nit 중 하나를 표시하라.
```

## 죽은 코드 정리

리팩터링이나 구현 변경 후에는 남겨진 코드를 확인한다.

1. 도달할 수 없거나 사용하지 않게 된 코드를 식별한다.
2. 명시적으로 나열한다.
3. **삭제 전에 묻는다:** “이제 사용하지 않는 다음 요소를 제거할까요: [list]?”

죽은 코드를 방치하면 이후 독자와 에이전트가 혼란스러워진다. 하지만 확실하지 않은 것을 조용히 삭제하지 않는다. 의심스러우면 묻는다.

```
식별한 죽은 코드:
- src/utils/date.ts의 formatLegacyDate() — formatDate()로 대체됨
- src/components/의 OldTaskCard 컴포넌트 — TaskCard로 대체됨
- src/config.ts의 LEGACY_API_URL 상수 — 남은 참조 없음
→ 제거해도 안전한가?
```

## 검토 속도

느린 검토는 팀 전체를 막는다. 검토를 위해 맥락을 전환하는 비용은 다른 사람에게 부과하는 대기 비용보다 작다.

- **영업일 기준 하루 안에 답한다** — 목표가 아니라 최대 시간이다.
- **이상적인 주기:** 깊이 집중해 코딩 중이 아니라면 검토 요청을 받은 직후 답한다. 일반적인 변경은 하루 안에 여러 차례 검토를 마칠 수 있어야 한다.
- **빠른 개별 응답을 우선한다.** 빠른 최종 승인보다 빠른 피드백이 중요하다. 여러 차례 검토가 필요하더라도 답이 빠르면 답답함이 줄어든다.
- **큰 변경:** 하나의 거대한 변경 묶음을 검토하지 말고 작성자에게 분할을 요청한다.

## 의견 충돌 처리

검토 의견 충돌을 해결할 때 다음 우선순위를 적용한다.

1. **기술적 사실과 데이터**는 의견과 취향보다 우선한다.
2. **스타일 가이드**는 스타일 문제에서 절대적인 기준이다.
3. **소프트웨어 설계**는 개인 취향이 아니라 공학 원칙으로 평가한다.
4. **코드베이스 일관성**은 전반적인 건전성을 해치지 않는다면 허용할 수 있다.

**“나중에 정리하겠다”는 말을 받아들이지 않는다.** 경험상 미룬 정리는 좀처럼 이루어지지 않는다. 정말 긴급한 경우가 아니면 제출 전에 정리를 요구한다. 주변 문제를 이번 변경에서 해결할 수 없다면 버그를 등록하고 작성자 자신에게 배정하도록 요구한다.

## 정직한 검토

자신, 다른 에이전트, 인간 중 누가 작성했든 코드를 검토할 때는:

- **도장만 찍지 않는다.** 검토 근거 없는 “LGTM”은 누구에게도 도움이 되지 않는다.
- **실제 문제를 약하게 표현하지 않는다.** 운영 환경에서 발생할 버그를 “사소한 우려일 수도 있다”라고 하는 것은 정직하지 않다.
- **가능하면 문제를 수치화한다.** “느릴 수 있다”보다 “이 N+1 쿼리는 목록 항목마다 약 50ms를 추가한다”가 낫다.
- **명확한 문제가 있는 접근에는 반대한다.** 비위를 맞추는 태도는 검토의 실패 방식이다. 구현에 문제가 있다면 직접 말하고 대안을 제안한다.
- **판단이 뒤집혀도 정중하게 받아들인다.** 작성자가 전체 맥락을 알고도 동의하지 않는다면 그 판단을 따른다. 사람이 아니라 코드에 의견을 낸다. 개인을 향한 비판은 코드 자체에 초점을 맞추도록 바꾼다.

## 의존성 규율

코드 검토에는 의존성 검토도 포함된다.

**의존성을 추가하기 전에:**
1. 기존 스택으로 해결할 수 있는가? (대개 가능하다.)
2. 의존성의 크기는 얼마인가? (번들 영향을 확인한다.)
3. 활발히 유지보수되는가? (마지막 커밋과 열린 이슈를 확인한다.)
4. 알려진 취약점이 있는가? (`npm audit`)
5. 라이선스는 무엇인가? (프로젝트와 호환되어야 한다.)

**규칙:** 새 의존성보다 표준 라이브러리와 기존 유틸리티를 선호한다. 모든 의존성은 부담이다.

**기존 의존성 업그레이드**도 다른 변경과 같은 코드 변경이다. “의존성 버전 올리기” 같은 메시지로 일괄 병합하는 업그레이드가 가장 위험하다. 같은 규율로 검토한다.

1. **버전 번호만 보지 말고 변경 이력을 읽는다.** Semver는 유지보수자가 지키지 않았을 수도 있는 약속이다. “패치”에도 동작 변화가 있을 수 있다. 메이저 업그레이드는 마이그레이션 지침을 읽고 무엇이 깨지는지 찾는다.
2. **변경 하나당 의존성 하나.** 개별적으로 또는 작은 관련 묶음으로 업그레이드하고 병합한다. 일괄 업그레이드로 빌드가 깨지면 원인 패키지를 놓친다. 단일 패키지 변경은 원인이 명확하고 되돌리기 쉽다.
3. **테스트로 판단한다.** 업그레이드는 “설치됐다”가 아니라 전후의 테스트 통과로 검증한다. 의존성 동작 주변의 검증 범위가 얇다면 그 공백이 실제 발견 사항이므로 먼저 테스트를 추가한다.
4. **전이 의존 그래프를 살핀다.** 설치된 패키지 대부분은 누구도 직접 선택하지 않은 것들이다. `package.json`만 보지 말고 잠금 파일 diff를 검토한다. 직접 의존성 하나를 올려도 수십 개의 간접 변경이 들어올 수 있다.
5. **잠금 파일을 정직하게 유지한다.** 커밋하고 diff를 검토하며 손으로 편집하지 않는다. 실제로 배포되는 것을 고정하는 것은 잠금 파일이다.

`npm audit` 발견 사항과 공급망 위험(타이포스쿼팅, 침해된 유지보수자)을 분류하려면 `security-and-hardening` 스킬을 따른다. 이 절은 업그레이드 *작업 흐름*을, 해당 스킬은 보안 판정을 다룬다.

## 검토 체크리스트

```markdown
## 검토: [PR/Change title]

### 맥락
- [ ] 이 변경이 무엇을 왜 하는지 이해함

### 정확성
- [ ] 변경이 명세/작업 요구사항에 맞음
- [ ] 경계 사례를 처리함
- [ ] 오류 경로를 처리함
- [ ] 테스트가 변경을 충분히 검증함

### 가독성
- [ ] 이름이 명확하고 일관됨
- [ ] 로직이 단순함
- [ ] 불필요한 복잡성이 없음

### 아키텍처
- [ ] 기존 패턴을 따름
- [ ] 불필요한 결합이나 의존성이 없음
- [ ] 추상화 수준이 적절함
- [ ] 리팩터링이 복잡성을 옮기는 대신 줄임
- [ ] 공용 모듈에 기능 로직이 없고 파일 크기가 건전한 수준임

### 보안
- [ ] 코드에 비밀정보가 없음
- [ ] 경계에서 입력을 검증함
- [ ] 주입 취약점이 없음
- [ ] 인증/인가 확인이 있음
- [ ] 외부 데이터를 신뢰하지 않는 데이터로 취급함

### 성능
- [ ] N+1 패턴이 없음
- [ ] 상한 없는 작업이 없음
- [ ] 목록 엔드포인트에 페이지 나누기가 있음

### 검증
- [ ] 테스트 통과
- [ ] 빌드 성공
- [ ] 해당하는 경우 수동 검증 완료

### 판정
- [ ] **승인** — 병합할 준비가 됨
- [ ] **변경 요청** — 문제를 해결해야 함
```

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "동작하니 충분하다" | 읽기 어렵거나 안전하지 않거나 아키텍처가 잘못된 작동 코드는 누적되는 부채를 만든다. |
| "내가 작성했으니 올바르다는 것을 안다" | 작성자는 자신의 가정을 보지 못한다. 모든 변경은 다른 시선의 도움을 받는다. |
| "나중에 정리하겠다" | 나중은 오지 않는다. 검토는 품질 게이트이므로 활용한다. 병합 후가 아니라 전에 정리를 요구한다. |
| "AI가 만든 코드는 괜찮을 것이다" | AI 코드에는 더 적은 것이 아니라 더 많은 검토가 필요하다. 틀려도 자신감 있고 그럴듯하다. |
| "테스트를 통과하니 좋다" | 테스트는 필요조건이지만 충분조건은 아니다. 아키텍처 문제, 보안 문제, 가독성 우려는 잡지 못한다. |
| "리팩터링으로 더 깔끔해진다" | 복잡성을 옮기는 것은 줄이는 것이 아니다. 독자가 기억할 개념 수가 같다면 구조가 개선되지 않았다. 분기가 사라지는 버전을 찾는다. |
| "파일에 조금 추가할 뿐이다" | 작은 diff도 파일을 건전한 크기 밖으로 밀고 무관한 흐름에 분기를 덧붙인다. diff 크기가 아니라 결과 구조를 평가한다. |
| "버전만 올리는 것이다" | 버전 업그레이드는 자신이 작성하지 않은 동작 변경이다. 변경 이력을 읽는다. Semver는 호환성 유지를 보장하지 않는다. |
| "시간을 아끼려고 한 PR에서 전부 업그레이드하겠다" | 일괄 업그레이드로 빌드가 깨지면 원인 패키지를 알기 어렵다. 변경 하나당 의존성 하나를 다루면 원인과 되돌리기가 명확하다. |

## 위험 신호

- 검토 없이 PR을 병합함
- 다른 축은 무시하고 테스트 통과 여부만 확인하는 검토
- 실제 검토 근거 없는 “LGTM”
- 보안에 민감한 변경에 보안 중심 검토가 없음
- “너무 커서 제대로 검토할 수 없는” 큰 PR(분할할 것)
- 버그 수정 PR에 회귀 테스트가 없음
- 검토 의견에 심각도 표시가 없어 필수와 선택을 구별하기 어려움
- “나중에 고치겠다”를 받아들임 — 그때는 오지 않음
- 독자가 기억할 개념 수를 줄이지 않고 코드 위치만 바꾸는 리팩터링
- 이미 큰 파일을 분해하지 않고 더 키우는 변경
- 관련 없는 코드 경로에 새 조건문을 흩뿌림(추상화 누락)
- 기존 정본 헬퍼를 중복하는 맞춤형 헬퍼 또는 공용 모듈에 둔 기능 로직
- 변경 이력 검토와 패키지별 격리 없는 일괄 “의존성 버전 올리기” PR
- 손으로 편집했거나 커밋하지 않았거나 diff를 검토하지 않고 병합한 잠금 파일 변경

## 검증

검토를 마친 뒤 확인한다.

- [ ] 모든 Critical 문제가 해결됨
- [ ] 접두어 없는 모든 Required 변경이 해결되거나 근거와 함께 명시적으로 연기됨
- [ ] 테스트 통과
- [ ] 빌드 성공
- [ ] 무엇을 바꾸고 어떻게 검증했는지 검증 근거를 기록함
- [ ] 의존성 업그레이드의 변경 이력을 검토했고 패키지별로 격리했으며 테스트 통과로 검증하고 잠금 파일 diff도 검토함

**잠정 차단 사유:** 다음 각 항목을 드러내고 더 단순한 설계를 제안한다. 변경이 실제로 구조를 악화할 때만 Required로 올린다. 복잡성을 줄이지 않고 옮기는 리팩터링, 분해 없이 파일을 크기 경계 밖으로 미는 변경, 공용 모듈에 추가한 기능 로직, 기존 정본 헬퍼와 거의 같은 중복 헬퍼, 불명확한 불변식을 가리는 조용한 대체 동작.
