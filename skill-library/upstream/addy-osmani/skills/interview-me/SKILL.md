# 인터뷰해 주세요

## 개요

사람이 요청하는 것과 실제로 원하는 것은 다르다. "대시보드"가 문제를 해결해서가 아니라 보통 그렇게 요청하기 때문에 대시보드를 요구한다. 목표 수치 없이 "더 빠르게 해 줘"라고 말한다.

이 간극을 가장 적은 비용으로 찾을 수 있는 시점은 계획·명세·코드가 생기기 전이다. 만들기 시작하면 전환 비용이 실제로 발생하고, 사용자는 잘못된 결과를 "이 정도면 충분하다"고 합리화한다. 맞지 않는 선택이 굳어진다.

이 스킬은 비용이 들기 전에 간극을 해소한다. 정의 단계의 다른 스킬은 원하는 것을 대략 안다고 가정한다. `idea-refine`은 아이디어에서 변형을 만들고, `spec-driven-development`는 요구사항을 기록하며, `doubt-driven-development`는 초안을 작성한 계획을 검증한다. Interview-me는 그보다 앞에서, 사용자가 말하기 전에 답을 예측할 수 있을 때까지 최선의 추측을 붙여 한 번에 한 질문씩 묻는 과정이다.

## 사용 시점

다음 경우에 이 스킬을 적용한다:

- 요청에서 다음 중 하나 이상이 빠졌다: 사용자가 **누구**인지, **왜** 원하는지, **성공**이 어떤 모습인지, 구속력 있는 **제약**이 무엇인지
- 요청이 구체적이지 않고 관행적이며("X를 만들어 줘", "더 빠르게 해 줘"), 추측 없이는 그 관행의 의미를 풀 수 없다
- 드러내지 않은 가정에서 출발하고 싶어진다
- 합리적인 가치 둘이 충돌할 때 사용자가 무엇을 우선하는지 말하지 않았다(단순함과 유연성, 비용과 속도)
- 사용자가 명시적으로 호출한다: "인터뷰해 줘", "집요하게 물어봐 줘", "시작 전에, 확실한가?", "내 생각을 검증해 줘"

**사용하지 않을 때:**

- 요청이 명확하고 그 자체로 완결됐다("이 변수 이름을 바꿔 줘", "이 오타를 고쳐 줘")
- 사용자가 검증보다 속도를 명시적으로 요청했다
- 순수한 정보 요청이다("X는 어떻게 작동하나?", "이 코드는 무엇을 하나?")
- 기계적 작업이다(이름 변경, 서식 변경, 파일 이동)
- 이미 확신이 95% 이상이다. 그렇지 않다고 가정하기 전에 아래 중단 조건을 다시 읽는다

## 로딩 제약

이 스킬에는 실시간으로 응답하는 사용자가 필요하다. CI 파이프라인, 예약 실행, `/loop`, autonomous-loop 같은 **비대화형 맥락에서는 호출하지 않는다**. 그런 환경에서 요청이 불충분하다면 추측 대신 사용자에게 블로커로 알린다.

## 절차

### 1단계: 확신 수치를 붙여 가설 세우기

질문하기 전에 현재 가장 타당한 사용자 의도 해석을 **한 문장**으로 적고, 솔직한 확신 수치(0~100%)를 붙인다:

```
가설: 스탠드업에서 "우리가 잘하고 있나?"에 답할 방법이 필요하고, 관행적으로 "대시보드"가 떠오른 것이다.
확신: 약 30% — 빠진 것: 누구를 위한 것인지, 이 맥락에서 "지표"가 무엇인지, 성공이 어떤 모습인지
```

수치를 쓰면 솔직해져야 한다. 높은 수치를 적었어도 다음에 물을 세 질문에 대한 사용자 반응을 실제로 예측할 수 없다면 그 수치는 틀렸다. 설명할 수 있는 확신 수준에서 시작한다.

확신이 약 70% 미만이면 같은 줄에 짧은 이유를 붙인다. 아직 해결되지 않았거나 빠진 것이 무엇인지 적는다. 그러면 사용자는 인터뷰에서 무엇을 밝혀야 하는지 정확히 알고, 수치도 막연한 신호에 그치지 않는다.

### 2단계: 추측을 붙여 한 번에 한 질문씩 묻기

형식:

```
질문: <one focused question>
추측: <your hypothesis for the answer, with the reasoning that produced it>
```

다음 질문을 하기 전에 사용자 반응을 기다린다.

**여러 질문을 묶지 않고 하나씩 묻는 이유:**

- 가설을 목록 속에 묻으면 사용자가 반응하기 어렵다
- 묶음 질문은 훑어읽기와 피상적 답을 유도한다
- 세 번째 질문은 첫 번째 답에 달린 경우가 많다. 한꺼번에 물으면 잘못된 틀이 굳어진다
- 사용자가 신중하게 생각할 에너지는 한정돼 있다. 한 질문씩 쓴다

**추측을 붙이는 이유:**

- 사용자는 처음부터 답을 만들기보다 틀린 추측에 더 빨리 반응한다
- 틀렸음이 드러날 수 있는 가설에 입장을 걸게 하므로 솔직해진다
- 인터뷰에서 드러내야 할 대상인 *자신의* 가정이 드러난다

예의 바른 사용자가 맞장구를 치려고 추측에 동의할 위험이 있다. 기꺼이 틀릴 수 있음을 드러내고, 때로는 사용자가 반박할 법한 방향으로 추측해서 이를 줄인다.

### 3단계: "원하는 것과 원해야 한다는 것" 구별하기

가장 위험한 답은 사용자가 실제로 원하는 것 대신 사려 깊은 답이 *들릴 법한 모습*을 말하는 경우다. 다음을 살핀다:

- 구체적인 내용 없이 모범 사례 표현에 맞춘 답("확장 가능했으면 좋겠다", "깔끔한 아키텍처")
- 관행에 기대는 답("대부분의 앱이 하는 방식", "표준 접근법")
- "아마 해야 할 것 같다…", "해야 하는 것으로 안다…", "좋은 엔지니어링 관행에 따르면…" 같은 표현
- 구체적인 결과 대신 "현대적", "확장 가능", "견고함" 같은 유행어가 목표가 되는 경우

이런 말을 들으면 다음을 묻는다:

> *"누구에게도 정당화할 필요가 없다면, 실제로 무엇을 원하나요?"*

이 한 질문이 앞선 다섯 질문보다 더 많은 일을 해내는 경우가 많다.

### 4단계: 사용자 자신의 말로 의도 다시 말하기

확신이 높아지면 이제 사용자가 무엇을 원한다고 생각하는지 써서 돌려준다. 간결하게(5~8줄), 가능하면 사용자의 표현을 사용하고 줄마다 확인하거나 수정할 수 있게 구성한다:

```
현재 이해한 요청은 다음과 같습니다:

- 결과:      <one line>
- 사용자:    <one line — who benefits>
- 왜 지금:   <one line — what changed>
- 성공:      <one line — how we know it worked>
- 제약:      <one line — the binding limit>
- 범위 제외: <one line — what we're explicitly not doing>

맞나요 / 아닌가요 / 다듬을까요?
```

"범위 제외"는 반드시 포함한다. 불일치의 절반은 무엇을 만들지 *않는가*에 대한 말 없는 의견 차이다.

### 5단계: 확인 — "알아서 해 주세요"가 아닌 명시적인 예

게이트는 명시적인 "예"다. 다음은 "예"가 **아니다**:

- "가장 좋다고 생각하는 대로 해 주세요." → 사용자가 위임한다는 것은 본인도 95% 확신하지 못한다는 뜻이다. 구체적인 선택지 둘을 제시해 다시 묻는다.
- "좋네요." → 모호하다. "다듬고 싶은 부분이 있나요?"라고 묻는다. 침묵은 확인이 아니다.
- "네, 진행하죠." → 동의보다 예의 바르게 대화를 끝내려는 말일 때가 많다. 같은 후속 질문을 한다.
- 침묵 뒤 "좋아요, 시작하죠." → 합의에 도달한 것이 아니라 인터뷰를 포기한 것이다. 멈추고 놓친 것이 있는지 묻는다.

사용자가 정정하면 반영해서 다시 말한다. 명시적인 예를 받을 때까지 반복한다.

### 6단계: 마지막 응답과 중단 규칙(중요)

사용자가 의도 진술을 명시적인 "예"로 확인하면:

1. **확인된 의도 진술을 전달한다.**
2. **후속 경로를 제안한다**(`docs/intent/[topic].md`에 저장, `spec-driven-development`로 명세 초안 작성, 명세 이후 작업 계획으로 진행).
3. **즉시 이번 응답을 끝낸다.** 이번 응답에서 도구를 호출하거나 후속 작업을 시작하지 않는다. 다음 단계를 고르도록 사용자에게 제어권을 돌려준다.

### 확신 95%에서 중단하기

다음 질문에 예라고 답할 수 있으면 끝이다:

> *다음에 물을 세 질문에 대한 사용자 반응을 예측할 수 있는가?*

그렇다면 이해가 일치한다. 인터뷰를 멈추고 다시 정리해 전달한다. 아니라면 아직 끝나지 않았다. 다음 질문을 한다.

이는 감이 아니라 확인 가능한 시험이다. 하한도 있다. 여러 차례 진행해도 예측할 수 없다면 계속 밀어붙일 이유가 아니라 요청에 관한 정보다. 멈추고 사용자에게 말한다. "질문을 X개 했는데 아직 반응을 예측할 수 없습니다. 근본적인 무언가가 빠져 있습니다. 한발 물러나 볼까요?"

## 산출물

이 스킬의 산출물은 **확인된 의도 진술**이다. 4단계의 재진술과 5단계의 명시적인 예가 납품물이다. 명세, 계획, 작업 목록은 후속 산출물이며 이 스킬이 만든 의도를 사용한다.

사용자가 의도를 지속적으로 남기고 싶다면(여러 세션에 걸친 프로젝트, 다른 협업자에게 인계) `docs/intent/[topic].md`에 저장하겠다고 제안한다. 확인받은 경우에만 저장한다.

## 예시

짧은 전후 비교다.

**`interview-me` 없이:**

```
사용자: 우리 지표를 위한 대시보드를 만들어 줘
에이전트: <starts proposing chart libraries and layouts>
```

에이전트는 누구를 위한 것인지, 어떤 지표인지, "우리 팀을 위한"이 무엇인지, 성공이 어떤 모습인지 가정했다. 어느 것도 명시되지 않았다. 모든 가정은 나중에 사용자가 "그 뜻이 아니었다"고 할 수 있는 지점이다.

**`interview-me` 사용:**

```
사용자: 우리 지표를 위한 대시보드를 만들어 줘

에이전트:
가설: 스탠드업에서 "우리가 잘하고 있나?"에 답할 방법이 필요하고, 관행적인 답이어서 "대시보드"가 떠오른 것이다.
확신: 약 30% — 빠진 것: 누구를 위한 것인지, "지표"가 무엇인지, 성공이 어떤 모습인지

질문: "우리가 잘하고 있나?"라고 할 때 누가 묻나요? 혼자인가요, 스탠드업의 엔지니어링 팀인가요, 아니면 상위 조직(예: 관리자, 임원, 이사회)인가요?
추측: 스탠드업의 엔지니어링 팀입니다. "우리"는 보통 그 범위이고 스탠드업에서 이런 질문을 하기 때문입니다. 임원을 위한 것이라면 지표와 구도가 크게 달라집니다.

사용자: 사실 저를 위한 거예요. 어떤 실험이 진행 중이고 초기 신호가 어떤지 계속 놓치고 있어요.

에이전트:
수정한 해석: 팀 대시보드가 아니라 개인 실험 추적기다. 확신: 약 60% — 아직 빠진 것: "초기 신호"가 무엇인지, 완료가 어떤 모습인지.

질문: 어떤 실험이 있는지 모르는 것이 문제인가요, 아니면 결과를 한곳에서 볼 수 없는 것이 문제인가요?
추측: 두 번째입니다. 실험 목록은 어딘가에 있지만 결과가 서로 다른 도구 다섯 개에 흩어져 있어 수작업으로 맞추는 데 지친 것입니다.

사용자: 사실 첫 번째예요. 정말 목록이 없어요. 여러 문서에 흩어져 있어요.

에이전트: <continues>
```

두 질문 만에 에이전트는 실제 요청이 "대시보드"가 아니라 "목록"임을 알아냈다. 산출물도 범위도 작업도 다르다. 대시보드는 잘못된 결과였을 것이다.

## 다른 스킬과의 관계

- **`idea-refine`**: 후속 단계다. 확인된 의도가 "X를 원하지만 범위를 어떻게 잡을지 모르겠다"라면, 이제 명시된 의도를 바탕으로 변형을 만들도록 `idea-refine`에 넘긴다.
- **`spec-driven-development`**: 후속 단계다. 확인된 의도가 구체적이면("Y 사용자를 위해 성공 기준 Z를 갖춘 X를 원한다"), 기록하도록 `spec-driven-development`에 넘긴다.
- **`planning-and-task-breakdown`**: 이 스킬에서 두 단계 뒤에 있다(명세 이후).
- **`doubt-driven-development`**: 시간 흐름의 반대편에 있다. Interview-me는 결정 전 의도 추출이며, doubt-driven은 결정 후 산출물 검토다. 둘 다 어긋남을 잡지만 시점이 다르다.
- **`source-driven-development`**: 별개 축이다. Interview-me는 사용자 의도를 명확히 하고 SDD는 프레임워크 사실을 검증한다. 서로 경쟁하지 않는다.

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "요청은 충분히 명확하다" | 지금 사용자가 바라는 결과를 한 문장으로 쓸 수 없다면 요청은 명확하지 않다. 판단 전에 1단계를 진행한다. |
| "질문을 너무 많이 하면 시간을 낭비한다" | 초점 있는 질문 4~6개로 쓰는 시간은 적다. 잘못된 것을 만드는 데 낭비하는 시간은 막대하며 그 비용은 사용자가 부담한다. |
| "만들면서 알아내겠다" | 코드가 생긴 뒤 전환 비용은 지금의 10배다. 구현 중 발견은 재작업이다. |
| "'알아서 해 달라'고 했으니 내가 결정해야 한다" | "알아서 해 달라"는 위임이지 결정이 아니다. 구체적인 선택지 둘로 다시 묻는다. |
| "고를 수 있게 여러 선택지를 줘야 한다" | 선택지는 사용자가 원하는 것을 알고 절충안을 고를 때 효과가 있다. 아직 원하는 것을 모른다. 선택지 나열은 탐색을 넓히고 질문은 좁힌다. |
| "추측을 붙이면 유도하는 것이다" | 유도가 목적이다. 반응이 처음부터 만들어 내기보다 빠르다. 위험은 유도가 아니라 비위 맞추기다. 기꺼이 틀릴 수 있음을 드러내 이를 줄인다. |
| "충분히 이야기했으니 이해했다" | 시험해 본다. 다음 세 질문에 대한 반응을 예측할 수 있는가? 아니라면 아직 이해하지 못했다. |
| "사용자가 예라고 했으니 끝났다" | 모호한 재진술이나 막연한 "좋네요" 뒤의 예는 알맹이가 없다. 구체적으로 다시 말하고 다시 확인한다. |

## 위험 신호

- 한 메시지에서 세 개 이상의 질문: 인터뷰가 아니라 묶음 질문이다
- 가설을 붙이지 않은 질문: 입장을 거는 것이 아니라 설문이다
- "가장 좋다고 생각하는 대로 해 주세요"를 최종 답으로 수용하기
- 사용자가 재진술을 명시적으로 확인하기 전에 명세, 계획, 작업 목록 만들기
- 의도 확인 직후 응답을 끝내지 않고 도구를 호출하거나 후속 작업 시작하기
- "실제로 무엇을 원하나요?" 대신 "모범 사례는 무엇일까요?"로 질문 구성하기
- 사용자가 전문적으로 들리는 답("확장 가능", "깔끔함", "현대적")을 했는데 실제로 원하는 것인지 더 묻지 않고 수용하기
- 확신이 눈에 띄게 높아지지 않은 채 세 차례 이상 진행: 질문이 잘못됐다. 물러서서 틀을 바꾼다
- 이유 없는 약 70% 미만의 확신 수치: 무엇이 빠졌는지 모르면 사용자는 간극을 메울 수 없다
- 사용자 확인 전에 의도 문서 저장하기(문서 자체가 사용자가 하지 않은 동의를 암시한다)
- 재진술에서 "범위 제외" 줄 생략하기(비목표에 대한 말 없는 의견 차이가 불일치의 절반이다)

## 검증

interview-me 적용 후:

- [ ] 첫 응답에서 확신 수치를 붙인 명시적 가설을 밝혔다
- [ ] 약 70% 미만인 모든 확신 수치에 한 줄 이유를 붙였다(아직 해결되지 않았거나 빠진 것)
- [ ] 에이전트의 추측을 붙여 한 번에 한 질문씩 물었다
- [ ] 사용자가 전문성이나 관행을 드러내는 답을 했을 때 "정당화할 필요가 없다면 실제로 무엇을 원하는가?"라는 질문을 한 번 이상 했다
- [ ] 구체적인 재진술(결과 / 사용자 / 왜 지금 / 성공 / 제약 / 범위 제외)을 사용자에게 돌려줬다
- [ ] 사용자가 명시적인 예로 재진술을 확인했다("알아서 해 주세요", "좋네요", 침묵이 아님)
- [ ] 중단 시점에 에이전트는 다음에 물을 세 질문의 반응을 예측할 수 있었다
- [ ] 명시적 확인을 받자 도구 호출이나 후속 작업 없이 즉시 응답을 끝냈다
- [ ] 후속 스킬(`idea-refine`, `spec-driven-development`)로 넘길 때 최초의 불충분한 요청 대신 확인된 의도로 설명했다
