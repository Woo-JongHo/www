# 명세 기반 개발

## 개요

코드를 작성하기 전에 구조화된 명세를 작성한다. 명세는 에이전트와 인간 엔지니어가 공유하는 정본이다. 무엇을 왜 만들고, 완료를 어떻게 판단할지 정의한다. 명세 없이 코드를 작성하는 것은 추측이다.

## 사용 시점

- 새 프로젝트나 기능을 시작할 때
- 요구사항이 모호하거나 불완전할 때
- 변경이 여러 파일이나 모듈에 영향을 줄 때
- 아키텍처 결정을 내리려 할 때
- 구현에 30분 이상 걸릴 작업일 때

**사용하지 않을 때:** 한 줄 수정, 오타 수정, 요구사항이 명확하고 자체 완결적인 변경.

## 게이트가 있는 작업 흐름

명세 기반 개발에는 네 단계가 있다. 하나의 요청에 독립적으로 테스트할 수 있는 여러 기능이 묶인 경우에만 활성화되는 범위 확인(0단계)이 그 앞에 온다. 현재 단계를 검증하기 전에는 다음 단계로 넘어가지 않는다.

```
명세 ──→ 계획 ──→ 작업 ──→ 구현
 │        │        │        │
 ▼        ▼        ▼        ▼
인간      인간      인간      인간
검토      검토      검토      검토
```

### 0단계: 범위 확인

대부분의 요청은 기능 하나를 설명한다. 이번 요청도 그렇다면 이 단계를 건너뛰고 바로 명세 단계로 간다. 0단계는 일반적인 경우가 아닌 예외를 위해 있으며, 단일 기능에 계층을 강제하지 않는다.

**감지.** 하나의 요구사항에 독립적으로 테스트할 수 있는 여러 기능이 묶여 있으면 명세 전에 분해한다.

- 요구사항에 각자의 소비자나 데이터를 가진 서로 다른 기능이 명시된다(예: 신원, 결제, 알림, 보고).
- 수용 기준이 별도로 출시하고 검증할 수 있는 묶음으로 나뉜다.
- 다른 기능의 요구사항을 다시 작성하지 않고도 기능 하나를 제외하거나 교체할 수 있다.

**명세를 작성하기 전에 기능 지도를 제안한다.** 프로젝트 계획이 아니라 모듈 표와 구현 순서로 구성해 작고 검토하기 쉽게 만든다.

```markdown
# 기능 지도: [Initiative Name]

| 모듈 id | 책임 | 의존 대상 |
|---|---|---|
| identity | 계정, 세션, SSO | — |
| billing | 요금제, 청구서, 결제 | identity |
| notifications | 이메일과 웹훅 일괄 전달 | identity |
| reporting | 사용량 대시보드 | billing, notifications |

구현 순서: identity → billing, notifications → reporting
```

- **안정적인 모듈 id.** Kebab-case로 한 번 정하고 이니셔티브 중간에 바꾸지 않는다. 명세, 계획, 후속 명령은 활성 명세를 추측하지 않고 이 id로 작업을 선택한다.
- **의존성은 한 방향이며 순환하지 않는다.** 화살표는 한 방향을 가리킨다. 두 모듈이 서로를 필요로 한다면 하나의 모듈이다.
- **인터페이스는 경계에 둔다.** 지도에는 `billing`이 `identity`에 의존함을 기록한다. 둘 사이의 계약은 제공자 모듈의 명세에 둔다(설계 방법은 `api-and-interface-design` 참조).

**지도에도 각 단계와 같은 게이트를 적용한다.** 모듈 명세를 쓰기 전에 인간이 모듈 경계, 의존 방향, 구현 순서를 검토한다. 지도를 잘못 정하면 비용이 크지만 열 줄을 검토하는 비용은 크지 않다.

**그다음 모듈별로 반복한다.** 의존 순서에 따라 각 모듈에서 명세 → 계획 → 작업 → 구현을 수행한다. 각 모듈에는 그 모듈의 목적, 경계, 성공 기준으로 범위를 한정한 자체 명세를 둔다. 승인된 지도는 프로젝트 루트에 저장하고 모듈 명세를 그 옆에 모듈 id로 이름 붙여 저장한다(`SPEC-identity.md`, `SPEC-billing.md`). 파일명을 추측하는 대신 지도가 존재하는 산출물의 색인이다.

### 1단계: 명세

큰 방향부터 시작한다. 요구사항이 구체적일 때까지 인간에게 확인 질문을 한다.

**가정을 즉시 드러낸다.** 명세 본문을 작성하기 전에 가정하는 내용을 나열한다.

```
현재 두고 있는 가정:
1. 네이티브 모바일이 아니라 웹 애플리케이션이다
2. 인증은 JWT가 아니라 세션 기반 쿠키를 사용한다
3. 데이터베이스는 기존 Prisma 스키마에 근거해 PostgreSQL이다
4. 최신 브라우저만 지원하며 IE11은 지원하지 않는다
→ 지금 정정하지 않으면 이 가정으로 진행하겠다.
```

모호한 요구사항을 조용히 메우지 않는다. 명세의 목적 자체가 코드를 작성하기 *전에* 오해를 드러내는 것이다. 가정은 가장 위험한 형태의 오해다.

**다음 여섯 핵심 영역을 다루는 명세 문서를 작성한다.**

1. **목적** — 무엇을 왜 만드는가? 사용자는 누구인가? 성공한 모습은 무엇인가?

2. **명령** — 도구 이름만 적지 말고 플래그를 포함한 완전한 실행 명령을 적는다.
   ```
   Build: npm run build
   Test: npm test -- --coverage
   Lint: npm run lint -- --fix
   Dev: npm run dev
   ```

3. **프로젝트 구조** — 소스 코드, 테스트, 문서가 각각 어디에 위치하는지 적는다.
   ```
   src/           → 애플리케이션 소스 코드
   src/components → React 컴포넌트
   src/lib        → 공용 유틸리티
   tests/         → 단위 및 통합 테스트
   e2e/           → 종단 간 테스트
   docs/          → 문서
   ```

4. **코드 스타일** — 스타일을 설명하는 세 문단보다 실제 코드 예시 하나가 낫다. 명명 규칙, 서식 규칙, 좋은 결과의 예시를 포함한다.

5. **테스트 전략** — 프레임워크, 테스트 위치, 기대 커버리지, 관심사별 테스트 수준을 적는다.

6. **경계** — 세 단계 체계:
   - **항상 할 일:** 커밋 전에 테스트 실행, 명명 규칙 준수, 입력 검증
   - **먼저 물을 일:** 데이터베이스 스키마 변경, 의존성 추가, CI 설정 변경
   - **절대 하지 않을 일:** 비밀정보 커밋, vendor 디렉터리 편집, 승인 없이 실패 테스트 제거

**명세 템플릿:**

```markdown
# 명세: [Project/Feature Name]

## 목적
[What we're building and why. User stories or acceptance criteria.]

## 기술 스택
[Framework, language, key dependencies with versions]

## 명령
[Build, test, lint, dev — full commands]

## 프로젝트 구조
[Directory layout with descriptions]

## 코드 스타일
[Example snippet + key conventions]

## 테스트 전략
[Framework, test locations, coverage requirements, test levels]

## 경계
- 항상: [...]
- 먼저 질문: [...]
- 금지: [...]

## 성공 기준
[How we'll know this is done — specific, testable conditions]

## 열린 질문
[Anything unresolved that needs human input]
```

**외부 명세 도구:** 이 작업 흐름은 형식에 종속되지 않는다. 프로젝트가 이미 OpenSpec이나 다른 명세 체계를 사용한다면 중복된 `SPEC.md`를 만들지 말고 기존 체계의 산출물 형식과 저장 규칙을 유지한다. 이 스킬은 요구사항 명확화, 내용, 승인 게이트를 소유하고, 외부 도구는 승인된 명세를 표현하는 방식을 소유한다.

**지시를 성공 기준으로 바꾼다.** 모호한 요구사항을 받으면 구체적인 조건으로 바꾼다.

```
요구사항: "대시보드를 더 빠르게 해 주세요"

다시 정의한 성공 기준:
- 4G 연결에서 대시보드 LCP < 2.5s
- 초기 데이터 로드가 < 500ms 안에 완료
- 로드 중 레이아웃 이동 없음(CLS < 0.1)
→ 이 목표가 맞는가?
```

그러면 “빠르게”의 의미를 추측하는 대신 명확한 목표를 향해 반복하고 재시도하며 문제를 해결할 수 있다.

**명세를 작성한 뒤 멈춘다(중요).** 명세를 저장한 뒤에는:

1. 내용을 요약하고 열린 질문을 나열한다.
2. 인간에게 승인하거나 변경을 요청해 달라고 한다.
3. **즉시 이번 턴을 끝낸다.** 이번 턴에 2단계를 시작하거나 `planning-and-task-breakdown`을 호출하거나 코드를 작성하지 않는다. 계획은 인간이 이후 턴에서 명세를 승인한 뒤에만 시작한다.

### 2단계: 계획

검증된 명세로 기술 구현 계획을 만든다.

1. 주요 컴포넌트와 의존성을 식별한다.
2. 구현 순서, 즉 무엇을 먼저 만들어야 하는지 정한다.
3. 위험과 완화 전략을 기록한다.
4. 병렬로 만들 수 있는 부분과 순차적으로 만들어야 하는 부분을 구분한다.
5. 단계 사이의 검증 확인 지점을 정의한다.

> 이 단계들의 의존성 그래프 작성과 수직 분할 방법은 정본인 `planning-and-task-breakdown`을 따른다. 위 목록은 간단한 요약이며 서로 달라지면 `planning-and-task-breakdown`이 우선한다.
>
> **출력 규칙:** 계획은 `tasks/plan.md`에 저장하고 작업 목록은 `planning-and-task-breakdown`이 정한 대상에 기록한다(기본값 `tasks/todo.md`, 프로젝트에서 외부 추적기를 지정할 수도 있음). `tasks/`가 없으면 만든다. 후속 명령(`/build` 등)은 이 기본값을 기대한다.

인간이 읽고 “이 접근이 맞다” 또는 “X를 바꿔라”라고 말할 수 있도록 계획을 검토 가능하게 작성한다.

### 3단계: 작업

계획을 개별적으로 구현할 수 있는 작업으로 나눈다.

- 각 작업은 한 번의 집중 세션에서 완료할 수 있어야 한다.
- 각 작업에는 명시적인 수용 기준이 있어야 한다.
- 각 작업에는 검증 단계(테스트, 빌드, 수동 확인)가 있어야 한다.
- 작업은 중요해 보이는 순서가 아니라 의존 순서로 정렬한다.
- 어느 작업도 약 5개보다 많은 파일을 변경해야 해서는 안 된다.

> 전체 작업 크기와 의존 순서 결정 방법은 정본인 `planning-and-task-breakdown`을 따른다. 아래 템플릿은 간단한 인라인 형식이며 서로 달라지면 `planning-and-task-breakdown`이 우선한다.

**작업 템플릿:**
```markdown
- [ ] 작업: [Description]
  - 수용: [What must be true when done]
  - 검증: [How to confirm — test command, build, manual check]
  - 파일: [Which files will be touched]
```

### 4단계: 구현

`skills/incremental-implementation/SKILL.md`(`incremental-implementation`)와 `skills/test-driven-development/SKILL.md`(`test-driven-development`)를 따라 작업을 하나씩 실행한다. 에이전트에 전체 명세를 밀어 넣는 대신 각 단계에서 필요한 명세 절과 소스 파일을 불러오도록 `skills/context-engineering/SKILL.md`(`context-engineering`)를 사용한다.

## 명세를 살아 있게 유지하기

명세는 일회성 산출물이 아니라 계속 갱신하는 문서다.

- **결정이 바뀌면 갱신한다** — 데이터 모델을 바꿔야 한다는 사실을 발견하면 먼저 명세를 갱신한 뒤 구현한다.
- **범위가 바뀌면 갱신한다** — 추가하거나 제외한 기능을 명세에 반영한다.
- **명세를 커밋한다** — 명세는 코드와 함께 버전 관리한다.
- **PR에서 명세를 참조한다** — 각 PR이 구현하는 명세 절로 연결한다.

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "단순하니 명세는 필요 없다" | 단순한 작업에 *긴* 명세는 필요 없지만 수용 기준은 필요하다. 두 줄짜리 명세도 괜찮다. |
| "코드를 작성한 뒤 명세를 쓰겠다" | 그것은 명세가 아니라 문서화다. 명세의 가치는 코드 *이전에* 명확히 생각하도록 한다는 데 있다. |
| "명세가 속도를 늦출 것이다" | 15분짜리 명세는 몇 시간의 재작업을 막는다. 15시간 디버깅보다 15분짜리 폭포수 방식이 낫다. |
| "어차피 요구사항은 바뀐다" | 그래서 명세를 계속 갱신해야 한다. 낡은 명세도 없는 것보다 낫다. |
| "사용자는 자신이 원하는 것을 안다" | 명확한 요청에도 암묵적인 가정이 있다. 명세는 그 가정을 드러낸다. |
| "하나의 큰 기능이니 분할은 낭비다" | 수용 기준이 독립적으로 테스트 가능한 묶음으로 나뉜다면 하나의 거대 명세는 모든 후속 작업이 전체 계약을 이해하도록 강제한다. 열 줄짜리 기능 지도가 더 저렴한 대안이다. |
| "계획할 때 분해하겠다" | 계획은 명세 안에서 작업을 나눈다. 그때는 이미 너무 큰 산출물이 만들어진 뒤다. 모듈 경계와 의존 방향은 명세 작성 후가 아니라 전에 정해야 한다. |

## 위험 신호

- 작성된 요구사항 없이 코드를 쓰기 시작함
- “완료”의 의미를 명확히 하기 전에 “그냥 구현을 시작할까요?”라고 물음
- 명세나 작업 목록에 없는 기능을 구현함
- 아키텍처 결정을 기록하지 않음
- “무엇을 만들지 명백하다”며 명세를 생략함
- 같은 턴에 명세를 작성하고 계획이나 코드를 시작함
- 하나의 명세 요구사항이 독립적으로 테스트 가능한 여러 기능에 걸침
- 사전에 기능 지도가 승인되지 않아 구현 중 모듈 경계나 구현 순서를 암묵적으로 결정함

## 검증

구현으로 넘어가기 전에 확인한다.

- [ ] 명세가 여섯 핵심 영역을 모두 다룸
- [ ] 인간이 명세를 검토하고 승인함
- [ ] 명세를 저장한 뒤 턴이 끝났고 이후 턴에서 승인받음
- [ ] 성공 기준이 구체적이고 테스트 가능함
- [ ] 경계(항상/먼저 질문/금지)가 정의됨
- [ ] 명세가 저장소의 파일에 저장됨
- [ ] 요청이 독립적으로 테스트 가능한 여러 기능을 묶는 경우, 어떤 모듈 명세도 작성하기 전에 기능 지도(모듈 id, 의존 방향, 구현 순서)가 승인됨
- [ ] 모든 모듈 명세가 승인된 지도의 모듈 id에 연결됨
