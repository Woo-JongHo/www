# 계획 및 작업 분해

## 개요

작업을 명시적인 수용 기준이 있는 작고 검증 가능한 과제로 분해합니다. 좋은 작업 분해는 일을 안정적으로 완료하는 에이전트와 뒤엉킨 결과물을 만드는 에이전트를 가릅니다. 모든 과제는 집중 세션 한 번에 구현하고 테스트하고 검증할 수 있을 만큼 작아야 합니다.

## 사용 시점

- 명세가 있고 이를 구현 가능한 단위로 나눠야 할 때
- 과제가 너무 크거나 모호해서 시작하기 어려울 때
- 여러 에이전트나 세션에 작업을 병렬화해야 할 때
- 사람에게 범위를 전달해야 할 때
- 구현 순서가 명확하지 않을 때

**사용하지 말아야 할 때:** 범위가 명확한 단일 파일 변경 또는 명세에 이미 잘 정의된 과제가 있을 때.

## 계획 절차

### 1단계: 계획 모드 진입

코드를 작성하기 전에 읽기 전용 모드로 작업합니다.

- 명세와 관련 코드베이스 영역을 읽습니다
- 기존 패턴과 관례를 파악합니다
- 컴포넌트 간 의존성을 정리합니다
- 위험과 미지의 사항을 기록합니다

**계획 중에는 코드를 작성하지 마세요.** 결과물은 구현이 아니라 `tasks/plan.md`에 저장된 계획 문서와 작업 목록 대상(출력 파일 참고, 기본값은 `tasks/todo.md`)에 기록된 작업 목록입니다.

### 2단계: 의존성 그래프 파악

무엇이 무엇에 의존하는지 정리합니다.

```
데이터베이스 스키마
    │
    ├── API 모델/타입
    │       │
    │       ├── API 엔드포인트
    │       │       │
    │       │       └── 프런트엔드 API 클라이언트
    │       │               │
    │       │               └── UI 컴포넌트
    │       │
    │       └── 검증 로직
    │
    └── 초기 데이터 / 마이그레이션
```

구현 순서는 의존성 그래프를 아래에서 위로 따릅니다. 기반을 먼저 구축하세요.

### 3단계: 수직으로 분할

데이터베이스 전체, API 전체, UI 전체를 차례로 만드는 대신 완전한 기능 경로를 한 번에 하나씩 구축합니다.

**나쁜 예(수평 분할):**
```
과제 1: 전체 데이터베이스 스키마 구축
과제 2: 모든 API 엔드포인트 구축
과제 3: 모든 UI 컴포넌트 구축
과제 4: 전체 연결
```

**좋은 예(수직 분할):**
```
과제 1: 사용자가 계정을 생성할 수 있음(등록 스키마 + API + UI)
과제 2: 사용자가 로그인할 수 있음(인증 스키마 + API + 로그인 UI)
과제 3: 사용자가 작업을 생성할 수 있음(작업 스키마 + API + 생성 UI)
과제 4: 사용자가 작업 목록을 볼 수 있음(쿼리 + API + 목록 UI)
```

각 수직 조각은 작동하고 테스트 가능한 기능을 제공합니다.

### 4단계: 과제 작성

마크다운 작업 목록에 들어가든 외부 트래커의 항목이 되든(출력 파일 참고) 각 과제는 다음 구조를 따릅니다.

```markdown
## 과제 [N]: [Short descriptive title]

**설명:** 이 과제가 달성하는 바를 설명하는 문단 하나.

**수용 기준:**
- [ ] [Specific, testable condition]
- [ ] [Specific, testable condition]

**검증:**
- [ ] 테스트 통과: [the repository's focused-test command]
- [ ] 빌드 성공: [the repository's build command]
- [ ] 수동 확인: [description of what to verify]

**의존성:** [Task numbers this depends on, or "None"]

**수정할 가능성이 있는 파일:**
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**예상 범위:** [Small: 1-2 files | Medium: 3-5 files | Large: 5+ files]
```

### 5단계: 순서 지정 및 체크포인트

다음 조건을 충족하도록 과제를 배치합니다.

1. 의존성이 충족됩니다(기반을 먼저 구축)
2. 각 과제 후에도 시스템이 작동하는 상태로 남습니다
3. 과제 2~3개마다 검증 체크포인트가 있습니다
4. 고위험 과제가 앞에 옵니다(빠르게 실패)

작업 목록 대상에 명시적인 체크포인트를 추가합니다.

```markdown
## 체크포인트: 과제 1~3 이후
- [ ] 모든 테스트 통과
- [ ] 애플리케이션이 오류 없이 빌드됨
- [ ] 핵심 사용자 흐름이 엔드투엔드로 작동함
- [ ] 계속하기 전에 사람과 검토
```

## 과제 크기 지침

| 크기 | 파일 | 범위 | 예시 |
|------|-------|-------|---------|
| **XS** | 1 | 단일 함수 또는 구성 변경 | 검증 규칙 추가 |
| **S** | 1-2 | 컴포넌트나 엔드포인트 하나 | 새 API 엔드포인트 추가 |
| **M** | 3-5 | 기능 조각 하나 | 사용자 등록 흐름 |
| **L** | 5-8 | 여러 컴포넌트에 걸친 기능 | 필터링과 페이지네이션이 있는 검색 |
| **XL** | 8+ | **너무 큼 — 더 작게 분해** | — |

과제가 L 이상이면 더 작은 과제로 나눠야 합니다. 에이전트는 S와 M 과제에서 가장 좋은 성과를 냅니다.

**과제를 더 작게 나눠야 할 때:**
- 집중 세션 한 번보다 오래 걸릴 때(에이전트 작업 약 2시간 이상)
- 수용 기준을 글머리표 3개 이하로 설명할 수 없을 때
- 서로 독립적인 하위 시스템을 둘 이상 건드릴 때(예: 인증과 결제)
- 과제 제목에 "및"을 쓰게 될 때(과제가 두 개라는 신호)

## 출력 파일

- **계획 문서:** 구현 계획을 `tasks/plan.md`에 저장합니다. 이는 언제나 마크다운 파일입니다. 설계 결정, 위험, 미해결 질문은 개별 트래커 이슈에 깔끔하게 대응되지 않습니다.
- **작업 목록:** 각 과제를 아래 정의된 **작업 목록 대상**에 기록합니다.

`tasks/` 디렉터리가 없으면 생성합니다.

**미완료 계획을 절대 덮어쓰지 마세요.** `tasks/plan.md` 또는 `tasks/todo.md`를 작성하기 전에 이미 존재하며 아직 확인되지 않은 과제가 있는지 확인합니다.

- 같은 작업을 다시 계획하는 경우(사용자가 이 계획의 수정 또는 확장을 요청함) → 기존 파일을 제자리에서 갱신합니다.
- 다른 작업인 경우 → **멈추고 물어보세요.** 다른 세션에서 확인되지 않은 과제를 구축 중일 수 있습니다. 기존 파일을 임의로 삭제하거나 덮어쓰거나 이름을 바꾸지 말고, 충돌을 제시한 뒤 사용자가 결정하게 하세요(이전 계획을 먼저 완료하거나, 명시적으로 폐기하거나, 새 계획 위치를 지정).

같은 규칙이 외부 작업 목록 대상에도 적용됩니다. 새 계획을 위한 자리를 만들려고 다른 계획의 열린 트래커 항목을 일괄 종료하거나 삭제하지 마세요.

### 작업 목록 대상

작업 목록 대상은 과제와 체크포인트를 기록하는 위치입니다. 여기서 한 번 정의하며 이 스킬의 다른 모든 참조는 이 정의를 따릅니다.

- **기본값: `tasks/todo.md`의 체크리스트 형식 마크다운 파일.** `/build` 명령과 기타 다운스트림 도구가 기대하는 관례입니다. 프로젝트가 달리 정하지 않았다면 이를 사용합니다.
- **외부 트래커:** 프로젝트의 에이전트 규칙(`CLAUDE.md`, `AGENTS.md` 등)이나 사용자가 이슈 트래커(예: GitHub Issues, Jira, Linear, `bd`/beads)를 지정했다면 `tasks/todo.md`를 작성하지 말고 과제마다 트래커 항목 하나를 만듭니다. 4단계 구조를 트래커 필드에 대응시키세요. 항목 본문에는 수용 기준과 검증 단계를, 트래커 연결 메커니즘(`bd dep add`, "blocked by" 등)에는 의존성을 넣습니다. 5단계 체크포인트도 트래커 항목으로 기록하거나, 트래커에 자연스러운 대응물이 없으면 계획 문서의 체크리스트로 기록합니다.

외부 트래커를 사용할 때는 다운스트림 단계와 미래 세션이 찾을 위치를 알 수 있도록 `tasks/plan.md`에 이를 기록하고(예: "Tasks tracked in Linear project FOO"), 계획 문서의 작업 목록 절은 중복 체크리스트가 아니라 트래커 항목 ID 또는 링크의 순서 있는 색인으로 유지합니다.

```markdown
# 구현 계획: [Feature/Project Name]

## 개요
[One paragraph summary of what we're building]

## 아키텍처 결정
- [Key decision 1 and rationale]
- [Key decision 2 and rationale]

## 작업 목록

### 1단계: 기반
- [ ] 과제 1: ...
- [ ] 과제 2: ...

### 체크포인트: 기반
- [ ] 테스트 통과, 깔끔한 빌드

### 2단계: 핵심 기능
- [ ] 과제 3: ...
- [ ] 과제 4: ...

### 체크포인트: 핵심 기능
- [ ] 엔드투엔드 흐름 작동

### 3단계: 다듬기
- [ ] 과제 5: ...
- [ ] 과제 6: ...

### 체크포인트: 완료
- [ ] 모든 수용 기준 충족
- [ ] 검토 준비 완료

## 위험과 완화책
| 위험 | 영향 | 완화책 |
|------|--------|------------|
| [Risk] | [High/Med/Low] | [Strategy] |

## 미해결 질문
- [Question needing human input]
```

## 병렬화 기회

여러 에이전트나 세션을 사용할 수 있을 때:

- **안전하게 병렬화 가능:** 독립적인 기능 조각, 이미 구현된 기능의 테스트, 문서
- **반드시 순차 실행:** 데이터베이스 마이그레이션, 공유 상태 변경, 의존성 체인
- **조율 필요:** API 계약을 공유하는 기능(계약을 먼저 정의한 다음 병렬화)

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "진행하면서 알아내면 돼" | 그렇게 하면 뒤엉킨 결과와 재작업이 생깁니다. 계획 10분이 몇 시간을 절약합니다. |
| "과제는 명백해" | 그래도 적으세요. 명시적인 과제는 숨은 의존성과 잊힌 경계 사례를 드러냅니다. |
| "계획은 오버헤드야" | 계획이 곧 과제입니다. 계획 없는 구현은 그저 타이핑일 뿐입니다. |
| "전부 머릿속에 담아둘 수 있어" | 컨텍스트 창은 유한합니다. 기록된 계획은 세션 경계와 압축 후에도 남습니다. |
| "이전 `tasks/plan.md`는 낡았으니 그냥 바꿀게" | 확인되지 않은 과제가 다른 세션에서 구축 중일 수 있습니다. 덮어쓰면 다른 곳에는 없는 작업 상태가 사라집니다. 멈추고 물어보세요. |

## 위험 신호

- 기록된 작업 목록 없이 구현 시작
- 다른 작업의 확인되지 않은 과제가 남은 `tasks/plan.md` 또는 `tasks/todo.md`를 묻지 않고 덮어쓰기
- 프로젝트가 외부 트래커를 지정했는데 `tasks/todo.md`를 작성하거나 두 곳에 과제를 흩어 놓기
- 수용 기준 없이 "기능 구현"이라고만 적힌 과제
- 계획에 검증 단계가 없음
- 모든 과제의 크기가 XL
- 과제 사이에 체크포인트가 없음
- 의존성 순서를 고려하지 않음

## 검증

구현을 시작하기 전에 확인합니다.

- [ ] 모든 과제에 수용 기준이 있음
- [ ] 모든 과제에 검증 단계가 있음
- [ ] 과제 의존성이 식별되고 올바른 순서로 정렬됨
- [ ] 과제가 작업 목록 대상(기본값 `tasks/todo.md`)에 기록됨
- [ ] 명시적인 사용자 확인 없이 기존 미완료 계획을 덮어쓰지 않음
- [ ] 어떤 과제도 약 5개보다 많은 파일을 건드리지 않음
- [ ] 주요 단계 사이에 체크포인트가 있음
- [ ] 사람이 계획을 검토하고 승인함

## 함께 보기
