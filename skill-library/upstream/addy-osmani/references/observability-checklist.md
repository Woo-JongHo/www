## 온콜 질문(여기서 시작)

질문 없는 텔레메트리는 잡음이다. 무엇이든 계측하기 전에 다음을 확인한다.

- [ ] 온콜 엔지니어가 이 기능에 관해 물을 질문 2~4개를 적어 둠
- [ ] 아래의 모든 신호가 그 질문 중 하나에 대응함
- [ ] 각 질문이 올바른 신호 유형과 연결됨. 메트릭은 무언가 잘못되었다는 **사실**을, 추적은 **어디서** 잘못되었는지를, 로그는 **왜** 잘못되었는지를 알려 줌

## 구조화된 로깅

- [ ] 로그가 자유 형식 문자열이 아니라 안정적인 이벤트 이름을 사용하는 구조화된 형식(JSON)임
- [ ] 모든 로그 줄에 시스템 경계에서 생성하거나 수락한 상관관계/요청 ID가 포함됨
- [ ] 모든 아웃바운드 호출과 비동기 경계에서 상관관계 ID를 전파함(HTTP 헤더, 큐 메타데이터)
- [ ] 둘 이상의 진입점(스케줄러, 재실행 엔드포인트, 수동 실행)이 기록하는 모든 로그 스트림에 진입점 필드가 포함되며, 실행 시작 지점에서 설정되어 상관관계 ID와 함께 전파됨
- [ ] 로그 수준이 일관됨. `error` = 불변식이 깨져 누군가 조치할 수 있음, `warn` = 성능이 저하되었지만 처리됨, `info` = 중요한 비즈니스 이벤트, `debug` = 프로덕션에서 꺼짐
- [ ] 어떤 로그 줄에도 비밀, 토큰, 비밀번호, 마스킹되지 않은 PII가 없음(`security-and-hardening`의 엄격한 규칙)
- [ ] 필드는 허용 목록으로 제한됨. 전체 요청/응답 본문이나 인증 헤더가 없음
- [ ] 외부 서비스 호출은 엔드포인트, 상태, 지연 시간, 시도 횟수, 정제된 식별자 등 메타데이터만 기록함
- [ ] 실제 로그 출력을 표본 확인함. `[object Object]`가 아니라 구조화된 필드임

## 메트릭

- [ ] 모든 엔드포인트와 모든 외부 의존성에 **RED**를 계측함. Rate, Errors, Duration
- [ ] 모든 리소스(큐, 풀, 호스트)에 **USE**를 계측함. Utilization, Saturation, Errors
- [ ] 지연 시간은 히스토그램이며 p50/p95/p99를 조회할 수 있음. 평균은 절대 사용하지 않음
- [ ] 모든 레이블이 작고 고정된 집합에서 나옴(라우트 템플릿, 상태 클래스, 제공자 이름)
- [ ] 제한 없는 레이블 값이 없음. 사용자 ID, 테넌트 ID, 이메일, 원시 URL, 요청 ID, 오류 메시지 텍스트를 사용하지 않음
- [ ] 상태 코드를 클래스별로 묶음(`503`이 아니라 `5xx`)
- [ ] 모든 워커/큐의 큐 깊이와 처리 시간을 추적함

## 분산 추적

- [ ] OpenTelemetry(또는 동등한 도구)를 다른 import보다 먼저 서비스 시작 시 초기화함
- [ ] HTTP, gRPC, DB 클라이언트에 자동 계측을 활성화함
- [ ] 모든 아웃바운드 호출에서 추적 컨텍스트(W3C `traceparent`/`tracestate`)를 전파하고 모든 인바운드 요청에서 추출함
- [ ] 컨텍스트가 비동기 경계를 넘어 유지됨. 큐 메시지에 추적 메타데이터가 포함됨
- [ ] 의미 있는 내부 작업 단위에만 수동 스팬을 두고, 온콜 담당자가 필터링할 속성을 포함함
- [ ] 스팬 속성에 비밀이나 PII가 없음
- [ ] 기본 비율이 낮은 헤드 기반 샘플링을 사용하며, 테일 샘플링을 사용할 수 있으면 오류는 100% 보존함

## 알림

- [ ] 모든 알림은 증상 기반임(오류율, p99 지연 시간, 큐 경과 시간). 원인(CPU, 디스크, 재시작)은 호출기가 아니라 대시보드로 보냄
- [ ] 모든 알림에 조치할 수 있음. "무시해도 자체 복구됨" 알림은 삭제함
- [ ] 모든 알림이 런북으로 연결됨. 최소 세 줄로 의미, 처음 실행할 쿼리, 에스컬레이션 경로를 제공함
- [ ] 임계값과 지속 시간이 추측이 아니라 SLO나 과거 데이터로 정당화됨
- [ ] 심각도는 두 개뿐임. **page**(사용자 영향, 즉시 조치)와 **ticket**(성능 저하, 이번 주에 조치)
- [ ] 새 알림을 각각 한 번 시험 발송함. 올바른 채널에 도달하고 런북 링크가 동작함
- [ ] 매일 발생하고 조치 없이 확인 처리되는 알림이 없음

## 대시보드

- [ ] 서비스 상태 대시보드가 있음. 오류율, p99 지연 시간, 트래픽, 포화도
- [ ] 의존성 상태 패널에 서비스별 오류율과 지연 시간이 표시됨
- [ ] 대시보드가 이 체크리스트 상단의 온콜 질문에 답함. "답만 빼고 전부" 보여 주지 않음
- [ ] 기본 시간 범위가 합리적임(30d가 아니라 1h~6h)

## 텔레메트리 검증

계측도 코드이므로 잘못될 수 있다.

- [ ] 스테이징에서 오류를 강제로 발생시킨 뒤 상관관계 ID로 로그에서 찾음
- [ ] 테스트 트래픽을 보낸 뒤 예상 레이블과 합리적인 값으로 메트릭 시계열이 나타남
- [ ] 추적 UI에서 요청 하나를 처음부터 끝까지 따라가며 끊어진 스팬이 없음을 확인함
- [ ] 소스를 읽지 않고 텔레메트리만으로 유도된 장애를 진단함

## 출시 전 관문

기능을 프로덕션에 출시하기 전에 다음이 모두 참이어야 한다.

- [ ] 구조화된 로그가 로그 집계기로 흐름
- [ ] 모든 새 엔드포인트와 의존성의 RED 메트릭이 대시보드에 표시됨
- [ ] 런북이 연결된 증상 기반 알림을 하나 이상 구성하고 시험 발송함
- [ ] 요청이 거치는 모든 서비스에서 요청을 추적할 수 있음
- [ ] 온콜 담당자가 런북 위치를 알고 있음

출시 당일 모니터링 순서와 롤백 트리거는 `shipping-and-launch` 스킬을 참조한다.
