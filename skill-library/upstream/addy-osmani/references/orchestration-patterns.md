# 오케스트레이션 패턴

이 저장소가 권장하는 에이전트 오케스트레이션 패턴과 피해야 할 안티패턴을 모은 참조 카탈로그다. 여러 페르소나를 조율하는 새 슬래시 명령을 추가하거나 기존 페르소나를 "감싸는" 새 페르소나를 도입하기 전에 읽는다.

지배 원칙: **사용자(또는 슬래시 명령)가 오케스트레이터다. 페르소나는 다른 페르소나를 호출하지 않는다.** 스킬은 페르소나 워크플로 안의 필수 단계다.

---

## 권장 패턴

### 1. 직접 호출(오케스트레이션 없음)

단일 페르소나, 단일 관점, 단일 산출물이다. 기본이자 가장 저렴한 선택이다.

```
사용자 → code-reviewer → 보고서 → 사용자
```

**사용 시점:** 하나의 산출물을 하나의 관점에서 다루며 이를 한 문장으로 설명할 수 있을 때.

**예시:**
- "이 PR을 검토해 줘" → `code-reviewer`
- "`auth.ts`에서 보안 문제를 찾아 줘" → `security-auditor`
- "체크아웃 흐름에 어떤 테스트가 빠졌어?" → `test-engineer`

**비용:** 한 번의 왕복. 오케스트레이션 패턴과 항상 비교해야 할 기준선이다.

---

### 2. 단일 페르소나 슬래시 명령

프로젝트 스킬과 함께 하나의 페르소나를 감싸는 슬래시 명령이다. 사용자가 매번 워크플로를 다시 설명하지 않아도 된다.

```
/review → code-reviewer (code-review-and-quality 스킬 사용) → 보고서
```

**사용 시점:** 같은 설정으로 동일한 단일 페르소나 호출이 반복될 때.

**이 저장소의 예시:** `/review`, `/test`, `/code-simplify`.

**비용:** 직접 호출과 같다. 슬래시 명령은 저장된 프롬프트일 뿐이다.

**안티 신호:** 슬래시 명령 본문의 대부분이 "어떤 페르소나를 호출할지 결정"하는 내용이라면 삭제하고 사용자가 페르소나를 직접 호출하게 한다.

---

### 3. 병합을 포함한 병렬 팬아웃

여러 페르소나가 같은 입력을 동시에 다루며 각각 독립적인 보고서를 만든다. 병합 단계(주 에이전트의 컨텍스트)가 이를 하나의 결정으로 종합한다.

```
                    ┌─→ code-reviewer    ─┐
/ship → 병렬 분배  ───┼─→ security-auditor ─┤→ 병합 → 출시 여부 + 롤백
                    └─→ test-engineer    ─┘
```

**사용 시점:**
- 하위 작업이 실제로 독립적일 때(공유 변경 가능 상태나 순서 의존성이 없음)
- 각 하위 에이전트가 자체 컨텍스트 창의 이점을 얻을 때
- 병합 단계가 주 컨텍스트에 들어갈 만큼 작을 때
- 실제 경과 시간 지연이 중요할 때

**이 저장소의 예시:** `/ship`.

**비용:** N개의 병렬 하위 에이전트 컨텍스트와 한 번의 병합 턴. 직접 호출보다 비싸지만 실제 경과 시간은 짧고, 각 하위 에이전트가 하나의 관점에 집중하므로 더 나은 보고서를 만든다.

**이 패턴을 채택하기 전 검증 체크리스트:**
- [ ] 순서 문제 없이 모든 하위 에이전트를 동시에 실행할 수 있는가?
- [ ] 각 페르소나가 같은 발견을 다른 각도에서 말하는 데 그치지 않고 서로 다른 *종류*의 발견을 만드는가?
- [ ] 병합 단계가 주 에이전트의 남은 컨텍스트에 들어가는가?
- [ ] 병렬 처리가 실제로 체감될 만큼 사용자의 대기 시간이 긴가?

하나라도 "아니요"라면 직접 호출이나 단일 페르소나 명령으로 돌아간다.

---

### 4. 사용자가 주도하는 슬래시 명령의 순차 파이프라인

사용자가 정해진 순서로 슬래시 명령을 실행하며 명령 사이에 컨텍스트(또는 커밋 이력)를 전달한다. 오케스트레이터 에이전트는 없으며, 사용자가 곧 오케스트레이터다.

```
사용자 실행:  /spec  →  /plan  →  /build  →  /test  →  /review  →  /ship
```

**사용 시점:** 워크플로에 의존성이 있고(각 단계가 이전 단계의 출력을 필요로 함) 단계 사이의 인간 판단이 가치를 더할 때.

**이 저장소의 예시:** 전체 DEFINE → PLAN → BUILD → VERIFY → REVIEW → SHIP 생명주기.

**비용:** 단계마다 하나의 하위 에이전트 컨텍스트. 오케스트레이터 에이전트가 없으므로 오케스트레이션 계층 비용은 없다.

**자동화하지 않는 이유:** LLM "생명주기 오케스트레이터"는 (a) 인계를 위해 요약해야 하므로 단계 사이의 뉘앙스를 잃고, (b) 잘못된 방향의 작업을 일찍 잡는 사람의 확인 지점을 건너뛰며, (c) 바꿔 말하는 턴 때문에 토큰 비용을 두 배로 만든다.

---

### 5. 연구 격리(컨텍스트 보존)

주 컨텍스트를 오염시키지 말아야 할 대량의 자료를 읽어야 하는 작업에서는 요약만 반환하는 연구 하위 에이전트를 생성한다.

```
주 에이전트 → 연구 하위 에이전트(파일 50개 읽기) → 요약 → 주 에이전트 계속 진행
```

**사용 시점:**
- 주 세션이 후속 작업에 집중해야 할 때
- 조사 결과가 소비한 입력보다 훨씬 작을 때
- 이후 주 에이전트가 생각할 여유를 확보하면 결정 품질이 좋아질 때

**예시:** "모노레포 전체에서 폐기 예정 API의 모든 호출 지점을 찾아 줘", "이 30개 ADR에서 캐싱에 관해 말하는 내용을 요약해 줘."

**비용:** 격리된 하위 에이전트 컨텍스트 하나. 대안이 수백 개 파일을 주 컨텍스트에 불러오는 것이라면 언제나 그만한 가치가 있다.

**Claude Code에서는 사용자 정의 연구 페르소나를 만들지 말고 내장 `Explore` 하위 에이전트를 사용한다.** `Explore`는 Haiku에서 실행되고 쓰기/편집 도구가 거부되며 이 패턴에 맞게 설계되었다. `Explore`가 맞지 않을 때만(예: 모델이 추론하기 어려운 도메인별 시스템 프롬프트가 필요할 때) 사용자 정의 연구 하위 에이전트를 정의한다.

---

## Claude Code 호환성

이 카탈로그는 하네스에 구애받지 않지만 대부분의 독자는 Claude Code에서 실행할 것이다. 각 패턴이 Claude Code의 기본 요소에 어떻게 대응하는지, 플랫폼이 어디에서 규칙을 대신 강제하는지 설명한다.

### 페르소나 위치

플러그인 하위 에이전트는 플러그인 루트의 `agents/`에 둔다. 이 저장소는 플러그인(`.claude-plugin/plugin.json`)이므로 플러그인을 활성화하면 `agents/code-reviewer.md`, `agents/security-auditor.md`, `agents/test-engineer.md`를 자동으로 찾는다. 경로 설정은 필요 없다.

### 하위 에이전트와 Agent Teams

Claude Code에는 두 가지 병렬 처리 기본 요소가 있다. 패턴 3(병합을 포함한 병렬 팬아웃)은 **하위 에이전트**에 대응한다. 서로 대화하는 팀원이 필요하다면 대신 **Agent Teams**를 사용한다.

| | 하위 에이전트 | Agent Teams |
|--|-----------|-------------|
| 조율 | 주 에이전트가 팬아웃하고 하위 에이전트는 보고만 반환 | 팀원끼리 메시지를 주고받고 작업 목록을 공유 |
| 컨텍스트 | 하위 에이전트마다 자체 컨텍스트 창 | 팀원마다 자체 컨텍스트 창 |
| 사용 시점 | 보고서를 만드는 독립 작업 | 토론이 필요한 협업 작업 |
| 상태 | 안정적 | 실험적 — `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 필요 |
| 비용 | 낮음 | 높음 — 팀원마다 별도 Claude 인스턴스 |

**이 저장소의 페르소나는 두 모드 모두에서 동작한다.** 하위 에이전트로 생성되면(예: `/ship`) 발견 사항을 주 세션에 보고한다. 팀원으로 생성되면(`Spawn a teammate using the security-auditor agent type…`) 서로의 발견에 직접 이의를 제기할 수 있다. 페르소나 정의는 같고 생성 컨텍스트만 다르다.

한 가지 미묘한 점이 있다. 페르소나의 `skills`와 `mcpServers` frontmatter 필드는 하위 에이전트로 실행할 때는 반영되지만 **팀원으로 실행할 때는 무시된다**. 팀원은 일반 세션과 마찬가지로 프로젝트 및 사용자 설정에서 스킬과 MCP 서버를 불러온다. 페르소나가 특정 스킬이나 MCP 서버 로드에 의존한다면 두 모드 모두에서 사용할 수 있도록 세션 수준에서 구성한다.

### 플랫폼이 강제하는 규칙

이 카탈로그의 규칙 중 두 가지는 단순한 관례가 아니라 Claude Code가 강제한다.

- **"Subagents cannot spawn other subagents"**(문서 원문). 안티패턴 B(페르소나가 페르소나 호출)와 안티패턴 D(깊은 페르소나 트리)는 Claude Code의 구조상 존재할 수 없다.
- **"No nested teams"** — 팀원은 자체 팀을 생성할 수 없다. 팀 수준에서도 같은 안티패턴이 차단된다.

따라서 기여자가 실수로 안티패턴을 만들까 걱정하지 않고 이 카탈로그의 패턴을 채택할 수 있다. 그런 구성은 로드에 실패할 뿐이다.

### 알아둘 내장 하위 에이전트

사용자 정의 하위 에이전트를 정의하기 전에 다음 중 역할을 충족하는 것이 있는지 확인한다.

| 내장 항목 | 목적 |
|----------|---------|
| `Explore` | 읽기 전용 코드베이스 검색 및 분석. 패턴 5(연구 격리)에 사용한다. |
| `Plan` | 계획 모드에서 수행하는 읽기 전용 연구. |
| `general-purpose` | 탐색과 수정이 모두 필요한 다단계 작업. |

이를 다시 정의하지 않는다. 전문 페르소나(code-reviewer, security-auditor, test-engineer)를 그 위에 계층화한다.

### 플러그인 에이전트의 frontmatter 제한

플러그인 하위 에이전트는 `hooks`, `mcpServers`, `permissionMode` frontmatter 필드를 지원하지 않으며, 이 필드들은 조용히 무시된다. 향후 페르소나에 이 중 하나가 필요하다면 사용자가 파일을 `.claude/agents/` 또는 `~/.claude/agents/`로 복사해야 한다.

플러그인 에이전트에서 실제로 동작하는 필드는 `name`, `description`, `tools`, `disallowedTools`, `model`, `maxTurns`, `skills`, `memory`, `background`, `effort`, `isolation`, `color`, `initialPrompt`다. 비용을 최적화하려면 페르소나별로 `model`을 사용한다(예: `test-engineer` 커버리지 스캔에는 Haiku, `code-reviewer`에는 Sonnet, `security-auditor`에는 Opus).

### 여러 하위 에이전트를 병렬로 생성하기

Claude Code에서 병렬 팬아웃(패턴 3)을 수행하려면 **하나의 어시스턴트 턴에서 여러 Agent 도구 호출**을 실행해야 한다. 순차 턴은 실행을 직렬화한다. `/ship`은 이를 명시적으로 언급한다. 새 오케스트레이터 명령도 똑같이 해야 한다.

## 실전 예시: 경쟁 가설 디버깅을 위한 Agent Teams

이 예시는 `/ship`의 하위 에이전트 팬아웃 대신 **Agent Teams**를 사용해야 할 때를 보여 준다. 멀리서 보면 두 패턴 모두 같은 세 페르소나를 생성하므로 비슷하지만, 가치는 서로 다른 지점에서 나온다.

### 시나리오

> *체크아웃이 완료되기 전 간헐적으로 약 30초 동안 멈춥니다. 세션 약 50개당 한 번 발생합니다. 로그에는 오류가 없습니다. 지난주 릴리스 후 시작되었습니다.*

가능한 근본 원인(상호 배타적이며 모두 증상에 부합함):

1. 새 결제 확인 흐름의 경쟁 조건
2. 간헐적으로 느린 동기식 네트워크 호출로 빠지는 인증 검사
3. 장바구니 크기에 따라 확장되는 쿼리의 인덱스 누락
4. SDK가 타임아웃 전에 조용히 재시도하는 불안정한 서드파티 API

단일 에이전트는 그럴듯한 첫 번째 이론을 선택하고 조사를 멈춘다. `/ship` 방식의 하위 에이전트 팬아웃에서는 각 페르소나가 독립적으로 보고하지만 보고서끼리 만나지 않으므로 잘못된 이론을 배제하지 못한다.

이는 Agent Teams 문서가 설명하는 바로 그 사례다. *"With multiple independent investigators actively trying to disprove each other, the theory that survives is much more likely to be the actual root cause."*

### 이것이 `/ship` 작업이 *아닌* 이유

| | `/ship`(하위 에이전트) | Agent Teams |
|--|--------------------|-------------|
| 하위 에이전트가 보는 것 | 같은 diff, 서로 다른 관점 | 공유 작업 목록, 서로의 메시지 |
| 출력 | 독립 보고서 세 개 → 한 번의 병합 | 적대적 토론 → 근본 원인 합의 |
| 적합한 경우 | 알려진 산출물에 대한 판정이 필요함 | 여러 가설 중에서 산출물을 *찾아야* 함 |

`/ship`은 판정이고 Agent Teams는 조사다.

### 설정(환경별 최초 한 번)

Agent Teams는 실험적 기능이다. `~/.claude/settings.json`에서 다음과 같이 설정한다.

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

Claude Code v2.1.32 이상이 필요하다. 이 저장소의 페르소나는 자동으로 감지되므로 팀 구성 파일을 직접 작성할 필요가 없다.

### 트리거 프롬프트

리드 세션에 자연어로 다음을 입력한다.

```
사용자들이 지난주 릴리스 이후 체크아웃이 간헐적으로 약 30초간
멈춘다고 보고합니다. 로그에는 오류가 없습니다.

경쟁 가설로 디버깅할 에이전트 팀을 만드세요. 기존 에이전트 유형으로
팀원 세 명을 생성하세요.

  - code-reviewer — 체크아웃 코드 경로의 경쟁 조건과 차단 호출 조사

  - security-auditor — 인증 검사, 세션 처리,
                       최근 추가된 동기식 네트워크 호출 조사
  - test-engineer — 가설들을 구별할 테스트 제안 및
                    체크아웃 테스트 커버리지 공백 확인

팀원들이 서로 직접 메시지를 보내 각자의 이론에 이의를 제기하게 하세요.
합의가 형성되면 발견 사항을 갱신하세요. 두 팀원이 다른 이론을
반증할 수 있다는 데 동의할 때만 결론을 모으세요.
```

리드는 기존 페르소나 이름을 참조해 팀원 세 명을 생성한다. 페르소나 본문은 각 팀원의 시스템 프롬프트에 추가 지침으로 **덧붙여지고**(리드가 설치하는 팀 조율 지침 위에 추가됨), 위 트리거 프롬프트는 팀원의 작업이 된다.

### 진행 과정

1. 각 팀원은 자체 컨텍스트 창에서 코드베이스를 자신의 관점으로 탐색한다.
2. 팀원은 `message`를 사용해 서로에게 직접 발견 사항을 보낸다. 리드가 중계할 필요가 없다.
3. 공유 작업 목록에는 누가 무엇을 조사하는지 표시되며, 인프로세스 모드에서는 `Ctrl+T`, 분할 모드에서는 tmux 창으로 언제든 볼 수 있다.
4. `code-reviewer`가 순차 실행되어야 할 `Promise.all`을 발견하면 `security-auditor`에게 인증 호출이 경쟁 조건의 일부가 아닌지 확인해 달라고 메시지를 보낸다. `security-auditor`는 확인 후 경쟁 조건이 실제 문제임을 확증하거나 반대 증거를 제시한다.
5. `test-engineer`는 우세한 이론을 구별해 줄 집중 통합 테스트를 제안하고, 팀은 합의를 선언하기 전에 이를 사용해 검증한다.
6. 리드는 수렴한 발견을 종합해 사용자에게 제시한다.

`Shift+Down`으로 팀원을 순환하며 입력해 언제든 방해할 수 있다. 잘못된 경로로 빠진 조사자의 방향을 바꿀 때 유용하다.

### 정리 시점

조사가 근본 원인에 도달하면 리드에게 다음과 같이 말한다.

```
팀을 정리하세요
```

항상 팀원이 아니라 리드를 통해 정리한다(문서에 따르면 팀원에게는 정리에 필요한 전체 팀 컨텍스트가 없다).

### 예상 비용

Sonnet 팀원 세 명이 약 10~15분 조사하면 같은 세 페르소나를 `/ship`의 하위 에이전트로 생성할 때보다 눈에 띄게 비싸다. 이를 정당화하는 것은 *결론의 품질*이다. 잘못된 수정의 비용이 큰 프로덕션 디버깅에서는 추가 토큰이 충분히 가치 있다. 일상적인 PR 검토에는 `/ship`을 사용한다.

### 이 시나리오의 안티패턴

이를 하위 에이전트를 팬아웃하는 `/debug` 슬래시 명령으로 다시 만들지 **않는다**. 하위 에이전트끼리는 메시지를 주고받을 수 없으므로 이 패턴을 유용하게 만드는 적대적 토론을 잃게 된다. 워크플로가 계속 필요하다면 하위 에이전트를 잘못 사용하는 슬래시 명령으로 감싸는 대신 위 트리거 프롬프트를 스니펫으로 문서화한다.

### Agent Teams를 사용하지 *말아야* 할 때

- 알려진 diff에 대한 프로덕션 출시 판정 → `/ship`(하위 에이전트)을 사용한다.
- 하나의 산출물에 대한 한 전문가의 관점 → 페르소나를 직접 호출한다.
- 순차 생명주기(spec → plan → build) → 사용자가 주도하는 슬래시 명령(패턴 4)을 사용한다.
- 많은 내용을 읽고 짧은 요약을 만드는 연구 → 내장 `Explore` 하위 에이전트를 사용한다.

올바른 답을 만들기 위해 팀원들이 서로에게 **이의를 제기해야** 할 때만 Agent Teams를 사용한다.

## 안티패턴

### A. 라우터 페르소나("메타 오케스트레이터")

다른 어떤 페르소나를 호출할지 결정하는 것이 역할인 페르소나다.

```
/work → router-persona → "검토가 필요함" → code-reviewer → router(바꿔 말함) → 사용자
```

**실패하는 이유:**
- 도메인 가치가 없는 순수 라우팅 계층
- 바꿔 말하는 단계를 두 번 추가하여 정보 손실과 약 2배의 토큰 비용을 유발함
- 사용자는 이미 검토를 원한다는 것을 알고 있으므로 `/review`를 직접 호출할 수 있었음
- 슬래시 명령과 `AGENTS.md`의 의도 매핑이 이미 하는 작업을 복제함

**대신 할 일:** 슬래시 명령을 추가하거나 다듬는다. `AGENTS.md`에 의도 → 명령 매핑을 문서화한다.

---

### B. 다른 페르소나를 호출하는 페르소나

인증 코드를 발견하면 내부적으로 `security-auditor`를 호출하는 `code-reviewer`다.

**실패하는 이유:**
- 페르소나는 단일 관점을 만들도록 설계되었으며 연결하면 그 목적이 무너짐
- 호출하는 페르소나가 전달하는 요약에서 호출받은 페르소나에 필요한 컨텍스트가 손실됨
- 실패 모드가 늘어남(어떤 페르소나의 출력 형식을 따르는가? 누구의 규칙을 적용하는가?)
- 사용자에게 비용을 숨김

**대신 할 일:** 호출하는 페르소나가 보고서에서 후속 감사를 *권고*하게 한다. 사용자나 슬래시 명령이 두 번째 검사를 실행한다.

---

### C. 바꿔 말하는 순차 오케스트레이터

사용자를 대신해 `/spec`, `/plan`, `/build` 등을 차례로 호출하는 에이전트다.

**실패하는 이유:**
- 잘못된 방향의 작업을 잡는 사람의 확인 지점을 잃음
- 인계마다 컨텍스트를 요약하므로 긴 파이프라인에서 편차가 누적됨
- 단계마다 오케스트레이터 턴과 하위 에이전트 턴이 있어 토큰 비용이 두 배가 됨
- 판단이 가장 중요한 지점에서 사용자 주도권을 제거함

**대신 할 일:** 사용자를 오케스트레이터로 유지한다. `README.md`에 권장 순서를 문서화하고 사용자가 호출하게 한다.

---

### D. 깊은 페르소나 트리

`/ship`이 `quality-coordinator`를 호출하고, 그것이 `code-reviewer`를 호출하는 `pre-ship-coordinator`를 호출한다.

**실패하는 이유:**
- 각 계층이 결정 가치는 더하지 않고 지연 시간과 토큰만 추가함
- 디버깅이 여러 수준의 조사가 됨
- 잎 페르소나는 여러 번의 요약 단계를 거치며 컨텍스트를 잃음

**대신 할 일:** 오케스트레이션 깊이를 최대 1(슬래시 명령 → 페르소나)로 유지한다. 병합은 주 에이전트에서 일어난다.

## 결정 흐름

새 오케스트레이션 워크플로를 고려할 때 다음 흐름을 따른다.

```
하나의 산출물을 하나의 관점에서 다루는 작업인가?
├── 예 → 직접 호출. 종료.
└── 아니요 → 같은 구성이 반복되는가?
         ├── 아니요 → 필요에 따라 직접 호출. 종료.
         └── 예 → 하위 작업이 독립적인가?
                  ├── 아니요 → 사용자가 순차 슬래시 명령 실행(패턴 4).
                  └── 예 → 병합을 포함한 병렬 팬아웃(패턴 3).
                           위 체크리스트로 검증.
                           하나라도 실패하면 → 단일 페르소나 명령으로 복귀(패턴 2).
```

## 이 카탈로그에 새 패턴을 추가할 때

다음 조건을 모두 충족한 후에만 새 항목을 추가한다.

1. 실제 작업에서 해당 패턴을 두 번 이상 사용함
2. 이를 보여 주는 이 저장소의 구체적인 산출물을 지목할 수 있음
3. 기존 패턴이 동작하지 않았을 이유를 설명할 수 있음
4. 그 패턴의 안티패턴 그림자(사람들이 대신 잘못 만들게 될 것)를 설명할 수 있음

성급한 카탈로그 항목은 아무도 따르지 않는 희망 사항 문서가 된다.
