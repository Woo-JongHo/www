# 기능 개발 플러그인

코드베이스 탐색, 아키텍처 설계 및 품질 검토를 위한 전문 에이전트를 갖춘 포괄적이고 체계적인 기능 개발 워크플로입니다.

## 개요

기능 개발 플러그인은 새 기능을 구축하는 체계적인 7단계 접근법을 제공합니다. 곧바로 코드 작성에 뛰어드는 대신 코드베이스 이해, 명확화 질문, 아키텍처 설계 및 품질 보장을 안내하여 기존 코드와 매끄럽게 통합되는 더 잘 설계된 기능을 만들게 합니다.

## 철학

기능 구축에는 코드 작성 이상의 것이 필요합니다. 다음이 필요합니다.
- 변경하기 전에 **코드베이스 이해하기**
- 모호한 요구사항을 명확히 하기 위해 **질문하기**
- 구현하기 전에 **신중하게 설계하기**
- 구축한 후 **품질 검토하기**

이 플러그인은 `/feature-dev` 명령을 사용할 때 자동으로 실행되는 체계적인 워크플로에 이러한 실천 방식을 내장합니다.

## 명령: `/feature-dev`

서로 구분되는 7단계의 안내식 기능 개발 워크플로를 시작합니다.

**사용법:**
```bash
/feature-dev Add user authentication with OAuth
```

또는 간단히 다음과 같이 실행합니다.
```bash
/feature-dev
```

명령이 전체 과정을 대화형으로 안내합니다.

## 7단계 워크플로

### 1단계: 발견

**목표**: 무엇을 구축해야 하는지 이해하기

**진행 내용:**
- 기능 요청이 불명확하면 명확히 합니다
- 해결하려는 문제가 무엇인지 질문합니다
- 제약 조건과 요구사항을 식별합니다
- 이해한 내용을 요약하고 사용자에게 확인합니다

**예시:**
```
사용자: /feature-dev 캐싱 추가
Claude: 무엇이 필요한지 이해해 보겠습니다...
        - 무엇을 캐시해야 하나요? (API 응답, 계산된 값 등)
        - 성능 요구사항은 무엇인가요?
        - 선호하는 캐싱 솔루션이 있나요?
```

### 2단계: 코드베이스 탐색

**목표**: 관련 기존 코드와 패턴 이해하기

**진행 내용:**
- 2~3개의 `code-explorer` 에이전트를 병렬로 시작합니다
- 각 에이전트가 서로 다른 측면(유사 기능, 아키텍처, UI 패턴)을 탐색합니다
- 에이전트가 읽어야 할 핵심 파일을 포함한 포괄적인 분석을 반환합니다
- Claude가 식별된 모든 파일을 읽어 깊이 이해합니다
- 발견 사항의 포괄적인 요약을 제시합니다

**시작되는 에이전트:**
- "[feature]과 유사한 기능을 찾고 구현 추적하기"
- "[area]의 아키텍처와 추상화 매핑하기"
- "[related feature]의 현재 구현 분석하기"

**출력 예시:**
```
유사한 기능을 찾았습니다:
- 사용자 인증(src/auth/): JWT 토큰, middleware 패턴 사용
- 세션 관리(src/session/): Redis 기반, 24시간 만료
- API 보안(src/api/middleware/): Rate limiting, CORS

이해해야 할 핵심 파일:
- src/auth/AuthService.ts:45 - 핵심 인증 로직
- src/middleware/authMiddleware.ts:12 - 요청 인증
- src/config/security.ts:8 - 보안 구성
```

### 3단계: 명확화 질문

**목표**: 빈틈을 메우고 모든 모호성 해소하기

**진행 내용:**
- 코드베이스 발견 사항과 기능 요청을 검토합니다
- 명세가 부족한 측면을 식별합니다:
  - 경계 사례
  - 오류 처리
  - 통합 지점
  - 하위 호환성
  - 성능 요구
- 모든 질문을 정리된 목록으로 제시합니다
- **진행하기 전에 사용자의 답변을 기다립니다**

**예시:**
```
아키텍처를 설계하기 전에 다음을 명확히 해야 합니다:

1. OAuth 제공자: 어떤 OAuth 제공자를 사용하나요? (Google, GitHub, custom?)
2. 사용자 데이터: OAuth 토큰을 저장하나요, 아니면 사용자 profile만 저장하나요?
3. 기존 인증: 현재 인증을 대체하나요, 아니면 함께 추가하나요?
4. 세션: 기존 세션 관리와 통합하나요?
5. 오류 처리: OAuth 실패를 어떻게 처리하나요?
```

**중요**: 이 단계는 설계를 시작하기 전에 모호한 부분이 남지 않게 합니다.

### 4단계: 아키텍처 설계

**목표**: 여러 구현 접근법 설계하기

**진행 내용:**
- 서로 다른 관점을 가진 2~3개의 `code-architect` 에이전트를 시작합니다:
  - **최소 변경**: 가장 작은 변경, 최대한의 재사용
  - **깔끔한 아키텍처**: 유지보수성, 우아한 추상화
  - **실용적 균형**: 속도 + 품질
- 모든 접근법을 검토합니다
- 이 작업에 가장 적합한 접근법에 관한 의견을 형성합니다
- 장단점 및 권고와 함께 비교 내용을 제시합니다
- **선호하는 접근법을 질문합니다**

**출력 예시:**
```
3가지 접근법을 설계했습니다:

접근법 1: 최소 변경
- 기존 AuthService를 OAuth method로 확장
- 기존 auth router에 새 OAuth route 추가
- 최소한의 refactoring 필요
장점: 빠르고 위험이 낮음
단점: OAuth가 기존 auth와 결합되며 테스트하기 더 어려움

접근법 2: 깔끔한 아키텍처
- 전용 interface를 갖춘 새 OAuthService
- 별도의 OAuth router와 middleware
- 공통 interface를 사용하도록 AuthService refactor
장점: 깔끔한 분리, 테스트 가능, 유지보수 가능
단점: 더 많은 파일과 refactoring

접근법 3: 실용적 균형
- 새 OAuthProvider 추상화
- 기존 AuthService에 통합
- 최소한의 refactoring, 좋은 경계
장점: 복잡성과 깔끔함의 균형
단점: 일부 결합이 남음

권고: 접근법 3 - 과도한 refactoring 없이 깔끔한 경계를 제공하고
기존 아키텍처에도 잘 맞습니다.

어떤 접근법을 사용하시겠습니까?
```

### 5단계: 구현

**목표**: 기능 구축하기

**진행 내용:**
- 시작하기 전에 **명시적 승인을 기다립니다**
- 이전 단계에서 식별한 모든 관련 파일을 읽습니다
- 선택한 아키텍처에 따라 구현합니다
- 코드베이스 규칙을 엄격히 따릅니다
- 깔끔하고 문서화가 잘 된 코드를 작성합니다
- 진행에 따라 todo를 갱신합니다

**참고:**
- 사용자가 승인한 후에만 구현을 시작합니다
- 2단계에서 발견한 패턴을 따릅니다
- 4단계에서 설계한 아키텍처를 사용합니다
- 진행 상황을 지속적으로 추적합니다

### 6단계: 품질 검토

**목표**: 코드가 단순하고 DRY하며 우아하고 기능적으로 올바른지 보장하기

**진행 내용:**
- 서로 다른 관점을 가진 3개의 `code-reviewer` 에이전트를 병렬로 시작합니다:
  - **단순성/DRY/우아함**: 코드 품질과 유지보수성
  - **버그/정확성**: 기능적 정확성과 로직 오류
  - **규칙/추상화**: 프로젝트 표준과 패턴
- 발견 사항을 통합합니다
- 심각도가 가장 높은 문제를 식별합니다
- **발견 사항을 제시하고 원하는 조치를 질문합니다**:
  - 지금 수정
  - 나중에 수정
  - 현재 상태로 진행
- 사용자의 결정에 따라 문제를 처리합니다

**출력 예시:**
```
코드 검토 결과:

우선순위가 높은 문제:
1. OAuth callback에 오류 처리 누락(src/auth/oauth.ts:67)
2. 메모리 누수: OAuth state가 정리되지 않음(src/auth/oauth.ts:89)

중간 우선순위:
1. token refresh 로직을 단순화할 수 있음(src/auth/oauth.ts:120)
2. OAuth config validation 추출 고려

모든 테스트가 통과합니다. 코드는 프로젝트 규칙을 따릅니다.

어떻게 처리하시겠습니까?
```

### 7단계: 요약

**목표**: 달성한 내용 문서화하기

**진행 내용:**
- 모든 todo를 완료로 표시합니다
- 다음을 요약합니다:
  - 구축한 내용
  - 내린 핵심 결정
  - 수정한 파일
  - 제안하는 다음 단계

**예시:**
```
기능 완료: OAuth 인증

구축한 내용:
- Google과 GitHub를 지원하는 OAuth provider 추상화
- 기존 auth와 통합된 OAuth route 및 middleware
- token refresh 및 session 통합
- 모든 OAuth 흐름의 오류 처리

핵심 결정:
- OAuthProvider 추상화를 사용한 실용적 접근법 채택
- 기존 session 관리와 통합
- CSRF 방지를 위해 OAuth state 추가

수정한 파일:
- src/auth/OAuthProvider.ts (신규)
- src/auth/AuthService.ts
- src/routes/auth.ts
- src/middleware/authMiddleware.ts

제안하는 다음 단계:
- OAuth 흐름 테스트 추가
- OAuth provider 추가(Microsoft, Apple)
- 문서 갱신
```

## 에이전트

### `code-explorer`

**목적**: 실행 경로를 추적하여 기존 코드베이스 기능을 깊이 분석합니다

**중점 영역:**
- 진입점과 호출 체인
- 데이터 흐름과 변환
- 아키텍처 계층과 패턴
- 의존성과 통합
- 구현 세부 사항

**시작되는 시점:**
- 2단계에서 자동으로 시작됩니다
- 코드를 탐색할 때 수동으로 호출할 수 있습니다

**출력:**
- file:line 참조가 있는 진입점
- 단계별 실행 흐름
- 핵심 컴포넌트와 책임
- 아키텍처 통찰
- 반드시 읽어야 할 파일 목록

### `code-architect`

**목적**: 기능 아키텍처와 구현 청사진을 설계합니다

**중점 영역:**
- 코드베이스 패턴 분석
- 아키텍처 결정
- 컴포넌트 설계
- 구현 로드맵
- 데이터 흐름과 구축 순서

**시작되는 시점:**
- 4단계에서 자동으로 시작됩니다
- 아키텍처 설계를 위해 수동으로 호출할 수 있습니다

**출력:**
- 발견한 패턴과 규칙
- 근거를 포함한 아키텍처 결정
- 완전한 컴포넌트 설계
- 구체적인 파일을 포함한 구현 지도
- 단계별 구축 순서

### `code-reviewer`

**목적**: 버그, 품질 문제 및 프로젝트 규칙을 기준으로 코드를 검토합니다

**중점 영역:**
- 프로젝트 지침 준수(CLAUDE.md)
- 버그 탐지
- 코드 품질 문제
- 신뢰도 기반 필터링(신뢰도가 높은 문제 ≥80만 보고)

**시작되는 시점:**
- 6단계에서 자동으로 시작됩니다
- 코드 작성 후 수동으로 호출할 수 있습니다

**출력:**
- 심각한 문제(신뢰도 75-100)
- 중요한 문제(신뢰도 50-74)
- file:line 참조가 있는 구체적인 수정 방법
- 프로젝트 지침 참조

## 모범 사례

1. **복잡한 기능에는 전체 워크플로를 사용합니다**: 7단계가 철저한 계획을 보장합니다
2. **명확화 질문에 신중하게 답합니다**: 3단계가 이후의 혼란을 방지합니다
3. **아키텍처를 신중하게 선택합니다**: 4단계가 선택지를 제공하는 데에는 이유가 있습니다
4. **코드 검토를 건너뛰지 않습니다**: 6단계가 프로덕션에 도달하기 전에 문제를 잡습니다
5. **제안된 파일을 읽습니다**: 2단계가 핵심 파일을 식별하므로 맥락을 이해하기 위해 읽습니다

## 이 플러그인을 사용할 때

**다음에 사용합니다:**
- 여러 파일을 건드리는 새 기능
- 아키텍처 결정이 필요한 기능
- 기존 코드와의 복잡한 통합
- 요구사항이 다소 불명확한 기능

**다음에는 사용하지 않습니다:**
- 한 줄짜리 버그 수정
- 사소한 변경
- 명확히 정의된 단순한 작업
- 긴급 hotfix

## 요구사항

- Claude Code 설치

- 기존 코드베이스가 있는 프로젝트(워크플로가 학습할 기존 코드를 전제함)

## 문제 해결

### 에이전트가 너무 오래 걸림

**문제**: 코드 탐색 또는 아키텍처 에이전트가 느립니다

**해결 방법**:
- 대규모 코드베이스에서는 정상입니다
- 가능한 경우 에이전트가 병렬로 실행됩니다
- 철저한 작업은 더 나은 이해라는 결실을 맺습니다

### 명확화 질문이 너무 많음

**문제**: 3단계에서 질문을 너무 많이 합니다

**해결 방법**:
- 최초 기능 요청을 더 구체적으로 작성합니다
- 제약 조건에 관한 맥락을 미리 제공합니다
- 정말 선호하는 바가 없다면 "가장 좋다고 생각하는 대로"라고 말합니다

### 아키텍처 선택지가 부담스러움

**문제**: 4단계의 아키텍처 선택지가 너무 많습니다

**해결 방법**:
- 권고를 신뢰합니다. 코드베이스 분석을 바탕으로 한 것입니다
- 여전히 확신이 없다면 더 자세한 설명을 요청합니다
- 의심스러울 때는 실용적인 선택지를 고릅니다

## 팁

- **기능 요청을 구체적으로 작성합니다**: 세부 정보가 많을수록 명확화 질문이 줄어듭니다
- **과정을 신뢰합니다**: 각 단계는 이전 단계를 바탕으로 합니다
- **에이전트 출력을 검토합니다**: 에이전트는 코드베이스에 관한 유용한 통찰을 제공합니다
- **단계를 건너뛰지 않습니다**: 각 단계에는 목적이 있습니다
- **학습에 활용합니다**: 탐색 단계에서 자신의 코드베이스를 배울 수 있습니다
