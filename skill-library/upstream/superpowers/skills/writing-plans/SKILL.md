# 계획 작성

## 개요

이 코드베이스나 이 명세를 본 적 없는 엔지니어를 위해 구현 계획을 작성한다. 정확한 인터페이스와 정확한 테스트를 알면 프로젝트 언어의 관용적 코드를 작성하고, 계획이 선택지를 열어 둔 곳에서는 합리적인 선택을 한다고 가정한다. 그들이 알 수 없는 것은 당신이 내린 결정이다. 어느 파일인지, 어떤 이름과 시그니처인지, 명세의 어떤 값인지, 각 작업을 증명하는 테스트가 무엇인지다. 이를 문서화한다. 전체 계획을 한입 크기 작업으로 제공한다. DRY. YAGNI. TDD. 자주 커밋한다.

**시작 시 알림:** "구현 계획을 작성하기 위해 writing-plans 스킬을 사용합니다."

**맥락:** 격리된 worktree에서 작업한다면, 실행 시점에 `superpowers:using-git-worktrees` 스킬로 생성되어 있어야 한다.

**계획 저장 위치:** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- (계획 위치에 대한 사용자 선호는 이 기본값을 재정의한다)

## 범위 점검

명세가 여러 독립 하위 시스템을 다룬다면, 브레인스토밍 중 하위 프로젝트 명세로 나누었어야 한다. 그렇지 않았다면 하위 시스템당 하나씩 별도 계획으로 나눌 것을 제안한다. 각 계획은 그 자체로 작동하고 테스트 가능한 소프트웨어를 만들어야 한다.

## 파일 구조

작업을 정의하기 전, 생성하거나 수정할 파일과 각 파일의 책임을 정리한다. 여기서 분해 결정이 확정된다.

- 명확한 경계와 잘 정의된 인터페이스를 가진 단위를 설계한다. 각 파일에는 하나의 명확한 책임이 있어야 한다.
- 한 번에 맥락으로 유지할 수 있는 코드에 대해 가장 잘 추론하며, 파일이 집중되어 있을수록 편집은 더 신뢰할 수 있다. 너무 많은 일을 하는 큰 파일보다 작고 집중된 파일을 선호한다.
- 함께 변경되는 파일은 함께 두어야 한다. 기술 계층이 아니라 책임으로 분리한다.
- 기존 코드베이스에서는 확립된 패턴을 따른다. 코드베이스가 큰 파일을 사용한다면 일방적으로 재구성하지 않는다. 다만 수정 중인 파일이 다루기 어려울 정도로 커졌다면 계획에 분리를 포함하는 것은 합리적이다.

이 구조가 작업 분해의 기준이 된다. 각 작업은 독립적으로 의미 있는 자족적 변경을 만들어야 한다.

## 작업 크기 조정

작업은 자체 테스트 주기를 가지며 새로운 검토자의 게이트를 통과할 가치가 있는 가장 작은 단위다. 작업 경계를 그을 때 설정, 구성, 스캐폴딩, 문서화 단계를 결과물이 이를 필요로 하는 작업에 포함한다. 검토자가 한 작업은 거부하면서 이웃 작업은 의미 있게 승인할 수 있는 경우에만 나눈다. 각 작업은 독립적으로 테스트 가능한 결과물로 끝난다.

## 단계 세분성

**각 단계는 확인 가능한 결과가 있는 하나의 행동이다:**
- "실패하는 테스트 작성" - 단계
- "실패하는지 확인하기 위해 실행" - 단계
- "테스트를 통과시키는 최소 코드 구현" - 단계
- "테스트가 통과하는지 확인하기 위해 실행" - 단계
- "커밋" - 단계

## 계획 문서 헤더

**모든 계획은 반드시 이 헤더로 시작해야 한다:**

```markdown
# [기능 이름] 구현 계획

> **에이전트 작업자용:** 필수 하위 스킬: 이 계획을 작업별로 구현하려면 superpowers:subagent-driven-development(권장) 또는 superpowers:executing-plans를 사용한다. 단계는 추적을 위해 체크박스(`- [ ]`) 문법을 사용한다.

**목표:** [이것이 만드는 것을 설명하는 한 문장]

**아키텍처:** [접근 방식을 설명하는 2-3문장]

**기술 스택:** [주요 기술/라이브러리]

**명세:** [이 계획이 구현하는 명세/설계 문서의 경로 — 계획은 명세로부터 논증하므로 명세는 함께 이동한다. 실행자는 둘 다 읽는다]

## 전역 제약

[명세의 프로젝트 전체 요구 사항 — 버전 하한, 의존성 제한, 명명 및 카피 규칙, 플랫폼 요구 사항 — 각 줄 하나씩, 명세의 정확한 값을 그대로 복사한다. 모든 작업의 요구 사항에는 암묵적으로 이 섹션이 포함된다.]

## 검토 초점

[명세가 암시하지만 어떤 작업의 테스트도 다루지 않는, 이 소프트웨어를 사용하는 사람에게 가장 문제를 일으킬 가능성이 큰 다섯 입력 클래스 또는 실패 모드 — 입력 또는 조건과 합리적인 사람이 기대할 동작을 명시하여 각 줄 하나씩, 가능성이 큰 것을 먼저 쓴다. 명세는 비전 문서다. 소프트웨어가 해야 할 일을 말할 뿐, 충족할 모든 일을 말하지 않으며, 입력에 대해 침묵한다고 그 입력이 프로그램을 망가뜨려도 된다는 허가가 되지 않는다. 명세를 앞에 두고 여기 한 번 목록을 쓴다. 그런 다음 각 줄마다 해당 코드를 소유한 작업에, 그 작업 고유의 단계 스타일로 고정하는 테스트를 추가한다.]

---
```

## 작업 구조

````markdown
### 작업 N: [구성 요소 이름]

**파일:**
- 생성: `exact/path/to/file.py`
- 수정: `exact/path/to/existing.py:123-145`
- 테스트: `tests/exact/path/to/test.py`

**인터페이스:**
- 소비: [이 작업이 앞선 작업에서 사용하는 것 — 정확한 시그니처]
- 생산: [뒤 작업이 의존하는 것 — 정확한 함수명, 매개변수 및 반환 타입. 작업 구현자는 자기 작업만 보므로, 이 블록으로 인접 작업이 사용하는 이름과 타입을 알게 된다.]

- [ ] **1단계: 실패하는 테스트 작성**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **2단계: 실패하는지 검증하기 위해 테스트 실행**

실행: `pytest tests/path/test.py::test_name -v`
예상: "function not defined"와 함께 FAIL

- [ ] **3단계: `exact/path/to/file.py`에 `function(input: InputType) -> ResultType` 구현**

시그니처와 테스트가 선택지를 남기는 경우 접근 방식에 대한 한 줄(어떤 라이브러리 호출, 어떤 데이터 구조)을 쓴다. 그들이 결정하지 않는 알고리즘에만 코드 블록을 쓴다.

- [ ] **4단계: 통과하는지 검증하기 위해 테스트 실행**

실행: `pytest tests/path/test.py::test_name -v`
예상: PASS

- [ ] **5단계: 커밋**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 단계에 포함되는 것

구현자가 그 단계에서 정확히 하나의 합리적인 것을 작성할 수 있으면 단계가 완료된 것이다. 그것이 전체 요구 사항이다. 완전함이 아니라 모호하지 않음이다. 각 종류의 단계에는 모호하지 않게 만드는 것만 담고 그 이상은 담지 않는다.

- **테스트 단계:** 테스트 이름과 assertion을 코드로, 명세의 정확한 값을 넣어 작성한다.
- **코드 단계:** 정확한 시그니처(이름, 매개변수, 반환 타입), 파일 위치, 명세가 고정한 특정 값을 작성한다. 구현자가 본문을 작성한다. 시그니처와 테스트가 결정하지 않는 알고리즘이나 명세가 고정한 정확한 카피에만 본문을 제시한다.
- **검증 단계:** 실행할 명령과 통과를 뜻하는 출력을 작성한다.
- **다른 작업 참조:** 그 작업의 인터페이스 블록이 사용할 것을 말하므로, 계획에서 그 작업의 코드를 반복하지 않는다.

계획은 구현자가 혼자 결정할 수 없는 결정들의 집합이다. 설명하는 코드보다 긴 계획은 코드를 작성해 버린 것이다. 아무것도 결정하지 않는 줄("TBD", "엣지 케이스 처리", "적절한 검증 추가", "위 항목 테스트 작성", 어떤 작업도 정의하지 않는 타입이나 함수)은 반대의 실패이며, 자체 검토에서 둘 다 잡는다.

## 자체 검토

완전한 계획을 작성한 뒤 새로운 눈으로 명세를 보고 계획과 대조한다. 이는 직접 실행하는 체크리스트이며 하위 에이전트 파견이 아니다.

**1. 명세 범위:** 명세의 각 섹션/요구 사항을 훑는다. 이를 구현하는 작업을 가리킬 수 있는가? 누락을 나열한다.

**2. 단계 검사:** 모든 단계는 구현자가 정확히 하나의 합리적인 것을 작성하게 해야 하며, 그 이상을 담아서는 안 된다. 아무것도 결정하지 않는 줄은 누락이고, 시그니처와 테스트가 이미 결정한 함수 본문은 전사본이다. 둘 다 수정한다.

**3. 타입 일관성:** 이후 작업에 사용한 타입, 메서드 시그니처, 속성 이름이 앞선 작업에서 정의한 것과 일치하는가? 3번 작업의 `clearLayers()`가 7번 작업에서 `clearFullLayers()`로 불리면 버그다.

**4. 검토 초점:** 명세가 암시하는 각 입력 클래스 또는 실패 모드에 대해 이를 테스트하는 작업이 있는가? 사람을 가장 문제에 빠뜨릴 가능성이 큰 다섯 미포함 항목을 검토 초점 섹션에 넣고, 각 줄의 테스트를 소유 작업에 추가한다. 빈 섹션은 확인했지만 없었다는 뜻이지 검사를 건너뛰었다는 뜻이 아니다.

**5. 비율:** 계획 길이를 명세와 비교한다. 구현할 명세보다 몇 배나 긴 계획은 계획이 아니라 프로그램의 전사본이다. 코드 블록이 문서 대부분이라면 본문을 시그니처, 테스트 이름 및 assertion으로 바꾸고 각 단계가 여전히 모호하지 않은지 확인한다.

문제를 찾으면 인라인으로 수정한다. 재검토할 필요 없이 수정하고 진행한다. 작업이 없는 명세 요구 사항을 찾으면 작업을 추가한다.

## 실행 인계

계획을 저장하고 자체 검토한 뒤, 사람이 읽을 수 있도록 링크한다. 이미 실행 방법을 명시적으로 제공했다면 계획을 검토하고 원하는 내용을 담았는지 확인하도록 요청한다. 구현 전 그 검토를 기다리고, 보존된 방법을 사용한다. 그렇지 않으면 구현 전에 계획을 검토하고 실행 방법을 선택하도록 요청한다.

**실행 방법이 아직 제공되지 않았을 때:**

**"계획을 완료하여 `docs/superpowers/plans/<filename>.md`에 저장했습니다. 계획을 검토해 주세요. 어떤 실행 방식을 선호하시나요?**

- **Subagent-driven** - 새로운 하위 에이전트가 각 작업을 구현하고, 다음 작업이 시작되기 전 새로운 검토자가 검사한 뒤 마지막에 전체 브랜치를 검토한다. 가장 철저하지만 작업과 검토마다 새로운 컨텍스트가 든다.
- **Native** - 이 하니스가 작업을 실행하는 방식으로 이 세션에서 모든 작업을 직접 구현한 뒤, 가장 성능 좋은 모델의 새 검토자가 전체 브랜치를 검사한다. 가장 저렴하고 빠르지만 끝까지 독립 검토가 없다. 계획에 설계가 담겨 있으므로 중간급 세션 모델에서도 잘 동작한다.

**이 계획에는 <두 방식 중 하나>를 권합니다. <작업들이 서로의 인터페이스에 얼마나 의존하는지, 작업 수가 얼마인지, 잘못된 결과를 배포하면 어떤 비용이 드는지 계획에 근거하여 한 문장으로 설명>. 계획이 원하시는 내용을 담고 있나요? 어떤 방식을 사용할까요?"**

**실행 방법이 이미 제공되었을 때:**

**"계획을 완료하여 `docs/superpowers/plans/<filename>.md`에 저장했습니다. 계획을 검토해 주세요. 원하시는 내용을 담고 있나요?"**

**Subagent-driven을 선택한 경우:**
- **필수 하위 스킬:** superpowers:subagent-driven-development 사용

**Native를 선택한 경우:**
- **필수 하위 스킬:** superpowers:executing-plans 사용
