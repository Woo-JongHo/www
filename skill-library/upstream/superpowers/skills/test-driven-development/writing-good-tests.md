# 좋은 테스트 작성하기

**다음 경우 이 참고 자료를 로드하세요:** 테스트를 작성하거나 변경할 때, 목을 추가할 때, 또는 테스트용 정리/헬퍼 메서드를 추가할 때.

## 개요

테스트는 특정한 문제를 포착하기 위해 존재합니다. 여기의 모든 것을 지배하는 두 가지 원칙이 있습니다:

```
1. 모든 테스트는 자신이 포착하는 문제를 이름으로 나타낸다
2. 모든 테스트는 실제 대상을 실행한다
```

엄격한 TDD는 두 가지를 자연스럽게 만들어 냅니다. 실제 코드에 대해 먼저 작성하고 실패하는 것을 확인한 테스트는 이미 실패할 수 있음을 증명했고, 실제 의존성이 느리거나 외부에 있을 때만 목을 사용할 자격을 얻습니다.

## 원칙 1: 문제의 이름을 붙이기

테스트 본문을 작성하기 전에 답하세요. **어떤 프로덕션 변경이 이 테스트를 실패하게 해야 하며, 그 변경은 버그인가 결정인가?** 테스트는 잘못된 분기, 누락된 부수 효과, 잘못된 인수, 경계 사례 또는 깨진 계약을 포착함으로써 존재할 자격을 얻습니다.

**기대값을 독립적으로 도출하세요.** 리터럴과 직접 확인한 픽스처를 사용하세요. 리터럴 `want` 값을 사용하는 테이블 주도 테스트가 권장되는 형태입니다. 테스트 대상 코드 또는 그 헬퍼가 계산한 기대값은 그 코드가 무엇을 하든 통과합니다:

```typescript
// ❌ Mirror assertion: the same builder computes both sides — always true
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ Hand-derived literal
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**변경 감지기를 만들지 마세요.** 상수 값, 정확한 메시지 문구, 비공개 구조처럼 의도적인 결정만이 테스트를 실패시킬 수 있다면, 재설계 시에는 울리지만 버그가 생기면 잠듭니다. 결정에 의존하는 동작을 테스트하세요. `expect(MAX_RETRIES).toBe(5)`가 아니라 "실패한 호출은 5회 재시도되고 6번째 시도는 절대 일어나지 않는다"를 테스트하세요.

**텍스트가 아니라 동작을 테스트하세요.** 스크립트, 스킬 또는 구성에 정확한 줄이 포함되었는지 단언하면 소스가 소스임만 증명합니다. 통제된 입력으로 스크립트를 실행하고 출력, 부수 효과 또는 종료 코드를 단언하세요. 에이전트에게 지시하는 문서는 소비 에이전트의 동작으로 테스트합니다(superpowers:writing-skills). 사람을 위한 산문에는 테스트가 전혀 필요하지 않습니다.

**프레임워크가 아니라 자신의 코드를 테스트하세요.** 경계에서 코드가 만드는 계약, 즉 등록하는 라우트, 내보내는 쿼리, 생성하는 페이로드를 테스트하세요. 업스트림 메커니즘은 그 유지 관리자가 작성할 테스트입니다(전형적인 예: 라우터가 등록된 핸들러를 호출한다고 단언하는 것은 자신의 테스트가 아니라 프레임워크의 테스트입니다). 업스트림 동작이 정말 예상 밖이었을 때는 그 가정을 이름으로 나타내는 좁은 특성화 테스트 하나를 작성하세요. 같은 경계는 코드 내부에도 적용됩니다. 생성자, getter, 상수, 단순 전달은 검증, 정규화, 기본값 설정, 도출, 강제 또는 부수 효과를 수행할 때에만 테스트할 가치가 있습니다. 그렇지 않으면 이에 의존하는 소비자에게 처음으로 보이는 결과를 단언하세요.

### 게이트 함수

```
테스트 본문을 작성하기 전에:
  이 테스트를 실패하게 할 프로덕션 변경의 이름을 붙인다.

  이름을 붙일 수 없음          → 관찰 가능한 동작 중심으로 재설계
  "소스 텍스트가 바뀜"         → 아티팩트를 실행하고 그 효과를 단언
  의도적인 결정만 해당         → 변경 감지기; 그 결정에
                               의존하는 동작을 테스트

  기대값이 테스트 대상 코드 없이 도출되었는지 확인한다.
  코드의 로직이나 헬퍼를 재사용한다면:
    리터럴 또는 직접 확인한 픽스처로 바꾼다
```

## 원칙 2: 실제 대상을 실행하기

**목은 단언할 자격이 없습니다.** 목 단언은 목이 있으면 통과하고 없으면 실패합니다. 이는 컴포넌트에 관해 아무 말도 하지 않습니다. 실제 컴포넌트의 동작을 단언하세요. 확인하는 것이 목이라면 목을 해제하거나 단언을 삭제하세요.

```typescript
// ✅ Real behavior
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ Mock existence
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**사람 파트너의 교정:** "목의 동작을 테스트하고 있는 건가요?"

**올바른 수준에서 목을 사용하세요.** 실제 메서드를 대체하기 전에 모든 부수 효과를 파악하세요. 느리거나 외부인 작업을 목으로 대체하고 테스트가 의존하는 것은 실제로 유지하세요. 확실하지 않으면 먼저 실제 구현에 대해 테스트를 실행하고 실제로 무슨 일이 일어나야 하는지 관찰하세요.

```typescript
// ❌ The mock swallows the config write that duplicate detection reads
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ Mock only the slow server startup; the config write stays real
vi.mock('MCPServerManager');
```

**테스트 대역을 구체적으로 만드세요.** 인수, 호출 횟수 또는 순서가 계약의 일부일 때는 이를 단언하세요. 무엇이든 받아들이는 가짜는 아무것도 검증하지 않습니다. 잘못된 분기가 기대를 만족할 수 없도록 각 분기(성공, 오류, 잘못된 형식)에 자체 픽스처 또는 스파이를 부여하세요.

**실제 데이터를 완전하게 반영하세요.** 테스트가 읽는 필드만이 아니라 현실에 존재하는 모든 문서화된 필드를 포함해 완전한 구조를 목으로 만드세요. 부분 목은 다운스트림 코드가 누락된 필드를 읽을 때 조용히 실패합니다. 테스트는 통과하지만 통합은 깨집니다.

**프로덕션 클래스에는 프로덕션 메서드만 둡니다.** 테스트만 필요한 정리는 프로덕션 클래스의 `destroy()`가 아니라 테스트 유틸리티에 둡니다. 질문하세요: 이 메서드는 테스트에서만 호출되는가? 이 클래스는 이 리소스의 수명 주기를 소유하는가? 잘못된 답 → 테스트 유틸리티입니다.

**복잡한 목보다 실제 컴포넌트를 선호하세요.** 목 설정이 테스트 로직보다 커지거나, 목이 실제 컴포넌트에 있는 메서드를 놓치거나, 목이 바뀔 때 테스트가 깨지면 실제 컴포넌트를 사용하는 통합 테스트로 전환하세요. **사람 파트너의 질문:** "여기서 목을 사용해야 하나요?"

### 게이트 함수

```
목 또는 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부수 효과를 나열한다. 테스트가
  의존하는 것은 실제로 유지하고, 그 아래의 느린/외부 수준을 목으로 대체한다.

  목 응답은 실제의 완전한 구조를 반영한다.

  테스트만 호출하는 메서드는 프로덕션이 아니라 테스트 유틸리티에 둔다.

  목 자체를 단언하려고 하는가?
    목을 해제하거나 단언을 삭제한다.
```

## 테스트는 구현과 함께 제공됩니다

실패하는 테스트, 최소 구현, 리팩터링으로 이루어진 TDD 주기가 "완료"의 의미입니다. 동작에 필요한 테스트와 그 테스트만 제공하세요. 사소한 코드와 사람을 위한 산문에는 테스트가 필요 없고, 프로세스를 만족시키기 위해 작성한 테스트는 영원히 유지 비용을 발생시킵니다.

## 변이 검사

완료하기 전에 프로덕션 코드를 머릿속으로 변이시키세요. 현실적인 각 변이에 대해 최소 하나의 테스트가 실패해야 합니다:

- 잘못된 상수 또는 인수
- 잘못된 분기 핸들러
- 누락된 상태 변경 또는 부수 효과
- 비어 있거나 기본값인 반환
- 0, 빈 값, nil, 권한 없음 또는 잘못된 형식 입력에 대한 검증 누락

아무 테스트도 포착하지 못하는 변이는 동작이 보호되지 않았거나 테스트가 동어반복임을 나타냅니다.

## 경고 신호

- 설정과 단언이 같은 객체를 공유하여 동등함이 보장됨
- 패닉, 충돌 또는 누락된 선택자로만 테스트가 실패할 수 있음
- 테스트가 의도적인 모든 변경에는 실패하고 우발적인 손상에는 절대 실패하지 않음
- 기대값이 반복문, 빌더 또는 헬퍼 뒤에 숨음
- 테스트가 소스 텍스트를 grep하거나 제거된 심볼이 계속 제거된 상태인지 단언함
- 프레임워크만 남아도 테스트가 여전히 중요함
- 테스트가 커버리지를 위해 존재하며 부수 효과나 결과를 확인하지 않음
- 단언이 `*-mock` 테스트 ID를 확인하거나 목을 제거하면 실패함
- 메서드가 테스트 파일에서만 호출됨
- 목 설정이 테스트의 절반 이상이거나 목이 필요한 이유를 설명할 수 없음
- "안전을 위해" 목 처리함
