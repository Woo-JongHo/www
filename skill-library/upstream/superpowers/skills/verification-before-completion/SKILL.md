# 완료 전 검증

## 개요

**핵심 원칙:** 항상 주장보다 증거를 우선한다.

**이 규칙의 문구를 어기는 것은 그 취지도 어기는 일이다.**

## 절대 법칙

```
최신 검증 증거 없이는 완료를 주장하지 않는다
```

이 메시지에서 검증 명령을 실행하지 않았다면, 통과했다고 주장할 수 없다.

## 게이트 함수

```
상태를 주장하거나 만족을 표현하기 전:

1. 식별: 이 주장을 증명하는 명령은 무엇인가?
2. 실행: 전체 명령을 실행한다(최신, 완전).
3. 읽기: 전체 출력을 읽고, 종료 코드를 확인하고, 실패 수를 센다.
4. 검증: 출력이 주장을 확인하는가?
   - 아니오: 증거와 함께 실제 상태를 말한다.
   - 예: 증거와 함께 주장을 말한다.
5. 그 후에만: 주장을 한다.

어느 단계든 건너뛰기 = 검증이 아니라 거짓말
```

## 흔한 실패

| 주장 | 필요 사항 | 불충분한 사항 |
|-------|----------|----------------|
| 테스트 통과 | 테스트 명령 출력: 실패 0건 | 이전 실행, "통과해야 함" |
| 린터 깨끗함 | 린터 출력: 오류 0건 | 부분 검사, 추론 |
| 빌드 성공 | 빌드 명령: 종료 0 | 린터 통과, 로그가 좋아 보임 |
| 버그 수정됨 | 원래 증상을 검사: 통과 | 코드 변경, 수정되었다고 가정 |
| 회귀 테스트 작동 | Red-Green 사이클 검증 | 테스트가 한 번 통과 |
| 에이전트 완료 | VCS diff가 변경을 보임 | 에이전트가 "성공" 보고 |
| 요구 사항 충족 | 줄 단위 체크리스트 | 테스트 통과 |

## 위험 신호 - 중지

- "그럴 것이다", "아마", "그런 것 같다"라는 표현 사용
- 검증 전 만족 표현("좋아!", "완벽해!", "완료!" 등)
- 검증 없이 커밋/push/PR하려 함
- 에이전트 성공 보고를 신뢰함
- 부분 검증에 의존함
- "이번 한 번만"이라고 생각함
- 피곤해서 작업을 끝내고 싶음
- **검증을 실행하지 않은 채 성공을 암시하는 모든 표현**

## 합리화 방지

| 변명 | 현실 |
|--------|---------|
| "이제 작동해야 해" | 검증을 실행하라 |
| "확신해" | 확신 ≠ 증거 |
| "이번 한 번만" | 예외 없음 |
| "린터가 통과했어" | 린터 ≠ 컴파일러 |
| "에이전트가 성공했다고 했어" | 독립적으로 검증하라 |
| "피곤해" | 피로 ≠ 변명 |
| "부분 검사는 충분해" | 부분 검사는 아무것도 증명하지 못함 |
| "다른 표현이니 규칙이 적용되지 않아" | 문구보다 취지 |

## 핵심 패턴

**테스트:**
```
✅ [테스트 명령 실행] [확인: 34/34 통과] "모든 테스트 통과"
❌ "이제 통과해야 해" / "올바르게 보임"
```

**회귀 테스트(TDD Red-Green):**
```
✅ 작성 → 실행(통과) → 수정 되돌리기 → 실행(반드시 실패) → 복원 → 실행(통과)
❌ "회귀 테스트를 작성했어"(red-green 검증 없이)
```

**빌드:**
```
✅ [빌드 실행] [확인: 종료 0] "빌드 통과"
❌ "린터 통과"(린터는 컴파일을 검사하지 않음)
```

**요구 사항:**
```
✅ 계획 다시 읽기 → 체크리스트 작성 → 각각 검증 → 누락 또는 완료 보고
❌ "테스트 통과, 단계 완료"
```

**에이전트 위임:**
```
✅ 에이전트 성공 보고 → VCS diff 확인 → 변경 검증 → 실제 상태 보고
❌ 에이전트 보고 신뢰
```

## 적용 시점

**항상 다음 전에:**
- 성공/완료 주장에 대한 모든 변형
- 모든 만족 표현
- 작업 상태에 관한 모든 긍정적 진술
- 커밋, PR 생성, 작업 완료
- 다음 작업으로 이동
- 에이전트에게 위임

**규칙 적용 대상:**
- 정확한 문구
- 바꿔 말한 표현과 동의어
- 성공의 함의
- 완료/정확성을 시사하는 모든 의사소통
