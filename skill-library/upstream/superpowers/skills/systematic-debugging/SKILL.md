# 체계적 디버깅

## 개요

**핵심 원칙:** 수정을 시도하기 전에 항상 근본 원인을 찾습니다. 증상만 고치는 것은 실패입니다.

**이 프로세스의 문구를 어기는 것은 디버깅의 취지도 어기는 일입니다.**

## 철칙

```
근본 원인 조사 없이는 수정하지 않는다
```

1단계를 완료하지 않았다면 수정안을 제시할 수 없습니다.

## 사용 시점

모든 기술 문제에 사용합니다:
- 테스트 실패
- 프로덕션 버그
- 예기치 않은 동작
- 성능 문제
- 빌드 실패
- 통합 문제

**특히 다음 경우에 사용합니다:**
- 시간 압박이 있을 때(긴급 상황은 추측을 유혹함)
- "빠른 수정 하나만"이 명백해 보일 때
- 이미 여러 수정을 시도했을 때
- 이전 수정이 효과가 없었을 때
- 문제를 완전히 이해하지 못할 때

**다음 경우에도 건너뛰지 마세요:**
- 문제가 단순해 보일 때(단순한 버그에도 근본 원인이 있음)
- 서두를 때(서두르면 반드시 재작업하게 됨)
- 관리자가 지금 당장 수정하라고 할 때(체계적인 방식이 마구 시도하는 것보다 빠름)

## 네 단계

다음 단계로 진행하기 전에 각 단계를 반드시 완료해야 합니다.

### 1단계: 근본 원인 조사

**수정을 시도하기 전에:**

1. **오류 메시지를 주의 깊게 읽기**
   - 오류나 경고를 넘기지 마세요
   - 종종 정확한 해결책이 들어 있습니다
   - 스택 추적을 완전히 읽으세요
   - 줄 번호, 파일 경로, 오류 코드를 기록하세요

2. **일관되게 재현하기**
   - 신뢰성 있게 트리거할 수 있나요?
   - 정확한 단계는 무엇인가요?
   - 매번 발생하나요?
   - 재현할 수 없다면 → 더 많은 데이터를 수집하고 추측하지 마세요

3. **최근 변경 사항 확인하기**
   - 이를 유발할 수 있는 변경 사항은 무엇인가요?
   - Git diff, 최근 커밋
   - 새 의존성, 설정 변경
   - 환경 차이

4. **다중 구성 요소 시스템에서 증거 수집하기**

   **시스템에 여러 구성 요소가 있을 때(CI → build → signing, API → service → database):**

   **수정안을 제시하기 전에 진단 계측을 추가하세요:**
   ```
   각 구성 요소 경계마다:
     - 구성 요소에 들어오는 데이터 기록
     - 구성 요소에서 나가는 데이터 기록
     - 환경/설정 전파 검증
     - 각 계층의 상태 점검

   어디에서 중단되는지 보여 주는 증거를 수집하기 위해 한 번 실행
   그런 다음 증거를 분석하여 실패한 구성 요소 식별
   그런 다음 해당 구성 요소 조사
   ```

   **예시(다중 계층 시스템):**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY in environment" || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **이것이 보여 주는 것:** 어느 계층이 실패하는지(secrets → workflow ✓, workflow → build ✗)

5. **데이터 흐름 추적하기**

   **오류가 호출 스택 깊은 곳에 있을 때:**

   완전한 역방향 추적 기법은 이 디렉터리의 `root-cause-tracing.md`를 참조하세요.

   **간단 버전:**
   - 잘못된 값은 어디에서 시작되나요?
   - 무엇이 잘못된 값으로 이를 호출했나요?
   - 원본을 찾을 때까지 계속 위로 추적하세요
   - 증상이 아니라 원본에서 수정하세요

### 2단계: 패턴 분석

**수정하기 전에 패턴을 찾으세요:**

1. **작동하는 예제 찾기**
   - 같은 코드베이스에서 유사하게 작동하는 코드를 찾으세요
   - 망가진 것과 유사하지만 작동하는 것은 무엇인가요?

2. **참조와 비교하기**
   - 패턴을 구현 중이라면 참조 구현을 완전히 읽으세요
   - 훑어보지 말고 모든 줄을 읽으세요
   - 적용하기 전에 패턴을 완전히 이해하세요

3. **차이점 식별하기**
   - 작동하는 것과 망가진 것의 차이는 무엇인가요?
   - 아무리 사소해도 모든 차이를 나열하세요
   - "그건 중요할 리 없어"라고 가정하지 마세요

4. **의존성 이해하기**
   - 이것에 필요한 다른 구성 요소는 무엇인가요?
   - 어떤 설정, 구성, 환경이 필요한가요?
   - 어떤 가정을 하나요?

### 3단계: 가설과 테스트

**과학적 방법:**

1. **단일 가설 세우기**
   - 명확히 진술하세요: "Y 때문에 X가 근본 원인이라고 생각합니다"
   - 기록하세요
   - 모호하지 않게 구체적으로 하세요

2. **최소한으로 테스트하기**
   - 가설을 테스트할 수 있는 가장 작은 변경을 만드세요
   - 한 번에 하나의 변수만 바꾸세요
   - 한꺼번에 여러 가지를 고치지 마세요

3. **계속하기 전에 검증하기**
   - 작동했나요? 예 → 4단계
   - 작동하지 않았나요? 새로운 가설을 세우세요
   - 그 위에 더 많은 수정을 추가하지 마세요

4. **모를 때**
   - "X를 이해하지 못합니다"라고 말하세요
   - 안다고 가장하지 마세요
   - 도움을 요청하세요
   - 더 조사하세요

### 4단계: 구현

**증상이 아니라 근본 원인을 수정하세요:**

1. **실패하는 테스트 사례 만들기**
   - 가능한 가장 단순한 재현
   - 가능하면 자동화된 테스트
   - 프레임워크가 없으면 일회성 테스트 스크립트
   - 수정 전에 반드시 있어야 함
   - 적절한 실패 테스트 작성은 `superpowers:test-driven-development` 스킬을 사용하세요

2. **단일 수정 구현하기**
   - 식별한 근본 원인을 해결하세요
   - 한 번에 하나만 변경
   - "여기까지 왔으니" 개선 금지
   - 묶음 리팩터링 금지

3. **수정 검증하기**
   - 이제 테스트가 통과하나요?
   - 다른 테스트는 망가지지 않았나요?
   - 문제가 실제로 해결되었나요?
   - 성공을 주장하기 전에 `superpowers:verification-before-completion` 스킬을 사용하세요

4. **수정이 효과가 없을 때**
   - 멈추세요
   - 몇 번의 수정을 시도했는지 세세요
   - 3회 미만이면: 1단계로 돌아가 새 정보로 다시 분석
   - **3회 이상이면: 멈추고 아키텍처를 의심하세요(아래 5단계)**
   - 아키텍처 논의 없이 수정 #4를 시도하지 마세요

5. **3회 이상 수정이 실패한 경우: 아키텍처 의심하기**

   **아키텍처 문제를 나타내는 패턴:**
   - 각 수정이 서로 다른 위치의 새로운 공유 상태/결합/문제를 드러냄
   - 수정을 구현하려면 "대규모 리팩터링"이 필요함
   - 각 수정이 다른 곳에서 새 증상을 만듦

   **멈추고 근본을 의심하세요:**
   - 이 패턴은 근본적으로 타당한가요?
   - "순전히 관성 때문에 계속 고수하고 있는가?"
   - 증상을 계속 수정하는 대신 아키텍처를 리팩터링해야 하나요?

   **추가 수정을 시도하기 전에 인간 파트너와 논의하세요**

   이것은 실패한 가설이 아니라 잘못된 아키텍처입니다.

## 위험 신호 - 멈추고 프로세스를 따르기

다음과 같이 생각하는 자신을 발견한다면:
- "지금은 빠르게 수정하고 나중에 조사하자"
- "X를 바꿔 보고 작동하는지 보자"
- "여러 변경을 추가하고 테스트를 실행하자"
- "테스트를 건너뛰고 수동으로 확인하자"
- "아마 X일 테니 수정하자"
- "완전히 이해하지는 못하지만 이건 작동할 수 있어"
- "패턴에는 X라고 되어 있지만 다르게 적용하겠어"
- "주요 문제는 이거야: [조사 없이 수정 목록을 나열함]"
- 데이터 흐름을 추적하기 전에 해결책 제시
- **"수정을 한 번 더 시도하자"(이미 2회 이상 시도했을 때)**
- **각 수정이 서로 다른 위치의 새 문제를 드러냄**

**이 모든 것은 다음을 의미합니다: 멈추세요. 1단계로 돌아가세요.**

**수정이 3회 이상 실패한 경우:** 아키텍처를 의심하세요(4.5단계 참조)

## 인간 파트너가 당신이 잘못하고 있음을 알리는 신호

**다음과 같은 방향 전환에 주의하세요:**
- "그게 일어나지 않는 건가?" - 검증 없이 가정함
- "그게 우리에게 보여 줄까...?" - 증거 수집을 추가했어야 함
- "추측하지 마" - 이해 없이 수정안을 제시함
- "이를 더 깊이 생각해 봐" - 증상만이 아니라 근본을 의심해야 함
- "우리가 막힌 건가?"(좌절한 상태) - 접근 방식이 작동하지 않음

**이런 신호를 보면:** 멈추고 1단계로 돌아가세요.

## 흔한 합리화

| 변명 | 현실 |
|--------|---------|
| "문제가 단순하니 프로세스가 필요 없어" | 단순한 문제에도 근본 원인이 있습니다. 프로세스는 단순한 버그에 빠릅니다. |
| "긴급 상황이라 프로세스에 쓸 시간이 없어" | 체계적 디버깅은 추측하고 확인하며 허둥대는 것보다 빠릅니다. |
| "이것만 먼저 시도하고 조사할게" | 첫 수정이 패턴을 정합니다. 처음부터 제대로 하세요. |
| "수정이 작동하는지 확인한 후 테스트를 작성할게" | 테스트되지 않은 수정은 유지되지 않습니다. 테스트 우선은 이를 증명합니다. |
| "한꺼번에 여러 수정을 하면 시간이 절약돼" | 무엇이 작동했는지 분리할 수 없습니다. 새 버그를 만듭니다. |
| "참조가 너무 길어서 패턴을 변형할게" | 부분적 이해는 버그를 보장합니다. 완전히 읽으세요. |
| "문제가 보이니 수정할게" | 증상을 보는 것 ≠ 근본 원인을 이해하는 것. |
| "수정을 한 번 더 시도하자"(2회 이상 실패 후) | 3회 이상 실패 = 아키텍처 문제. 다시 수정하지 말고 패턴을 의심하세요. |

## 빠른 참조

| 단계 | 핵심 활동 | 성공 기준 |
|-------|---------------|------------------|
| **1. 근본 원인** | 오류 읽기, 재현, 변경 확인, 증거 수집 | 무엇과 왜를 이해함 |
| **2. 패턴** | 작동하는 예제 찾기, 비교 | 차이점 식별 |
| **3. 가설** | 이론 수립, 최소 테스트 | 확정되었거나 새 가설 |
| **4. 구현** | 테스트 생성, 수정, 검증 | 버그 해결, 테스트 통과 |

## 프로세스가 "근본 원인 없음"을 드러낼 때

체계적 조사를 통해 문제가 실제로 환경적이거나, 타이밍 의존적이거나, 외부적임이 밝혀진 경우:

1. 프로세스를 완료했습니다
2. 조사한 내용을 문서화하세요
3. 적절한 처리(retry, timeout, error message)를 구현하세요
4. 미래 조사를 위해 모니터링/로깅을 추가하세요

**하지만:** "근본 원인 없음" 사례의 95%는 불완전한 조사입니다.

## 지원 기법

이 기법들은 체계적 디버깅의 일부이며 이 디렉터리에서 사용할 수 있습니다:

- **`defense-in-depth.md`** - 근본 원인을 찾은 뒤 여러 계층에 검증 추가
- **`condition-based-waiting.md`** - 임의 시간 초과를 조건 폴링으로 대체
