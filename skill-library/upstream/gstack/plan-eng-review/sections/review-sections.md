## 기록 검토 및 쓰기 정책

- **대상:** Scope 게이트에서 선택한 계획, 차이점 또는 코드 경로입니다. 고정된 상태로 유지됩니다.
- **작업 계획:** 제안된 작업 및 현재 승인. 계획 대상으로는
  그 계획부터 시작하세요. 코드의 경우 결과를 바탕으로 해결 계획을 수립합니다. 이것은
  구현을 편집하거나 다른 파일을 생성할 수 있는 권한이 아니라 콘텐츠를 검토할 수 있는 권한입니다.
- **보고서 파일:** 작업 계획, 조사 결과, 결정을 위한 단일 대상
  원장 및 최종 구조화된 보고서. 선택한 계획일 수도 있고 별도의 파일일 수도 있습니다.

| 대상 | 조사할 증거 |
|---|---|
| 계획 또는 설계 문서 | 기존 인터페이스 및 테스트와 비교하여 확인된 제안된 경로 |
| 지점 차이 | 진입점에서 추적된 변경된 동작 및 주변 코드 |
| 특정 파일 또는 디렉터리 | 기존 동작 및 관련 호출자/테스트 |

테스트 검토 또는 외부 음성이 계획을 언급하는 경우 현재 작업 중인 계획을 사용합니다.

별도로. 외부 음성의 제한된 입력에 실제 결정을 포함합니다.

## 사전 학습

이전 세션에서 관련 학습 내용을 검색하세요.

```bash
_CROSS_PROJ=$(~/.claude/skills/gstack/bin/gstack-config get cross_project_learnings 2>/dev/null || echo "unset")
echo "CROSS_PROJECT: $_CROSS_PROJ"
if [ "$_CROSS_PROJ" = "true" ]; then
  { _LE=$(~/.claude/skills/gstack/bin/gstack-learnings-search --limit 10 --cross-project 2>&1 >&3 3>&-); _LR=$?; } 3>&1
else
  { _LE=$(~/.claude/skills/gstack/bin/gstack-learnings-search --limit 10 2>&1 >&3 3>&-); _LR=$?; } 3>&1
fi
[ "$_LR" = 0 ] || { _LE=${_LE%%$'\n'*}; echo "LEARNINGS: unavailable (${_LE:-exit $_LR})"; }
```

`CROSS_PROJECT`이 `unset`인 경우(처음): 서문 형식을 사용하여 이러한 사실과 옵션으로부터 전체 결정 요약을 작성한 후 질문하고 기다립니다.

## 신뢰도 교정

모든 결과 MUST에는 심각도 CRITICAL(배송 차단) 또는 INFORMATIONAL가 포함됩니다.
(심각도가 낮지만 여전히 조치를 취하고 있음) 및 신뢰도 점수(1~10):

| 점수 | 의미 | 표시 규칙 |
|-------|---------|-------------|
| 9-10 | 특정 코드를 읽어서 확인했습니다. 구체적인 버그나 익스플로잇이 시연되었습니다. | 정상적으로 표시 |
| 7-8 | 높은 신뢰도 패턴 일치. 아마도 정확할 것입니다. | 정상적으로 표시 |
| 5-6 | 보통의. 거짓 긍정일 수 있습니다. | 경고와 함께 표시: "보통 신뢰도, 이것이 실제로 문제인지 확인하십시오." |
| 3-4 | 낮은 자신감. 패턴이 의심스럽긴 하지만 괜찮을 수도 있습니다. | 기본 보고서에서 억제합니다. 부록에만 포함합니다. |
| 1-2 | 추측. | 릴리스를 차단하는 것으로 의심되는 재앙(광범위한 데이터 손실, 전체 중단 또는 시스템 전체 손상)만 CRITICAL 심각도로 보고하고 명시적으로 추측으로 표시합니다. |

**찾기 형식:**

`[CRITICAL|INFORMATIONAL] (confidence: N/10) file:line — description`

예:
`[CRITICAL] (confidence: 9/10) app/models/user.rb:42 — SQL injection via string interpolation in where clause`
`[INFORMATIONAL] (confidence: 5/10) app/controllers/api/v1/users_controller.rb:18 — Possible N+1 query, verify with production logs`

### 사전 방출 검증 게이트

1. **발견에 동기를 부여하는 특정 코드 라인을 인용하십시오** — file:line plus
   이를 트리거한 줄의 축어적 텍스트입니다. 결과가 "필드"인 경우
   X는 모델 Y에 존재하지 않습니다." 필드가 있는 클래스 Y의 행을 인용합니다.
   살 것이다. "dict.get()이 None을 반환할 수 있는 경우" dict 초기화를 인용하세요.
   "A와 B 사이의 경쟁 조건"인 경우 A와 B를 모두 인용합니다.

2. **동기 부여 문구를 인용할 수 없으면 결과가 검증되지 않은 것입니다.**
   자신감을 4-5로 만듭니다. 메인에서 억제해야 할 경우 4를 사용하십시오.
   보고; 신뢰도가 중간인 보고서에 속하는 경우에만 5를 사용하세요.
   주의 사항. 투기적 자신감을 만들어내지 마세요 7+.

**프레임워크-메타 넛지:** 프레임워크에 의해 기호가 생성되는 경우
메타클래스, 설명자, ORM 메타 내부 클래스 또는 마이그레이션 기록(Django
`Meta`, 레일 `has_many`/`scope`, SQLAlchemy `relationship`/`Column`,
TypeORM 데코레이터, Sequelize `init`/`belongsTo`, Prisma 생성 클라이언트),
메타 구성(`Meta` 블록, 마이그레이션, 데코레이터,
스키마 파일) 클래스 본문에서 리터럴 이름을 기대하는 대신.
검증은 "이 심벌을 생성하는 소스를 읽었다"는 것이지 "이름을 grep했지만 찾지 못했다"는 것이 아니다.

게이트가 포착하는 거짓양성 클래스:

| FP반 | 게이트가 그것을 잡는 이유 |
|---|---|
| "모델에 필드가 존재하지 않습니다." | 모델 클래스 본문 또는 메타를 인용해야 합니다. 필드의 부재가 분명해진다 |
| "dict.get()은 None일 수 있습니다." | dict 초기화를 인용해야 합니다(예: Django 양식의 `cleaned_data`은 `{}`-초기화됨) |
| "save()는 필드를 잃을 수 있습니다." | ORM 서명 또는 모델 정의를 인용해야 합니다 |
| "update_fields가 X를 놓칠 수 있음" | 필드 세트를 인용해야 합니다. X가 존재하지 않으면 FP는 자명합니다 |

**보정 학습:** 점수가 < 7인 보고된 결과를 사용자가 확인한 경우
실제로는 수정된 패턴을 학습으로 기록합니다.

   또는 저장 세부 사항)은 둘 이상의 모듈에 있습니다. 재수출 운송
   유형은 누출입니다. 외부 데이터를 경계에서 도메인 유형으로 구문 분석합니다.
3. **시간적 분해.** 실행 순서(로드,
   자신이 소유한 지식을 사용하는 대신 검증, 변환, 저장)을 수행합니다.
4. **통과 방법.** 동일한 인수를 전달하는 함수
   같은 모양의 다른 것; 그것을 제거하거나 책임을 옮기십시오.
5. **소유권 분할.** 두 모듈이 동일한 상태를 쓰거나 각각 복사본을 유지합니다.
   하나를 편집하는 상담원은 다른 하나를 볼 수 없습니다. 상태당 하나의 소유자입니다.
6. **하나의 작업을 수행하는 두 가지 방법.** 에이전트는 먼저 만나는 것을 복사합니다.
   하나를 유지하십시오. 발신자를 이동하고 동일한 변경으로 나머지를 삭제합니다.
7. **가져올 수 있는 내부 요소.** 컴파일하는 최단 경로는 이를 가져오고
   인터페이스가 됩니다. 외부 가져오기가 빌드에 실패하도록 만듭니다.
8. **직접 동기화된 목록.** 두 위치에 동일한 항목이 있습니다. 하나를 보는 에이전트
   목록이 하나 편집됩니다. 두 번째를 파생시키거나 동의하지 않으면 빌드가 실패합니다.

그리고 수정 사항이 있는 각 플래그.

### 3. 테스트 리뷰

적용 범위 목표: 변경된 모든 동작은 실제 회귀를 포착하는 테스트를 통해 보호됩니다. 테스트 횟수는 목표가 아닙니다. 계획된 각 코드 경로에 필요한 테스트를 식별합니다. 다시 묻지 않고 정확하게 승인된 행동에 대해 필요한 증거를 추가하세요. 테스트를 승인된 작업으로 처리하기 전에 결정 게이트를 통해 새로운 정책이나 선택적인 검증 깊이를 취하십시오. 여기에서 요구 사항을 검토하세요. 제안된 테스트를 빌드하지 마세요.

#### 테스트 프레임워크 감지

적용 범위를 분석하기 전에 프로젝트의 테스트 프레임워크를 감지하십시오.

1. **CLAUDE.md를 읽습니다** — 테스트 명령과 프레임워크 이름이 있는 `## Testing` 섹션을 찾습니다. 발견된 경우 이를 신뢰할 수 있는 소스로 사용하세요.
2. **CLAUDE.md에 테스트 섹션이 없는 경우 자동 감지:**

```bash
setopt +o nomatch 2>/dev/null || true  # zsh compat
# Runtime markers: evidence, not commands to run
[ -f manage.py ] && echo "RUNTIME:python FRAMEWORK:django"
{ [ -f pyproject.toml ] || [ -f pytest.ini ] || [ -f tox.ini ] || [ -f setup.cfg ] || [ -f requirements.txt ]; } && echo "RUNTIME:python"
{ [ -f Gemfile ] || [ -f Rakefile ] || [ -f .rspec ]; } && echo "RUNTIME:ruby"
[ -f package.json ] && echo "RUNTIME:node"
[ -f go.mod ] && echo "RUNTIME:go"
[ -f Cargo.toml ] && echo "RUNTIME:rust"
[ -f pubspec.yaml ] && echo "RUNTIME:dart"
[ -f pom.xml ] && echo "RUNTIME:jvm BUILD:maven"
{ [ -f build.gradle ] || [ -f build.gradle.kts ]; } && echo "RUNTIME:jvm BUILD:gradle"
# Test infra: configs, scripts, test files
ls jest.config.* vitest.config.* playwright.config.* cypress.config.* .rspec pytest.ini tox.ini phpunit.xml dart_test.yaml 2>/dev/null
[ -f package.json ] && grep -q '"test"[[:space:]]*:' package.json && echo "SCRIPT:package.json test"
[ -f Makefile ] && grep -qE '^(test|check):' Makefile && echo "TARGET:make test"
git ls-files | grep -cE '(^|/)(tests?|spec|__tests__)/|(^|/)tests?\.py$|(^|/)test_[^/]+\.py$|_test\.(go|py|rb|ts|js|exs|dart)$|\.(test|spec)\.[jt]sx?$|_spec\.rb$|Test\.(java|kt)$' | sed 's/^/TESTFILES:/'
```

3. **프레임워크가 감지되지 않은 경우:** 프레임워크를 알 수 없다고 명시합니다. 다이어그램과 계획된 주장을 계속하십시오. 새로운 프레임워크를 제안하는 경우 테스트 5단계의 결정 절차를 통해 선택을 확정합니다. 정확한 사전 승인을 재사용합니다. 선택이 제안되지 않은 경우 프레임워크에 대한 질문을 하지 않습니다. 이 검토 중에는 프레임워크를 설치하거나 제안된 테스트를 작성하지 마십시오.

정의: 구체적인 소스/테스트 파일이라는 이름의 **대상 감사** 검토 또는
지점 차이 **프로토타입**은 계획에서 참조하는 기존 실행 가능 코드입니다.
제안된 미래 구성 요소가 아닙니다.

모든 대상에 대해 범위 이후 섹션 3 내에서 이 5가지 테스트 단계를 실행하세요.
챌린지 및 아키텍처/코드 품질 검토. 다시 시작하지 마십시오.
테스트 1단계 내에서 추적 또는 다이어그램 작성 전에 구체적인 소스/테스트를 읽어보세요.
테스트 2단계에서는 사용자 흐름을 추가합니다. 향후 경로는 실행 가능한 코드가 아닌 제안으로 유지됩니다.

**1단계. 계획의 모든 코드 경로 추적:**

계획 문서를 읽어보세요. 설명된 각각의 새로운 기능, 서비스, 엔드포인트 또는 구성 요소에 대해 데이터가 코드를 통해 어떻게 흐르는지 추적하십시오. 단지 계획된 기능을 나열하는 데 그치지 말고 실제로 계획된 실행을 따르십시오.

1. **계획을 읽어보세요.** 계획된 각 구성 요소에 대해 기존 코드에 어떻게 연결되는지 확인하세요. 구체적인 소스 및 테스트 파일을 기반으로 하는 경우 다이어그램을 그리기 전에 전용 도구 호출에서 이를 읽으십시오(`cat -n src/f && echo -- && cat -n test/f`). 해당 읽기에 diff, grep, config, git 또는 설명을 혼합하지 마십시오. 컨텍스트에 대해 별도의 호출을 사용하십시오. 읽은 내용을 바탕으로 다이어그램을 작성하세요.
2. **데이터 흐름 추적.** 각 진입점(경로 핸들러, 내보낸 함수, 이벤트 리스너, 구성 요소 렌더링)에서 시작하여 모든 분기를 통해 데이터를 따릅니다.
   - 입력은 어디서 오는가? (요청 매개변수, 소품, 데이터베이스, API 호출)
   - 무엇이 그것을 변화시키는가? (검증, 매핑, 계산)
   - 어디로 가는 거죠? (데이터베이스 쓰기, API 응답, 렌더링된 출력, 부작용)
- 각 단계에서 무엇이 잘못될 수 있나요? (null/정의되지 않음, 잘못된 입력, 네트워크 오류, 빈 컬렉션)
3. **실행 다이어그램.** 선택한 대상의 기존 또는 제안된 구성 요소 각각에 대해 다음을 보여주는 ASCII 다이어그램을 그립니다.
   - 범위 내 기존 또는 제안된 모든 기능/방법
   - 모든 조건 분기(if/else, 스위치, 삼항, 가드 절, 조기 반환)
   - 모든 오류 경로(시도/잡기, 구조, 오류 경계, 대체)
   - 다른 기능에 대한 모든 호출(추적 - IT에 테스트되지 않은 분기가 있습니까?)
   - 모든 에지: null 입력이 발생하면 어떻게 되나요? 배열이 비어 있나요? 유형이 잘못되었나요?

이것이 중요한 단계입니다. 입력에 따라 다르게 실행될 수 있는 모든 코드 줄의 맵을 구축하는 것입니다. 이 다이어그램의 모든 분기에는 실제 회귀를 포착할 수 있는 적용 범위가 필요합니다. 아래의 테스트 값 막대는 해당 테스트가 새로운 테스트인지, 기존 테스트의 확장인지, 이미 적용된 테스트인지를 결정합니다.

**2단계. 사용자 흐름, 상호 작용 및 오류 상태 매핑:**

코드 범위만으로는 충분하지 않습니다. 실제 사용자가 선택한 대상과 상호 작용하는 방식을 다루어야 합니다. 기존 기능이나 제안된 기능 각각에 대해 다음 사항을 고려하세요.

- **사용자 흐름:** 이 코드를 터치하기 위해 사용자는 어떤 일련의 작업을 수행합니까? 전체 여정을 매핑합니다(예: "사용자가 '결제' 클릭 → 양식 확인 → API 통화 → 성공/실패 화면"). 여행의 각 단계에는 적용 범위가 필요합니다.
- **상호작용에 따른 예외 사례:** 사용자가 예상치 못한 일을 하면 어떻게 되나요?
  - 더블클릭/빠른 재제출
  - 작업 도중 다른 곳으로 이동(뒤로 버튼, 탭 닫기, 다른 링크 클릭)
  - 오래된 데이터로 제출(페이지가 30분 동안 열려 있고 세션이 만료됨)
  - 느린 연결(API 10초 소요 - 사용자에게 무엇이 표시됩니까?)
  - 동시 작업(두 개의 탭, 동일한 형식)
- **사용자가 볼 수 있는 오류 상태:** 코드가 처리하는 모든 오류에 대해 사용자는 실제로 무엇을 경험하게 됩니까?
  - 명확한 오류 메시지나 자동 실패가 있습니까?
  - 사용자가 복구(재시도, 돌아가기, 입력 수정)할 수 있습니까? 아니면 중단되었습니까?
- 네트워크가 없으면 어떻게 되나요? API의 500으로? 서버의 잘못된 데이터가 있습니까?
- **비어 있음/0/경계 상태:** 결과가 0인 경우 UI에 무엇을 표시합니까? 결과가 10,000개인가요? 단일 문자 입력으로? 최대 길이 입력이 있습니까?

코드 분기와 함께 다이어그램에 이를 추가합니다. 테스트가 없는 사용자 흐름은 테스트되지 않은 if/else만큼이나 공백입니다.

**3단계. 기존 테스트와 비교하여 각 분기를 확인합니다.**

다이어그램 분기를 분기별로 살펴보세요. 두 코드 경로 모두 AND 사용자 흐름입니다. 각각에 대해 이를 실행하는 테스트를 검색하세요.
- 함수 `processPayment()` → `billing.test.ts`, `billing.spec.ts`, `test/billing_test.rb`을 찾습니다.
- if/else → BOTH 실제 AND 거짓 경로를 다루는 테스트를 찾습니다.
- 오류 처리기 → 해당 특정 오류 조건을 트리거하는 테스트를 찾습니다.
- 자체 분기가 있는 `helperFn()`에 대한 호출 → 해당 분기도 테스트가 필요함
- 사용자 흐름 → 여정을 안내하는 통합 또는 E2E 테스트를 찾습니다.
- 상호작용 엣지 케이스 → 예상치 못한 동작을 시뮬레이션하는 테스트 찾기

품질 채점 기준표:
- ★★★ 엣지 케이스 AND 오류 경로로 동작을 테스트합니다.
- ★★ 올바른 동작, 행복한 경로만 테스트합니다.
- ★ 스모크 테스트 / 존재 확인 / 사소한 주장(예: "렌더링한다", "던지지 않는다"); 약함, 보장 범위로 간주되지 않음

**테스트 값 막대.** 4가지 답변이 모두 포함된 테스트만 제안하거나 작성합니다. 그렇지 않으면 기존 테스트를 확장하거나 삭제합니다.

1. 관찰 가능한 행동, 불변 또는 독립 계약은 무엇을 보호합니까?
2. 어떤 신뢰할 만한 회귀가 실패하게 만드는가?
3. 기존 보장에서는 왜 아직 이를 포착하지 못합니까? 거의 중복되는 것보다 기존 테이블 기반 테스트 또는 공유 고정 장치에 행을 추가하는 것을 선호합니다.
4. 프로덕션 호출자가 필요로 하지 않는 프로덕션 이음새(내보내기, 플래그, 래퍼, 주입 후크)가 필요합니까? 그렇다면 대신 실제 경계에서 테스트하십시오.

동작 보존 리팩터링에서 중단되는 테스트는 구현을 주장합니다. 정확한 출력이 선언된 계약(골든, 프롬프트 바이트, 연결 형식)이 아닌 한 소유 경계에서 다시 작성합니다.

값 카드: `Value: protects=<...>; fails_when=<...>; why_new=<...>; seam=none; no_claim=<...>`(이음새: `none` 또는 해당 이름; `no_claim`: 녹색이 무엇을 증명하지 못하고 어떤 고정 장치나 모조품이 무엇을 의미하는지에 대한 한 문장(예: `no_claim=provider acceptance (mocked provider; unit only)` 또는 `no_claim=none beyond protects`; 필수 실시간 확인을 포기하지 않음); 여기에서 각 필드는 최대 160 UTF-8바이트입니다(157에 고정하고 `...`로 고정하고 JSON로 작성하면 전체 값을 유지함). 테스트 계획 아티팩트의 중요 경로 및 엣지 케이스당 카드 1개. 누락된 업스트림 카드는 절대 차단되지 않습니다. 파생하세요. 알 수 없는 필드를 무시합니다.

예: Value: protects=refundPayment가 빈 사유를 거부함; fails_when=사유 가드가 제거되거나 반전됨; why_new=billing.test.ts는 processPayment만 검사; seam=none; no_claim=provider acceptance (mocked provider; unit only)
거부됨(covered_elsewhere): "결제 렌더링"; checkout.e2e.ts:15가 이를 다루므로 해당 테스트를 확장하세요.

약한 테스트(★ 연기/존재/사소한, 게이트 실패 또는 등급 없음)는 적용 범위로 간주되지 않습니다. X = ★★/★★★ 테스트가 있는 경로 / 총 경로(가중치; 게이트는 X를 사용함); Y = 테스트/전체 경로가 있는 경로입니다. /ship은 이를 계산합니다. 여기서 제안된 모든 테스트에는 카드가 필요합니다.

보존 막대: 공개 API, 프로토콜, 구성, 마이그레이션, 스토리지, 보안, 플랫폼, 기본, 프롬프트 바이트, 생성된 출력(골든), 패키지, 릴리스 또는 아키텍처 계약을 독립적으로 시행하는 테스트를 유지합니다. 정적이거나 느린 것은 삭제할 이유가 없습니다.

#### E2E 테스트 결정 매트릭스

각 분기를 확인할 때 단위 테스트 또는 E2E/통합 테스트가 올바른 도구인지도 결정하세요.

**RECOMMEND E2E(다이어그램에서 [→E2E]로 표시):**
- 3개 이상의 구성요소/서비스에 걸친 공통 사용자 흐름(예: 가입 → 이메일 확인 → 첫 번째 로그인)
- Mocking이 실제 실패를 숨기는 통합 지점(예: API → 대기열 → 작업자 → DB)
- 인증/결제/데이터 파괴 흐름 - 단위 테스트만 신뢰하기에는 너무 중요함

**RECOMMEND EVAL(다이어그램에서 [→EVAL]로 표시):**
- 품질 평가가 필요한 중요한 LLM 호출(예: 신속한 변경 → 테스트 출력이 여전히 품질 기준을 충족함)
- 프롬프트 템플릿, 시스템 지침 또는 도구 정의 변경

**STICK WITH UNIT TESTS:**
- 명확한 입력/출력을 갖춘 순수 기능
- 부작용이 없는 내부 도우미
- 단일 함수의 엣지 케이스(널 입력, 빈 배열)
- 고객과 직접 접촉하지 않는 모호하거나 드문 흐름

#### REGRESSION RULE(필수)

**IRON RULE:** 계획된 변경으로 인해 회귀 적용 범위 없이 기존 동작이 위험에 처할 경우 해당 적용 범위는 중요한 요구 사항입니다. 정확하게 승인된 회귀 계약을 진행합니다. 그렇지 않으면 승인된 계약을 계획에 추가하기 전에 하나의 전용 AskUserQuestion을 사용하여 이를 해결합니다(보존 동작, 의도적 변경 및 수락 주장). 건너뛸지 말지 말고 어떻게 덮을지 물어보세요. 다른 테스트 깊이의 질문에 자동으로 포함하지 마세요.

제안된 재작성은 회귀 위험이지 실행 중인 코드가 이미 손상되었다는 증거는 아닙니다. 기존 발신자와 위험에 처한 행동의 이름을 지정합니다. 변경되지 않은 동작을 유지하고 의도된 차이점을 명시적으로 식별합니다. 회귀 적용 범위를 건너뛰지 않습니다.

| 단계 | 터치된 모듈 | |에 따라 다름
|------|----------------|------------|
| (단계 이름) | (디렉터리/모듈, NOT 특정 파일) | (다른 단계 또는 —) |

**병렬 레인:** 분리된 모듈을 함께 사용합니다. 공유 모듈을 순차적으로, 종속성
나중에(`Lane A: step1 → step2 (shared models/)` / `Lane B: step3 (independent)`).
**실행 순서:** 실행/대기 지점("A + B 실행. 둘 다 병합. 그런 다음 C.").
**충돌 플래그:** 교차 차선 공유 모듈을 순서화하거나 조정합니다.

### 보고서 생성

사전 검토 항목을 보려면 `~/.claude/skills/gstack/bin/gstack-review-read`을 실행하세요.
이 검토 상태 및 조사 결과에 대한 현재 완료 요약을 사용하십시오.
아래의 검토 로그 필드 규칙을 적용하고 이전 실행 횟수에 정확히 1을 추가하세요.
보고서를 채우기 위해 이 실행을 미리 기록하지 마십시오.
상태, 귀속 및 최신성을 유지하면서 다른 리뷰에 이전 항목을 사용하세요.

기록된 출처를 사용하여 각 JSONL 항목을 구문 분석합니다. 기록 소스 "claude"는 기본 Claude 하위 에이전트입니다. "claude-code"는 외부 CLI입니다. 과거 코덱스 식별자를 유지하고 현재 하네스의 오래된 기록에 라벨을 다시 붙이지 마십시오. 알려지지 않은 모델 신원은 아직 알려지지 않았습니다. 새 레코드의 경우 호스트, 외부 제공자, 외부_상태 및 단계를 표시합니다. 완료된 외부 기록만이 외부 보장 범위를 설정합니다. 기본 대체는 그렇지 않습니다.

각 기술은 서로 다른 필드를 기록합니다.

- **계획-CEO-검토**: `status`, `unresolved`, `critical_gaps`, `mode`, `scope_proposed`, `scope_accepted`, `scope_deferred`, `commit`
  → 조사 결과: "{scope_proposed} 제안, {scope_accepted} 수락, {scope_deferred} 연기됨"
  → 범위 필드가 0이거나 누락된 경우(HOLD/REDUCTION 모드): "모드: {mode}, {critical_gaps} 중요한 간격"
- **계획 검토**: `status`, `unresolved`, `critical_gaps`, `issues_found`, `mode`, `commit`
  → 조사 결과: "{issues_found} 문제, {critical_gaps} 심각한 격차"
- **계획-설계-검토**: `status`, `initial_score`, `overall_score`, `unresolved`, `decisions_made`, `commit`
  → 조사 결과: "점수: {initial_score}/10 → {overall_score}/10, {decisions_made} 결정"
- **계획-개발-검토**: `status`, `initial_score`, `overall_score`, `product_type`, `tthw_current`, `tthw_target`, `mode`, `persona`, `competitive_tier`, `unresolved`, `commit`
  → 조사 결과: "점수: {initial_score}/10 → {overall_score}/10, TTHW: {tthw_current} → {tthw_target}"
- **devex-review**: `status`, `overall_score`, `product_type`, `tthw_measured`, `dimensions_tested`, `dimensions_inferred`, `boomerang`, `commit`
  → 조사 결과: "점수: {overall_score}/10, TTHW: {tthw_measured}, {dimensions_tested} 테스트됨/{dimensions_inferred} 추론됨"
- **코덱스 검토**: `status`, `gate`, `findings`, `findings_fixed`
  → 조사 결과: "{findings} 조사 결과, {findings_fixed}/{findings} 수정됨"

현재 행에서는 실제 리뷰를 설명합니다. 기록되지 않은 현재 실행을 지속되지 않는 것으로 표시합니다. 저장된 대시보드 항목으로 표시하지 마십시오.

`clean`을 CLEAR로, `issues_open`를 ISSUES OPEN로 표시하여 신선함과 지속되지 않는 레이블을 유지합니다. 다른 상태는 기록된 의미를 유지합니다.

다음 마크다운 테이블을 생성합니다.

```markdown
## GSTACK REVIEW REPORT

| 검토 | 트리거 | 왜 | 실행 | 상태 | 조사 결과 |
|--------|---------|-----|------|--------|----------|
| CEO 검토 | `/plan-ceo-review` | 범위 및 전략 | {runs} | {status} | {findings} |
| 외부 검토 | {recorded provider and trigger} | 독립적인 2차 의견 | {runs} | {outside_status} | {findings} |
| 영어 검토 | `/plan-eng-review` | 아키텍처 및 테스트(필수) | {runs} | {status} | {findings} |
| 디자인 검토 | `/plan-design-review` | UI/UX 격차 | {runs} | {status} | {findings} |
| DX 검토 | `/plan-devex-review` | 개발자 경험 격차 | {runs} | {status} | {findings} |
```

표 아래에 다음 줄을 추가합니다. **OUTSIDE COVERAGE** 및 **CROSS-MODEL**은 조건부입니다.
단계가 실행되거나 비활성화/건너뛰기/사용할 수 없거나 결과가 있는 경우 이를 포함합니다.
해당 단계가 적용되지 않는 경우에만 생략하세요. **VERDICT**은 항상 존재합니다.

- **OUTSIDE COVERAGE:** 공급자, 단계, 완료 상태 및 결과. 사용할 수 없는 단계, 비활성화된 단계, 건너뛴 단계를 포함합니다. 다른 단계에서 완료를 추론하지 마십시오.
- **CROSS-MODEL:** 기본 및 완료된 외부 리뷰가 있는 경우에만 — 기록된 공급자 및 알려진 모델 ID와 중복 분석을 수행합니다. 하네스 이름에서 고유한 모델 패밀리를 추론하지 마십시오.
- **VERDICT:** CLEAR인 리뷰를 나열합니다(예: "CEO + ENG CLEARED — 구현 준비 완료").
  Eng Review가 CLEAR이 아니고 전체적으로 건너뛰지 않는 경우 "eng review require"를 추가합니다.

**미해결 결정 상태(MANDATORY — 생략되지 않음, 보고서의 최종 비공백
행).** VERDICT 이후 보고서를 종료합니다(`## GSTACK REVIEW REPORT` 아래의 내용).
제목 — 굵은 라벨이며 새로운 `## ` 제목이 아닙니다. "비어있을 때 생략"에서 제외
규칙) 정확히 하나만: 굵은 글씨로 표시되지 않은 정확한 줄 `NO UNRESOLVED DECISIONS`(굵게 표시된 줄)
NOT 개수), 또는 `**UNRESOLVED DECISIONS:**` 헤더 + 열린 항목당 글머리 기호 1개
(마지막 글머리 기호 = 마지막 줄; N > 0인 경우에만 `+ N unresolved from prior reviews`을 추가하세요).
이렇게 하면 이중 계산을 방지할 수 있습니다. 컨텍스트에서 THIS 리뷰의 열린 항목을 나열합니다. 사전 검토를 위해
기술당 최신 행(대시보드 7일 기간)에 대한 합계 `unresolved`
DROP 현재 스킬 행; 둘 다 0인 경우에만 센티널을 방출합니다.

### 보고서 파일에 쓰기

보고 대상이 없거나 쓰기가 금지된 경우 동일한 전체 작업 계획을 모으고 출력 및 터미널 보고서를 채팅에서 검토하고 지속되지 않음이라는 라벨을 붙입니다. 아래의 파일 쓰기 단계를 실행하거나 Read-back 게이트를 통과했다고 주장하지 마세요. 그런 다음 **결과 보고**를 사용하세요. 그렇지 않으면 승인된 변경 사항만 저장하고 해결되지 않은 선택 사항은 보류 상태로 유지합니다.

보고서는 항상 보고서 파일의 LAST 섹션이어야 하며 파일 중간에 위치해서는 안 됩니다.
단일 삭제 후 추가 흐름을 사용합니다.

1. 기존 보고서 파일(있는 경우)을 읽습니다. 내용을 보존하고만 적용
   변경 사항이 허용되었습니다. 전체 검토 결과를 포함합니다. 기존 위치 찾기
   `## GSTACK REVIEW REPORT` 섹션.
2. 찾은 경우 편집 도구를 사용하여 기존 섹션 전체를 DELETE로 만듭니다. 일치 항목:
   `## GSTACK REVIEW REPORT` 다음 `## ` 제목 또는 끝 부분까지
   파일 중 먼저 오는 것. 빈 문자열로 바꿉니다. 이는 적용됩니다
   섹션이 현재 어디에 있는지에 관계없이 중간 파일 삭제는
   특별한 경우가 아닌 의도적인 것입니다. 편집이 실패한 경우(예: 동시 편집
   내용 변경), 보고서 파일을 다시 읽고 한 번 다시 시도해 보세요.
3. 보고서가 삭제된 경우 업데이트된 파일을 읽어보세요. 새로 추가
   `## GSTACK REVIEW REPORT`(EOF). 편집을 사용하여 접미사 일치
   최신 읽기로 확인하거나 마지막에 보고서와 함께 전체 파일을 작성하십시오. 이전 신고서 유무를 첨부합니다.
   "미해결 결정"은 다른 섹션이 따르는 경우 EOF 앵커가 아닙니다.
4. **리드백 게이트:** 저장된 파일을 읽습니다. 승인된 변경 사항 확인, 전체 검토
   출력, 현재 검토 행, 평결 및 최종 미해결 결정 상태
   `## GSTACK REVIEW REPORT`을 마지막 섹션으로 사용합니다. 작성이나 인증에 실패할 경우,
   검토 로그 또는 결정 로깅 전에 오류를 보고하고 **차단된 결과**를 따르세요.

NOT 섹션을 교체하십시오. 이를 삭제하고 EOF에 새 보고서를 추가합니다.


두 번째 명령: `ARCH_SUMMARY` = 조사 결과/처분; `KEY_DECISION` = 내구성
아키텍처 선택. 없는 경우 생략합니다.

- **TIMESTAMP**: 현재 ISO 8601 날짜/시간
- **STATUS**: `issues_found=0`, `unresolved=0`, `critical_gaps=0`이면 "clean", 그 외는 "issues_open"이다. 해결된 발견도 센다. "issues_open"은 실패 대신 매핑된 작업을 뜻할 수 있다.
- **해결되지 않음**: 이 리뷰의 "해결되지 않은 결정" 개수입니다. 이전 리뷰를 포함하지 마세요.
- **critical_gaps**: "실패 모드: ___ 중요한 간격이 표시됨"의 숫자
- **문제 발견**: 4개 섹션으로만 계산됩니다(아키텍처 + 코드 품질 + 성능 + 테스트 격차). 범위 문제와 외부 의견 조사 결과를 별도로 보고합니다.
- **MODE**: FULL_REVIEW 범위 챌린지 결과 "범위가 있는 그대로 허용됨"에 대한 것입니다. SCOPE_REDUCED "권장사항에 따라 범위 감소".
- **COMMIT**: `git rev-parse --short HEAD`의 출력

성공적인 필수 로그만이 저장된 리뷰로 게시를 허용합니다.

## 검토 준비 대시보드

리뷰를 완료한 후 리뷰 로그 및 구성을 읽어 대시보드를 표시합니다.

```bash
~/.claude/skills/gstack/bin/gstack-review-read
```

**1. 표시할 기록을 선택하세요.** 아래 각 행에 최신 기록을 사용하세요.
행을 지우는 데 7일보다 오래된 기록을 사용하지 말고 더 오래된 기록으로 대체하지 마세요.
새로운 실패에 대한 성공. 배송 측정 항목은 검토 기록이 아닙니다.

| 행 | 다음 중 최신 항목을 선택하세요 | 상태 접미사 |
|---|---|---|
| 영어 검토 | `review` 또는 `plan-eng-review` | (DIFF) 또는 (PLAN) |
| CEO 검토 | `plan-ceo-review` | — |
| 디자인 검토 | `plan-design-review` 또는 `design-review-lite` | (FULL) 또는 (LITE) |
| 적대적 | `adversarial-review` 또는 기존 `codex-review` | — |
| 외부음성 | `codex-plan-review` CEO 또는 영어 검토 | — |

각 레코드의 호스트, 소스, Outside_provider, Outside_status 및 단계를 유지합니다.
기록 소스 "claude"는 기본 하위 에이전트입니다. "claude-code"는 외부 CLI입니다.
현재의 하네스에서 오래된 공급자나 알려지지 않은 모델을 추론하지 마십시오. 기본 결과
보장 범위 밖에서 누락, 비활성화 또는 생략된 내용을 채우지 않습니다.

**소스 속성:** 기록된 `via`을 접미사("CLEAR (PLAN 통해)에 추가합니다.
/자동계획)"); 하나도 없으면 "CLEAR (PLAN)" 또는 "CLEAR (DIFF)"을 유지합니다. 대시보드 아래 그룹 `autoplan-voices`
및 워크플로 실행 및 단계별 `design-outside-voices`. 각 단계의 공급자 표시
그리고 Outside_status; 부분적인 보장을 유지합니다. 이러한 세부 사항은 Eng Review를 삭제하지 않습니다.

**2. 평결을 선택하기 전에 최신성을 확인하세요.**

- **콘텐츠 우선 규칙:** `review`, `adversarial-review`, `codex-review`의 경우,
  배송 단계 검토 및 `design-review-lite`, `review_freshness.status` 사용
  `reason`을 표시한다. CURRENT는 완료된 clean 검토이며 시작·끝 콘텐츠 지문이 모두 현재 `---WTREE---` 지문과 같은 상태다.
  STALE 또는 UNVERIFIED에서는 Eng Review를 삭제할 수 없습니다. `review_freshness` 누락,
  레거시 로그 전용 레코드를 포함한다는 것은 UNVERIFIED을 의미합니다. HEAD으로 돌아가지 마세요.
  커밋이 0인 경우에도 diff 증거에 대한 동일성 또는 커밋 거리입니다.
  기록된 주기, 완료/수렴된 필드 및 누락된 소스/단계 표시
  적용 범위. 보장범위를 알 수 없는 경우 합격이 아닙니다.
- **계획 기록**(계획-CEO-검토, 계획-Eng-검토, 계획-설계-검토 및
codex-plan-review) 작업 트리 지문이 아닌 7일 창을 사용합니다.
  `plan_sha256`이 있는 경우 계획 파일을 비교하고 불일치를 보고할 수 있습니다.
  기록된 커밋을 `---HEAD---`과 비교합니다. 다르다면 실행
  `git rev-list --count STORED_COMMIT..HEAD` 및 보고
  "참고: {date}의 {skill} 리뷰는 오래되었을 수 있습니다. — {N} 리뷰 이후 커밋됩니다."
  실패한 명령은 UNKNOWN을 의미하며 오래된 것으로 간주됩니다. 커밋 추적 없이
  재실행을 제안합니다. 모든 리뷰가 최신인 경우 메모를 생략하세요.

**3. 과거 평결을 선택하세요.** CLEARED에는 선택한 엔지니어링 검토가 필요합니다.
7일 이내에 `clean`이어야 하고 2단계에 따라 새로워져야 합니다. 그렇지 않으면 NOT CLEARED을 보고하세요.
누락, 오래되었거나 공개된 문제의 이유. `skip_eng_review`이 true인 경우 다음을 표시합니다.
Eng Review의 경우 "SKIPPED(글로벌)"이고 이 대시보드의 경우 CLEARED입니다.
엔지니어링 검토는 기본적으로 필수입니다. `gstack-config set skip_eng_review true`은 해당 요구 사항을 비활성화합니다.

다른 행은 Eng Review를 대체하지 않고 컨텍스트를 제공합니다.
- 일상적인 수정이나 정리가 아닌 제품/비즈니스 또는 범위 결정에 대한 검토를 CEO 권장합니다.
- 백엔드, 인프라, 프롬프트 전용 작업이 아닌 UI/UX 작업에는 디자인 리뷰를 권장합니다.
- 적대적 검토에는 항상 기본 패스가 포함됩니다. 사용 가능, 외부에서 활성화됨
  도전이 이를 보완합니다. 200개 이상의 라인의 diff도 구조화된 P1 게이트를 얻습니다.
- 외부 음성은 CEO/Eng 검토 후 기본 계획 검토입니다. `codex_reviews`
  해당 추가 단계를 비활성화합니다. 공급자 오류는 기본 대체 및 기록을 사용합니다.
  외부 보장이 누락되었습니다. 이 대시보드 행에는 배송이 포함되지 않습니다.

**4. 대시보드를 표시합니다.** 누락, 오래됨, 비활성화 또는 사용할 수 없는 결과를 표시합니다.
명시적으로 절대 CLEAR으로 사용하지 마세요. 새로운 `clean` 결과를 CLEAR로 표시하고
`issues_open`은 저장된 상태를 변경하지 않고 ISSUES OPEN입니다.

```
+====================================================================+
|                    REVIEW READINESS DASHBOARD |
+====================================================================+
| 검토 | 실행 | 마지막 실행 | 상태 | 필수 |
|-----------------|------|---------------------|-----------|----------|
| 영어 검토 |  1 | 2026-03-16 15:00 | CLEAR | YES |
| CEO 검토 |  0 | — | — | 아니 |
| 디자인 검토 |  0 | — | — | 아니 |
| 적대적 |  0 | — | — | 아니 |
| 외부음성 |  0 | — | — | 아니 |
+--------------------------------------------------------------------+
| VERDICT: CLEARED — 영어 검토 통과 |
+====================================================================+
```

## 학습 캡처

도중에 명확하지 않은 패턴, 함정 또는 아키텍처 통찰력을 발견한 경우
이 세션을 기록하고 향후 세션을 위해 기록하세요.

```bash
~/.claude/skills/gstack/bin/gstack-learnings-log '{"skill":"plan-eng-review","type":"TYPE","key":"SHORT_KEY","insight":"DESCRIPTION","confidence":N,"source":"SOURCE","files":["path/to/relevant/file"]}'
```

**유형:** `pattern`(재사용 가능한 접근 방식), `pitfall`(NOT 수행할 작업), `preference`
(사용자 명시), `architecture`(구조적 결정), `tool`(라이브러리/프레임워크 통찰력),
`operational`(프로젝트 환경/CLI/워크플로 지식).

**출처:** `observed`(코드에서 찾았음), `user-stated`(사용자가 알려줌),
`inferred`(AI 공제), `cross-model`(Claude와 Codex 모두 동의).

**신뢰도:** 1-10. 솔직해지세요. 코드에서 확인한 관찰 패턴은 8-9입니다.
확실하지 않은 추론은 4-5입니다. 그들이 명시적으로 언급한 사용자 선호도는 10입니다.

**파일:** 이 학습에서 참조하는 특정 파일 경로를 포함합니다. 이를 통해
부실 감지: 해당 파일이 나중에 삭제되면 학습에 플래그가 지정될 수 있습니다.

**진짜 발견한 내용만 기록하세요.** 뻔한 내용은 기록하지 마세요. 사용자의 내용을 기록하지 마세요
이미 알고 있습니다. 좋은 테스트: 이 통찰력이 향후 세션에서 시간을 절약해 줄까요? 그렇다면 기록하십시오.



**보정 게이트 상태:** 지원되는 서문·구성 중 `BRAIN_CALIBRATION_WRITEBACK`을 생성하는 것은 없다. 그 출처가 명시적으로 활성화한 경우가 아니면 생략한다. 개인 신뢰·MCP 가용성으로는 활성화할 수 없으며 직접 설정하지 않는다.

## 뇌 교정 쓰기 저장(게이트)

`BRAIN_CALIBRATION_WRITEBACK`은 예약된 기본 오프 게이트입니다. 이 런타임은 이를 설정하지 않습니다. 이 섹션을 건너뛰고 종료 순서를 계속하세요. 활성화하거나 두뇌 가용성으로부터 허가를 추론하지 마십시오. 아래 계약은 지금 작성하라는 지시가 아닌 향후 Gated Integration을 위해 유지됩니다.

`BRAIN_CALIBRATION_WRITEBACK`가 설정되고 서문·brain-health 출력 또는 gstack 구성에 `brain_trust_policy@<endpoint-hash>=personal`이 표시된 경우에만 진행한다. 그 외와 알 수 없는 경우에는 생략한다. 두 게이트를 모두 통과하면 `mcp__gbrain__takes_add`로 지속해서 남길 타입이 있는 예측 하나를 기록한다. 도구가 없으면 `mcp__gbrain__put_page`에 gstack:takes fence 블록을 사용한다.
