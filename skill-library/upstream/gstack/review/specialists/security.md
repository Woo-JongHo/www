# 보안 전문가 검토 체크리스트

범위: SCOPE_AUTH=true 또는 (SCOPE_BACKEND=true이고 diff > 100줄)일 때
출력: 한 줄에 발견 사항 하나인 JSON 객체. 스키마:
{"severity":"CRITICAL|INFORMATIONAL","confidence":N,"path":"file","line":N,"category":"security","summary":"...","fix":"...","fingerprint":"path:line:security","specialist":"security"}
선택 사항: line, fix, fingerprint, evidence, test_stub.
발견 사항이 없는 경우: `NO FINDINGS`만 출력하고 다른 것은 출력하지 않는다.

---

이 체크리스트는 기본 CRITICAL 패스보다 더 깊이 검사한다. 기본 에이전트는 이미 SQL 인젝션, 경쟁 조건, LLM 신뢰, enum 완전성을 확인한다. 이 전문가는 auth/authz 패턴, 암호화 오용, 공격 표면 확대에 집중한다.

## 범주

### 신뢰 경계에서의 입력 검증
- 컨트롤러/핸들러 수준에서 검증 없이 받는 사용자 입력
- 데이터베이스 쿼리나 파일 경로에 직접 사용하는 쿼리 매개변수
- 타입 검사나 스키마 검증 없이 받는 요청 본문 필드
- 타입/크기/내용 검증이 없는 파일 업로드
- 서명 검증 없이 처리하는 웹훅 페이로드

### Auth 및 권한 부여 우회
- 인증 미들웨어가 누락된 엔드포인트(라우트 정의 확인)
- 기본값이 "deny"가 아니라 "allow"인 권한 부여 검사
- 역할 상승 경로(사용자가 자신의 역할/권한을 수정할 수 있음)
- 직접 객체 참조 취약점(사용자 A가 ID를 변경해 사용자 B의 데이터에 접근)
- 세션 고정 또는 세션 하이재킹 가능성
- 만료 여부를 확인하지 않는 토큰/API 키 검증
- 올바른 가드를 지나 정보가 유출되는 오류 페이지: 공유 403/404/500 렌더러가 권한 부여 경로 밖에서 본문을 구성하므로, 차단된 요청에도 해당 역할이 볼 수 없는 내부 이름, 개수 또는 탐색 메뉴가 반환된다. 가드뿐 아니라 오류 템플릿과 그 컨텍스트 빌더도 읽는다
- 역할 강등 후에도 유지되는 소유권: 생성 시 기록된 허용이 사용자의 역할이 축소되고 다시 로그인한 후에도 객체를 열어 준다. 읽을 때마다 현재 역할을 기준으로 소유권을 다시 확인해야 한다
- 한 객체의 목록, 상세 및 파일/다운로드 접근을 단일 항목으로 감사: 각각은 보통 서로 다른 코드 경로로 객체를 해석하므로 역할 매트릭스를 기준으로 각각 별도로 확인한다
- 콜백의 일회용 state 값을 검증하기 전에 세션을 지우거나 재생성하거나 다시 바인딩하는 계정 또는 ID 전환: 해당 URL로 강제 이동하면 사용자가 로그아웃된다(CSRF). 거부, 취소 및 오류 분기도 확인한다. 여기서 이전 세션을 활성 상태로 두면 사용자가 이전 ID로 계속 행동하게 된다

### 인젝션 벡터(SQL 이외)
- 사용자가 제어하는 인수를 포함한 subprocess 호출을 통한 명령어 인젝션
- 사용자 입력을 통한 템플릿 인젝션(Jinja2, ERB, Handlebars)
- 디렉터리 쿼리의 LDAP 인젝션
- 사용자가 제어하는 URL(fetch, redirect, 웹훅 대상)을 통한 SSRF
- 사용자가 제어하는 파일 경로(../../etc/passwd)를 통한 경로 순회
- HTTP 헤더에서 사용자가 제어하는 값을 통한 헤더 인젝션

### 암호화 오용
- 보안에 민감한 작업에 사용하는 약한 해싱 알고리즘(MD5, SHA1)
- 토큰이나 비밀값에 사용하는 예측 가능한 무작위성(Math.random, rand())
- 비밀값, 토큰 또는 다이제스트에 대한 비상수 시간 비교(==)
- 하드코딩된 암호화 키 또는 IV
- 비밀번호 해싱에서 salt 누락

### 비밀값 노출
- 소스 코드의 API 키, 토큰 또는 비밀번호(주석에 있는 경우도 포함)
- 애플리케이션 로그나 오류 메시지에 기록된 비밀값
- URL의 자격 증명(쿼리 매개변수 또는 URL의 basic auth)
- 사용자에게 반환되는 오류 응답의 민감한 데이터
- 암호화가 예상되는데도 평문으로 저장된 PII

### 이스케이프 해치를 통한 XSS
- Rails: 사용자가 제어하는 데이터에 대한 .html_safe, raw()
- React: 사용자 콘텐츠와 함께 사용하는 dangerouslySetInnerHTML
- Vue: 사용자 콘텐츠와 함께 사용하는 v-html
- Django: 사용자 입력에 대한 |safe, mark_safe()
- 일반: 정제하지 않은 데이터를 innerHTML에 할당

### 역직렬화
- 신뢰할 수 없는 데이터 역직렬화(pickle, Marshal, YAML.load, 실행 가능한 타입의 JSON.parse)
- 스키마 검증 없이 사용자 입력이나 외부 API에서 직렬화된 객체 수락
