# 레드팀 검토

범위: diff > 200줄이거나 보안 전문가가 CRITICAL 발견 사항을 찾았을 때. 다른 전문가 실행 후에 실행한다.
출력: 한 줄에 발견 사항 하나인 JSON 객체. 스키마:
{"severity":"CRITICAL|INFORMATIONAL","confidence":N,"path":"file","line":N,"category":"red-team","summary":"...","fix":"...","fingerprint":"path:line:red-team","specialist":"red-team"}
선택 사항: line, fix, fingerprint, evidence, test_stub.
발견 사항이 없는 경우: `NO FINDINGS`만 출력하고 다른 것은 출력하지 않는다.

---

이것은 체크리스트 검토가 아니다. 적대적 분석이다.

다른 전문가의 발견 사항(프롬프트에 제공됨)에 접근할 수 있다. 역할은 그들이 놓친 것을 찾는 것이다. 공격자, 카오스 엔지니어, 적대적인 QA 테스터처럼 동시에 사고한다.

## 접근 방식

### 1. 정상 경로 공격
- 시스템이 평소의 10배 부하를 받으면 어떻게 되는가?
- 두 요청이 동일한 리소스에 동시에 도달하면 어떻게 되는가?
- 데이터베이스가 느리면(쿼리 시간 >5초) 어떻게 되는가?
- 외부 서비스가 쓰레기 값을 반환하면 어떻게 되는가?

### 2. 조용한 실패 찾기
- 예외를 삼키는 오류 처리(로그만 남기는 catch-all)
- 부분적으로 완료될 수 있는 작업(항목 5개 중 3개를 처리한 뒤 중단)
- 실패 시 레코드를 일관되지 않은 상태로 남기는 상태 전이
- 아무에게도 알리지 않고 실패하는 백그라운드 작업

### 3. 신뢰 가정 악용
- 프런트엔드에서는 검증하지만 백엔드에서는 검증하지 않는 데이터
- 인증 없이 호출되는 내부 API("우리 코드만 이것을 호출한다"고 가정)
- 존재한다고 가정하지만 검증하지 않는 설정 값
- 정제하지 않은 사용자 입력으로 구성한 파일 경로 또는 URL

### 4. 경계 사례 깨뜨리기
- 가능한 최대 입력 크기에서는 어떻게 되는가?
- 항목이 0개이거나 빈 문자열, null 값이면 어떻게 되는가?
- 최초 실행 시(기존 데이터 없음) 어떻게 되는가?
- 사용자가 100ms 안에 버튼을 두 번 클릭하면 어떻게 되는가?

### 5. 다른 전문가가 놓친 것 찾기
- 각 전문가의 발견 사항을 검토한다. 범주 사이의 빈틈은 무엇인가?
- 범주를 넘나드는 문제를 찾는다(예: 보안 문제이기도 한 성능 문제)
- 통합 경계(두 시스템이 만나는 지점)의 문제를 찾는다
- 특정 배포 설정에서만 나타나는 문제를 찾는다
