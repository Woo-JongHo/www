# 명세 주도 개발(SDD)

## 주도권의 역전

수십 년 동안 코드는 왕이었다. 명세는 코드를 위해 존재했다. 코딩이라는 “진짜 작업”이 시작되면, 명세는 세웠다가 버리는 비계였다. 개발 방향을 잡으려고 제품 요구사항 문서(PRD)를 쓰고, 구현에 참고하려고 설계 문서를 만들고, 아키텍처를 시각화하려고 그림을 그렸다. 그러나 이들은 언제나 코드 자체에 종속돼 있었다. 코드가 진실이었다. 그 밖의 것은 기껏해야 좋은 의도였다. 코드는 진실의 원천이었고, 코드가 발전할 때 명세가 보조를 맞추는 경우는 드물었다. 자산인 코드와 구현이 하나이므로, 코드에서 다시 만들지 않고 별도의 병렬 구현을 갖기는 쉽지 않았다.

명세 주도 개발(SDD)은 이 권력 구조를 뒤집는다. 명세가 코드를 위해 존재하는 것이 아니라 코드가 명세를 위해 존재한다. PRD는 구현 안내서가 아니라 구현을 생성하는 원천이다. 기술 계획은 코딩에 참고하는 문서가 아니라 코드를 만들어 내는 정밀한 정의다. 이는 소프트웨어를 만드는 방식의 점진적인 개선이 아니라, 무엇이 개발을 이끄는지에 대한 근본적인 재고다.

명세와 구현 사이의 간극은 소프트웨어 개발이 시작된 이래 계속 문제였다. 더 나은 문서, 더 상세한 요구사항, 더 엄격한 절차로 이를 메우려 했다. 이런 접근은 간극을 불가피한 것으로 받아들이기 때문에 실패한다. 간극을 좁히려 할 뿐 없애지는 않는다. SDD는 명세와 그 명세에서 나온 구체적인 구현 계획을 실행 가능하게 만들어 간극을 없앤다. 명세와 구현 계획이 코드를 생성하면, 간극은 없고 변환만 남는다.

이제 AI가 복잡한 명세를 이해하고 구현하며 상세한 구현 계획을 만들 수 있기에 이러한 변환이 가능하다. 그러나 구조 없는 AI 생성은 혼란을 낳는다. SDD는 작동하는 시스템을 생성할 만큼 정확하고 완전하며 모호하지 않은 명세와 후속 구현 계획으로 그 구조를 제공한다. 명세가 핵심 산출물이 된다. 코드는 특정 언어와 프레임워크로 표현한 명세가 된다. 즉, 구현 계획으로부터 나온 구현이다.

이 새로운 세계에서 소프트웨어 유지보수는 명세를 발전시키는 일이다. 개발팀의 의도는 자연어(“**의도 주도 개발**”), 설계 자산, 핵심 원칙과 다른 지침으로 표현된다. 개발의 **공통 언어**는 더 높은 수준으로 옮겨 가고, 코드는 마지막 구간을 구현하는 수단이 된다.

디버깅은 잘못된 코드를 생성한 명세와 구현 계획을 고치는 일이다. 리팩터링은 명료성을 위해 구조를 바꾸는 일이다. 전체 개발 흐름은 명세를 진실의 중심 원천으로 삼아 재편되며, 구현 계획과 코드는 계속 재생성되는 결과물이 된다. 새로운 기능으로 앱을 갱신하거나, 창의성을 발휘해 새로운 병렬 구현을 만들려면 명세를 다시 살피고 새 구현 계획을 만든다. 따라서 이 과정은 0 -> 1, (1', ..), 2, 3, N으로 이어진다.

개발팀은 창의성, 실험, 비판적 사고에 집중한다.

## 실제 SDD 작업 흐름

작업 흐름은 흔히 모호하고 불완전한 아이디어에서 출발한다. AI와 반복해서 대화하면서 이 아이디어는 포괄적인 PRD가 된다. AI는 명확화를 위한 질문을 하고, 경계 사례를 찾아내고, 정확한 수용 기준을 정의하도록 돕는다. 전통적인 개발에서 며칠의 회의와 문서 작업이 필요했던 일이 몇 시간의 집중적인 명세 작업으로 이뤄진다. 이는 전통적인 소프트웨어 개발 생명주기(SDLC)를 바꾼다. 요구사항과 설계가 분리된 단계가 아니라 지속적인 활동이 된다. 팀에서 검토한 명세를 표현하고 버전 관리하며, 브랜치에서 만들고 병합하는 **팀 프로세스**를 지원한다.

제품 관리자가 수용 기준을 갱신하면 구현 계획은 영향받는 기술 결정을 자동으로 표시한다. 아키텍트가 더 나은 패턴을 발견하면 새로운 가능성을 반영하도록 PRD가 갱신된다.

이 명세 작성 과정 전반에서 조사 에이전트가 중요한 맥락을 수집한다. 라이브러리 호환성, 성능 벤치마크, 보안 영향을 조사한다. 조직의 제약도 자동으로 발견해 적용한다. 회사의 데이터베이스 표준, 인증 요구사항, 배포 정책이 모든 명세에 자연스럽게 통합된다.

AI는 PRD에서 요구사항을 기술 결정으로 연결하는 구현 계획을 생성한다. 모든 기술 선택에는 문서화한 근거가 있다. 모든 아키텍처 결정은 구체적인 요구사항으로 추적된다. 이 과정에서 일관성 검증이 지속적으로 품질을 높인다. AI는 명세의 모호함, 모순, 공백을 일회성 게이트가 아니라 지속적인 개선 과정으로 분석한다.

명세와 구현 계획이 충분히 안정되면 코드 생성을 시작한다. 이들이 “완성”될 필요는 없다. 초기 생성은 명세가 실제로 타당한지 시험하는 탐색일 수 있다. 도메인 개념은 데이터 모델이 되고, 사용자 스토리는 API 엔드포인트가 되며, 수용 시나리오는 테스트가 된다. 명세를 통해 개발과 테스트가 합쳐진다. 테스트 시나리오는 코드 뒤에 작성하는 것이 아니라 구현과 테스트를 함께 생성하는 명세의 일부다.

피드백 순환은 초기 개발 이후까지 이어진다. 운영 지표와 사고는 긴급 수정만 유발하는 것이 아니라 다음 재생성을 위해 명세를 갱신한다. 성능 병목은 새로운 비기능 요구사항이 된다. 보안 취약점은 모든 후속 생성에 영향을 미치는 제약이 된다. 명세, 구현, 운영 현실이 반복해서 상호작용하는 과정에서 진정한 이해가 생기며, 전통적인 SDLC는 지속적인 진화로 바뀐다.

## 지금 SDD가 중요한 이유

세 가지 흐름이 SDD를 가능하게 할 뿐 아니라 필요하게 만든다.

첫째, AI 역량이 자연어 명세로 작동하는 코드를 안정적으로 생성할 수 있는 수준에 도달했다. 이는 개발자를 대체하는 일이 아니다. 명세를 구현으로 기계적으로 변환하는 일을 자동화해 개발자의 효과를 높이는 것이다. 탐색과 창의성을 확대하고, 손쉽게 “처음부터 다시 시작”하도록 도우며, 추가·제거·비판적 사고를 지원할 수 있다.

둘째, 소프트웨어의 복잡성이 계속 기하급수적으로 증가한다. 현대 시스템은 수십 개의 서비스, 프레임워크, 의존성을 통합한다. 수작업으로 이 모든 조각을 원래 의도와 일치시키기는 점점 어려워진다. SDD는 명세 주도 생성을 통해 체계적인 정합성을 제공한다. 프레임워크는 사람 우선이 아닌 AI 우선 지원을 제공하거나, 재사용 가능한 컴포넌트를 중심으로 설계되도록 발전할 수 있다.

셋째, 변화의 속도가 빨라진다. 오늘날 요구사항은 어느 때보다 빠르게 바뀐다. 방향 전환은 더 이상 예외가 아니라 예상되는 일이다. 현대 제품 개발은 사용자 피드백, 시장 상황, 경쟁 압력에 따른 빠른 반복을 요구한다. 전통적인 개발에서는 이런 변화를 방해 요소로 취급한다. 방향을 전환할 때마다 문서, 설계, 코드에 변경을 수작업으로 전파해야 한다. 그 결과는 속도를 제한하는 느리고 신중한 갱신이거나, 기술 부채를 쌓는 빠르고 무모한 변경이다.

SDD는 가정과 시뮬레이션 실험을 지원할 수 있다. “티셔츠를 더 많이 팔려는 사업상의 필요를 뒷받침하도록 애플리케이션을 재구현하거나 변경해야 한다면, 이를 어떻게 구현하고 실험할 것인가?”

SDD는 요구사항 변경을 장애물에서 일상적인 작업 흐름으로 바꾼다. 명세가 구현을 이끌면 방향 전환은 수동 재작성 대신 체계적인 재생성이 된다. PRD의 핵심 요구사항을 바꾸면 영향받는 구현 계획이 자동으로 갱신된다. 사용자 스토리를 수정하면 해당 API 엔드포인트가 재생성된다. 이는 초기 개발뿐 아니라 피할 수 없는 변화 속에서도 엔지니어링 속도를 유지하는 일이다.

## 핵심 원칙

**명세를 공통 언어로 사용**: 명세가 핵심 산출물이 된다. 코드는 특정 언어와 프레임워크로 표현한 명세가 된다. 소프트웨어 유지보수는 명세를 발전시키는 일이다.

**실행 가능한 명세**: 명세는 작동하는 시스템을 생성할 만큼 정확하고 완전하며 모호하지 않아야 한다. 이를 통해 의도와 구현 사이의 간극을 없앤다.

**지속적인 개선**: 일관성 검증은 일회성 게이트가 아니라 계속 수행한다. AI는 명세의 모호함, 모순, 공백을 지속적으로 분석한다.

**조사에 기반한 맥락**: 조사 에이전트는 명세 과정 전반에서 기술적 선택지, 성능 영향, 조직의 제약을 조사해 중요한 맥락을 모은다.

**양방향 피드백**: 운영 현실은 명세의 진화에 반영된다. 지표, 사고, 운영에서 배운 점은 명세 개선의 입력이 된다.

**탐색을 위한 분기**: 같은 명세에서 여러 구현 방식을 생성해 성능, 유지보수성, 사용자 경험, 비용 등 서로 다른 최적화 목표를 탐색한다.

## 구현 접근법

오늘날 SDD를 실천하려면 기존 도구를 조합하고 과정 내내 규율을 유지해야 한다. 다음 수단으로 이 방법론을 실천할 수 있다.

- 반복적인 명세 개발을 위한 AI 도우미
- 기술적 맥락을 수집하는 조사 에이전트
- 명세를 구현으로 변환하는 코드 생성 도구
- 명세 우선 작업 흐름에 맞춘 버전 관리 시스템
- AI의 명세 문서 분석을 통한 일관성 검사

핵심은 명세를 진실의 원천으로 취급하고, 코드는 명세를 위해 존재하는 생성 결과물로 취급하는 것이다.

## 명령으로 SDD 간소화하기

명세 → 계획 → 작업 도출 흐름을 자동화하는 세 가지 강력한 명령으로 SDD 방법론을 크게 강화할 수 있다.

### `/speckit.specify` 명령

이 명령은 간단한 기능 설명인 사용자 프롬프트를 완전하고 구조적인 명세로 바꾸며 저장소 관리도 자동화한다.

1. **자동 기능 번호 지정**: 기존 명세를 검색해 다음 기능 번호를 결정한다(예: 001, 002, 003, …, 1000 — 자동으로 세 자리 이상으로 확장).
2. **브랜치 생성**: 설명에서 의미 있는 브랜치 이름을 만들어 자동으로 생성한다.
3. **템플릿 기반 생성**: 요구사항에 맞춰 기능 명세 템플릿을 복사하고 조정한다.
4. **디렉터리 구조**: 관련 문서 전체를 위한 올바른 `specs/[branch-name]/` 구조를 만든다.

### `/speckit.plan` 명령

기능 명세가 있으면 이 명령이 포괄적인 구현 계획을 만든다.

1. **명세 분석**: 기능 요구사항, 사용자 스토리, 수용 기준을 읽고 이해한다.
2. **헌법 준수**: 프로젝트 헌법과 아키텍처 원칙에 부합하는지 확인한다.
3. **기술적 변환**: 사업 요구사항을 기술 아키텍처와 구현 상세로 바꾼다.
4. **상세 문서화**: 데이터 모델, API 계약, 테스트 시나리오의 보조 문서를 생성한다.
5. **빠른 시작 검증**: 핵심 검증 시나리오를 담은 빠른 시작 가이드를 만든다.

### `/speckit.tasks` 명령

계획을 만든 뒤 이 명령이 계획과 관련 설계 문서를 분석해 실행 가능한 작업 목록을 생성한다.

1. **입력**: 필수인 `plan.md`를 읽고, 있으면 `data-model.md`, `contracts/`, `research.md`도 읽는다.
2. **작업 도출**: 계약, 엔티티, 시나리오를 구체적인 작업으로 바꾼다.
3. **병렬화**: 독립적인 작업에 `[P]`를 표시하고 안전한 병렬 그룹을 제시한다.
4. **출력**: 기능 디렉터리에 `tasks.md`를 작성해 Task 에이전트가 실행할 수 있게 한다.

### 예시: 채팅 기능 만들기

다음은 이 명령들이 전통적인 개발 흐름을 바꾸는 방식이다.

**전통적인 접근:**

```text
1. 문서로 PRD 작성(2~3시간)
2. 설계 문서 작성(2~3시간)
3. 프로젝트 구조 수동 설정(30분)
4. 기술 명세 작성(3~4시간)
5. 테스트 계획 작성(2시간)
합계: 문서 작업 약 12시간
```

**명령을 사용하는 SDD 접근:**

```bash
# Step 1: Create the feature specification (5 minutes)
/speckit.specify Real-time chat system with message history and user presence

# This automatically:
# - Creates branch "003-chat-system"
# - Generates specs/003-chat-system/spec.md
# - Populates it with structured requirements

# Step 2: Generate implementation plan (5 minutes)
/speckit.plan WebSocket for real-time messaging, PostgreSQL for history, Redis for presence

# Step 3: Generate executable tasks (5 minutes)
/speckit.tasks

# This automatically creates:
# - specs/003-chat-system/plan.md
# - specs/003-chat-system/research.md (WebSocket library comparisons)
# - specs/003-chat-system/data-model.md (Message and User schemas)
# - specs/003-chat-system/contracts/ (WebSocket events, REST endpoints)
# - specs/003-chat-system/quickstart.md (Key validation scenarios)
# - specs/003-chat-system/tasks.md (Task list derived from the plan)
```

15분이면 다음을 얻는다.

- 사용자 스토리와 수용 기준이 포함된 완전한 기능 명세
- 기술 선택과 근거가 포함된 상세 구현 계획
- 코드 생성에 사용할 준비가 된 API 계약과 데이터 모델
- 자동·수동 테스트를 모두 위한 포괄적인 테스트 시나리오
- 기능 브랜치에서 올바르게 버전 관리되는 모든 문서

### 구조화된 자동화의 힘

이 명령들은 시간을 절약하는 데 그치지 않고 일관성과 완전성을 강제한다.

1. **빠뜨리는 세부 사항 방지**: 템플릿은 비기능 요구사항부터 오류 처리까지 모든 측면을 고려하도록 한다.
2. **추적 가능한 결정**: 모든 기술 선택은 구체적인 요구사항과 연결된다.
3. **살아 있는 문서**: 명세가 코드를 생성하므로 코드와 동기화된 상태를 유지한다.
4. **빠른 반복**: 요구사항을 바꾸고 며칠 대신 몇 분 안에 계획을 재생성한다.

이 명령들은 명세를 정적인 문서가 아니라 실행 가능한 산출물로 취급해 SDD 원칙을 구현한다. 명세 과정을 필요악에서 개발을 이끄는 동력으로 바꾼다.

### 템플릿이 이끄는 품질: 구조로 LLM을 제약해 더 나은 결과를 얻는 방법

이 명령들의 진정한 힘은 자동화뿐 아니라 템플릿이 더 높은 품질의 명세를 만들도록 LLM의 행동을 이끄는 방식에 있다. 템플릿은 LLM의 출력을 생산적인 방향으로 제약하는 정교한 프롬프트 역할을 한다.

#### 1. **성급한 구현 상세 방지**

기능 명세 템플릿은 명시적으로 다음을 지시한다.

```text
- ✅ 사용자가 무엇을 필요로 하며 왜 필요한지에 집중
- ❌ 구현 방법은 피하기(기술 스택, API, 코드 구조 제외)
```

이 제약은 LLM이 적절한 추상화 수준을 유지하도록 한다. LLM이 자연스럽게 “React와 Redux를 사용해 구현”으로 넘어갈 수 있는 상황에서도, 템플릿은 “사용자는 자신의 데이터가 실시간으로 갱신되기를 원한다”에 집중하게 한다. 이러한 분리를 통해 구현 기술이 바뀌어도 명세의 안정성을 유지한다.

#### 2. **불확실성의 명시적 표시 강제**

두 템플릿 모두 `[NEEDS CLARIFICATION]` 표식을 의무적으로 사용하게 한다.

```text
사용자 프롬프트에서 이 명세를 만들 때:
1. **모든 모호함 표시**: [NEEDS CLARIFICATION: specific question] 사용
2. **추측 금지**: 프롬프트에 명시되지 않은 사항은 표시
```

이는 그럴듯하지만 틀릴 수 있는 가정을 세우는 LLM의 흔한 행동을 막는다. “로그인 시스템”이 이메일과 비밀번호 인증을 사용한다고 추측하는 대신, LLM은 `[NEEDS CLARIFICATION: auth method not specified - email/password, SSO, OAuth?]`로 표시해야 한다.

#### 3. **체크리스트를 통한 구조적 사고**

템플릿에는 명세의 “단위 테스트” 역할을 하는 포괄적인 체크리스트가 포함된다.

```markdown
### 요구사항 완전성

- [ ] [NEEDS CLARIFICATION] 표식이 남아 있지 않음
- [ ] 요구사항은 테스트할 수 있고 모호하지 않음
- [ ] 성공 기준을 측정할 수 있음
```

이 체크리스트는 LLM이 자신의 출력을 체계적으로 검토하도록 해, 그냥 지나칠 수 있는 공백을 찾아낸다. LLM에 품질 보증 프레임워크를 제공하는 것과 같다.

#### 4. **게이트를 통한 헌법 준수**

구현 계획 템플릿은 단계별 게이트를 통해 아키텍처 원칙을 강제한다.

```markdown
### 단계 -1: 구현 전 게이트

#### 단순성 게이트(제VII조)

- [ ] 프로젝트를 3개 이하로 사용하는가?
- [ ] 미래를 미리 대비한 불필요한 설계가 없는가?

#### 추상화 억제 게이트(제VIII조)

- [ ] 프레임워크를 직접 사용하는가?
- [ ] 모델 표현이 하나인가?
```

이 게이트들은 LLM이 모든 복잡성을 명시적으로 정당화하게 해 과잉 설계를 방지한다. 게이트를 통과하지 못하면 LLM은 “복잡성 추적” 절에 이유를 문서화해야 하며, 이를 통해 아키텍처 결정에 책임을 부여한다.

#### 5. **계층적인 상세 정보 관리**

템플릿은 올바른 정보 구조를 강제한다.

```text
**중요**: 이 구현 계획은 상위 수준을 유지하고 읽기 쉬워야 한다.
코드 예시, 상세 알고리즘, 방대한 기술 명세는 모두
적절한 `implementation-details/` 파일에 배치해야 한다.
```

이는 명세가 읽기 어려운 코드 더미가 되는 흔한 문제를 막는다. LLM은 적절한 상세 수준을 유지하는 법을 배운다. 복잡한 내용은 별도 파일로 분리하면서 주 문서를 쉽게 탐색할 수 있게 한다.

#### 6. **테스트 우선 사고**

구현 템플릿은 테스트 우선 개발을 강제한다.

```text
### 파일 생성 순서
1. API 명세가 담긴 `contracts/` 생성
2. 계약 → 통합 → e2e → 단위 순서로 테스트 파일 생성
3. 테스트를 통과시키는 소스 파일 생성
```

이 순서 제약은 LLM이 구현 전에 테스트 가능성과 계약을 생각하게 해, 더 견고하고 검증 가능한 명세로 이어진다.

#### 7. **추측에 기반한 기능 방지**

템플릿은 추측을 명시적으로 억제한다.

```text
- [ ] 추측에 기반하거나 “필요할지도 모르는” 기능이 없음
- [ ] 모든 단계에 명확한 선행 조건과 산출물이 있음
```

이는 LLM이 구현을 복잡하게 만드는 “있으면 좋은” 기능을 추가하지 못하게 한다. 모든 기능은 명확한 수용 기준이 있는 구체적인 사용자 스토리로 추적돼야 한다.

### 결합 효과

이 제약들은 함께 작용해 다음과 같은 명세를 만든다.

- **완전함**: 체크리스트로 빠뜨린 것이 없도록 한다.
- **명확함**: 필수 명확화 표식으로 불확실성을 드러낸다.
- **테스트 가능함**: 과정 자체에 테스트 우선 사고가 포함된다.
- **유지보수 가능함**: 적절한 추상화 수준과 정보 계층을 갖춘다.
- **구현 가능함**: 구체적인 산출물이 있는 명확한 단계로 구성된다.

템플릿은 LLM을 창의적인 글쓴이에서 규율 있는 명세 엔지니어로 바꾼다. 그 역량을 일관되게 높은 품질을 갖추고 실제로 개발을 이끄는 실행 가능한 명세를 만드는 데 집중시킨다.

## 헌법이라는 토대: 아키텍처 규율 강제

SDD의 중심에는 명세가 코드가 되는 방식을 다스리는 불변의 원칙 모음인 헌법이 있다. 헌법(`memory/constitution.md`)은 시스템의 아키텍처 DNA 역할을 하며, 생성되는 모든 구현이 일관성, 단순성, 품질을 유지하게 한다.

### 개발의 아홉 조항

헌법은 개발 과정의 모든 측면을 형성하는 아홉 조항을 정의한다.

#### 제I조: 라이브러리 우선 원칙

모든 기능은 예외 없이 독립적인 라이브러리로 시작해야 한다. 이는 처음부터 모듈식 설계를 강제한다.

```text
Specify의 모든 기능은 반드시 독립적인 라이브러리로 출발해야 한다.
먼저 재사용 가능한 라이브러리 컴포넌트로 추상화하지 않고
기능을 애플리케이션 코드 안에 직접 구현해서는 안 된다.
```

이 원칙은 명세가 거대한 단일 애플리케이션 대신 모듈화되고 재사용 가능한 코드를 생성하게 한다. LLM이 구현 계획을 만들 때에는 경계가 명확하고 의존성이 최소인 라이브러리로 기능을 구성해야 한다.

#### 제II조: CLI 인터페이스 의무

모든 라이브러리는 명령줄 인터페이스로 기능을 노출해야 한다.

```text
모든 CLI 인터페이스는 반드시 다음을 충족해야 한다.
- 텍스트 입력 수용(stdin, 인수 또는 파일 사용)
- 텍스트 출력 생성(stdout 사용)
- 구조적 데이터 교환을 위한 JSON 형식 지원
```

이는 관찰 가능성과 테스트 가능성을 강제한다. LLM은 불투명한 클래스 안에 기능을 숨길 수 없다. 모든 기능은 텍스트 기반 인터페이스로 접근하고 검증할 수 있어야 한다.

#### 제III조: 테스트 우선 명령

가장 큰 변화를 가져오는 조항이다. 테스트 전에는 코드를 작성하지 않는다.

```text
이는 타협할 수 없다. 모든 구현은 반드시 엄격한 테스트 주도 개발을 따라야 한다.
다음 조건을 충족하기 전에는 구현 코드를 작성해서는 안 된다.
1. 단위 테스트 작성
2. 사용자의 테스트 검증 및 승인
3. 테스트 실패 확인(Red 단계)
```

이는 전통적인 AI 코드 생성을 완전히 뒤집는다. 코드를 만들고 작동하기를 바라는 대신, LLM은 먼저 동작을 정의하는 포괄적인 테스트를 만들고 승인을 받은 뒤에만 구현을 생성해야 한다.

#### 제IV·V·VI조: 프로젝트가 정의하는 거버넌스

제IV·V·VI조는 Spec Kit이 정하는 대신 각 프로젝트의 헌법에서 의도적으로 정의하도록 한다. 헌법 템플릿은 자리표시자와 통합 테스트, 관찰 가능성, 버전 관리, 호환성을 깨는 변경 같은 관심사의 예시를 제공한다. 팀은 이 자리표시자를 자신의 시스템과 조직에 맞는 원칙으로 대체한다.

이를 통해 아홉 조항의 구조를 안정적으로 유지하면서 각 프로젝트가 타협할 수 없는 고유한 표준을 담을 수 있다. 어떤 프로젝트에서는 제IV조가 보안과 접근 경계를 다스리고, 다른 프로젝트에서는 통합 테스트 요구사항을 정의할 수 있다. `/speckit.analyze` 명령은 프로젝트의 구체적인 헌법을 평가하므로, 프로젝트에서 정의한 이 조항들도 기본 예시와 똑같이 준수 검사에 참여한다.

#### 제VII·VIII조: 단순성과 추상화 억제

이 두 조항은 함께 과잉 설계에 맞선다.

```text
절 7.3: 최소 프로젝트 구조
- 초기 구현은 최대 3개 프로젝트
- 추가 프로젝트는 문서화된 정당화가 필요함

절 8.1: 프레임워크 신뢰
- 프레임워크 기능을 감싸지 말고 직접 사용
```

LLM이 자연스럽게 정교한 추상화를 만들 수 있는 상황에서, 이 조항들은 복잡성을 더하는 모든 계층을 정당화하도록 강제한다. 구현 계획 템플릿의 “단계 -1 게이트”가 이 원칙들을 직접 강제한다.

#### 제IX조: 통합 우선 테스트

격리된 단위 테스트보다 실제 환경에서의 테스트를 우선한다.

```text
테스트는 반드시 현실적인 환경을 사용해야 한다.
- 모의 객체보다 실제 데이터베이스 우선
- 대역보다 실제 서비스 인스턴스 사용
- 구현 전 계약 테스트 필수
```

이는 생성된 코드가 이론뿐 아니라 실제로도 작동하게 한다.

### 템플릿을 통한 헌법 강제

구현 계획 템플릿은 구체적인 점검 항목으로 이 조항들을 실행에 옮긴다.

```markdown
### 단계 -1: 구현 전 게이트

#### 단순성 게이트(제VII조)

- [ ] 프로젝트를 3개 이하로 사용하는가?
- [ ] 미래를 미리 대비한 불필요한 설계가 없는가?

#### 추상화 억제 게이트(제VIII조)

- [ ] 프레임워크를 직접 사용하는가?
- [ ] 모델 표현이 하나인가?

#### 통합 우선 게이트(제IX조)

- [ ] 계약을 정의했는가?
- [ ] 계약 테스트를 작성했는가?
```

이 게이트들은 아키텍처 원칙의 컴파일 시점 검사처럼 작동한다. LLM은 게이트를 통과하거나 “복잡성 추적” 절에 정당한 예외를 문서화하지 않고는 진행할 수 없다.

### 불변 원칙의 힘

헌법의 힘은 불변성에 있다. 구현 상세는 발전할 수 있지만 핵심 원칙은 일정하게 유지된다. 이를 통해 다음을 얻는다.

1. **시간에 걸친 일관성**: 오늘 생성한 코드와 내년에 생성할 코드가 같은 원칙을 따른다.
2. **LLM 간 일관성**: 서로 다른 AI 모델이 아키텍처상 호환되는 코드를 만든다.
3. **아키텍처 무결성**: 모든 기능은 시스템 설계를 약화시키는 대신 강화한다.
4. **품질 보장**: 테스트 우선, 라이브러리 우선, 단순성 원칙이 유지보수 가능한 코드를 보장한다.

### 헌법의 진화

원칙은 불변이지만 적용 방식은 발전할 수 있다.

```text
절 4.2: 개정 절차
이 헌법을 수정하려면 다음이 필요하다.
- 변경 근거의 명시적 문서화
- 프로젝트 유지관리자의 검토와 승인
- 하위 호환성 평가
```

이를 통해 안정성을 유지하면서 방법론을 학습하고 개선할 수 있다. 헌법은 날짜가 있는 개정 기록으로 자신의 진화를 보여 주며, 실제 경험에 따라 원칙을 다듬는 방법을 제시한다.

### 규칙을 넘어: 개발 철학

헌법은 단순한 규칙집이 아니라 LLM이 코드 생성을 생각하는 방식을 형성하는 철학이다.

- **불투명함보다 관찰 가능성**: 모든 것은 CLI 인터페이스로 검사할 수 있어야 한다.
- **기교보다 단순성**: 단순하게 시작하고 필요성이 입증될 때만 복잡성을 더한다.
- **격리보다 통합**: 인위적인 환경 대신 실제 환경에서 테스트한다.
- **거대한 단일 구조보다 모듈성**: 모든 기능은 명확한 경계를 가진 라이브러리다.

이 원칙들을 명세와 계획 과정에 내장함으로써, SDD는 생성된 코드가 기능적으로 작동할 뿐 아니라 유지보수와 테스트가 가능하고 아키텍처상 건전하도록 한다. 헌법은 AI를 코드 생성기에서 시스템 설계 원칙을 존중하고 강화하는 아키텍처 파트너로 바꾼다.

## 변화

기계적인 변환을 자동화해 사람의 역량을 확대하는 일이다. 명세, 조사, 코드가 함께 발전하는 긴밀한 피드백 순환을 만들며, 반복할 때마다 더 깊은 이해와 의도·구현 사이의 더 나은 정합성을 얻는다. 개발자를 대체하거나 창의성을 자동화하려는 것이 아니다.

소프트웨어 개발에는 의도와 구현의 정합성을 유지할 더 나은 도구가 필요하다. SDD는 코드를 단순히 안내하는 데 그치지 않고 생성하는 실행 가능한 명세를 통해 이러한 정합성을 달성하는 방법론을 제공한다.
