## 체크리스트 목적: "영어를 위한 단위 테스트"

**핵심 개념**: 체크리스트는 **요구사항 작성의 단위 테스트**입니다. 특정 영역에서 요구사항의 품질, 명확성, 완전성을 검증합니다.

**검증/테스트 대상이 아닌 것**:

- ❌ "버튼 클릭이 올바르게 동작하는지 검증"
- ❌ "오류 처리가 동작하는지 테스트"
- ❌ "API가 200을 반환하는지 확인"
- ❌ 코드/구현이 명세와 일치하는지 점검

**요구사항 품질 검증의 대상**:

- ✅ "모든 카드 유형의 시각적 위계 요구사항이 정의되어 있는가?"(완전성)
- ✅ "'눈에 띄는 표시'가 구체적인 크기/위치로 정량화되어 있는가?"(명확성)
- ✅ "모든 상호작용 요소의 hover 상태 요구사항이 일관되는가?"(일관성)
- ✅ "키보드 탐색의 접근성 요구사항이 정의되어 있는가?"(범위)
- ✅ "로고 이미지 로드 실패 시의 동작을 명세가 정의하는가?"(경계 사례)

**비유**: 명세가 영어로 작성한 코드라면 체크리스트는 그 단위 테스트 모음입니다. 요구사항이 잘 작성되었는지, 완전하고 명확하며 구현할 준비가 되었는지를 테스트합니다. 구현의 동작 여부를 테스트하는 것이 **아닙니다**.

**소유권과 체크박스 생명주기**:

- 이 명령이 생성하는 맞춤 체크리스트는 검토자가 소유하는 요구사항 품질 검토 산출물입니다.
- `[x]`는 검토자가 요구사항 품질 기준을 충족했다고 판단했다는 뜻입니다.
- `[x]`는 구현 작업 완료를 뜻하지 **않습니다**.
- 이 명령은 체크리스트 항목을 생성하거나 추가합니다. 생성한 항목에 `[x]`를 표시해서는 **안 됩니다**.
- 에이전트는 검토자가 명시적으로 요청할 때만 항목 평가를 도울 수 있습니다.
- `checklists/requirements.md`는 `__SPECKIT_COMMAND_SPECIFY__`와 `__SPECKIT_COMMAND_CLARIFY__`가 관리하는 별도의 내장 명세 품질 체크리스트입니다. 그 예외를 여기서 생성하는 맞춤 체크리스트에 적용하지 마세요.

## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 사용자 입력이 비어 있지 않다면 **반드시** 고려해야 합니다.

## 실행 전 확인

**확장 훅 확인(체크리스트 생성 전)**:
- 프로젝트 루트에 `.specify/extensions.yml`이 있는지 확인합니다.
- 있으면 읽고 `hooks.before_checklist` 키 아래의 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않으면 조용히 건너뛰지 않습니다. 사용자에게 `.specify/extensions.yml`을 읽지 못했다는 사실(파서 오류 포함)과 그곳에 등록된 필수 훅(`optional: false`)을 포함해 어떤 훅도 확인하지 못했다는 사실을 알린 뒤 정상적으로 계속합니다.
- `enabled`가 명시적으로 `false`인 훅은 제외합니다. `enabled` 필드가 없으면 기본적으로 활성화된 것으로 취급합니다.
- 나머지 각 훅의 `condition` 표현식은 해석하거나 평가하려고 **시도하지 않습니다**:
  - `condition` 필드가 없거나 null/빈 값이면 실행 가능한 훅으로 취급합니다.
  - 비어 있지 않은 `condition`이 있으면 해당 훅을 건너뛰고 조건 평가는 HookExecutor 구현에 맡깁니다.
- 실행 가능한 각 훅에 대해 `optional` 플래그에 따라 다음 내용을 출력합니다:
  - **선택 훅**(`optional: true`):
    ```
    ## 확장 훅

    **선택 사전 훅**: {extension}
    명령: `/{command}`
    설명: {description}

    프롬프트: {prompt}
    실행하려면: `/{command}`
    ```
  - **필수 훅**(`optional: false`):
    ```
    ## 확장 훅

    **자동 사전 훅**: {extension}
    실행 중: `/{command}`
    EXECUTE_COMMAND: {command}

    실행 단계로 진행하기 전에 훅 명령의 결과를 기다리세요.
    ```
    위 블록을 출력한 뒤에는 **반드시** 실제로 훅을 호출하고 완료될 때까지 기다린 후 계속해야 합니다. 이 에이전트/세션에서 직접 명령을 실행할 때와 같은 방식으로 실행합니다(호출 형태는 위의 `{command}` ID 문자열과 다를 수 있습니다. 예를 들어 스킬 모드 에이전트는 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 훅이 실행되지 않습니다.
- 등록된 훅이 없거나 `.specify/extensions.yml`이 없으면 별도 출력 없이 건너뜁니다.

## 실행 단계

1. **설정**: 저장소 루트에서 `{SCRIPT}`를 실행하고 JSON에서 FEATURE_DIR, AVAILABLE_DOCS 목록, TEMPLATE_CONTENT를 파싱합니다.
   - 모든 파일 경로는 절대경로여야 합니다.
   - `I'm Groot`처럼 인수에 작은따옴표가 있으면 이스케이프 구문을 사용합니다. 예: `'I'\''m Groot'`(가능하면 큰따옴표 사용: `"I'm Groot"`).

2. **있는 경우**: 프로젝트 원칙과 거버넌스 제약을 위해 `/memory/constitution.md`를 읽습니다.

3. **의도 명확화(동적)**: 맥락에 맞는 초기 명확화 질문을 최대 **세 개** 도출합니다(미리 만든 질문 목록을 사용하지 않습니다). 질문은 **반드시** 다음을 따라야 합니다:
   - 사용자 표현과 spec/plan/tasks에서 추출한 신호를 바탕으로 생성합니다.
   - 체크리스트 내용에 실질적 변화를 주는 정보만 묻습니다.
   - `$ARGUMENTS`에서 이미 명확한 질문은 개별적으로 건너뜁니다.
   - 넓은 범위보다 정확성을 우선합니다.

   생성 알고리즘:
   1. 기능 영역 키워드(예: 인증, 지연 시간, UX, API), 위험 지표("중대", "필수", "규정 준수"), 이해관계자 단서("QA", "검토", "보안팀"), 명시적 산출물("a11y", "롤백", "계약")을 추출합니다.
   2. 신호를 최대 4개의 후보 집중 영역으로 묶고 관련성 순으로 정렬합니다.
   3. 명시되지 않았다면 예상 독자와 사용 시점(작성자, 검토자, QA, 릴리스)을 파악합니다.
   4. 범위의 폭, 깊이/엄격함, 위험 강조점, 제외 경계, 측정 가능한 수용 기준 중 빠진 차원을 찾습니다.
   5. 다음 유형에서 질문을 구성합니다:
      - 범위 조정(예: "X·Y와의 통합 접점도 포함할까요, 아니면 로컬 모듈의 정확성으로 한정할까요?")
      - 위험 우선순위(예: "잠재 위험 영역 중 어디에 필수 게이트 검사를 둘까요?")
      - 깊이 조정(예: "가벼운 커밋 전 점검표인가요, 정식 릴리스 게이트인가요?")
      - 독자 설정(예: "작성자만 사용하나요, PR 검토 시 동료도 사용하나요?")
      - 경계 제외(예: "이번에는 성능 튜닝 항목을 명시적으로 제외할까요?")
      - 시나리오 유형 누락(예: "복구 흐름을 찾지 못했습니다. 롤백/부분 실패 경로도 범위에 포함되나요?")

   질문 형식 규칙:
   - 선택지를 제시하면 선택지 | 후보 | 중요한 이유 열을 갖는 간결한 표를 생성합니다.
   - 선택지는 최대 A–E로 제한합니다. 자유 형식 답변이 더 명확하면 표를 생략합니다.
   - 사용자가 이미 말한 내용을 다시 묻지 않습니다.
   - 추측으로 범주를 만들지 않습니다(지어내지 않기). 불확실하면 "X가 범위에 속하는지 확인해 주세요."라고 명시적으로 묻습니다.

   상호작용이 불가능할 때의 기본값:
   - 깊이: 표준
   - 독자: 코드 관련이면 검토자(PR), 그 외에는 작성자
   - 집중점: 관련성이 높은 상위 2개 묶음

   질문을 출력합니다(Q1/Q2/Q3 표기). 답변 후 대안/예외/복구/비기능 영역 중 2개 이상의 시나리오 유형이 여전히 불명확하면, 각 질문에 한 줄 근거(예: "미해결 복구 경로 위험")를 붙여 구체적인 후속 질문을 최대 **두 개** 더 물을 **수 있습니다**(Q4/Q5). 전체 질문은 5개를 넘지 않습니다. 사용자가 추가 질문을 명시적으로 거절하면 확대하지 않습니다.

4. **사용자 요청 이해**: `$ARGUMENTS`와 명확화 답변을 결합합니다:
   - 체크리스트 주제(예: 보안, 검토, 배포, ux)를 도출합니다.
   - 사용자가 언급한 명시적인 필수 항목을 모읍니다.
   - 집중점 선택을 범주 구조에 대응시킵니다.
   - 빠진 맥락은 spec/plan/tasks에서 추론합니다(지어내지 **마세요**).

5. **기능 맥락 읽기**: FEATURE_DIR에서 읽습니다:
   - spec.md: 기능 요구사항과 범위
   - plan.md(있는 경우): 기술 세부 사항, 의존성
   - tasks.md(있는 경우): 구현 작업

   **맥락 읽기 전략**:
   - 현재 집중 영역과 관련된 필요한 부분만 읽습니다(파일 전체를 쏟아 넣지 않기).
   - 긴 절은 간결한 시나리오/요구사항 항목으로 요약하는 편을 우선합니다.
   - 점진적으로 공개합니다. 누락이 발견될 때만 후속 조회를 추가합니다.
   - 원본 문서가 크면 원문을 삽입하는 대신 중간 요약 항목을 생성합니다.

6. **체크리스트 생성** - TEMPLATE_CONTENT를 구조 템플릿으로 사용해 "요구사항의 단위 테스트"를 만듭니다:
   - `FEATURE_DIR/checklists/` 디렉터리가 없으면 만듭니다.
   - 고유한 체크리스트 파일명을 생성합니다:
     - 영역에 맞는 짧고 설명적인 이름을 사용합니다(예: `ux.md`, `api.md`, `security.md`).
     - 형식: `[domain].md`
   - 파일 처리 동작:
     - 파일이 없으면 새 파일을 만들고 CHK001부터 항목 번호를 매깁니다.
     - 파일이 있으면 마지막 CHK ID 다음부터 새 항목을 추가합니다(예: 마지막이 CHK015면 CHK016부터 시작).
   - 기존 체크리스트 내용을 삭제하거나 대체하지 않습니다. 항상 보존하고 추가합니다.
   - 새 항목은 모두 미선택 상태(`[ ]`)로 둡니다. 체크박스 상태는 검토자 소유입니다.

   **핵심 원칙 - 구현이 아닌 요구사항을 테스트합니다**:
   모든 체크리스트 항목은 **요구사항 자체**에 대해 **반드시** 다음을 평가해야 합니다:
   - **완전성**: 필요한 요구사항이 모두 있는가?
   - **명확성**: 요구사항이 명료하고 구체적인가?
   - **일관성**: 요구사항이 서로 정합적인가?
   - **측정 가능성**: 요구사항을 객관적으로 검증할 수 있는가?
   - **범위**: 모든 시나리오/경계 사례를 다루는가?

   **범주 구조** - 요구사항 품질 차원으로 항목을 묶습니다:
   - **요구사항 완전성**(필요한 요구사항을 모두 문서화했는가?)
   - **요구사항 명확성**(구체적이고 명료한가?)
   - **요구사항 일관성**(충돌 없이 정합적인가?)
   - **수용 기준 품질**(성공 기준을 측정할 수 있는가?)
   - **시나리오 범위**(모든 흐름/사례를 다루는가?)
   - **경계 사례 범위**(경계 조건을 정의했는가?)
   - **비기능 요구사항**(성능, 보안, 접근성 등을 명세했는가?)
   - **의존성 및 가정**(문서화하고 검증했는가?)
   - **모호함 및 충돌**(무엇을 명확히 해야 하는가?)

   **체크리스트 항목 작성법 - "영어의 단위 테스트"**:

   ❌ **잘못된 예**(구현 테스트):
   - "랜딩 페이지에 에피소드 카드 3개가 표시되는지 검증"
   - "데스크톱에서 hover 상태가 동작하는지 테스트"
   - "로고를 클릭하면 홈으로 이동하는지 확인"

   ✅ **올바른 예**(요구사항 품질 테스트):
   - "주요 에피소드의 정확한 개수와 배치가 명세되어 있는가?" [완전성]
   - "'눈에 띄는 표시'가 구체적인 크기/위치로 정량화되어 있는가?" [명확성]
   - "모든 상호작용 요소의 hover 상태 요구사항이 일관되는가?" [일관성]
   - "모든 상호작용 UI의 키보드 탐색 요구사항이 정의되어 있는가?" [범위]
   - "로고 이미지 로드 실패 시의 대체 동작이 명세되어 있는가?" [경계 사례]
   - "비동기 에피소드 데이터의 로딩 상태가 정의되어 있는가?" [완전성]
   - "경쟁하는 UI 요소의 시각적 위계를 명세가 정의하는가?" [명확성]

   **항목 구조**:
   각 항목은 다음 형식을 따릅니다:
   - 요구사항 품질을 묻는 질문 형식
   - 명세/계획에 쓰인 것(또는 쓰이지 않은 것)에 집중
   - 대괄호에 품질 차원 포함 [완전성/명확성/일관성/기타]
   - 기존 요구사항을 확인할 때 명세 절 `[Spec §X.Y]` 참조
   - 빠진 요구사항을 확인할 때 `[Gap]` 표시 사용

   **품질 차원별 예시**:

   완전성:
   - "모든 API 실패 유형에 대한 오류 처리 요구사항이 정의되어 있는가? [Gap]"
   - "모든 상호작용 요소의 접근성 요구사항이 명세되어 있는가? [완전성]"
   - "반응형 배치의 모바일 중단점 요구사항이 정의되어 있는가? [Gap]"

   명확성:
   - "'빠른 로딩'이 구체적인 시간 임계값으로 정량화되어 있는가? [명확성, Spec §NFR-2]"
   - "'관련 에피소드' 선택 기준이 명시적으로 정의되어 있는가? [명확성, Spec §FR-5]"
   - "'눈에 띄는'이 측정 가능한 시각적 속성으로 정의되어 있는가? [Ambiguity, Spec §FR-4]"

   일관성:
   - "모든 페이지의 탐색 요구사항이 정합적인가? [일관성, Spec §FR-10]"
   - "랜딩 페이지와 상세 페이지의 카드 컴포넌트 요구사항이 일관되는가? [일관성]"

   범위:
   - "초기 빈 상태(에피소드 없음) 시나리오의 요구사항이 정의되어 있는가? [범위, 경계 사례]"
   - "사용자 동시 상호작용 시나리오를 다루는가? [범위, Gap]"
   - "부분적인 데이터 로드 실패의 요구사항이 명세되어 있는가? [범위, 예외 흐름]"

   측정 가능성:
   - "시각적 위계 요구사항을 측정/테스트할 수 있는가? [수용 기준, Spec §FR-1]"
   - "'균형 잡힌 시각적 무게'를 객관적으로 검증할 수 있는가? [측정 가능성, Spec §FR-2]"

   **시나리오 분류 및 범위**(요구사항 품질에 집중):
   - 기본, 대안, 예외/오류, 복구, 비기능 시나리오의 요구사항 존재 여부를 확인합니다.
   - 각 시나리오 유형마다 "[시나리오 유형] 요구사항이 완전하고 명확하며 일관되는가?"라고 묻습니다.
   - 시나리오 유형이 없으면 "[시나리오 유형] 요구사항은 의도적으로 제외되었는가, 아니면 누락되었는가? [Gap]"라고 묻습니다.
   - 상태 변경이 발생하면 복원력/롤백을 포함합니다: "마이그레이션 실패에 대한 롤백 요구사항이 정의되어 있는가? [Gap]"

   **추적성 요구사항**:
   - 최소한 항목의 80% 이상은 추적성 참조를 하나 이상 **반드시** 포함해야 합니다.
   - 각 항목은 명세 절 `[Spec §X.Y]`를 참조하거나 `[Gap]`, `[Ambiguity]`, `[Conflict]`, `[Assumption]` 표시를 사용합니다.
   - ID 체계가 없으면 "요구사항 및 수용 기준의 ID 체계가 수립되어 있는가? [추적성]"라고 묻습니다.

   **문제 드러내기와 해결**(요구사항 품질 문제):
   요구사항 자체에 대해 질문합니다:
   - 모호함: "'빠른'이라는 용어가 구체적인 지표로 정량화되어 있는가? [Ambiguity, Spec §NFR-1]"
   - 충돌: "§FR-10과 §FR-10a 사이의 탐색 요구사항이 충돌하는가? [Conflict]"
   - 가정: "'팟캐스트 API가 항상 사용 가능하다'는 가정이 검증되었는가? [Assumption]"
   - 의존성: "외부 팟캐스트 API 요구사항이 문서화되어 있는가? [의존성, Gap]"
   - 정의 누락: "'시각적 위계'가 측정 가능한 기준으로 정의되어 있는가? [Gap]"

   **내용 통합**:
   - 권장 상한: 원시 후보 항목이 40개를 넘으면 위험/영향에 따라 우선순위를 정합니다.
   - 같은 요구사항 측면을 확인하는 유사 중복 항목을 합칩니다.
   - 영향이 작은 경계 사례가 5개를 넘으면 하나의 항목으로 만듭니다: "경계 사례 X, Y, Z를 요구사항에서 다루는가? [범위]"

   **🚫 절대 금지** - 다음은 요구사항 테스트를 구현 테스트로 바꿉니다:
   - ❌ "검증", "테스트", "확인", "점검"으로 시작하면서 구현 동작을 다루는 항목
   - ❌ 코드 실행, 사용자 행동, 시스템 동작 참조
   - ❌ "올바르게 표시된다", "제대로 동작한다", "예상대로 기능한다"
   - ❌ "클릭", "탐색", "렌더링", "로드", "실행"
   - ❌ 테스트 케이스, 테스트 계획, QA 절차
   - ❌ 구현 세부 사항(프레임워크, API, 알고리즘)

   **✅ 필수 패턴** - 다음은 요구사항 품질을 테스트합니다:
   - ✅ "[시나리오]에 대한 [요구사항 유형]이 정의/명세/문서화되어 있는가?"
   - ✅ "[모호한 용어]가 구체적인 기준으로 정량화/명확화되어 있는가?"
   - ✅ "[절 A]와 [절 B] 사이의 요구사항이 일관되는가?"
   - ✅ "[요구사항]을 객관적으로 측정/검증할 수 있는가?"
   - ✅ "[경계 사례/시나리오]를 요구사항에서 다루는가?"
   - ✅ "명세가 [빠진 측면]을 정의하는가?"

7. **구조 참조**: 제목, 메타정보 절, 범주 제목, 소유권 안내, 비고 절, ID 형식은 `templates/checklist-template.md`의 정본 템플릿에 따라 생성합니다. 템플릿이 없으면 H1 제목, 목적/생성일 메타정보 줄, `[x]`가 요구사항 품질에 대한 검토자 승인을 뜻한다는 소유권 안내, CHK001부터 전역적으로 증가하는 ID의 `- [ ] CHK### <requirement item>` 행을 담은 `##` 범주 절, 그리고 `__SPECKIT_COMMAND_IMPLEMENT__`가 체크리스트 상태를 읽되 표시는 수정하지 않는다는 비고를 사용합니다.

8. **보고**: 체크리스트 파일의 전체 경로와 항목 수를 출력하고 이번 실행이 새 파일을 만들었는지 기존 파일에 추가했는지 요약합니다. 다음을 요약합니다:
   - 선택한 집중 영역
   - 깊이 수준
   - 실행 주체/사용 시점
   - 반영한 사용자 지정 필수 항목

**중요**: 각 `__SPECKIT_COMMAND_CHECKLIST__` 호출은 짧고 설명적인 파일명을 사용하며 새 파일을 만들거나 기존 파일에 추가합니다. 이에 따라 다음이 가능합니다:

- 서로 다른 유형의 여러 체크리스트(예: `ux.md`, `test.md`, `security.md`)
- 목적을 알려 주는 간단하고 기억하기 쉬운 파일명
- `checklists/` 폴더에서 쉽게 식별하고 탐색

복잡해지지 않도록 설명적인 유형을 사용하고 완료 후에는 낡은 체크리스트를 정리합니다.

## 실행 후 확인

**확장 훅 확인(체크리스트 생성 후)**:
프로젝트 루트에 `.specify/extensions.yml`이 있는지 확인합니다.
- 있으면 읽고 `hooks.after_checklist` 키 아래의 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않으면 조용히 건너뛰지 않습니다. 사용자에게 `.specify/extensions.yml`을 읽지 못했다는 사실(파서 오류 포함)과 그곳에 등록된 필수 훅(`optional: false`)을 포함해 어떤 훅도 확인하지 못했다는 사실을 알린 뒤 정상적으로 계속합니다.
- `enabled`가 명시적으로 `false`인 훅은 제외합니다. `enabled` 필드가 없으면 기본적으로 활성화된 것으로 취급합니다.
- 나머지 각 훅의 `condition` 표현식은 해석하거나 평가하려고 **시도하지 않습니다**:
  - `condition` 필드가 없거나 null/빈 값이면 실행 가능한 훅으로 취급합니다.
  - 비어 있지 않은 `condition`이 있으면 해당 훅을 건너뛰고 조건 평가는 HookExecutor 구현에 맡깁니다.
- 실행 가능한 각 훅에 대해 `optional` 플래그에 따라 다음 내용을 출력합니다:
  - **선택 훅**(`optional: true`):
    ```
    ## 확장 훅

    **선택 훅**: {extension}
    명령: `/{command}`
    설명: {description}

    프롬프트: {prompt}
    실행하려면: `/{command}`
    ```
  - **필수 훅**(`optional: false`):
    ```
    ## 확장 훅

    **자동 훅**: {extension}
    실행 중: `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    위 블록을 출력한 뒤에는 **반드시** 실제로 훅을 호출하고 완료될 때까지 기다린 후 계속해야 합니다. 이 에이전트/세션에서 직접 명령을 실행할 때와 같은 방식으로 실행합니다(호출 형태는 위의 `{command}` ID 문자열과 다를 수 있습니다. 예를 들어 스킬 모드 에이전트는 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 훅이 실행되지 않습니다.
- 등록된 훅이 없거나 `.specify/extensions.yml`이 없으면 별도 출력 없이 건너뜁니다.
