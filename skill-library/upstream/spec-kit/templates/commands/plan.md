## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 사용자 입력이 비어 있지 않다면 **반드시** 고려해야 합니다.

## 실행 전 검사

**확장 훅 확인(계획 전에)**:
- 프로젝트 루트에 `.specify/extensions.yml`이 있는지 확인합니다.
- 있다면 파일을 읽고 `hooks.before_plan` 키 아래의 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않다면 조용히 건너뛰지 마십시오. 사용자에게 `.specify/extensions.yml`을 읽을 수 없었다고 알리고(파서 오류 포함), 그곳에 등록된 필수(`optional: false`) 훅을 포함해 어떤 훅도 확인되지 않았다고 알린 다음 정상적으로 계속합니다.
- `enabled`가 명시적으로 `false`인 훅을 제외합니다. `enabled` 필드가 없는 훅은 기본적으로 활성화된 것으로 처리합니다.
- 남은 각 훅의 `condition` 표현식을 해석하거나 평가하려고 **시도하지 마십시오**.
  - 훅에 `condition` 필드가 없거나 null/빈 값이면 실행 가능한 것으로 처리합니다.
  - 훅에 비어 있지 않은 `condition`이 정의되어 있으면 훅을 건너뛰고 조건 평가는 HookExecutor 구현에 맡깁니다.
- 실행 가능한 각 훅에 대해 `optional` 플래그에 따라 다음을 출력합니다.
  - **선택적 훅** (`optional: true`):
    ```
    ## 확장 훅

    **선택적 사전 훅**: {extension}
    명령: `/{command}`
    설명: {description}

    프롬프트: {prompt}
    실행 방법: `/{command}`
    ```
  - **필수 훅** (`optional: false`):
    ```
    ## 확장 훅

    **자동 사전 훅**: {extension}
    실행 중: `/{command}`
    EXECUTE_COMMAND: {command}

    개요로 진행하기 전에 훅 명령의 결과를 기다리십시오.
    ```
    위 블록을 출력한 뒤 계속하기 전에 훅을 실제로 호출하고 완료될 때까지 **반드시** 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행할 때와 같은 방식으로 실행하십시오(호출 방식은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 스킬 모드 에이전트는 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록만 출력해서는 훅이 실행되지 않습니다.
- 등록된 훅이 없거나 `.specify/extensions.yml`이 존재하지 않으면 조용히 건너뜁니다.

## 개요

1. **설정**: 저장소 루트에서 `{SCRIPT}`를 실행하고 JSON에서 FEATURE_SPEC, IMPL_PLAN, FEATURE_DIR, BRANCH를 파싱합니다. "I'm Groot"처럼 인수에 작은따옴표가 있으면 이스케이프 구문을 사용합니다. 예: 'I'\''m Groot' (가능하면 큰따옴표 사용: "I'm Groot").

2. **맥락 로드**: FEATURE_SPEC과 `/memory/constitution.md`를 읽습니다. IMPL_PLAN 템플릿(이미 복사됨)을 로드합니다.

3. **계획 워크플로 실행**: IMPL_PLAN 템플릿 구조를 따라 다음을 수행합니다.
   - 기술 맥락을 채웁니다(알 수 없는 항목은 "NEEDS CLARIFICATION"으로 표시).
   - 헌법에서 헌법 검사 섹션을 채웁니다.
   - 게이트를 평가합니다(위반을 정당화하지 못하면 ERROR).
   - 0단계: research.md를 생성합니다(모든 NEEDS CLARIFICATION 해결).
   - 1단계: data-model.md, contracts/, quickstart.md를 생성합니다.
   - 설계 후 헌법 검사를 다시 평가합니다.

## 완료 보고

명령은 1단계 설계 후 종료됩니다. 브랜치, IMPL_PLAN 경로, 생성된 산출물을 보고합니다.

## 단계

### 0단계: 개요 및 조사

1. 위의 **기술 맥락에서 알 수 없는 항목을 추출**합니다.
   - 각 NEEDS CLARIFICATION → 조사 작업
   - 각 의존성 → 모범 사례 작업
   - 각 통합 → 패턴 작업

2. **조사 에이전트를 생성하고 전달**합니다.

   ```text
   기술 맥락의 알 수 없는 각 항목에 대해:
     작업: "{feature context}를 위한 {unknown} 조사"
   각 기술 선택에 대해:
     작업: "{domain}에서 {tech}의 모범 사례 찾기"
   ```

3. 다음 형식을 사용하여 `research.md`에 **조사 결과를 통합**합니다.
   - 결정: [선택한 내용]
   - 근거: [선택한 이유]
   - 검토한 대안: [평가한 다른 항목]

**출력**: 모든 NEEDS CLARIFICATION이 해결된 research.md

### 1단계: 설계 및 계약

**전제 조건:** `research.md` 완료

1. **기능 명세에서 엔터티 추출** → `data-model.md`:
   - 엔터티 이름, 필드, 관계
   - 요구사항의 유효성 검사 규칙
   - 해당하는 경우 상태 전이

2. **인터페이스 계약 정의**(프로젝트에 외부 인터페이스가 있는 경우) → `/contracts/`:
   - 프로젝트가 사용자나 다른 시스템에 노출하는 인터페이스를 식별합니다.
   - 프로젝트 유형에 적합한 계약 형식을 문서화합니다.
   - 예: 라이브러리의 공개 API, CLI 도구의 명령 스키마, 웹 서비스의 엔드포인트, 파서의 문법, 애플리케이션의 UI 계약
   - 프로젝트가 순수 내부용(빌드 스크립트, 일회성 도구 등)이면 건너뜁니다.

3. **빠른 시작 검증 가이드 생성** → `quickstart.md`:
   - 기능이 엔드투엔드로 작동함을 입증하는 실행 가능한 검증 시나리오를 문서화합니다.
   - 전제 조건, 설정 명령, 테스트/실행 명령, 예상 결과를 포함합니다.
   - 내용을 중복하는 대신 계약과 데이터 모델 세부 정보에 대한 링크나 참조를 사용합니다.
   - 전체 구현 코드, 모델/서비스/컨트롤러 본문, 마이그레이션 또는 완전한 테스트 스위트를 포함하지 마십시오.
   - 이 산출물은 검증/실행 가이드로 유지합니다. 구현 세부 정보는 `tasks.md`와 구현 단계에 속합니다.

**출력**: data-model.md, /contracts/*, quickstart.md

## 핵심 규칙

- 파일 시스템 작업에는 절대 경로를 사용하고, 문서 내 참조에는 프로젝트 상대 경로를 사용합니다.
- 게이트 실패나 해결되지 않은 명확화가 있으면 ERROR를 발생시킵니다.
