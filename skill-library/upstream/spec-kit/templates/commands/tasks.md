## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 사용자 입력이 비어 있지 않다면 **반드시** 고려해야 합니다.

## 실행 전 검사

**확장 훅 확인(작업 생성 전에)**:
- 프로젝트 루트에 `.specify/extensions.yml`이 있는지 확인합니다.
- 있다면 파일을 읽고 `hooks.before_tasks` 키 아래의 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않다면 조용히 건너뛰지 마십시오. 사용자에게 `.specify/extensions.yml`을 읽을 수 없었다고 알리고(파서 오류 포함), 그곳에 등록된 필수(`optional: false`) 훅을 포함해 어떤 훅도 확인되지 않았다고 알린 다음 정상적으로 계속합니다.
- `enabled`가 명시적으로 `false`인 훅을 제외합니다. `enabled` 필드가 없는 훅은 기본적으로 활성화된 것으로 처리합니다.
- 남은 각 훅의 `condition` 표현식을 해석하거나 평가하려고 **시도하지 마십시오**.
  - 훅에 `condition` 필드가 없거나 null/빈 값이면 실행 가능한 것으로 처리합니다.
  - 훅에 비어 있지 않은 `condition`이 정의되어 있으면 훅을 건너뛰고 조건 평가는 HookExecutor 구현에 맡깁니다.
- 실행 가능한 각 훅에 대해 `optional` 플래그에 따라 다음을 출력합니다.
  - **선택적 훅** (`optional: true`):
    ```
    ## 확장 훅

    **선택적 사전 훅**: {extension}
    명령: `/{command}`
    설명: {description}

    프롬프트: {prompt}
    실행 방법: `/{command}`
    ```
  - **필수 훅** (`optional: false`):
    ```
    ## 확장 훅

    **자동 사전 훅**: {extension}
    실행 중: `/{command}`
    EXECUTE_COMMAND: {command}

    개요로 진행하기 전에 훅 명령의 결과를 기다리십시오.
    ```
    위 블록을 출력한 뒤 계속하기 전에 훅을 실제로 호출하고 완료될 때까지 **반드시** 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행할 때와 같은 방식으로 실행하십시오(호출 방식은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 스킬 모드 에이전트는 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록만 출력해서는 훅이 실행되지 않습니다.
- 등록된 훅이 없거나 `.specify/extensions.yml`이 존재하지 않으면 조용히 건너뜁니다.

## 개요

1. **설정**: 저장소 루트에서 `{SCRIPT}`를 실행하고 FEATURE_DIR, TASKS_TEMPLATE_CONTENT, TASKS_TEMPLATE, AVAILABLE_DOCS 목록을 파싱합니다. 제공된 경우 `FEATURE_DIR`과 `TASKS_TEMPLATE`은 절대 경로여야 합니다. `AVAILABLE_DOCS`는 `FEATURE_DIR` 아래에서 사용할 수 있는 문서 이름/상대 경로 목록입니다(예: `research.md` 또는 `contracts/`). "I'm Groot"처럼 인수에 작은따옴표가 있으면 이스케이프 구문을 사용합니다. 예: 'I'\''m Groot' (가능하면 큰따옴표 사용: "I'm Groot").

2. **설계 문서 로드**: FEATURE_DIR에서 읽습니다.
   - **필수**: plan.md(기술 스택, 라이브러리, 구조), spec.md(우선순위가 있는 사용자 스토리)
   - **선택**: data-model.md(엔터티), contracts/(인터페이스 계약), research.md(결정), quickstart.md(테스트 시나리오)
   - **존재하는 경우**: 프로젝트 원칙과 거버넌스 제약을 위해 `/memory/constitution.md`를 로드합니다.
   - 참고: 모든 프로젝트에 모든 문서가 있는 것은 아닙니다. 사용 가능한 내용을 바탕으로 작업을 생성합니다.

3. **작업 생성 워크플로 실행**:
   - plan.md를 로드하고 기술 스택, 라이브러리, 프로젝트 구조를 추출합니다.
   - spec.md를 로드하고 우선순위(P1, P2, P3 등)가 있는 사용자 스토리를 추출합니다.
   - data-model.md가 있으면 엔터티를 추출하여 사용자 스토리에 매핑합니다.
   - contracts/가 있으면 인터페이스 계약을 사용자 스토리에 매핑합니다.
   - research.md가 있으면 설정 작업을 위한 결정을 추출합니다.
   - 사용자 스토리별로 구성된 작업을 생성합니다(아래 작업 생성 규칙 참조).
   - 사용자 스토리 완료 순서를 보여 주는 의존성 그래프를 생성합니다.
   - 사용자 스토리별 병렬 실행 예시를 만듭니다.
   - 작업 완전성을 검증합니다(각 사용자 스토리에 필요한 모든 작업이 있고 독립적으로 테스트 가능함).

4. **tasks.md 생성**: 위 JSON 출력의 TASKS_TEMPLATE_CONTENT를 구조로 사용합니다. TASKS_TEMPLATE_CONTENT를 생략하는 이전 설정 스크립트와의 호환성을 위해 대신 TASKS_TEMPLATE을 읽습니다. 다음 내용으로 채웁니다.
   - plan.md의 정확한 기능 이름
   - 1단계: 설정 작업(프로젝트 초기화)
   - 2단계: 기반 작업(모든 사용자 스토리를 차단하는 전제 조건)
   - 3단계 이상: 사용자 스토리별 한 단계(spec.md의 우선순위 순서)
   - 각 단계에 포함할 내용: 스토리 목표, 독립 테스트 기준, 테스트(요청된 경우), 구현 작업
   - 최종 단계: 다듬기 및 횡단 관심사
   - 모든 작업은 엄격한 체크리스트 형식을 따라야 합니다(아래 작업 생성 규칙 참조).
   - 각 작업의 명확한 파일 경로
   - 스토리 완료 순서를 보여 주는 의존성 섹션
   - 스토리별 병렬 실행 예시
   - 구현 전략 섹션(MVP 우선, 점진적 제공)

## 작업 생성 규칙

**중요**: 독립적인 구현과 테스트가 가능하도록 작업은 사용자 스토리별로 **반드시** 구성해야 합니다.

**테스트는 선택 사항입니다**: 기능 명세에서 명시적으로 요청하거나 사용자가 TDD 접근 방식을 요청한 경우에만 테스트 작업을 생성합니다.

### 체크리스트 형식(필수)

모든 작업은 다음 형식을 엄격히 따라야 합니다.

```text
- [ ] [TaskID] [P?] [Story?] 파일 경로가 포함된 설명
```

**형식 구성 요소**:

1. **체크박스**: 항상 `- [ ]`로 시작합니다(마크다운 체크박스).
2. **작업 ID**: 실행 순서에 따른 일련번호(T001, T002, T003...)
3. **[P] 표시**: 작업을 병렬화할 수 있는 경우에만 포함합니다(서로 다른 파일이며 완료되지 않은 작업에 의존하지 않음).
4. **[Story] 레이블**: 사용자 스토리 단계 작업에만 필수입니다.
   - 형식: [US1], [US2], [US3] 등(spec.md의 사용자 스토리에 매핑)
   - 설정 단계: 스토리 레이블 없음
   - 기반 단계: 스토리 레이블 없음
   - 사용자 스토리 단계: 스토리 레이블 필수
   - 다듬기 단계: 스토리 레이블 없음
5. **설명**: 정확한 파일 경로가 포함된 명확한 행동

**예시**:

- ✅ 올바름: `- [ ] T001 구현 계획에 따라 프로젝트 구조 생성`
- ✅ 올바름: `- [ ] T005 [P] src/middleware/auth.py에 인증 미들웨어 구현`
- ✅ 올바름: `- [ ] T012 [P] [US1] src/models/user.py에 User 모델 생성`
- ✅ 올바름: `- [ ] T014 [US1] src/services/user_service.py에 UserService 구현`
- ❌ 잘못됨: `- [ ] User 모델 생성` (ID와 스토리 레이블 누락)
- ❌ 잘못됨: `T001 [US1] 모델 생성` (체크박스 누락)
- ❌ 잘못됨: `- [ ] [US1] User 모델 생성` (작업 ID 누락)
- ❌ 잘못됨: `- [ ] T001 [US1] 모델 생성` (파일 경로 누락)

### 작업 구성

1. **사용자 스토리(spec.md)에서** - 주요 구성 기준:
   - 각 사용자 스토리(P1, P2, P3...)에 고유한 단계를 부여합니다.
   - 모든 관련 컴포넌트를 해당 스토리에 매핑합니다.
     - 해당 스토리에 필요한 모델
     - 해당 스토리에 필요한 서비스
     - 해당 스토리에 필요한 인터페이스/UI
     - 테스트가 요청된 경우: 해당 스토리에 특화된 테스트
   - 스토리 의존성을 표시합니다(대부분의 스토리는 독립적이어야 함).

2. **계약에서**:
   - 각 인터페이스 계약을 그것이 제공하는 사용자 스토리에 매핑합니다.
   - 테스트가 요청된 경우: 각 인터페이스 계약 → 해당 스토리 단계에서 구현보다 앞선 계약 테스트 작업 [P]

3. **데이터 모델에서**:
   - 각 엔터티를 그것이 필요한 사용자 스토리에 매핑합니다.
   - 엔터티가 여러 스토리에 쓰이면 가장 이른 스토리 또는 설정 단계에 둡니다.
   - 관계 → 적절한 스토리 단계의 서비스 계층 작업
   - data-model.md에서 제약이 있는 각 필드(최대 길이, nullable/required, enum 값, 유효성 검사 규칙)는 구현 시점의 재량으로 남지 않도록 작업 설명에 제약을 그대로 인용합니다.

4. **설정/인프라에서**:
   - 공유 인프라 → 설정 단계(1단계)
   - 기반/차단 작업 → 기반 단계(2단계)
   - 스토리별 설정 → 해당 스토리 단계 내부

### 단계 구조

- **1단계**: 설정(프로젝트 초기화)
- **2단계**: 기반(차단 전제 조건 - 사용자 스토리보다 먼저 완료해야 함)
- **3단계 이상**: 우선순위 순서의 사용자 스토리(P1, P2, P3...)
  - 각 스토리 내부: 테스트(요청된 경우) → 모델 → 서비스 → 엔드포인트 → 통합
  - 각 단계는 완전하고 독립적으로 테스트 가능한 증분이어야 합니다.
- **최종 단계**: 다듬기 및 횡단 관심사
