## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 사용자 입력이 비어 있지 않다면 **반드시** 고려해야 합니다.

## 실행 전 검사

**확장 훅 확인(명세 작성 전에)**:
- 프로젝트 루트에 `.specify/extensions.yml`이 있는지 확인합니다.
- 있다면 파일을 읽고 `hooks.before_specify` 키 아래의 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않다면 조용히 건너뛰지 마십시오. 사용자에게 `.specify/extensions.yml`을 읽을 수 없었다고 알리고(파서 오류 포함), 그곳에 등록된 필수(`optional: false`) 훅을 포함해 어떤 훅도 확인되지 않았다고 알린 다음 정상적으로 계속합니다.
- `enabled`가 명시적으로 `false`인 훅을 제외합니다. `enabled` 필드가 없는 훅은 기본적으로 활성화된 것으로 처리합니다.
- 남은 각 훅의 `condition` 표현식을 해석하거나 평가하려고 **시도하지 마십시오**.
  - 훅에 `condition` 필드가 없거나 null/빈 값이면 실행 가능한 것으로 처리합니다.
  - 훅에 비어 있지 않은 `condition`이 정의되어 있으면 훅을 건너뛰고 조건 평가는 HookExecutor 구현에 맡깁니다.
- 실행 가능한 각 훅에 대해 `optional` 플래그에 따라 다음을 출력합니다.
  - **선택적 훅** (`optional: true`):
    ```
    ## 확장 훅

    **선택적 사전 훅**: {extension}
    명령: `/{command}`
    설명: {description}

    프롬프트: {prompt}
    실행 방법: `/{command}`
    ```
  - **필수 훅** (`optional: false`):
    ```
    ## 확장 훅

    **자동 사전 훅**: {extension}
    실행 중: `/{command}`
    EXECUTE_COMMAND: {command}

    개요로 진행하기 전에 훅 명령의 결과를 기다리십시오.
    ```
    위 블록을 출력한 뒤 계속하기 전에 훅을 실제로 호출하고 완료될 때까지 **반드시** 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행할 때와 같은 방식으로 실행하십시오(호출 방식은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 스킬 모드 에이전트는 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록만 출력해서는 훅이 실행되지 않습니다.
- 등록된 훅이 없거나 `.specify/extensions.yml`이 존재하지 않으면 조용히 건너뜁니다.

## 개요

트리거 메시지에서 사용자가 `__SPECKIT_COMMAND_SPECIFY__` 뒤에 입력한 텍스트가 기능 설명**입니다**. 아래에 `{ARGS}`가 리터럴로 표시되더라도 이 대화에서 항상 사용할 수 있다고 가정합니다. 사용자가 빈 명령을 제공하지 않은 한 반복해 달라고 요청하지 마십시오.

해당 기능 설명을 바탕으로 다음을 수행합니다.

1. 기능에 대한 **간결한 짧은 이름 생성**(2~4단어):
   - 기능 설명을 분석하고 가장 의미 있는 키워드를 추출합니다.
   - 기능의 본질을 담은 2~4단어의 짧은 이름을 만듭니다.
   - 가능하면 동작-명사 형식을 사용합니다(예: "add-user-auth", "fix-payment-bug").
   - 기술 용어와 약어(OAuth2, API, JWT 등)를 보존합니다.
   - 한눈에 기능을 이해할 수 있을 만큼 설명적이면서 간결하게 유지합니다.
   - 예시:
     - "사용자 인증을 추가하고 싶습니다" → "user-auth"
     - "API에 OAuth2 통합 구현" → "oauth2-api-integration"
     - "분석용 대시보드 생성" → "analytics-dashboard"
     - "결제 처리 시간 초과 버그 수정" → "fix-payment-timeout"

2. **브랜치 생성**(선택 사항, 훅을 통해):

   위 실행 전 검사에서 `before_specify` 훅이 성공적으로 실행되었다면 git 브랜치를 생성/전환하고 `BRANCH_NAME`과 `FEATURE_NUM`이 포함된 JSON을 출력했을 것입니다. 이 값을 참고용으로 기록하되, 브랜치 이름이 명세 디렉터리 이름을 결정하지는 **않습니다**.

   사용자가 `GIT_BRANCH_NAME`을 명시적으로 제공했다면 훅에 그대로 전달하여 브랜치 스크립트가 접두사/접미사 생성을 모두 우회하고 정확한 값을 브랜치 이름으로 사용하게 합니다.

3. **명세 기능 디렉터리 생성**:

   사용자가 `SPECIFY_FEATURE_DIRECTORY`를 명시적으로 제공하지 않는 한 명세는 기본 `specs/` 디렉터리 아래에 있습니다.

   **`SPECIFY_FEATURE_DIRECTORY` 해석 순서**:
   1. 사용자가 `SPECIFY_FEATURE_DIRECTORY`를 명시적으로 제공했다면(예: 환경 변수, 인수 또는 구성) 그대로 사용합니다.
   2. 그렇지 않으면 `specs/` 아래에 자동 생성합니다.
      - `.specify/init-options.json`에서 `feature_numbering`(선호) 또는 `branch_numbering`(사용 중단 예정, 마이그레이션 전용 — 향후 릴리스에서 제거 예정)을 확인합니다.
      - `"timestamp"`이면 접두사는 `YYYYMMDD-HHMMSS`(현재 타임스탬프)입니다.
      - `"sequential"`이거나 없으면 접두사는 `NNN`(`specs/`의 기존 디렉터리를 스캔한 뒤 다음 사용 가능한 3자리 숫자)입니다.
      - 디렉터리 이름을 `<prefix>-<short-name>` 형식으로 구성합니다(예: `003-user-auth` 또는 `20260319-143022-user-auth`).
      - `SPECIFY_FEATURE_DIRECTORY`를 `specs/<directory-name>`으로 설정합니다.
      - `branch_numbering`이 사용되었고 `feature_numbering`이 없다면 한 줄 경고를 출력합니다. "⚠️ init-options.json의 `branch_numbering`은 사용 중단 예정입니다. 이름을 `feature_numbering`으로 바꾸십시오."

   **디렉터리와 명세 파일 생성**:
   - 저장소 루트에서 `{SCRIPT}`를 실행하고 `TEMPLATE_CONTENT`를 활성 `spec-template`로 파싱합니다. 공유 해석기는 `append`, `prepend`, `wrap` 전략을 포함하여 핵심 템플릿 위에 프로젝트 재정의, 프리셋 계층, 확장 계층을 합성합니다. 실패하면 중지하고 해석 오류를 보고합니다. 기여 템플릿 계층 하나만으로 계속하지 마십시오.
   - `mkdir -p SPECIFY_FEATURE_DIRECTORY`
   - 시작점으로 `TEMPLATE_CONTENT`를 `SPECIFY_FEATURE_DIRECTORY/spec.md`에 씁니다. 대신 디스크에서 템플릿 파일을 복사하지 마십시오. 프리셋이 `spec-template`을 합성하면 어떤 단일 파일에도 전체 템플릿이 들어 있지 않습니다.
   - `SPEC_FILE`을 `SPECIFY_FEATURE_DIRECTORY/spec.md`로 설정합니다.
   - 해석된 경로를 `.specify/feature.json`에 영속화합니다.
     ```json
     {
       "feature_directory": "<resolved feature dir>"
     }
     ```
     리터럴 문자열 `SPECIFY_FEATURE_DIRECTORY`가 아니라 실제로 해석된 디렉터리 경로 값(예: `specs/003-user-auth`)을 씁니다.
     그러면 후속 명령(`__SPECKIT_COMMAND_PLAN__`, `__SPECKIT_COMMAND_TASKS__` 등)이 git 브랜치 이름 규칙에 의존하지 않고 기능 디렉터리를 찾을 수 있습니다.

   **중요**:
   - `__SPECKIT_COMMAND_SPECIFY__` 호출 한 번에 기능 하나만 생성해야 합니다.
   - 명세 디렉터리 이름과 git 브랜치 이름은 독립적입니다. 같을 수 있지만 이는 사용자의 선택입니다.
   - 명세 디렉터리와 파일은 항상 이 명령이 생성하며 훅이 생성하지 않습니다.

4. `TEMPLATE_CONTENT`를 사용하여 필수 섹션을 파악합니다.

5. **존재하는 경우**: 프로젝트 원칙과 거버넌스 제약을 위해 `/memory/constitution.md`를 로드합니다.

6. 다음 실행 흐름을 따릅니다.
    1. 인수에서 사용자 설명을 파싱합니다.
       비어 있으면: ERROR "No feature description provided"
    2. 설명에서 핵심 개념을 추출합니다.
       식별 항목: 행위자, 동작, 데이터, 제약
    3. 불명확한 측면에 대해:
       - 맥락과 업계 표준을 바탕으로 정보에 근거한 추측을 합니다.
       - 다음 조건을 만족할 때만 [NEEDS CLARIFICATION: specific question]으로 표시합니다.
         - 선택이 기능 범위나 사용자 경험에 큰 영향을 미침
         - 서로 다른 함의를 지닌 합리적인 해석이 여러 개 존재함
         - 합리적인 기본값이 없음
       - **제한: [NEEDS CLARIFICATION] 표시는 총 최대 3개**
       - 영향에 따라 명확화 우선순위를 정합니다: 범위 > 보안/개인정보 보호 > 사용자 경험 > 기술 세부 정보
    4. 사용자 시나리오 및 테스트 섹션을 채웁니다.
       명확한 사용자 흐름이 없으면: ERROR "Cannot determine user scenarios"
    5. 기능 요구사항을 생성합니다.
       각 요구사항은 테스트 가능해야 합니다.
       명시되지 않은 세부 정보에는 합리적인 기본값을 사용합니다(가정 섹션에 가정을 문서화).
    6. 성공 기준을 정의합니다.
       측정 가능하고 기술에 구애받지 않는 결과를 만듭니다.
       정량 지표(시간, 성능, 규모)와 정성 지표(사용자 만족도, 작업 완료)를 모두 포함합니다.
       각 기준은 구현 세부 정보 없이 검증 가능해야 합니다.
    7. 핵심 엔터티를 식별합니다(데이터가 관련된 경우).
    8. 반환: SUCCESS (계획 준비가 된 명세)

7. 템플릿 구조를 사용해 명세를 SPEC_FILE에 씁니다. 섹션 순서와 제목을 보존하면서 자리표시자를 기능 설명(인수)에서 도출한 구체적인 세부 정보로 바꿉니다.

8. **명세 품질 검증**: 초기 명세를 작성한 후 품질 기준에 따라 검증합니다.

   a. **명세 품질 체크리스트 생성**: 다음 검증 항목이 포함된 체크리스트 템플릿 구조를 사용하여 `SPECIFY_FEATURE_DIRECTORY/checklists/requirements.md`에 체크리스트 파일을 생성합니다.

      ```markdown
      # 명세 품질 체크리스트: [FEATURE NAME]

      **목적**: 계획을 진행하기 전에 명세의 완전성과 품질을 검증
      **생성일**: [DATE]
      **기능**: [spec.md 링크]

      ## 콘텐츠 품질

      - [ ] 구현 세부 정보(언어, 프레임워크, API)가 없음
      - [ ] 사용자 가치와 비즈니스 요구에 집중함
      - [ ] 비기술 이해관계자를 대상으로 작성됨
      - [ ] 모든 필수 섹션이 완료됨

      ## 요구사항 완전성

      - [ ] [NEEDS CLARIFICATION] 표시가 남아 있지 않음
      - [ ] 요구사항이 테스트 가능하고 모호하지 않음
      - [ ] 성공 기준이 측정 가능함
      - [ ] 성공 기준이 기술에 구애받지 않음(구현 세부 정보 없음)
      - [ ] 모든 수용 시나리오가 정의됨
      - [ ] 엣지 케이스가 식별됨
      - [ ] 범위가 명확히 한정됨
      - [ ] 의존성과 가정이 식별됨

      ## 기능 준비 상태

      - [ ] 모든 기능 요구사항에 명확한 수용 기준이 있음
      - [ ] 사용자 시나리오가 주요 흐름을 포함함
      - [ ] 기능이 성공 기준에 정의된 측정 가능한 결과를 충족함
      - [ ] 구현 세부 정보가 명세에 노출되지 않음

      ## 참고

      - 미완료로 표시된 항목은 `__SPECKIT_COMMAND_CLARIFY__` 또는 `__SPECKIT_COMMAND_PLAN__` 전에 명세 업데이트가 필요함
      ```

   b. **검증 검사 실행**: 각 체크리스트 항목을 기준으로 명세를 검토합니다.
      - 각 항목의 통과 또는 실패를 판단합니다.
      - 발견한 구체적인 문제를 문서화합니다(관련 명세 섹션 인용).

   c. **검증 결과 처리**:

      - **모든 항목이 통과한 경우**: 체크리스트를 완료로 표시하고 필수 실행 후 훅 섹션으로 진행합니다.

      - **항목이 실패한 경우([NEEDS CLARIFICATION] 제외)**:
        1. 실패한 항목과 구체적인 문제를 나열합니다.
        2. 각 문제를 해결하도록 명세를 업데이트합니다.
        3. 모든 항목이 통과할 때까지 검증을 다시 실행합니다(최대 3회 반복).
        4. 3회 후에도 실패하면 체크리스트 참고에 남은 문제를 문서화하고 사용자에게 경고합니다.

      - **[NEEDS CLARIFICATION] 표시가 남아 있는 경우**:
        1. 명세에서 모든 [NEEDS CLARIFICATION: ...] 표시를 추출합니다.
        2. **제한 검사**: 표시가 3개보다 많으면 가장 중요한 3개만 유지하고(범위/보안/UX 영향 기준) 나머지는 정보에 근거해 추측합니다.
        3. 필요한 각 명확화(최대 3개)를 다음 형식으로 사용자에게 제시합니다.

           ```markdown
           ## 질문 [N]: [주제]

           **맥락**: [관련 명세 섹션 인용]

           **알아야 할 내용**: [NEEDS CLARIFICATION 표시의 구체적인 질문]

           **제안 답변**:

           | 선택지 | 답변 | 영향 |
           |--------|------|------|
           | A      | [첫 번째 제안 답변] | [기능에 미치는 의미] |
           | B      | [두 번째 제안 답변] | [기능에 미치는 의미] |
           | C      | [세 번째 제안 답변] | [기능에 미치는 의미] |
           | 사용자 지정 | 직접 답변 제공 | [사용자 지정 입력 제공 방법 설명] |

           **선택**: _[사용자 응답 대기]_
           ```

        4. **중요 - 표 형식**: 마크다운 표 형식이 올바른지 확인합니다.
           - 파이프가 정렬되도록 일관된 간격을 사용합니다.
           - 각 셀의 내용 주변에 공백을 둡니다: `|Content|`가 아니라 `| Content |`
           - 헤더 구분선에는 대시가 3개 이상 있어야 합니다: `|--------|`
           - 마크다운 미리보기에서 표가 올바르게 렌더링되는지 테스트합니다.
        5. 질문에 순차적으로 번호를 매깁니다(Q1, Q2, Q3 - 총 최대 3개).
        6. 응답을 기다리기 전에 모든 질문을 함께 제시합니다.
        7. 사용자가 모든 질문의 선택으로 응답할 때까지 기다립니다(예: "Q1: A, Q2: Custom - [details], Q3: B").
        8. 각 [NEEDS CLARIFICATION] 표시를 사용자가 선택하거나 제공한 답변으로 바꾸어 명세를 업데이트합니다.
        9. 모든 명확화가 해결된 후 검증을 다시 실행합니다.

   d. **체크리스트 업데이트**: 각 검증 반복 후 현재 통과/실패 상태로 체크리스트 파일을 업데이트합니다.

## 필수 실행 후 훅

**사용자에게 완료를 보고하기 전에 이 섹션을 반드시 완료해야 합니다.**

프로젝트 루트에 `.specify/extensions.yml`이 있는지 확인합니다.
- 파일이 없거나 `hooks.after_specify` 아래에 등록된 훅이 없으면 완료 보고로 건너뜁니다.
- 있다면 파일을 읽고 `hooks.after_specify` 키 아래의 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않다면 조용히 건너뛰지 마십시오. 사용자에게 `.specify/extensions.yml`을 읽을 수 없었다고 알리고(파서 오류 포함), 그곳에 등록된 필수(`optional: false`) 훅을 포함해 어떤 훅도 확인되지 않았다고 알린 다음 완료 보고로 계속합니다.
- `enabled`가 명시적으로 `false`인 훅을 제외합니다. `enabled` 필드가 없는 훅은 기본적으로 활성화된 것으로 처리합니다.
- 남은 각 훅의 `condition` 표현식을 해석하거나 평가하려고 **시도하지 마십시오**.
  - 훅에 `condition` 필드가 없거나 null/빈 값이면 실행 가능한 것으로 처리합니다.
  - 훅에 비어 있지 않은 `condition`이 정의되어 있으면 훅을 건너뛰고 조건 평가는 HookExecutor 구현에 맡깁니다.
- 실행 가능한 각 훅에 대해 `optional` 플래그에 따라 다음을 출력합니다.
  - **필수 훅** (`optional: false`) — 각 필수 훅에 대해 **반드시 `EXECUTE_COMMAND:`를 출력해야 합니다**:
    ```
    ## 확장 훅

    **자동 훅**: {extension}
    실행 중: `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    위 블록을 출력한 뒤 계속하기 전에 훅을 실제로 호출하고 완료될 때까지 **반드시** 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행할 때와 같은 방식으로 실행하십시오(호출 방식은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 스킬 모드 에이전트는 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록만 출력해서는 훅이 실행되지 않습니다.
  - **선택적 훅** (`optional: true`):
    ```
    ## 확장 훅

    **선택적 훅**: {extension}
    명령: `/{command}`
    설명: {description}

    프롬프트: {prompt}
    실행 방법: `/{command}`
    ```

## 완료 보고

다음과 함께 사용자에게 완료를 보고합니다.
- `SPECIFY_FEATURE_DIRECTORY` — 기능 디렉터리 경로
- `SPEC_FILE` — 명세 파일 경로
- 체크리스트 결과 요약
- 다음 단계(`__SPECKIT_COMMAND_CLARIFY__` 또는 `__SPECKIT_COMMAND_PLAN__`) 준비 상태

**참고:** 브랜치 생성은 `before_specify` 훅(git 확장)이 처리합니다. 명세 디렉터리와 파일 생성은 항상 이 핵심 명령이 처리합니다.

## 빠른 지침

- 사용자가 필요로 하는 **무엇**과 그 **이유**에 집중합니다.
- 구현 **방법**은 피합니다(기술 스택, API, 코드 구조 없음).
- 개발자가 아닌 비즈니스 이해관계자를 대상으로 작성합니다.
- 명세에 포함되는 체크리스트를 만들지 **마십시오**. 이는 별도 명령입니다.

### 섹션 요구사항

- **필수 섹션**: 모든 기능에 대해 완료해야 합니다.
- **선택 섹션**: 기능과 관련이 있을 때만 포함합니다.
- 섹션이 적용되지 않으면 완전히 제거합니다("N/A"로 남기지 않음).

### AI 생성 지침

사용자 프롬프트로 이 명세를 생성할 때:

1. **정보에 근거한 추측**: 맥락, 업계 표준, 일반적인 패턴을 사용해 빈 부분을 채웁니다.
2. **가정 문서화**: 가정 섹션에 합리적인 기본값을 기록합니다.
3. **명확화 제한**: [NEEDS CLARIFICATION] 표시는 최대 3개이며 다음에 해당하는 중요한 결정에만 사용합니다.
   - 기능 범위나 사용자 경험에 큰 영향을 미침
   - 서로 다른 함의를 지닌 합리적인 해석이 여러 개 있음
   - 합리적인 기본값이 전혀 없음
4. **명확화 우선순위**: 범위 > 보안/개인정보 보호 > 사용자 경험 > 기술 세부 정보
5. **테스터처럼 사고**: 모호한 모든 요구사항은 "테스트 가능하고 모호하지 않음" 체크리스트 항목을 통과하지 못해야 합니다.
6. **명확화가 흔히 필요한 영역**(합리적인 기본값이 없는 경우에만):
   - 기능 범위와 경계(특정 사용 사례 포함/제외)
   - 사용자 유형과 권한(서로 충돌하는 해석이 여러 개 가능한 경우)
   - 보안/규정 준수 요구사항(법적/재정적으로 중요한 경우)

**합리적인 기본값의 예시**(이에 대해서는 질문하지 않음):

- 데이터 보존: 해당 도메인의 업계 표준 관행
- 성능 목표: 달리 명시되지 않은 경우 표준 웹/모바일 앱 기대치
- 오류 처리: 적절한 대체 동작이 있는 사용자 친화적 메시지
- 인증 방식: 웹 앱의 표준 세션 기반 또는 OAuth2
- 통합 패턴: 프로젝트에 적합한 패턴(웹 서비스는 REST/GraphQL, 라이브러리는 함수 호출, 도구는 CLI 인수 등)

### 성공 기준 지침

성공 기준은 다음을 충족해야 합니다.

1. **측정 가능**: 구체적인 지표(시간, 백분율, 개수, 비율)를 포함합니다.
2. **기술에 구애받지 않음**: 프레임워크, 언어, 데이터베이스 또는 도구를 언급하지 않습니다.
3. **사용자 중심**: 시스템 내부가 아닌 사용자/비즈니스 관점의 결과를 설명합니다.
4. **검증 가능**: 구현 세부 정보를 몰라도 테스트/검증할 수 있습니다.

**좋은 예시**:

- "사용자가 3분 안에 결제를 완료할 수 있음"
- "시스템이 동시 사용자 10,000명을 지원함"
- "검색의 95%가 1초 이내에 결과를 반환함"
- "작업 완료율이 40% 향상됨"

**나쁜 예시**(구현 중심):

- "API 응답 시간이 200ms 미만" (너무 기술적임, "사용자가 결과를 즉시 확인함" 사용)
- "데이터베이스가 1000 TPS를 처리할 수 있음" (구현 세부 정보, 사용자 대면 지표 사용)
- "React 컴포넌트가 효율적으로 렌더링됨" (프레임워크에 종속됨)
- "Redis 캐시 적중률이 80%를 넘음" (특정 기술에 종속됨)
