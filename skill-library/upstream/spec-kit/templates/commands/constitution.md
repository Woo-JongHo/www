## 사용자 입력

```text
$ARGUMENTS
```

사용자 입력이 비어 있지 않으면 진행 전에 **반드시** 고려해야 합니다.

## 범위 제한

이 명령 자체의 작업은 프로젝트 헌법을 갱신하는 데 한정됩니다. 종속 템플릿과 명령은 실행 시 헌법을 읽으며 여기서는 수정하지 않습니다.

- 사용자 입력의 각 부분을 헌법 내용 또는 별개의 비거버넌스 의도로 분류하세요.
- 입력에 기능 구현, 코드 생성, 리팩터링, 빌드 또는 배포 요청이 포함되면 **절대로 실행하지 마세요**. 대신 보류된 의도로 추출하세요.
- 헌법 워크플로와 무관한 애플리케이션 소스 파일, 기능 경로, 컴포넌트, 테스트, 배포 파일 또는 기타 산출물을 만들거나 수정하거나 삭제해서는 **안 됩니다**.
- 지시가 헌법 내용인지 불분명하면 변경 전에 명확히 질문하세요.
- 헌법 갱신 후 각 보류된 의도에 대한 `Next Actions` 절을 포함하세요. 원래 의도를 나열하고 `__SPECKIT_COMMAND_SPECIFY__` 같은 적절한 후속 Spec Kit 명령을 제안하되 호출하지 마세요.
- 비거버넌스 의도가 없으면 `Next Actions` 절을 생략하세요.

## 실행 전 검사

**확장 훅 확인(헌법 갱신 전)**:
- 프로젝트 루트에 `.specify/extensions.yml`이 있는지 확인하세요.
- 있으면 읽고 `hooks.before_constitution` 키 아래의 항목을 찾으세요.
- YAML을 파싱할 수 없거나 유효하지 않으면 조용히 건너뛰지 마세요. `.specify/extensions.yml`을 읽지 못했다는 사실과 파서 오류를 사용자에게 알리고, 등록된 필수 훅(`optional: false`)을 포함해 어떤 훅도 확인하지 못했다고 설명한 뒤 정상적으로 계속하세요.
- `enabled`가 명시적으로 `false`인 훅은 제외하세요. `enabled` 필드가 없으면 기본적으로 활성화된 것으로 취급하세요.
- 남은 훅의 `condition` 표현식을 해석하거나 평가하려고 하지 **마세요**:
  - `condition` 필드가 없거나 null/빈 값이면 실행 가능한 훅으로 취급하세요.
  - 비어 있지 않은 `condition`이 있으면 훅을 건너뛰고 조건 평가는 HookExecutor 구현에 맡기세요.
- 실행 가능한 각 훅에 대해 `optional` 플래그에 따라 다음을 출력하세요:
  - **선택 훅**(`optional: true`):
    ```
    ## 확장 훅

    **선택적 사전 훅**: {extension}
    명령: `/{command}`
    설명: {description}

    프롬프트: {prompt}
    실행 방법: `/{command}`
    ```
  - **필수 훅**(`optional: false`):
    ```
    ## 확장 훅

    **자동 사전 훅**: {extension}
    실행 중: `/{command}`
    EXECUTE_COMMAND: {command}

    개요로 진행하기 전에 훅 명령의 결과를 기다리세요.
    ```
    위 블록을 출력한 뒤 계속하기 전에 훅을 실제로 호출하고 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행할 때와 같은 방식으로 실행하세요. 실제 호출은 위의 문자 그대로인 `{command}` ID와 다를 수 있습니다. 예를 들어 skills 모드 에이전트는 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다. 블록 출력만으로 훅이 실행되지는 않습니다.
- 등록된 훅이 없거나 `.specify/extensions.yml`이 없으면 조용히 건너뛰세요.

## 개요

`.specify/memory/constitution.md`의 프로젝트 헌법을 갱신합니다. 활성 헌법 골격은 명령 실행 시 Spec Kit 프리셋/템플릿 해석 스택을 통해 `constitution-template`에서 결정됩니다.

다음 실행 흐름을 따르세요:

1. 저장소 루트에서 `{SCRIPT}`를 실행하고 `TEMPLATE_CONTENT`를 활성 템플릿으로 파싱하세요.
   - 공유 해석기는 코어 템플릿으로 대체하기 전에 프로젝트 재정의, 프리셋 구성 계층, 확장 계층을 적용합니다. 계속하기 전에 반드시 성공해야 합니다.
   - 실패하면 중단하고 해석 오류를 보고하세요. 기여하는 템플릿 계층 하나만으로 계속하지 마세요.
   - `.specify/memory/constitution.md`가 있으면 현재 프로젝트 고유 값과 개정 사항의 출처로 읽으세요. 새로 해석된 골격을 적용할 때 여전히 유효한 정보는 보존하세요.
   - 없으면 해석된 템플릿을 초기 문서로 사용하세요.
   - 버전 관리되는 템플릿 계층에는 다시 쓰지 마세요.
   - `[ALL_CAPS_IDENTIFIER]` 형식의 모든 자리표시 토큰을 식별하세요.
   **중요**: 사용자는 템플릿보다 적거나 많은 원칙을 요구할 수 있습니다. 개수가 지정되면 이를 존중하고 일반적인 템플릿을 따르면서 문서를 알맞게 갱신하세요.

2. 자리표시자 값을 수집하거나 도출하세요:
   - 사용자 입력(대화)에 값이 있으면 사용하세요.
   - 그렇지 않으면 기존 저장소 맥락(README, 문서, 내장된 과거 헌법 버전)에서 추론하세요.
   - 거버넌스 날짜에서 `RATIFICATION_DATE`는 최초 채택일입니다(모르면 질문하거나 TODO로 표시). `LAST_AMENDED_DATE`는 변경이 있으면 오늘, 없으면 이전 값을 유지하세요.
   - `CONSTITUTION_VERSION`은 의미적 버전 규칙에 따라 올려야 합니다:
     - MAJOR: 하위 호환되지 않는 거버넌스/원칙 삭제 또는 재정의.
     - MINOR: 새 원칙/절 추가 또는 지침의 실질적 확장.
     - PATCH: 명확화, 문구·오탈자 수정, 의미를 바꾸지 않는 개선.
   - 버전 증가 유형이 모호하면 확정 전에 근거를 제안하세요.

3. 해석된 템플릿을 필수 구조로 사용하여 갱신할 헌법 내용을 작성하세요:
   - 모든 자리표시자를 구체적인 텍스트로 바꾸세요. 프로젝트가 아직 정의하지 않기로 선택해 의도적으로 남긴 템플릿 슬롯 외에는 대괄호 토큰이 없어야 하며, 남긴 것은 명시적으로 정당화하세요.
   - 제목 계층을 보존하세요. 대체된 주석은 여전히 설명을 보태는 경우를 제외하고 제거할 수 있습니다.
   - 각 원칙 절에 간결한 이름 행, 양보할 수 없는 규칙을 담은 문단(또는 목록), 자명하지 않으면 명시적 근거가 있는지 확인하세요.
   - 거버넌스 절에 개정 절차, 버전 정책, 준수 검토 기대 사항이 나열되도록 하세요.

4. 갱신 후 헌법 파일 상단에 HTML 주석으로 동기화 영향 보고서를 작성하세요.
   이 보고서는 사람이 개정을 검토하기 위한 임시 메모이며 거버넌스 내용이 아닙니다. 개정된 헌법 파일을 커밋하기 전에 제거하는 것을 전제로 합니다.
   - 버전 변경: 이전 → 이후
   - 수정된 원칙 목록(이름 변경 시 이전 제목 → 새 제목)
   - 추가된 절
   - 제거된 절
   - 의도적으로 보류한 자리표시자가 있으면 후속 TODO

5. 최종 출력 전에 검증하세요:
   - 설명되지 않은 대괄호 토큰이 남지 않음.
   - 버전 행이 보고서와 일치함.
   - 날짜는 ISO 형식 YYYY-MM-DD.
   - 원칙은 선언적이고 테스트 가능하며 모호한 표현이 없음("should"는 적절한 경우 MUST/SHOULD와 근거로 대체).

6. 완성된 헌법을 `.specify/memory/constitution.md`에 다시 쓰세요(덮어쓰기).

7. 다음을 포함하는 최종 요약을 사용자에게 출력하세요:
   - 새 버전과 버전 증가 근거.
   - 수동 후속 조치가 필요한 TODO 자리표시자 또는 보류 항목.
   - 제안 커밋 메시지(예: `docs: amend constitution to vX.Y.Z (principle additions + governance update)`).
   - 보류된 비거버넌스 의도에 대한 `Next Actions` 절.

서식 및 스타일 요구 사항:

- 템플릿의 Markdown 제목을 그대로 사용하세요(단계를 내리거나 올리지 마세요).
- 긴 근거 행은 읽기 좋게 줄바꿈하세요(가능하면 100자 미만). 부자연스러운 줄바꿈으로 강제하지는 마세요.
- 절 사이에는 빈 줄 하나를 유지하세요.
- 행 끝 공백을 피하세요.

사용자가 부분 갱신(예: 원칙 하나의 개정)만 제공해도 검증과 버전 결정 단계를 수행하세요.

핵심 정보가 없으면(예: 비준일을 정말 알 수 없음) `TODO(<FIELD_NAME>): explanation`을 삽입하고 동기화 영향 보고서의 보류 항목에 포함하세요.

`.specify/memory/constitution.md`만 쓰고 템플릿 소스 파일은 만들거나 수정하지 마세요.
