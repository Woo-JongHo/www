# 작업: [FEATURE NAME]

**입력**: `/specs/[###-feature-name]/`의 설계 문서

**사전 요구사항**: plan.md(필수), spec.md(사용자 스토리에 필수), research.md, data-model.md, contracts/

**테스트**: 아래 예에는 테스트 작업이 포함되어 있다. 테스트는 선택 사항이며, 기능 명세에서 명시적으로 요청한 경우에만 포함한다.

**구성**: 각 스토리를 독립적으로 구현하고 테스트할 수 있도록 사용자 스토리별로 작업을 묶는다.

## 형식: `[ID] [P?] [Story] 설명`

- **[P]**: 병렬로 실행 가능(서로 다른 파일, 의존성 없음)
- **[Story]**: 이 작업이 속한 사용자 스토리(예: US1, US2, US3)
- 설명에 정확한 파일 경로 포함

## 경로 규칙

- **단일 프로젝트**: 저장소 루트의 `src/`, `tests/`
- **웹 앱**: `backend/src/`, `frontend/src/`
- **모바일**: `api/src/`, `ios/src/` 또는 `android/src/`
- 아래 경로는 단일 프로젝트를 가정하므로 plan.md 구조에 따라 조정

## 의존성 및 실행 순서

### 단계 의존성

- **설정(1단계)**: 의존성 없음 - 즉시 시작 가능
- **기반(2단계)**: 설정 완료에 의존 - 모든 사용자 스토리를 차단
- **사용자 스토리(3단계 이상)**: 모두 기반 단계 완료에 의존
  - 이후 사용자 스토리를 병렬로 진행 가능(인력이 있는 경우)
  - 또는 우선순위(P1 → P2 → P3)에 따라 순차 진행
- **다듬기(최종 단계)**: 원하는 모든 사용자 스토리의 완료에 의존

### 사용자 스토리 의존성

- **사용자 스토리 1(P1)**: 기반(2단계) 후 시작 가능 - 다른 스토리에 의존하지 않음
- **사용자 스토리 2(P2)**: 기반(2단계) 후 시작 가능 - US1과 통합될 수 있지만 독립적으로 테스트할 수 있어야 함
- **사용자 스토리 3(P3)**: 기반(2단계) 후 시작 가능 - US1/US2와 통합될 수 있지만 독립적으로 테스트할 수 있어야 함

### 각 사용자 스토리 내부

- 테스트(포함된 경우)는 반드시 구현 전에 작성하고 실패해야 함
- 서비스 전에 모델
- 엔드포인트 전에 서비스
- 통합 전에 핵심 구현
- 다음 우선순위로 이동하기 전에 스토리 완료

### 병렬 처리 기회

- [P]로 표시된 모든 설정 작업은 병렬 실행 가능
- [P]로 표시된 모든 기반 작업은 병렬 실행 가능(2단계 내부)
- 기반 단계가 완료되면 모든 사용자 스토리를 병렬로 시작 가능(팀 여력이 허용하는 경우)
- [P]로 표시된 사용자 스토리의 모든 테스트는 병렬 실행 가능
- [P]로 표시된 스토리 내부 모델은 병렬 실행 가능
- 서로 다른 팀원이 서로 다른 사용자 스토리를 병렬로 작업 가능

## 구현 전략

### MVP 우선(사용자 스토리 1만)

1. 1단계 완료: 설정
2. 2단계 완료: 기반(중요 - 모든 스토리를 차단)
3. 3단계 완료: 사용자 스토리 1
4. **중지 후 검증**: 사용자 스토리 1을 독립적으로 테스트
5. 준비되면 배포/시연

### 점진적 제공

1. 설정 + 기반 완료 → 기반 준비 완료
2. 사용자 스토리 1 추가 → 독립적으로 테스트 → 배포/시연(MVP!)
3. 사용자 스토리 2 추가 → 독립적으로 테스트 → 배포/시연
4. 사용자 스토리 3 추가 → 독립적으로 테스트 → 배포/시연
5. 각 스토리는 이전 스토리를 깨뜨리지 않고 가치를 추가

### 병렬 팀 전략

개발자가 여러 명인 경우:

1. 팀이 설정 + 기반을 함께 완료
2. 기반이 완료되면:
   - 개발자 A: 사용자 스토리 1
   - 개발자 B: 사용자 스토리 2
   - 개발자 C: 사용자 스토리 3
3. 스토리를 독립적으로 완료하고 통합
