# 레시피와 함정

복사할 가치가 있는 프롬프트와 누구나 한 번쯤 저지르는 실수를 소개합니다. 자신의 경로와 완료 조건으로 바꾸세요. 레시피는 의도적으로 격식 없이 작성했습니다. 실제로도 그렇게 입력하며, 스킬은 의도를 잘 파악합니다.

![로봇들이 레시피 상자를 보고 요리하는 동안 한 여성이 완성된 요리를 맛보고 있으며, 조리대 위에는 /how, /tdd, /loop라고 적힌 카드가 꽂혀 있습니다.](https://github.com/cursor/plugins/blob/63912a91d52c43946f974f2aaf661334a6116a82/pstack/docs/guide/images/recipes.jpg?raw=true)

## 익숙하지 않은 하위 시스템 이해하기

```text
먼저 /how를 사용해 이 초기화가 어떻게 작동하는지 이해해. 그런 다음 /why를 사용해 최근에 왜 고장 났는지 알아내.
```

먼저 작동 방식, 그다음 이력을 살펴봅니다. 각 스킬의 보고서는 검색한 출처를 알려 주므로 답변의 근거를 알 수 있습니다.

## 코드를 건드리기 전에 산만한 보고서 다시 말하기

```text
/poteto-mode 이 스레드를 읽어. 근본적인 문제를 쉬운 말로 직접 다시 설명해. 아직 코드는 변경하지 마.
```

잘못 읽은 내용은 다시 설명하는 과정에서 드러나며, 메시지 하나로 바로잡을 수 있습니다. 에이전트가 자신의 설명을 제시할 때까지 자신의 이론은 말하지 마세요. `/in-your-own-words`는 플레이북 없이 다시 설명만 요청합니다.

## 보내기 전에 프롬프트 다듬기

```text
/sharpen 새 결제 서비스의 온보딩 문서를 작성해.
```

에이전트는 요청하지 않았지만 전문가라면 할 일, 시작할 때 사용할 원자료, 방법과 도구, 결과가 올바른지 확인할 외부 검사를 밝힙니다. 이를 요청하도록 프롬프트를 다시 작성해 돌려주며, 작업 자체는 수행하지 않습니다. 다시 작성된 내용이 적절하면 전송하세요.

## 선택하기 전에 프로토타입 만들기

```text
/poteto-mode 설정 레이아웃의 선택지 몇 가지를 프로토타입으로 만들어. 전환기로 바꿔 볼 수 있게 하고 각각의 스크린샷을 보내 줘.
```

설명이 아니라 실제로 작동하는 것 중에서 선택합니다. 에이전트는 진행하면서 레이아웃과 타이밍에 관한 자체 질문에 답합니다.

## 확정된 설계를 계획으로 바꾸기

```text
/poteto-mode 이 설계를 계획으로 바꿔. 각각 자체 증거를 갖춘 작고 검증 가능한 PR로 나눠.
```

설계가 확정된 뒤에만 요청하세요. 계획이 산출물이며, 이를 실행할 플레이북을 명시합니다.

## 설계에 대한 두 번째 의견 얻기

```text
/arena에 이 스레드와 우리의 접근 방식에 대한 두 번째 의견을 요청해
```

현재 설계는 여러 후보 중 하나가 되고, 종합 결과는 패널이 더 나은 것을 찾았는지 아니면 기존 설계를 확인했는지 알려 줍니다. 되돌리기 비싼 설계에 비하면 비용이 거의 들지 않습니다.

## 독립된 조각을 병렬로 확인하기

```text
/swarm packages/ 아래의 모든 패키지를 각자의 check.sh로 확인해. 패키지마다 작업자 한 명. 보고서는 하나.
```

각 작업자는 패키지 하나를 맡습니다. 부모는 모든 조각을 기다린 뒤 작업자의 원시 출력 대신 `PASS`, `ISSUES`, `BLOCKED` 중 하나인 보고서 하나를 반환합니다.

## 브랜치를 의심하는 시각으로 검토하기

```text
/interrogate 전체 브랜치를 의심하는 시각으로 검토해. 아직 아무것도 변경하지 마. 실제 버그나 동작 회귀가 아니라면 사소한 지적은 하지 마.
```

한정 표현이 실제 역할을 합니다. "아직 아무것도 변경하지 마"는 읽기 전용 상태를 유지하고, 사소한 지적에 관한 규칙은 잡음을 미리 걸러 검증된 발견 사항에 시간을 쓸 가치가 있게 합니다.

## 실패하는 테스트를 통해 버그 수정하기

```text
/poteto-mode 먼저 중복 쓰기를 재현해. 저렴한 테스트 경로가 있다면 /tdd로 처리해. 그런 다음 수정하고 다시 실행해.
```

"저렴한 테스트 경로가 있다면"이 중요합니다. 취약한 모의 객체로 테스트를 억지로 만드는 것은 실제 명령 실행보다 증명하는 바가 적으며, 플레이북은 그렇게 말할 수 있습니다.

## 증거를 갖춰 보고 내용을 재현하고 수정하기

```text
/poteto-mode /verify-<app>으로 이것을 재현해. main에서 재현되면 수정하고 증거로 영상을 보여 줘.
```

"main에서 재현되면"은 버그가 이미 사라졌을 때 실행을 일찍 중단할 수 있게 합니다. 영상이 있으면 diff를 읽기 전에 수정 사항을 확인할 수 있습니다.

## 테스트가 좀처럼 닿지 못하는 속성 입증하기

```text
/create-formal-verification-skill 재시도 큐. 메시지는 절대 두 번 전달되어서는 안 돼.
```

명시된 범위 안의 모든 경우에 검사된 속성 하나, 코드가 이미 해당 속성을 위반한다면 코드 용어로 표현된 반례, 그리고 다음 에이전트가 그 코드의 모든 변경에 실행할 프로젝트 스킬을 얻게 됩니다.

## 수치를 게시하기 전에 검토하기

```text
/benchmark-checklist 이 40% 속도 향상 수치를 pr 설명에 넣기 전에 검토해
```

실행 횟수, 범위, 수치의 한계와 함께 더 빠름, 더 느림, 측정 가능한 차이 없음, 결론 불가 중 하나를 받습니다.

## 같은 실수를 반복해서 바로잡지 않기

```text
/correct 에이전트들이 새 config 플래그를 스키마에 등록하지 않고 계속 추가해
```

수정 사항은 아키텍처, 타입, 린트 또는 테스트로 저장소에 반영되므로 다음 에이전트는 그 실수를 할 수 없습니다.

## 작업을 시작하지 않고 방법 묻기

```text
/poteto-help poteto-mode가 매 턴 유지되게 하려면 어떻게 해야 해?
```

답변, 전송할 프롬프트, 출처 링크를 받습니다. 해당 프롬프트를 전송할 때까지 아무것도 실행되지 않습니다.

## 자리를 비운 동안 실행을 정직하게 유지하기

```text
이제 잘 거야. 모든 fixture가 통과할 때까지 자율적으로 계속 진행해. 멈추지 마. 아침에 감사할 수 있도록 결정 로그를 유지해.
```

전체 계약은 [야간 페이지](./07-overnight.md)에 있습니다. 작업과 완료 조건이 대화에 이미 들어 있다면 짧은 형식으로도 작동합니다.

## 표류하는 실행의 방향 바로잡기

방향 조정 프롬프트는 한 줄입니다.

```text
목표는 재현이라고 했어. 아직 수정은 요청하지 않았어.
```

```text
작동함을 입증하라를 적용해. 빌드 로그가 아니라 실제 출력을 보여 줘.
```

```text
/unslop 처리해. em dash는 사용하지 마.
```

더 많은 말이 필요한 경우는 드뭅니다. 올바른 이름이 필요하며, [원칙 페이지](./08-principles.md)가 그 어휘를 제공합니다.

## 쉬운 말로 답변 받기

```text
/bro
```

이것이 프롬프트의 전부입니다. [`/bro`](https://github.com/cursor/plugins/blob/63912a91d52c43946f974f2aaf661334a6116a82/pstack/skills/bro/SKILL.md)는 전문 용어 없이 더 짧게, 사람끼리 대화하듯 마지막 메시지를 다시 설명합니다. 답변이 기술적으로 철저한데도 무슨 말인지 모르겠을 때 사용하세요.

## 실행해 둔 채 떠났던 채팅 따라잡기

```text
/ketchup
```

[`/ketchup`](https://github.com/cursor/plugins/blob/63912a91d52c43946f974f2aaf661334a6116a82/pstack/skills/ketchup/SKILL.md)은 마지막 메시지 이후 달라진 내용을 쉬운 말로 알려 주고, 사용자의 결정을 기다리는 각 사안을 선택안, 증거, 위험과 함께 나열합니다. 보고하는 동안 아무것도 변경하지 않습니다.

따라잡는 내용을 영상으로 보려면 [`/ketchup-video`](https://github.com/cursor/plugins/blob/63912a91d52c43946f974f2aaf661334a6116a82/pstack/skills/ketchup-video/SKILL.md)를 실행하세요. 무슨 일이 있었는지 자막이 있는 짧은 슬라이드 영상으로 보여 주고, 사용자의 결정을 기다리는 사안을 그 아래에 텍스트로 나열합니다.

## 함정

- **프롬프트에 스킬 나열하기.** "use /how then /architect then /arena"는 플레이북이 이미 순서를 정한 단계를 재배열합니다. 목표와 제약을 밝히세요. 기본값을 재정의할 때만 스킬 이름을 지정하세요.
- **모호한 완료 조건.** "더 좋게 만들어"는 `/loop`가 확인할 대상을 주지 않습니다. 통과하거나 실패할 수 있는 명령이나 산출물을 제시하세요.
- **원인에 대한 자신의 이론부터 제시하기.** 에이전트는 사용자가 가리킨 곳을 검색합니다. 먼저 문제를 다시 설명하게 한 다음 추측을 공유하세요.
- **첫 번째 설계 채택하기.** 한 번의 시도는 모델이 처음 생각한 형태를 고정합니다. 프로토타입이나 `/architect`를 요청하고 증거를 바탕으로 선택하세요.
- **추상적인 계획 다듬기.** 뒷받침하는 코드가 없는 계획을 적대적으로 검토하면 절대 발생하지 않을 위험을 만들어 냅니다. 프로토타입으로 열린 질문을 해결한 다음 만들어진 것을 검토하세요.
- **하나의 worktree에서 병렬 에이전트 실행하기.** 서로의 변경을 덮어쓰며, 어느 에이전트가 무엇을 변경했는지 아무도 알 수 없습니다. cloud agents로 실행하거나 "시도마다 자체 worktree"라고 말하세요.
- **루프를 신뢰하기 전에 반복하기.** 자체 작업을 검증할 수 없는 루프는 확인되지 않은 작업을 더 빠르게 만들 뿐입니다. 먼저 검증 스킬이 작동하게 하세요.
- **검토하지 않은 수치 신뢰하기.** 예열된 캐시나 건너뛴 코드 경로가 속도 향상을 꾸며낼 수 있습니다. 수치를 어디엔가 사용하기 전에 `/benchmark-checklist`를 실행하세요.
- **같은 실수를 손으로 바로잡기.** 채팅의 수정은 한 번의 실행에 도움이 됩니다. `/correct`는 저장소를 수정해 이후 실행에서 같은 실수를 반복하지 않게 합니다.
- **검토 범위를 위해 `/arena` 사용하기.** `/arena`는 하나의 설계나 코드 브리프를 반복한 다음 기반을 선택하고 가장 좋은 부분을 접목합니다. `/swarm`은 조각이나 명시된 경쟁 항목을 분할하고 보고서 하나로 집계합니다.
- **모든 검토 코멘트 수용하기.** 봇과 사람 모두 실제 발견 사항과 잡음을 한 목록에 올립니다. `/interrogate`는 재실행으로 입증된 발견 사항만 유지하고 제외한 내용과 이유를 나열하며, 사용자는 어느 쪽이든 재정의할 수 있습니다.
- **`auto`를 모델 슬러그로 취급하기.** `auto`와 `inherit-parent`는 "하위 에이전트가 부모 채팅 모델을 상속하도록 model 필드를 생략한다"는 뜻입니다. [설정](./01-setup.md)에서 역할을 다룹니다.
- **성공한 빌드만으로 성공 보고하기.** 빌드는 컴파일된다는 사실을 입증합니다. 실제 명령, 흐름, 저장된 값 또는 프로파일을 요청하고 답변에서 증거를 확인하세요.
- **`SKILL.md`를 즉석에서 작성하기.** 검증과 검토가 이루어지도록 [스킬 작성 또는 수정 플레이북](https://github.com/cursor/plugins/blob/63912a91d52c43946f974f2aaf661334a6116a82/pstack/skills/poteto-mode/playbooks/authoring-a-skill.md)을 통해 처리하세요.

가이드는 여기까지입니다. 건너뛰어 읽었다면 [설정](./01-setup.md)으로 돌아가 실제 작업 하나를 실행하세요. 습관은 읽기가 아니라 사용을 통해 자리 잡습니다.

[가이드 목차](./README.md)로 돌아갑니다.
