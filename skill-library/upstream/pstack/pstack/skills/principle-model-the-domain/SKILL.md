# 도메인을 모델링하라

실제 도메인을 조건문 곳곳에 흩어 놓지 말고 데이터 구조로 표현한다. 도메인과 일치하는 구조는 유효하지 않은 상태를 표현할 수 없게 하고 분기를 없앤다. 작성할 때 구조를 선택하는 비용은 작다. 나중에 구조를 복원하려 하면 리팩터링처럼 보여 미뤄진다.

다음을 선택한다.

- 흩어진 불리언, 단계 또는 수명 주기 검사 대신 상태 머신.
- 느슨한 매개변수나 반복되는 형태 가정 대신 타입이 지정된 모델.
- 여러 파일에 퍼진 분기 대신 맵, 레지스트리, 조회 테이블 또는 판별 유니온.
- 임시방편의 상태 변경 대신 리듀서 또는 명령/이벤트 모델.
- 불러오기, 검증, 변환, 저장 같은 순서 대신 하나의 도메인 지식 체계를 중심으로 구성한 모듈. 실행 순서는 소유권이 아니다.
- 반복되는 동작, 소유권 또는 불변 조건을 모으는 작은 모듈 경계.
- 접근 패턴에 필요하다면 큐, 캐시, 인덱스, 그래프, 트리 또는 정규화된 컬렉션.
- 그 밖에 적합한 모든 구조. 적합한 것이 없다면 코드가 절대 허용해서는 안 되는 것이 무엇이고 데이터를 어떻게 읽는지 파악한 다음, 바로 그것을 표현하는 구조를 찾는다.

추상화를 억지로 적용하지 않는다. 현재 형태가 이미 명확하고 국소적이며 커질 가능성이 낮다면 평범한 코드를 선호한다. 분기, 중복된 규칙, 유효하지 않은 상태 또는 수명 주기 위험은 없애지 않으면서 간접 계층만 추가하는 추상화는 의심한다.

새 기능 때문에 기존 if/else 연쇄에 분기가 하나 더 늘어나거나, 첫 번째 불리언과 동기화 상태를 유지해야 하는 두 번째 불리언이 생겼다면 이 원칙을 건너뛰었다는 신호다. 시간 순서에 따른 분해도 또 다른 신호다. 단계 이름을 붙인 모듈은 여러 단계에 걸쳐 같은 도메인 규칙을 반복한다.
