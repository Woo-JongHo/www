# 수치를 설명하라

- **실행하기 전에 결정을 적는다.** 어떤 결과가 결정을 바꿀지와 노이즈 하한을 명시한다. 실행 간 편차가 효과보다 크면 중단한다.
- **"왜 두 배가 아닌가?"라고 묻는다.** 코어, 잠금, 디스크, 네트워크 또는 부하 생성기 자체처럼 결과의 한계를 정하는 리소스나 코드 경로를 명시한다. 실행 중에 수집한 프로파일이나 시스템 카운터에서 이를 얻은 다음 소스에 대응시킨다. 코드를 읽고 한 추측은 제한 요인이 아니다. 수치가 왜 두 배 더 좋지 않은지 말할 수 없다면 무엇을 측정했는지 모르는 것이다.
- **그 수치가 달리 무엇을 측정했을 수 있는지 나열하고 각각을 증거로 배제한다.** 흔히 의심할 대상은 오류, 건너뛰거나 캐시된 작업, 실행되지 않은 코드, 조정되지 않은 한쪽(기본 설정으로 둔 쪽), 노이즈, 그리고 엔드 투 엔드에서 영향을 주기에는 너무 작은 부분이다.
- **증거를 수치와 함께 보관한다.** 실행 횟수, 편차, 제한 요인을 메모나 연결된 아티팩트에 넣는다.

성능 수치에는 [benchmark-checklist](https://github.com/cursor/plugins/blob/63912a91d52c43946f974f2aaf661334a6116a82/pstack/skills/benchmark-checklist/SKILL.md) 스킬로 전체 절차를 실행한다. 평가 결과에는 시행에 대해 같은 질문을 한다. 모든 실행이 작업을 수행했는가, 시행과 모델이 달라도 격차가 유지되는가, 해당 시나리오가 중요한가.

결정을 바꿀 결과를 정하지 않고 실행을 시작했거나, 수치의 근거가 되는 증거에 실행 횟수, 편차 또는 명시된 제한 요인이 없거나, 절약한 시간이 변경된 부분에 걸리던 시간보다 크다면 이 원칙을 건너뛴 것이다.
