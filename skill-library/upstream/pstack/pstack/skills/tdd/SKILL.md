# TDD 버그 수정

명확하고 저렴한 테스트 경로가 있는 버그를 수정할 때는 프로덕션 코드를 변경하기 전에 망가진 행동을 실행 가능한 형태로 만든다. 목표는 수정 전에는 실패하고 수정 후에는 통과하는, 초점이 명확한 회귀 테스트다.

테스트가 비현실적이라면 억지로 만들지 않는다. 가능한 테스트에 광범위한 harness 설정, 깨지기 쉬운 mock, 느린 end-to-end 인프라, 프로덕션에만 있는 상태, 모호한 재현 단계 또는 관련 없는 대규모 fixture 변경이 필요하다면 새 테스트 추가를 건너뛰고 그 대신 가장 가까이에서 유용한 검증을 사용한다.

## 워크플로

1. **버그를 이해한다.** 의도한 행동, 현재 행동, 영향받는 경로와 관찰 가능한 최소 재현 방법을 식별한다.
2. **실행 가능한 가장 좁은 검사를 선택한다.** 해당 코드 경로에 이미 사용되는 가장 가까운 단위, 컴포넌트, 통합 또는 회귀 테스트를 우선한다. 실용적인 테스트 경로가 명백하지 않다면 워크플로를 충족하려는 목적으로 처음부터 만들지 않는다.
3. **실패하는 테스트를 먼저 작성한다.** 버그를 잡았을, 초점이 명확한 최소 테스트를 추가한다. 테스트는 현재 구현을 그대로 반영하지 말고 의도한 행동을 표현해야 한다.
4. **수정 전에 새 테스트를 실행한다.** 의도한 이유로 실패하는지 확인한다. 통과하거나 무관한 이유로 실패한다면 구현을 편집하기 전에 테스트나 재현 방법을 바로잡는다.
5. **버그를 수정한다.** 인접한 계약을 보존하면서 의도한 행동을 충족하는 최소한의 프로덕션 변경을 한다.
6. **회귀 테스트를 다시 실행한다.** 이제 테스트가 통과하는지 확인한다.

## 실패하는 테스트가 비현실적인 경우

그 대신 가장 가까운 실행 가능한 회귀 검사를 사용한다. 대상이 명확한 스크립트, 수동 재현 명령, 브라우저 자동화, snapshot 비교, 로그 단언 또는 초점이 명확한 통합 검사가 이에 해당한다.

나쁜 테스트보다는 새 테스트를 만들지 않는 편이 낫다. 나쁜 테스트란 대부분 mock을 테스트하거나, 현재 구현 세부 사항을 표현하거나, 타이밍 또는 관련 없는 전역 상태에 의존하거나, 작은 수정에 비싼 인프라가 필요하거나, 수정 사항을 증명한 직후 삭제할 테스트다.

## 보호 원칙

- 잘못된 구현에 맞추려고 테스트를 변경하지 않는다.
- 예상 행동이 실제로 바뀌었고 이유가 명확한 경우가 아니라면 기존 단언을 약화하지 않는다.
- 회귀 테스트는 버그에 초점을 맞춘다. 광범위한 fixture 변경이나 무관한 coverage 확대를 피한다.
- 버그가 flaky하다면 가능한 경우 테스트를 결정적으로 만들고 고정하는 신호를 문서화한다.
- 버그가 더 광범위한 실패 유형을 드러낸다면 먼저 초점이 명확한 회귀 경로를 반영한 다음 관련된 추가 coverage를 고려한다.

## 최종 응답

결과만이 아니라 증거를 보고한다.

- 수정 전 실패한 테스트 또는 실행 가능한 검사의 이름과 그 검사에서 발생한 실패를 밝힌다.
- 수정 후 통과한 테스트 실행과 수행한 인접 검증을 밝힌다.
- 수정 전 실패 증거를 입증할 수 없었다면 그 이유와 대신 사용한 가장 가까운 회귀 검사를 설명한다.
