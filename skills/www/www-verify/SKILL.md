# WWW 검증

## 호출 조건

사용자가 `www-verify`를 직접 호출하거나 `www-dev` 역할이 허용된 요청의 검증 단계로 선택할 때 실행한다.

## 입력

작업 ID, UUID로 스캔해 찾은 실제 작업 폴더의 수용 기준, diff, 실제 실행 가능한 검사와 환경. 문서 폴더를 작업 ID로 이어붙이지 않는다.

## 진입 조건

검증 대상 소스 상태와 필수 기준을 식별할 수 있다.

## 절차

1. [공통 계약](../../../docs/skills/WORKFLOW.md), [모델·추론 노력 권고](../../../docs/skills/MODEL_POLICY.md), [데스크톱 프로필](../../../docs/skills/profiles/desktop.md)을 읽는다.
2. 구현 후 검증 대상 코드·테스트·설정의 범위와 내용 식별, 작업 수용 기준 정의의 식별과 당시 사본 `criteriaSnapshot`을 확보한다. 요구 참조 문서도 검사 입력에 포함하고 범위를 바꾸면 현재 결과를 미검증으로 재평가한다. commit과 dirty 여부도 기록하고 상태를 사실에 맞게 `verifying`으로 둔다. 요청·실제 모델과 추론 노력은 관찰한 범위로 구분한다.
3. 관찰 행동, 경계값, 오류 경로를 검사한다. 실패·경고를 숨기거나 실행하지 않은 검사를 통과로 쓰지 않는다.
4. BoxBox 적용 파일은 [개발 문서의 작성·검증 경계](../../../docs/DEVELOPMENT.md#boxbox-작성검증-경계)에 따라 최종 source check를 실행하고 구문 상태, `PASS`·`FIXABLE`·`REFUSE` 수, 미지원 파일과 누락 축을 기능 검사와 구분해 기록한다. 감지 그룹 0을 전체 가독성 통과로 승격하지 않는다.
5. `verification.md`에 시도별 섹션을 추가하고 정제한 요약 앵커를 만든다.
6. 각 기준의 `result`와 증거 연결을 갱신한다. 검사 중 입력 변화와 완료·재개 시 현재 소스·기준·환경·입력 범위에 적용할 수 있는지를 확인한다. 과거 시도는 보존한다. legacy의 과거 PASS를 새 증거로 옮겨 쓰지 않는다. push, 색인, 업무 수용, 프로세스 종료를 테스트 통과와 섞지 않는다.
7. [공통 계약](../../../docs/skills/WORKFLOW.md#독립-검토의-책임)의 읽기 전용 검토와 프로젝트 정책을 적용한다. 모든 필수 기준의 현재 적용 가능한 증거와 필요한 검토가 충족하고 차단이 없을 때만 `done`으로 바꾼다. 검토 미실행은 통과로 쓰지 않는다.

## 출력 경로

UUID로 찾은 실제 작업 폴더의 `verification.md`, 같은 폴더의 `work.json`.

## 허용 변경

검증 기록, 기준 결과, 검증에 직접 필요한 테스트만 변경한다. 제품 수정은 `www-build`, 불명확한 실패는 `www-diagnose`에 인계한다. 자동 commit·push는 하지 않는다.

## 완료 조건

각 필수 기준의 결과와 현재 증거 적용성이 구분되고 실행 명령, 핵심 결과, 대상 소스·기준 식별, 검토·미검증 한계가 재현 가능하게 남았다.

## 인계

[검증 템플릿](../../../docs/skills/templates/verification.md)을 사용한다. 실패는 구체적 재현과 함께 `www-build` 또는 `www-diagnose`로 돌려보낸다. 같은 범위 구현 권한이 있으면 수정·재검증을 이어가고, 검증만 요청했으면 수정 필요 사항을 전달한다. 통과는 게시·서버 색인을 자동 의미하지 않는다.
