# WWW 구현

## 호출 조건

사용자가 `www-build`을 직접 호출하거나 `www-dev` 역할이 구현·실패 수정 단계로 선택하고 요청에 해당 변경 권한이 있을 때 실행한다. 명확한 구현 요청에서 받은 같은 범위의 권한은 단계 전환 후에도 유지한다.

## 입력

작업 ID, UUID로 찾은 실제 작업 폴더의 `work.json` 수용 기준·권한 연결과 `spec.md`, 있으면 `design.md`와 `tasks.md`, 관련 현행 명세와 저장소 상태. 문서 폴더를 작업 ID로 이어붙이지 않는다.

## 진입 조건

저장소 root·branch·dirty 상태를 확인했고 수용 기준과 변경 권한이 명확하다. 명세 작성만으로는 진입할 수 없다.

## 절차

1. [공통 계약](../../../docs/skills/WORKFLOW.md), [모델·추론 노력 권고](../../../docs/skills/MODEL_POLICY.md), [데스크톱 프로필](../../../docs/skills/profiles/desktop.md)을 읽고 예상 밖 변경을 보존한다.
2. `status`를 사실에 맞게 `in_progress`로 갱신한다.
3. 코드·테스트·개발 도구를 변경할 때는 [TypeScript 작성 및 하네스](../../../docs/DEVELOPMENT.md#typescript-작성-및-하네스)를 읽고 공식 진입점과 파일별 사전 작성·검사 절차를 따른다.
4. 끝까지 동작하는 가장 작은 단위를 구현하고 직접 영향받는 호출부·테스트·문서를 함께 갱신한다. 완료 전 문서 영향 검토는 [공통 계약](../../../docs/skills/WORKFLOW.md#문서-영향-검토)에 따라 수행한다.
5. stub, 가짜 fallback, TODO 전용 구현, 자동 dirty 덮어쓰기를 남기지 않는다.
6. 관련 기준의 집중 검사와 위 정본의 소스 정책·타입·사후 BoxBox 검사를 실행한다. 실제 검증 기록과 증거 적용성·최종 판정은 `www-verify`에 인계한다. 같은 범위의 실패는 기존 권한으로 수정·재검증하며 수용 기준을 약화하지 않는다.

## 출력 경로

승인 범위의 제품 파일과 테스트·문서, 해당 작업의 `work.json` 및 필요한 `tasks.md`.

## 허용 변경

승인된 구현과 직접 영향받는 파일만 변경한다. 자동 branch 생성, commit, push, 원격 실행, 소스 동기화는 하지 않는다.

## 완료 조건

동작 단위가 stub 없이 구현됐고 관련 호출부·테스트·문서가 일관되며 실제 변경과 실행 결과 목록이 준비됐다. 이 조건만으로 `done`으로 바꾸지 않는다.

## 인계

[작업 템플릿](../../../docs/skills/templates/tasks.md)에 연결된 기준, diff, 실행 결과와 한계를 같은 작업 ID의 `www-verify`에 전달한다. 실패 원인이 불명확하면 `www-diagnose`로 전달한다.
