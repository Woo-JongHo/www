# WWW 구현

## 호출 조건

사용자가 `www-build`을 명시적으로 호출하고 제품 변경을 승인했거나 요청 자체가 명확한 구현 권한인 경우에만 실행한다.

## 입력

작업 ID, UUID로 스캔해 찾은 실제 작업 폴더의 승인된 `spec.md`, 있으면 `design.md`와 `tasks.md`, 저장소 상태. 문서 폴더를 작업 ID로 이어붙이지 않는다.

## 진입 조건

저장소 root·branch·dirty 상태를 확인했고 수용 기준과 변경 권한이 명확하다. 명세 작성만으로는 진입할 수 없다.

## 절차

1. [공통 계약](../../../docs/skills/WORKFLOW.md), [모델·추론 노력 권고](../../../docs/skills/MODEL_POLICY.md), [데스크톱 프로필](../../../docs/skills/profiles/desktop.md)을 읽고 예상 밖 변경을 보존한다.
2. `status`를 사실에 맞게 `in_progress`로 갱신한다.
3. 끝까지 동작하는 가장 작은 단위를 구현하고 직접 영향받는 호출부·테스트·문서를 함께 갱신한다.
4. stub, 가짜 fallback, TODO 전용 구현, 자동 dirty 덮어쓰기를 남기지 않는다.
5. 관련 기준을 확인할 수 있는 집중 검사를 실행한다. 실제 검증 기록과 최종 판정은 `www-verify`에 인계한다.

## 출력 경로

승인 범위의 제품 파일과 테스트·문서, 해당 작업의 `work.json` 및 필요한 `tasks.md`.

## 허용 변경

승인된 구현과 직접 영향받는 파일만 변경한다. 자동 branch 생성, commit, push, 원격 실행, 소스 동기화는 하지 않는다.

## 완료 조건

동작 단위가 stub 없이 구현됐고 관련 호출부·테스트·문서가 일관되며 실제 변경과 실행 결과 목록이 준비됐다. 이 조건만으로 `done`으로 바꾸지 않는다.

## 인계

[작업 템플릿](../../../docs/skills/templates/tasks.md)에 연결된 기준, diff, 실행 결과와 한계를 같은 작업 ID의 `www-verify`에 전달한다. 실패 원인이 불명확하면 `www-diagnose`로 전달한다.
