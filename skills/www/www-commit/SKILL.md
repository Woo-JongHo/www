# WWW 커밋

## 호출 조건

사용자가 `www-commit`을 명시적으로 호출하거나 WWW의 커밋 준비·실행을 직접 요청했을 때 적용한다. `www-dev` 역할도 해당 요청을 근거로 이 스킬을 선택한다. 역할 선택과 스킬 생성·수정은 커밋 실행 승인이 아니다. 준비·검토만 요청했으면 index와 HEAD를 바꾸지 않는다. 사용자가 이미 대상과 실행을 명확히 승인했다면 같은 승인을 반복해서 묻지 않는다.

합의된 기본값은 **“커밋해” = commit + push**, **“로컬에만 커밋해” = commit만**이다. 실행 없이 스킬을 호출하거나 계획·준비만 요청한 경우에는 둘 다 실행하지 않는다. 실행 범위와 원격 대상이 명확하면 commit 직후 push 여부를 다시 묻지 않는다. 이 기본값은 현재 변경 전체의 포괄 승인이나 원격 대상 변경·force push 권한이 아니다.

## 입력

요청한 저장소와 작업 UUID 또는 범위, 현재 브랜치·HEAD, staged/unstaged/untracked 변경, 관련 명세·검증 기록. 작업 UUID는 `docs/work/`의 `work.json`에서 찾아 실제 `영역/번호-작업명` 경로로 연결한다. 파일 경로만 승인됐더라도 그 파일에 섞인 모든 변경까지 승인됐다고 보지 않는다.

## 진입 조건

[공통 계약](../../../docs/skills/WORKFLOW.md), [모델 정책](../../../docs/skills/MODEL_POLICY.md), 저장소 `AGENTS.md`를 읽는다. 관련 작업과 검증 범위를 설명할 수 있어야 한다. 커밋은 하나의 명확한 목적을 가지며, 미완료 작업을 체크포인트로 저장할 경우에도 미완료 상태를 정직하게 유지한다. 커밋 자체가 `done`이나 게시·색인을 뜻하지 않는다.

## 절차

### 용도와 역할별 후보 분리

스테이징 전에 실제 diff를 독립적으로 검토·되돌릴 수 있는 변경 목적별로 나눈다. 저장소, 작업 UUID, 디렉터리, 파일 수가 같다는 이유로 한 커밋으로 합치지 않는다. “전체 변경을 커밋해”는 포함 범위의 승인이지 단일 커밋 지시가 아니다. 여러 후보로 나누어도 이미 승인된 범위의 실행 권한은 승계하며 후보마다 같은 승인을 다시 묻지 않는다.

- 후보마다 하나의 목적·역할, 경로 또는 hunk, 제목, 필요한 검증, 선행 후보, 제외할 변경을 정한다. 하나의 정직한 제목과 되돌리기 이유로 설명되는지 확인한다.
- 기능, 동작을 보존하는 이관·리팩터링, 독립적인 정렬·정리, 번역·자료 갱신, 별도 도구·정책 변경은 분리 후보로 검토한다. 한 기능을 성립시키는 UI·인터페이스·구현·테스트·직접 관련 문서는 함께 둘 수 있다. 역할별 분리는 계층이나 확장자마다 쪼개라는 뜻이 아니다.
- 공통 기반이 필요한 경우 기반 후보를 먼저 둔다. 각 후보는 선행 커밋만 적용된 상태에서 필요한 검증을 만족해야 한다. 뒤 후보의 미커밋 변경을 빌려 앞 후보가 통과한 것으로 쓰지 않는다.
- 같은 파일에 목적이 섞였으면 검토한 hunk만 분리할 수 있는지 확인한다. 안전하게 분리할 수 없는 공유 변경은 함께 두는 이유와 의존 관계를 기록한다. 파일 수 제한이나 검사 통과만으로 분할을 강제하거나 면제하지 않는다.
- 전체 후보 목록을 준비 양식으로 먼저 보여준다. 하나뿐이면 그 목적을 명시하면 충분하고 별도 분할 문서를 만들지 않는다. 사용자가 명시적으로 한 커밋을 요청한 경우에는 묶는 이유를 남긴다.
- 한 후보의 stage·검증·commit·결과 확인을 끝낸 뒤 다음 후보로 진행한다. 편의를 위해 모든 후보의 경로를 먼저 합쳐 stage하지 않는다. 마지막에는 완료한 커밋·보류 후보·남은 변경을 구분한다.

이 기준은 다른 저장소에서도 커밋 단위를 정할 때 참조할 수 있다. 아래 WWW 전용 언어·실행·push 기본값은 해당 저장소의 정책을 대체하지 않는다. 이미 게시한 이력을 다시 나누는 것은 별도의 이력 재작성 요청이며, 향후 절차 보완만으로 실행하지 않는다.

### 1. 읽기 전용 준비

- 저장소 루트·현재 브랜치·HEAD·worktree를 확인하고 전체 staged/unstaged/untracked 변경을 구분한다. detached HEAD, 충돌, 진행 중 merge/rebase/cherry-pick이면 임의로 해결·종료하지 않고 상황과 필요한 결정을 알린다.
- `git status --short`, `git diff --stat`, `git diff --cached --stat`와 관련 diff를 읽는다. 실제 경로 처리에는 `-z` 출력과 인자 배열을 사용해 공백·한글·이름 변경을 보존한다.
- 포함할 파일과 변경 묶음, 제외할 변경을 명시한다. 기존 index를 사용자 상태로 취급한다. 다른 작업의 staged 변경이 있으면 해제하거나 이번 커밋에 섞지 않는다. 같은 파일의 일부 변경만 대상이면 전체 파일을 stage하지 않는다.
- 비밀정보·자격증명·개인 원본 로그·기기 절대 경로·빌드 산출물·원본 대화가 섞였는지 검토한다. 검사하지 못한 바이너리나 대용량 파일을 안전하다고 보고하지 않는다. 민감한 원문을 보고서에 재출력하지 않는다.
- 기본 push 요청에서는 원격 push URL·브랜치·upstream과 공개 범위를 확인한다. 이 프로젝트의 GitHub 저장소는 공개이므로 개인용 앱이라는 이유로 로그·비밀을 게시하지 않는다. 대상이 없거나 여러 push URL·서로 다른 설정으로 모호하면 조용히 새 대상을 만들지 않고 확인한다.
- 원격 브랜치의 최신 관측 상태를 기준으로 함께 게시될 기존 미게시 커밋을 모두 검토한다. 이번 변경 외 커밋이 승인 범위에 포함되지 않으면 commit 전에 범위를 확인한다. 신규 원격 브랜치도 게시될 이력과 목적지를 설명한다. 이력 확인을 위해 사용자 변경을 자동 pull·rebase·덮어쓰기하지 않는다.

### 2. 검증과 메시지 제안

- 관련 집중 테스트와 저장소의 타입·빌드·문서 계약 검사를 실제로 실행하고 명령·결과·대상 소스 상태를 기록한다. 이전 세션의 성공을 이번 변경의 증거로 재사용하지 않는다.
- 검증은 후보의 변경과 의존 범위에 맞춘다. 분할된 후보의 격리 검증과 전체 후보를 합친 최종 검증을 구분하며, 입력이 바뀌지 않은 전체 검사를 후보 수만큼 반복하지 않는다.
- 작업 트리에 다른 변경이 섞여 있으면 테스트가 커밋 후보만 검증했는지 구분한다. 후보와 검증 대상이 다르면 후보 기준의 격리 검증을 마련하거나, 범위가 불명확한 상태에서 실행하지 않고 한계를 알린다. 사용자 작업을 stash/reset해서 격리하지 않는다.
- 테스트·훅 실패를 숨기거나 `--no-verify` 등으로 우회하지 않는다. 실패한 검사를 통과했다고 쓰지 않고 해결 또는 사용자의 다음 결정을 기다린다.
- 제목은 변경 결과·문제를 설명하는 한국어 문장으로 쓴다. `feat:`·`fix(scope):` 같은 접두어는 붙이지 않는다. 본문이 필요하면 변경 이유·핵심 내용·검증·남은 한계를 짧게 적는다. 예: `Native 실행 상태와 승인 대기를 구분한다`.
- [커밋 준비 양식](../../../docs/skills/templates/commit.md)으로 범위·검증·메시지·제외 항목을 보여준다. 명시적 실행 승인이 없으면 여기서 멈춘다. 작은 변경에 별도 영구 준비 문서를 강제하지 않는다.

### 3. 승인된 범위만 stage·commit

- 실행 승인 후 저장소·브랜치·HEAD와 후보 diff가 준비 때와 같은지 다시 확인한다. 바뀌었으면 재검토하며 이전 승인을 확대하지 않는다.
- 정확히 선택한 경로 또는 변경 묶음만 stage한다. `git add .`, `git add -A`, `git commit -a`, 임의의 `reset`·`restore --staged`·`stash`·amend·rebase를 사용하지 않는다. Git pathspec 특수문자가 있는 이름은 literal pathspec으로 처리한다. 파일 선택을 셸 문자열로 조합하지 않는다.
- 전체 `git diff --cached`를 다시 읽어 이번 후보의 경로·hunk·목적과 승인 범위에 일치하는지 확인한다. 다른 후보나 외부 staged 내용이 섞이면 그대로 두고 실행을 중단한다. 다른 작업을 먼저 커밋하거나 index를 비워 문제를 숨기지 않는다.
- 검토한 index의 tree OID를 `git write-tree`로 식별하고 HEAD·브랜치와 함께 실행 직전에 다시 대조한다. 후보가 바뀌면 재검토·필요한 검증을 수행한다. tree OID는 임시 실행 맥락에서만 다루며 그 tree에 포함될 문서 안에 자기 tree 해시를 기록하지 않는다.
- 승인된 메시지로 `git commit`한다. 일반 Git 명령 사이의 확인만으로 동시 변경을 원자적으로 차단할 수는 없으므로, 다른 writer가 같은 index를 사용 중이면 실행을 중단한다. 커밋 오류나 훅 변경 후에는 HEAD·index·diff를 재관찰하고 커밋을 맹목적으로 반복하지 않는다.

### 4. 결과 확인

- 성공 메시지만 믿지 않고 실제 HEAD의 해시·부모·메시지·tree·변경 파일을 확인한다. 승인된 후보와 결과가 다르면 이상을 보고하고 자동 revert·amend하지 않는다.
- 남은 staged/unstaged/untracked 변경이 보존됐는지 확인한다. 결과 해시·포함 범위·검증·남은 변경을 한국어로 보고한다.

### 5. 기본 push와 원격 확인

- 로컬 전용 요청이면 push를 생략하고 그 이유를 보고한다. 그 외에는 위에서 확인한 원격 URL·브랜치·게시 커밋 범위가 그대로인지 확인한 뒤 이어서 실행한다.
- 명시한 원격과 브랜치 refspec만 push한다. 기본 `push` 설정에 맡겨 다른 ref까지 게시하거나 `--all`, `--mirror`, `--tags`, ref 삭제, force 계열 옵션을 사용하지 않는다. 태그·merge·release는 범위 밖이다.
- non-fast-forward·브랜치 보호·인증 실패 시 자동 pull/rebase/force로 해결하지 않는다. 결과가 불명확하거나 응답이 유실되면 원격 ref부터 조회하고 맹목적으로 재시도하지 않는다. 커밋이 이미 생성됐다면 같은 변경을 다시 커밋하지 않는다.
- 명령 성공뿐 아니라 대상 원격 ref가 의도한 커밋을 가리키는지 확인한다. 확인할 수 없으면 `push 미확인`이며, 로컬 커밋 성공과 구분한다. 원격이 확인 중 바뀌었으면 관측 결과를 보고하고 덮어쓰지 않는다.
- 최종 결과는 `로컬 커밋`, `원격 push`, `서버 색인`을 각각 보고한다. 서버 색인 통합이 없으므로 push만으로 서버 반영을 완료했다고 하지 않는다.

## 출력 경로

기본 출력은 대화의 커밋 준비 요약과, 승인된 실행 후 실제 커밋 해시·push 대상과 확인 결과다. 사용자가 기록을 요청한 경우에만 해당 작업 폴더의 `commit.md`를 [양식](../../../docs/skills/templates/commit.md)에 맞춰 작성한다. 관련 검증은 그 작업의 `verification.md`를 사용한다. 후보 tree·자기 커밋 해시를 같은 커밋의 필수 기록으로 강제하지 않는다.

## 허용 변경

준비 단계에서는 읽기와 승인된 검사만 수행한다. 검사기가 생성하는 임시 산출물과 부작용은 먼저 확인한다. 명시적 커밋 실행 승인 뒤에만 선택한 변경을 stage·commit하고, 로컬 전용이 아니면 확인된 범위를 push한다. 기존 사용자 변경을 되돌리거나 해제·삭제하지 않는다. 훅 설치·전역 Git 설정·서명 설정·credential 변경은 범위 밖이다. 제품 코드 수정은 별도 승인된 `www-build` 작업이며 커밋 실패를 이유로 임의로 고치지 않는다.

## 완료 조건

준비 요청은 범위·제외 항목·실제 검증 결과·한국어 메시지·미결정 사항이 설명되면 끝난다. 실행 요청은 실제 커밋 결과가 승인된 후보와 일치하고 남은 사용자 변경이 보존됐으며 기본 push의 원격 ref까지 확인했을 때 전체 성공이다. 로컬 전용 요청은 커밋 확인으로 끝난다. `로컬 커밋 완료·push 실패/미확인`은 부분 결과이지 전체 성공이 아니다. 준비 완료를 커밋 완료로, 커밋 완료를 기능 수용이나 원격 반영으로 표시하지 않는다. 이 문서는 에이전트 절차이지 자동 Git 권한 차단기가 아니다.

## 인계

검증이 부족하면 같은 작업의 `www-verify`, 원인이 불명확하면 `www-diagnose`에 근거를 전달한다. 요구·구현 범위 변경은 원 작업 명세와 사용자 결정으로 되돌린다. 확인된 commit + push 범위에는 같은 승인을 반복해서 요구하지 않는다. 원격 대상·게시 이력이 바뀌거나 승인 밖 변경이 발견되면 그 차이에 한해서 사용자 결정을 받는다.
