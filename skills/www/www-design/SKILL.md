# WWW 설계

## 호출 조건

사용자가 `www-design`을 직접 호출하거나 `www-dev` 역할이 허용된 요청의 설계 단계로 선택할 때 실행한다.

## 입력

작업 UUID, UUID로 찾은 실제 작업 폴더의 `work.json`·`spec.md`, 관련 현행 기능 요구·구조, 현재 코드와 요청 권한. 문서 폴더를 작업 UUID로 이어붙이지 않는다.

## 진입 조건

작업 ID가 유효하고 범위와 수용 기준이 구현 결정을 내릴 만큼 준비돼 있다.

## 절차

1. [공통 계약](../../../docs/skills/WORKFLOW.md), [모델·추론 노력 권고](../../../docs/skills/MODEL_POLICY.md), [데스크톱 프로필](../../../docs/skills/profiles/desktop.md), 기존 코드 경계를 읽는다.
2. 기존 패턴과 의존성 기능을 먼저 확인한다.
3. [사용자 여정과 기준별 추적](../../../docs/skills/WORKFLOW.md#사용자-여정과-기준별-추적)에 따라 명세의 여정별 입력부터 결과 확인까지 실제 경계·호출부·상태 소유자를 조사한다. 최소 데이터 흐름, 인터페이스, 실패·복원 시 인계, 영향 파일과 확인 방법을 정한다.
4. WWW의 채택된 Electron 기준과 기존 모듈을 사용한다. Tauri 비교 스파이크는 과거 이력이며 제품 이주를 전제하지 않는다.
5. 각 위험을 작업 레코드의 수용 기준 ID와 구체적 검증 방법에 연결해 `design.md`를 작성한다. 구현 단위가 둘 이상이면 `tasks.md`도 작성하고 [작업 내부 모델 배분](../../../docs/skills/MODEL_POLICY.md#분해와-실행)에 따라 소유 파일·의존성·선택 이유·검증을 연결한다. 바뀌는 동작·책임에 따라 현행 명세·구조의 갱신 필요를 판단한다.

## 출력 경로

구현 인계 전에는 [구현 전 산출물 검토](../../../docs/skills/ARTIFACT_REVIEW.md)의 `consistency`로 명세·설계·작업과 기준별 연결을 검토·기록한다. 작은 수정은 brief로 필요한 근거를 남긴다. 발견한 모순은 소유 문서에서 해소하고 새 digest로 다시 검토한다.

UUID로 찾은 실제 작업 폴더의 `design.md`, 필요한 경우 같은 폴더의 `tasks.md`.

## 허용 변경

해당 작업의 설계·작업 기록만 변경한다. 제품 소스, 자동 브랜치 생성, commit, push는 금지한다.

## 완료 조건

기존 패턴 재사용, 여정별 끝까지의 인계·상태 소유, 실패 모드, 영향 파일, 기준별 검증 전략과 선점하지 않는 미래 범위가 설명됐다. 여러 구현 단위의 순서·의존성과 다음 단계는 [계획과 칸반 인계](../../../docs/skills/WORKFLOW.md#계획과-칸반-인계)로 같은 작업에 연결됐다.

## 인계

[설계 템플릿](../../../docs/skills/templates/design.md) 형식의 기록을 같은 작업 ID의 `www-build`에 전달한다. 조사 중 확인된 버그는 원인으로 단정하지 말고 `www-diagnose`에 전달한다.
