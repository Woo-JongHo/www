# WWW 명세

## 호출 조건

사용자가 `www-spec`을 명시적으로 호출한 경우에만 실행한다. 스킬 발견 지원 여부는 클라이언트마다 다르며 현재 세션에 자동 로드됐다고 주장하지 않는다.

## 입력

사용자 목표, 저장소의 현재 사실, 제약, 기존 작업 ID(있는 경우).

## 진입 조건

요청 대상 저장소와 안전 규칙을 읽었고 실제 요청 또는 변경할 기존 명세가 있다.

## 절차

1. [공통 계약](../../../docs/skills/WORKFLOW.md), [모델·추론 노력 권고](../../../docs/skills/MODEL_POLICY.md), 적용할 [데스크톱 프로필](../../../docs/skills/profiles/desktop.md)을 읽는다.
2. 기존 기록과 구현을 먼저 읽고, 이미 확인된 목적이나 결정은 다시 질문하지 않는다. 사실·사용자 확인·스킬의 제안·열린 결정을 구분해 사용자에게 현재 이해를 설명한다.
3. 구현을 바꿀 미결정 사항이 있을 때만 가장 중요한 질문 하나를 하고 답변을 기다린다. 문서 파일을 생성했다는 보고로 대화를 대신하지 않는다. 명확한 작은 요청에 의례적인 질문을 강제하지 않는다.
4. 사용자 답변을 반영해 시나리오·범위·제외 범위와 관찰 가능한 수용 기준을 보여준다. UI/Dev/Ops 영향 영역은 다중 선택하고 주 책임 하나를 정하되 팀 생성을 뜻하지 않는다.
5. 새 요청이면 기능 영역, 그 영역의 다음 번호, 읽기 좋은 제목을 정한 뒤 `crypto.randomUUID()` 기반 ID를 발급한다. `docs/work/<영역>/<최소 3자리 번호>-<작업명>/`에 `work.json`과 `spec.md`만 만들고 `docs/work/INDEX.md`에 제목·목적과 링크를 등록한다. 기존 요청은 UUID로 전체 작업 기록을 스캔해 발견한 실제 경로의 초안을 갱신한다. [템플릿](../../../docs/skills/templates/spec.md)의 대괄호를 실제 사실로 바꾸고, 제안이나 미검증 내용을 사용자 합의로 쓰지 않는다.
6. 명세 초안을 사용자와 확인하기 전에는 `draft`를 유지하고 구현·설계로 자동 진행하지 않는다. 이미 명시적으로 확정된 요청은 확인을 반복하지 않는다. 작은 수정은 짧은 절로 끝내고 불필요한 인터뷰나 설계 문서를 만들지 않는다.

## 출력 경로

`docs/work/<영역>/<번호>-<작업명>/work.json`, 같은 폴더의 `spec.md`, `docs/work/INDEX.md`.

## 허용 변경

위 두 작업 기록과 `docs/work/INDEX.md`의 해당 작업 항목, 사용자가 명시한 기존 작업 기록만 변경한다. 제품 소스, 브랜치, commit, push는 변경하지 않는다. 명세 작성은 제품 변경 승인이 아니다.

## 완료 조건

필수 기준·제외 범위·열린 결정이 정직하게 기록되고 사용자에게 설명됐다. 중요한 모호성이나 확인이 남으면 `draft`이며 명세 확정을 주장하지 않는다. 사용자 확인으로 구현을 바꿀 모호성이 해소된 경우에만 `ready`로 정리한다. 명세 확정은 제품 구현 승인이 아니다.

## 인계

설계가 필요하면 `www-design`, 명확한 승인 작업이면 `www-build`가 같은 작업 ID를 읽는다. 버그는 `www-diagnose`에 증상과 기존 작업 관계를 전달한다.
