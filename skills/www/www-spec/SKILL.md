# WWW 명세

## 호출 조건

사용자가 `www-spec`을 직접 호출하거나 `www-dev` 역할이 접수한 요청의 명세 단계로 선택할 때 실행한다. 역할 밖의 호출은 기존 명시 선택을 유지한다. 스킬 발견·호스트 로딩과 실제 수용 여부는 관측한 범위로 기록한다.

## 입력

사용자 목표, 관련 현행 기능 요구, 저장소의 현재 사실, 제약, 접수된 작업 ID와 권한의 근거(있는 경우).

## 진입 조건

요청 대상 저장소와 안전 규칙을 읽었고 실제 요청 또는 변경할 기존 명세가 있다.

## 절차

1. [공통 계약](../../../docs/skills/WORKFLOW.md), [모델·추론 노력 권고](../../../docs/skills/MODEL_POLICY.md), 적용할 [데스크톱 프로필](../../../docs/skills/profiles/desktop.md)을 읽는다.
2. 기존 기록과 구현을 먼저 읽고, 이미 확인된 목적이나 결정은 다시 질문하지 않는다. 사실·사용자 확인·스킬의 제안·열린 결정을 구분해 사용자에게 현재 이해를 설명한다.
3. 구현을 바꿀 미결정 사항이 있을 때만 가장 중요한 질문 하나를 하고 답변을 기다린다. 문서 파일을 생성했다는 보고로 대화를 대신하지 않는다. 명확한 작은 요청에 의례적인 질문을 강제하지 않는다.
4. 사용자 답변을 반영해 시나리오·범위·제외 범위와 관찰 가능한 수용 기준을 보여준다. UI/Dev/Ops 영향 영역은 다중 선택하고 주 책임 하나를 정하되 팀 생성을 뜻하지 않는다.
5. 역할 접수에서 확보한 UUID가 있으면 그 작업을 재사용한다. 없으면 관련 작업을 확인한 뒤 신규 접수 규칙으로 기능 영역·다음 번호·읽기 좋은 제목과 UUID를 만들고 최소 `work.json`, `spec.md`, 작업 목차 항목을 등록한다. 기존 schema1을 현재 역할로 이어갈 때는 공통 계약의 명시 연결로 원래 레코드·검증을 보존하고 같은 UUID의 현재 결과를 다시 확인한다. 수용 기준 정의·필수 여부는 `work.json.criteria`에만 두고 [템플릿](../../../docs/skills/templates/spec.md)에 기준 ID와 배경·시나리오를 연결한다. 제안이나 미검증 내용을 사용자 합의로 쓰지 않는다.
6. 구현을 바꿀 중요한 모호성이 남으면 `draft`로 기록하고 그 결정만 확인한다. 명확한 구현 요청의 범위와 권한이 있으면 명세 정리 후 필요한 설계·구현으로 이어간다. 명세만 요청했으면 그 범위에서 끝낸다. 이미 확인된 같은 결정을 반복 질문하거나 작은 수정에 불필요한 인터뷰·설계 문서를 만들지 않는다.

## 출력 경로

`docs/work/<영역>/<번호>-<작업명>/work.json`, 같은 폴더의 `spec.md`, `docs/work/INDEX.md`.

## 허용 변경

위 두 작업 기록과 `docs/work/INDEX.md`의 해당 작업 항목, 사용자가 명시한 기존 작업 기록만 변경한다. 제품 소스, 브랜치, commit, push는 변경하지 않는다. 명세 작성은 제품 변경 승인이 아니다.

## 완료 조건

필수 기준 정의가 작업 레코드에 있고 명세에는 배경·제외 범위·기준 ID·열린 결정이 기록됐다. 중요한 모호성이 남으면 `draft`, 해소됐으면 `ready`로 정리한다. 명세 작성은 새 구현 권한을 만들지 않으며 기존 명확한 구현 요청의 권한은 공통 계약에 따라 승계한다.

## 인계

설계가 필요하면 `www-design`, 명확한 승인 작업이면 `www-build`가 같은 작업 ID를 읽는다. 버그는 `www-diagnose`에 증상과 기존 작업 관계를 전달한다.
