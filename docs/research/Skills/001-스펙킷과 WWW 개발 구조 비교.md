# Spec Kit과 WWW 개발 구조 비교

확인일: 2026-11-16. 사용자 요청: `https://github.com/github/spec-kit.git`의 스펙·개발 생태계 관리 기능을 현재 WWW 구조와 비교한다.

이 문서는 정보 조사 결과다. 설치·제품 수정·개발 절차 변경은 수행하지 않았다. 정보 질문은 작업 등록을 의무화하지 않는 WWW 개발 역할 계약에 따라 신규 작업 UUID를 발급하지 않았다. 현행 명세나 작업 이력과 혼동하지 않도록 비교 자료를 `docs/research/Skills/`에 보존한다.

## 판단

Spec Kit은 명세 주도 개발 절차와 개발 방법론을 조합·배포하는 도구 모음을 제공한다. WWW는 개인용 AI 개발 작업 공간이며, 이를 개발하는 별도의 역할·스킬·작업·증거 관리 체계를 갖는다. 비교할 때 WWW 제품과 WWW 자체 개발 절차를 나누어야 한다.

WWW 개발 절차는 Spec Kit과 명세→설계→작업→구현이라는 골격을 공유한다. 읽은 계약·코드 기준으로 WWW는 권한의 근거, 작업 UUID, 증거의 현재 적용성, 독립 검토와 완료 판단을 더 세부적으로 명시한다. Spec Kit은 명세 품질 검토, 산출물 간 의미 정합성 분석, 재사용 가능한 방법론의 설치·조합·출처 조회가 더 명시적이다. 이는 범위와 구조의 비교이며 실행 신뢰성이나 품질의 우열을 실측한 결론은 아니다.

권고는 WWW의 정본과 증거 모델을 유지하고, Spec Kit의 구현 전 정합성 검토 및 개발 구성요소 조회 방식을 선택적으로 반영하는 것이다. 전면 교체의 필요성은 확인되지 않았다.

## 조사 기준과 한계

- Spec Kit `main`의 확인 SHA: `2ee2b1e8005905db05f5717300a469b3068b908f`. `git ls-remote`로 확인했다. 아래 GitHub 소스 링크는 이 SHA로 고정했다.
- WWW 기준 HEAD: `2ec109f06906426eac2819086e31d52c436b63e7`. 비교 대상은 미커밋 변경을 포함한 현재 작업 트리다. 특히 아키텍처·개발 안내·생성 구조 자료가 수정 중이므로 HEAD만으로 이번 관측을 재현할 수 없다.
- GitHub 연결 도구로 README와 주요 문서·템플릿을 읽고, 공식 웹 문서로 실행 흐름·정합성 분석·명세 변경·산출물 조회를 확인했다. 공식 웹 문서는 가변 페이지이며 고정 SHA 문서와 동일한 빌드라고 보장하지 않는다.
- Spec Kit 설치, CLI 실행, WWW 하네스·GUI·테스트 실행은 하지 않았다. 문서와 소스가 설명하는 계약을 비교했다. 호스트의 실제 수용이나 현재 테스트 통과를 확인한 것으로 쓰지 않는다.
- WWW에 어떤 기능이 없다는 표현은 읽은 역할·스킬·공통 계약·관련 모듈에서 동등한 전용 표면을 확인하지 못했다는 뜻이다. 모든 파일의 부재를 증명한 것은 아니다.
- 독립 provider 검토·최종 감사는 실행하지 않았다. 이 문서는 채택이 확정된 설계나 감사 통과 산출물이 아니다.

현재 README는 기능 개발 외에 버그 수정, 아이디어 평가, 자체 프로세스 구성을 독립 진입점으로 설명한다. SDD는 core, 버그 수정과 평가는 선택 설치하는 확장이다. [공식 README](https://github.com/github/spec-kit/blob/2ee2b1e8005905db05f5717300a469b3068b908f/README.md)

| 구성요소 | 관리 책임 | WWW 대응과 차이 |
|---|---|---|
| Constitution | 프로젝트의 원칙·제약 | `AGENTS.md`, 공통 작업 계약, 제품·구조 기준에 역할별로 분산. 한 파일로 합칠 필요는 없다. |
| Integration | 코딩 에이전트별 명령·스킬 연결 | 발견용 링크, Codex/GJC 어댑터와 대응. WWW 제품 Native 연결과 개발 하네스의 호스트 연결은 구분해야 한다. |
| Extension | 새 명령·품질 게이트·외부 서비스 연결 | `skills/www/`, 실행 어댑터·검토 core와 일부 대응. WWW 전용 소스 구조와 설치 가능한 독립 패키지는 다르다. |
| Preset | 기존 템플릿·명령·스크립트의 우선순위 있는 변경 | WWW 프로필·템플릿과 목적 일부 공유. 프로필이 자동 합성·우선순위 resolver라는 근거는 없다. |
| Workflow / Overlay / Step | 실행 순서·게이트·분기·재개, 기존 정의의 수정과 실행 동작 확장 | WWW 역할이 단계 의미를 판단하고 `route/run/record/work`가 실행 조건·상태를 관리. 동일한 YAML 조합 엔진으로 볼 수 없다. |
| Bundle / Catalog | 역할·팀별 구성 묶음의 배포와 검색 | WWW에는 정본 워크스페이스·스킬 발견 경로가 있다. 읽은 범위에서 WWW 자체의 동등한 범용 배포 카탈로그는 확인하지 못했다. |
| Artifact inventory | 명령·템플릿·스크립트·훅의 제공 계층과 선택 상태 조회 | WWW의 코드 지도·리소스 관측과 별개. ‘어느 설정이 최종 적용되는가’ 조회에 참고할 수 있다. |

## 명세부터 완료까지의 대응

| 단계 | Spec Kit | WWW 현행 | 비교 판단 |
|---|---|---|---|
| 요청 접수 | specify, bug, assess 등 목적별 진입 | `www-dev`가 정보 질문·변경·진단·검증을 분류 | WWW에는 요청 권한·기존 작업 연결 책임까지 명시돼 있다. |
| 명세 | specify, clarify | `www-spec`, `work.json.criteria`, `spec.md` | 목표·범위·기준은 공통. WWW는 기준 정의의 정본을 JSON에 둔다. |
| 명세 품질 | checklist | 중요한 모호성 확인, 정상·경계·오류 시나리오 | WWW에 관련 규칙은 있다. 전용 요구 품질 검토 표면은 덜 명시적이다. |
| 설계·작업 분해 | plan, tasks | `www-design`, `design.md`, 필요한 `tasks.md` | WWW는 최소 설계와 작은 요청의 간소화를 명시한다. |
| 구현 전 의미 정합성 | analyze | 요구 참조 검증·구조 계약·설계 검토 일부 | WWW의 형식·참조 검사와 ‘문서 간 의미 충돌 검사’는 다른 책임이다. |
| 구현 | implement | `www-build`, typed 하네스 | WWW는 허용 경로·소스 정책·타입·저작 검사 조건을 별도로 둔다. |
| 구현 누락 확인 | converge | verify, review, complete와 실패 시 build 복귀 | 기능은 겹치지만 완료 조건과 결과 저장 방식은 다르다. |
| 완료 판단 | 산출물 대비 수렴 후 후속 리뷰·PR | 현재 기준·증거·문서 영향 검토·필수 독립 검토를 결합 | Spec Kit의 수렴 결과를 WWW의 완료 증거로 바로 승격하면 안 된다. |

Spec Kit의 clarify/checklist/analyze는 선택 품질 게이트다. checklist는 요구가 명확하고 완전한지를 점검하며 코드 테스트 결과와 다르다. analyze는 명세·계획·작업의 충돌·누락을 읽기 전용으로 보고한다. converge는 구현을 산출물과 대조하며 남은 작업을 `tasks.md`에 추가할 수 있다. [명령 계약](https://github.github.io/spec-kit/reference/agentic-sdd.html), [analyze 원문](https://github.com/github/spec-kit/blob/2ee2b1e8005905db05f5717300a469b3068b908f/templates/commands/analyze.md)

## 명세의 수명과 정본

Spec Kit은 완료 뒤 산출물을 어떻게 보존할지 하나로 강제하지 않는다. 공식 문서는 Flow-back, Flow-forward, Living spec, Constitution-only를 팀이 선택하는 관례로 설명한다. Spec Kit 자체 저장소도 기능 산출물 전체를 장기 관리하는 예제는 아니다. [명세 보존 정책](https://github.com/github/spec-kit/blob/2ee2b1e8005905db05f5717300a469b3068b908f/docs/how-to/persisting-specs.md)

WWW는 이미 아래 사실을 나눈다.

- 현행 의도: `docs/specs/`의 기능 명세.
- 이번 변경 목표·결정: `docs/work/`의 작업 명세와 설계.
- 기준 정의·결과·권한·연결: 작업 `work.json`.
- 실제 동작의 근거: 대상 소스에 연결한 검증 시도와 검토.
- 구조 책임: `docs/architecture/structure.json`과 architecture 요구 catalog.

따라서 WWW를 네 모델 중 하나와 완전히 동일하다고 분류하기 어렵다. ‘유지되는 현행 계약과 작업별 변경 이력을 함께 보존하는 방식’이라고 설명하는 것이 정확하다. 작업의 과거 결정을 의례적으로 최신화하지 않는 규율도 있다. [정보별 정본](../../skills/WORKFLOW.md#현행-기준과-정보별-정본)

Spec Kit core도 변경된 문서 사이의 차이를 자동으로 모두 화해시키지 않는다. analyze는 발견을 보고하고, converge는 남은 구현 작업을 추가한다. 합의된 의도와 문서를 고치는 책임은 별도로 남는다. [명세 진화 안내](https://github.github.io/spec-kit/how-to/evolving-specs.html)

## WWW에서 보존할 기반

1. **업무 식별과 권한:** `work.ts`와 `route.ts`는 작업 UUID, 요청 해시, 직접 요청에서 받은 권한과 단계를 연결한다. 단계 선택을 새 권한으로 보지 않는 규칙을 유지한다.
2. **증거의 현재성:** `evidence.ts`는 소스·기준·환경·결과를 연결하고 `evaluateEvidence`로 적용성을 평가한다. 문서 검토도 관련 지문이 바뀌면 재판단한다.
3. **독립 검토와 완료:** `work.ts`의 `assessRecord`는 필수 기준별 증거, 문서 검토, 정책에 맞는 검토를 확인한다. 코드 존재를 실제 호스트 수용으로 보지 않는 한계도 유지한다.
4. **구조 추적과 지도:** 안정 구조·요구 ID, `@architecture`·`@implements`·`@verifies`, 실제 import와 생성 snapshot은 코드 구조를 추적한다. 선언의 존재와 실행 통과는 구분한다.

근거: [작업 core](../../../scripts/workflow/work.ts), [경로·권한](../../../scripts/workflow/route.ts), [증거](../../../scripts/workflow/evidence.ts), [문서 영향](../../../scripts/workflow/documentation.ts), [검토 core](../../../scripts/workflow/review.ts), [코드 설계도](../../CODE_BLUEPRINT.md).

최종 감사 모델은 전역 규칙의 Opus 고정과 저장소 검토 정책의 fallback 선언에 차이가 있다. 이번 조사에서 실행하거나 충돌을 해결하지 않았다. 정책 선언을 독립 감사 수행 증거로 취급하지 않는다.

## 우선 반영할 제안

| 순서 | 제안 | 구체적 결과와 통과 기준 |
|---|---|---|
| 1 | 구현 전 명세·설계·작업 정합성 검토 | 요구별 구현 작업 연결, 근거 없는 작업, 충돌한 용어·동작, 미결정 사항을 위치와 함께 보고한다. 자동 문서 수정이나 자기 승인 없이 소유 문서에서 해소한다. |
| 2 | 명세 품질 검토 항목 보강 | 큰 기능에는 우선순위 있는 사용자 여정, 독립 검증 방법, 경계·실패, 관측 가능한 성공 기준을 확인한다. 정의는 `work.json.criteria`에 유지하고 문서에 중복 정본을 만들지 않는다. |
| 3 | 개발 구성요소의 출처·적용 상태 조회 | 역할·스킬·프로필·정책의 정본 경로, 내용 식별, 발견 경로, 충돌·우선순위, 실제 읽기·호출·호스트 수용 증거를 구분해 보여 준다. |
| 4 | 다른 프로젝트 배포 필요가 확인될 때 구성 묶음 도입 | 기능 추가·규칙 변경·실행 순서·배포 묶음을 분리한다. 한 저장소 안의 폴더 이동만으로 범용 패키지 시스템을 먼저 만들지는 않는다. |

두 번째 제안의 참고 원문은 우선순위별 독립 검증 여정, 수용 시나리오, 기능 요구, 측정 가능한 성공 기준과 가정을 분리한다. WWW 템플릿은 기준 ID와 정상·경계·오류 시나리오를 이미 요구하므로 부족한 관점만 보강할 수 있다. [Spec Kit 명세 템플릿](https://github.com/github/spec-kit/blob/2ee2b1e8005905db05f5717300a469b3068b908f/templates/spec-template.md)

세 번째 제안은 `specify artifact`의 계층·제공 출처·선택 상태 조회를 참고한다. 그 명령도 선택 상태가 내용의 유효성이나 실행 성공을 보장하지 않는다고 명시한다. WWW 코드 의존 지도와 별개인 개발 도구 구성 조회 책임이다. [Artifact inventory](https://github.github.io/spec-kit/overview/artifacts.html)

Spec Kit Workflow는 YAML로 명령·프롬프트·shell·게이트·제어 흐름을 연결하고 실행 ID와 상태를 보존한다. 단순히 프롬프트 파일만 제공하는 도구로 비교하면 이 부분을 놓친다. 다만 체크포인트 전 부수효과가 반복될 수 있다는 한계가 있어, WWW의 권한·증거 체계와 같다고 가정해서는 안 된다. [Workflow](https://github.github.io/spec-kit/workflows/overview.html)

## 후속 설계에서 확인할 결정

현재 요청은 비교이므로 다음을 채택된 요구로 기록하지 않는다.

- 명세 정합성 검토를 기존 `www-design` 인계 조건으로 넣을지, 별도 선택 절차로 둘지.
- 요구→작업 연결을 명시 ID로 관리할지, 읽기 전용 분석이 추론해서 보고할지.
- 출처 조회가 WWW 자체 도구만 다룰지, 선택한 외부 저장소의 개발 구성도 다룰지.
- 실제 Spec Kit 재사용을 검토한다면 WWW 정본을 입력으로 연결할지, 격리된 다른 프로젝트에서 먼저 평가할지.

판별 실험은 같은 작은 기능에 대해 현행 WWW 방식과 ‘구현 전 정합성 검토 추가’ 방식을 비교하는 것이다. 검출한 실제 누락·오탐·추가 시간·기록 중복을 측정한다. 이번 조사에서는 이 실험을 실행하지 않았다.
