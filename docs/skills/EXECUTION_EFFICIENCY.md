# 개발 실행의 문맥과 완료 단위

이 문서는 개발 운영 절차다. 승인·수용 기준·증거의 유효성·필수 검토·완료 판정은 기존 공통 계약과 현재 사용자 지침을 유지한다. 여기의 예산은 운영 중 점검 기준이며 실행기의 토큰 차단 기능이 아니다.

## 작업을 닫는 순서

1. 현재 실행의 위치·요청·소유 파일·미완료 UUID·다음 행동을 짧게 확인한다. 같은 대상을 조사한 기록은 필요한 부분만 읽고 원문 위치와 hash를 보존한다. 전체 원장·누적 HTML·도구 출력 전문을 매번 문맥에 넣지 않는다.
2. [woo-issue](../../skills/www/woo-issue/SKILL.md)로 GitHub 백로그에서 연관된 이슈를 세션당 최대 다섯 개 고른다. 각 이슈는 별도 worktree에서 구현하고 해당 동작의 집중 검사를 거쳐 PR을 연다. 공용 변경에는 한 담당자를 지정하고 소비 PR에 선행 관계를 표시한다.
3. 모델 감사 전에 기준별 실제 명령·평탄한 argv·허용 범위·실제로 검사하는 assertion을 확인한다. 첨부 파일이나 일반 정적 검사를 수행하지 않은 의미 검사의 통과로 연결하지 않는다. 연결 불가능은 정확한 blocker로 남기고 같은 실패의 감사 호출을 반복하지 않는다.
4. 참여 PR이 모두 준비되면 기준 main과 각 head, 적용 순서, 결합 트리를 기록한다. 결합 후보에서 공통 통합 검사·실기·필수 감사를 진행한다. 실패는 소유 PR에서 수정하고 새 결합 후보에서 실패 검사와 영향받는 소비 기준을 검사한다. 기존 core가 근거를 현재에도 수용하면 연결하고, 영향 범위나 환경이 불확실하면 해당 범위 전체를 검사한다. 병합 직전 후보가 달라지면 변경분을 다시 평가한다. 독립 배포가 어려운 변경은 통합 PR로 함께 병합한다.
5. Sonnet 읽기 전용 교차검증은 최종 감사 전에 지적을 회수하는 보조 절차다. 현재 지침이 요구하는 최종 Opus 및 공식 core를 대체하지 않는다. UUID별 필수 감사가 필요하면 유지하며 다른 UUID의 PASS를 복사하지 않는다. Opus가 불가하면 낮은 모델로 자동 대체하지 않고 미실행으로 남긴다.
6. 현재 증거가 수용되면 문서 영향·저작 보고서·앱 읽기·공식 완료·재조회를 같은 작업군에서 끝낸다. 게시에는 별도 기존 권한이 필요하다.

## 작업별 worktree와 병합 검증

- 작업별 브랜치가 승인된 경우 최신 원격 기본 브랜치를 기준으로 별도 worktree를 만든다. 같은 작업 UUID의 원장은 한 브랜치에서만 갱신한다. 번호와 목차가 충돌하면 실제 작업 UUID와 검증 이력을 보존하며 통합 담당자가 해소한다.
- 공통 코드에는 소유 PR을 하나 지정한다. 다른 PR은 선행 PR을 명시하고, 선행 변경이 병합된 뒤 최신 기본 브랜치에서 통합 검증한다. worktree마다 검증 산출물, 설치 의존성, 임시 앱 프로필을 분리하고 공용 경로를 쓰는 검사는 동시에 실행하지 않는다.
- 로컬 작업 증거는 검사한 파일과 조건에 귀속된다. PR 병합 증거는 원격 기본 SHA, PR head SHA, 결합 Git 트리와 해당 트리의 검사 결과에 귀속된다. 한쪽 결과를 다른 쪽의 통과로 쓰지 않는다. CI의 `WWW_VERIFIED_TREE`가 실제 점검한 커밋과 트리를 기록한다.
- GitHub merge queue를 사용하는 경우 `merge_group`에서 결합 후보를 검사한다. 큐가 없으면 통합 담당자가 PR을 한 건씩 처리하며 최신 기본 SHA와 PR head에서 만든 결합 트리를 CI 기록과 대조한다. 병합 직전에 두 SHA를 다시 확인하고 head를 고정해 병합한다. 기본 SHA는 이 방법으로 원자적으로 고정되지 않으므로 병합 직후 원격 결과의 트리도 대조한다. 차이가 생기면 실제 병합 결과를 검사하고 다음 병합을 보류한다.
- 검증에 첨부하는 원문은 명령 실행 전부터 있어야 하며 실행 중 바뀌지 않아야 한다. 검사 명령이 새로 생성하는 로그는 실행 후 고정한 사본으로 보관한다. 명령 종료, 소스·환경·첨부 자료의 안정성, 현재 기준 적용 가능성을 구분해 기록하고, 증거가 바뀐 경우 실패한 경계를 먼저 확인한다.

## PR 집중 검사와 결합 후보의 전체 검사

세션 선정 도구를 운영하는 담당자는 최초 작업 선정 시 저장소 소유자 계정으로 상위 GitHub 이슈에 새 코멘트 하나를 남긴다. 사람이 읽는 선정 이유·범위 뒤에 고유한 양의 이슈 번호를 최대 다섯 개까지 한 줄로 적는다. 예를 들어 `<!-- www-session-v1: 25,26,27 -->`이다. 작업 도구는 코멘트 URL 끝의 숫자를 사용해 `codex/session-<코멘트 ID>/issue-<이슈 번호>-<이름>` 브랜치로 worktree를 만들고 같은 저장소의 main을 향해 draft PR을 연다. 이름은 영문 소문자·숫자·하이픈이다. CI가 같은 저장소 API로 해당 코멘트를 조회해 작성자 관계 OWNER·표식·참여 이슈를 대조한다. API 실패·다른 작성자·누락·중복 표식은 전체 검사로 승격한다. 이슈 원문 편집이나 PR별 라벨 작업은 필요하지 않다.

일반 개별 PR과 세션 초안 모두 PR #33처럼 보관 중인 한국어 스킬 문서와 그 파일들의 현재 바이트 수·해시, 같은 작업의 검증 기록에 덧붙인 서술만 바뀐 경우에는 기본 브랜치에 있는 `scripts/pr-verification.ts`가 집중 검사를 선택한다. 보관 목록의 원문 식별·라이선스·경로·언어, 평문 설명 이외의 스킬 메타데이터, 파일 추가·삭제·모드, 기존 검증 서술 또는 다른 파일이 바뀌면 전체 검사를 선택한다.

앱 초안의 첫 적용 범위는 `src/input.ts`, `chat-composer.tsx`, `chat-status.ts`, `command-preview.ts`, `command-card.tsx`의 기존 일반 파일 수정과 동반된 `src/architecture.generated.json`이다. 기본 브랜치 판정기가 부모와 양쪽 diff의 blob을 대조하고 해당 소스에 연결된 기존 Bun 테스트를 합집합으로 고른다. macOS에서 타입 검사, 빌드 전 구조 지도 현재성 검사, 앱 빌드, 선택된 테스트를 실행하고 깨끗한 후보 checkout을 앞뒤로 확인한다. 집중 결과는 `세션 초안 앱 검사`와 `WWW_PR_DRAFT_APP_TREE`로 기록한다. 테스트·설치·CI·하네스·공용 파일·기타 소스·새 파일·삭제·모드 변경이 섞이거나 지도가 단독으로 바뀌면 전체 검사로 승격된다.

일반 앱 PR은 전체 검사를 받고, 일반 번역 PR은 기존 #38의 콘텐츠 증명이 성립할 때 집중 검사를 받는다. 세션 등록은 앱 집중 검사의 선행조건이다. 초안을 ready로 전환하는 이벤트는 내용에 관계없이 같은 SHA에서 전체 검사를 시작한다.

여러 작업을 모아 게시할 때는 `codex/integrate-<이름>` 브랜치를 사용한다. `integrate`, `integration`, `batch`로 시작하는 경로 요소를 예약하고, PR 전용 커밋 범위에 merge commit이 있어도 전체로 승격한다. 순차 cherry-pick이나 squash만 있는 브랜치의 작업 목적은 Git 그래프로 식별할 수 없으므로 예약 브랜치를 쓰거나 명시적으로 결합 SHA를 dispatch한다. merge_group, 수동 결합 검사와 main push는 변경 파일과 관계없이 전체 검사를 실행한다.

집중 검사는 스킬 보관소 전체의 출처·경로·해시, 검사기 회귀, 작업 원장과 문서 링크를 확인한다. 평문 설명이 스킬 선택에 줄 영향과 문장별 번역 의미는 해당 이슈의 독립 검토에서 판정한다. 성공한 `WWW_PR_FOCUSED_TREE`에는 base·PR head·실제 후보 트리와 판정기·검사 명령·런타임을 포함한 지문이 남는다. 체크아웃이 달라지면 같은 결과를 현재 증거로 사용할 수 없다.

병합 담당자는 최신 결합 후보의 전체 검사에서 나온 `WWW_VERIFIED_TREE`와 실제 병합 트리를 대조한다. `merge_group`은 자동으로 전체 검사를 실행한다. 병합 큐를 쓰지 않으면 결합 커밋을 원격에서 조회할 수 있는 상태로 만든 뒤 `gh workflow run ci.yml --ref main -f candidate_sha=<결합 커밋 SHA>`로 그 후보를 검사한다. 수동 후보의 부모는 같은 결과에 기록된 `WWW_VERIFIED_PARENTS`에서 확인한다. 이 저장소의 보호 규칙이 요구하는 필수 검사와 병합 큐는 2026-11-24 조회 시 설정돼 있지 않았다. 병합 담당자는 개별 PR 집중 검사 성공과 관계없이 결합 트리에 전체 검사 결과가 있는지 확인한다.

## 모델과 호출

Sol은 상태·권한·통합 판단, Terra는 일상 조사·검증, Luna는 목록·축자 수집을 맡는다. 모델 하나로 끝낼 수 있는 단위를 의무 분할하지 않는다. 단순 목록을 Sol이나 Astra에 반복 위임하지 않는다. 독립 검토자는 소스를 수정하지 않는다.

새 위임 전에 대상·선정 이유·소유 및 제외 파일·선행 결과·실제 명령·종료 조건·결과 경로를 제공한다. `fork_turns: none`으로 필요한 사실만 전달하며 같은 저장소의 이웃 작업자를 알린다. 이미 실행 중이거나 완료된 같은 목적의 담당자가 있으면 새로 생성하지 않는다. 결과 전문은 파일에 저장하고 주 문맥에는 판정과 3~5줄만 회수한다.

최초 개선 실험은 작성자 1명과 필요할 때 독립 읽기/검증 담당 1명 이내로 운영한다. 이는 보편적인 동시성 최적값이나 OS 강제가 아니다. 단일 작업군의 독립 검사를 병렬 실행하는 것은 허용한다. 감사·실제 모델 검사도 비용에 포함하고 불합격을 모델 교체로 해결하지 않는다.

## 문맥 교체와 실행 보존

오래된 세션의 반복 입력이 커지면 작은 인계로 새 세션을 시작할 수 있다. 자동 주기 재시작은 하지 않는다.

- 인계에는 원문 요청, Task UUID, 정확한 경로, 현재 소스 SHA 목록, 다음 행동, 허용 명령과 금지 범위, 남은 실패, 증거 위치를 연결한다. 본문은 8KiB 이내를 목표로 하되 필수 사실을 버리지 않는다. 필수 지침은 경로와 hash로 연결하고 필요한 지침은 읽는다.
- 기존 세션에 실행 중인 저작·검사 명령이 없고, 작업 잠금이 없고, 원장 쓰기가 2분 이상 안정됐으며 다른 제품 writer가 없는지 확인한다. 실행 보조 host 프로세스는 실제 저작·검사 프로세스와 구분한다.
- 위 선행조건의 실제 관측 시각·진행 중 명령 목록·잠금 목록·마지막 원장 쓰기 시각·대상 PID와 자식 목록을 종료 전에 원시 영수증으로 보존한다. 종료 뒤의 SHA 일치만으로 종료 전 안전 조건까지 입증했다고 쓰지 않는다.
- Git 상태·diff·현재 기술 파일 SHA·원장과 요청 파일을 checkpoint한다. 종료 가능한 안전 경계에서 기존 CLI에 SIGINT를 보내고 정상 종료를 확인한다. 강제 kill, 살아 있는 잠금 삭제, 원장/소스 롤백으로 넘기지 않는다. 종료되지 않으면 새 writer를 시작하지 않고 차단을 보고한다.
- 종료 뒤 기존 PID·자식·고아 프로세스, Task JSON 파싱, 잠금, checkpoint 대비 기술 파일·원장 SHA를 확인한다. 예기치 않은 차이는 조사 전까지 새 writer의 차단이다. 새 세션은 이전 thread를 resume하지 않고 인계를 실제 상태와 대조한 뒤 실행한다.
- 새 세션에 알려지지 않은 이전 에이전트를 재호출하지 않는다. 최초 위임 전 가용성·동일 담당 여부를 확인하며 한도 오류를 반복 재시도하지 않는다.

## 예산과 재실행

작업군 시작에 입력·캐시 입력·출력·요청 모델·위임·검토 호출·완료 UUID의 baseline을 남긴다. reasoning이 출력에 포함되면 더하지 않는다. 세션 누적 차이를 모든 provider 청구 총액으로 표시하지 않는다.

20분 경과, 같은 원인 실패 2회, 위임 2회, 마지막 입력 60,000토큰 중 하나를 관측하면 다음 안전 경계에서 점검한다. 필수 검사를 중간에 끊거나 입력을 임의로 잘라 통과시키지 않는다. 실행기의 실제 지원이 확인되지 않은 한도는 hard limit으로 주장하지 않는다. 계속할 근거·추가 필요한 범위·완료 또는 blocker를 checkpoint하고 이유 없는 동일 재호출은 하지 않는다.

검증 재사용은 공식 core가 현재 source·criteria·환경·명령·artifact 동일성을 수용할 때만 한다. 비교 불가 또는 stale은 재사용 불가다. 동일 실패의 진단 로그 회수와 기능 재검증은 구분하며, 전체 검사는 관련 기술 변경 뒤 필요한 시점에 실행한다. 보고서 작성만으로 변한 전체 기록의 일관성 검사는 기능 테스트 전체 재실행과 구분한다.

운영 상태는 `계획됨`, `인계됨`, `적용 관측`, `작업군 완료`, `차단`을 구분한다. 새 PID나 인계 파일의 존재는 Task 완료가 아니다. 절감률은 같은 수용 조건을 지킨 전후 실측이 있을 때만 보고한다.

## 실행·대기 시간 재생

검증·검토 요청이 공식 실행기에 접수되면 `.www/evidence/workflow-timing/`에 요청별 NDJSON을 남긴다. 작업 UUID·요청 해시와 시도 ID로 검증 원장에 연결한다. 실제 프로세스의 시작·종료, 주입된 검사, 검증 세션 큐, 원장 잠금 재시도, 결과 등록 및 회수를 구분한다. 검토 제공자가 확인한 할당량 소진은 발생 사건으로 기록한다. 재개할 때까지의 대기 시간은 직접 측정한 구간에서만 합산한다.

`node scripts/replay-workflow-timing.ts 시작시각 종료시각 .www/evidence/workflow-timing`으로 재생한다. 두 시각에는 시간대를 포함하고, 다른 worktree의 계측 디렉터리와 과거 작업의 `work.json`을 인자로 더할 수 있다. `coveredMs`는 조회 구간에서 겹친 관측을 한 번만 센 시간이며 `unmeasuredMs`는 남은 시간이다. `phaseMs`의 각 값은 같은 단계의 겹침을 제거한다. 여러 단계가 병렬이면 단계별 값의 합이 전체보다 클 수 있다. `processStarts`는 운영체제가 프로세스 생성을 확인한 횟수다. 옛 원장의 시작·종료로 알 수 있는 것은 당시 시도의 전체 구간이다. 도중에 끊긴 기록은 마지막으로 관측한 사건까지만 반영한다.

### Chat/007 AC-11 화면 관찰

`bun scripts/verification/chat007-monitor.ts`는 현재 소스를 빌드하고 실제 Electron의 채팅 탭을 연다. 기본 사이드바에서 보이는 이름과 설명을 읽고, 합성 요청·문서 읽기·읽기 명령을 전달한 뒤 상세 모니터로 이동한다. 역할·스킬 여덟 행을 펼쳐 이름·설명·경로·상태와 실제 적용 확인 안내를 비교한다. 원장은 실제 출력값, 표준 출력 지문, 사용한 명령·인자와 소스 입력을 보존한다.

다른 테스트나 빌드 시 재생성되는 구조 지도만 바뀌면 이 근거를 재사용한다. 소스·스타일·개발 도구·검증용 Native fixture·정본 정의·패키지 잠금·기준 정의가 바뀌면 재검사한다. 빌드의 실제 모듈 목록에서 등록하지 않은 입력, 외부 모듈, 동적 모듈 경로를 발견하면 실행이 실패한다. 이 기준에서 전용 관찰이 없는 과거 기록과 다른 명령은 미확인으로 처리한다. 현재 판정은 같은 실행 호스트와 잠금 파일에 맞게 설치한 의존성을 전제로 한다.
