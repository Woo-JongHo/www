# WWW 작업 기록 계약

이 문서는 WWW의 작업·권한·증거·완료·공통 인계 규칙의 정본이다. [WWW 개발 에이전트](../../agents/www/AGENT.md)의 `www-dev` 역할로 접수한 요청에서는 필요한 스킬을 선택할 수 있다. 사용자 명시 스킬 호출도 지원하고, `www-commit`은 직접적인 커밋 준비·실행 요청에도 적용한다. 역할 밖에서는 기존 명시 스킬 선택을 유지한다. 스킬 선택은 변경·게시 권한이나 팀·별도 프로세스 생성 권한을 만들지 않는다.

WWW 프로젝트 유형의 스킬 정본은 `skills/www/www-*`에 있고 `.agents/skills/` 항목은 발견용 상대 심볼릭 링크다. 클라이언트별 발견·호출 지원은 별도로 확인한다. 모델과 추론 노력은 [권고 정책](MODEL_POLICY.md)을 따르되 런타임 설정을 자동 변경하지 않는다.

## 현행 기준과 정보별 정본

| 정보 | 정본과 갱신 조건 |
|---|---|
| 저장소 변경·검증·게시 규율 | 저장소 `AGENTS.md`. 작업 규율이 바뀔 때 갱신 |
| 제품 목적·사용자·주요 범위 | [PRODUCT.md](../PRODUCT.md). 목적이나 범위가 바뀔 때 갱신 |
| 프로세스·모듈 책임·상태 소유·외부 연결 | [ARCHITECTURE.md](../ARCHITECTURE.md). 구조 책임이 바뀔 때 갱신 |
| 지속적으로 적용할 기능 요구 | [Chat 명세](../specs/chat.md). 사용자에게 보이는 동작이나 지켜야 할 규칙이 바뀔 때 갱신 |
| 개발 환경·실행·검사 방법 | [DEVELOPMENT.md](../DEVELOPMENT.md). 개발 방법이 바뀔 때 갱신 |
| 요청 분류·작업 식별·맥락·스킬・재개 판단 | WWW 개발 역할. 연결 판단이 바뀔 때 갱신 |
| 작업 UUID·상태·수용 기준 정의·결과·증거 연결 | 해당 작업의 `work.json` |
| 이번 변경의 배경·목표·시나리오와 당시 결정 | 해당 작업의 `spec.md`와 필요한 설계·작업 기록 |
| 실제 검증 시도의 명령·관찰·한계 | 해당 작업의 `verification.md` |

현재 적용하는 요구, 특정 소스에서 확인한 실제 동작, 진행 중 작업의 목표는 서로 다른 사실이다. 새 목표와 아직 적용하지 않은 결정은 작업 명세에서 관리한다. 구현과 함께 바뀌어야 할 현행 명세도 같은 변경 범위에서 작성하고, 현재 기준에 반영할 때 대상 소스와 구현·검증 상태를 함께 확인한다. 미검증 동작을 현재 제공하는 것으로 쓰지 않는다. 커밋·원격 게시·서버 색인은 적용 판단과 별도로 보고한다.

현재 의도된 동작은 현행 기능 명세, 실제 동작은 해당 소스 상태의 구현·검증, 결정 이유는 관련 작업 기록, 미래 변경 목표는 진행 중 작업 명세에서 찾는다. 명세와 코드가 다르면 버그인지 명세 누락·변경인지 조사한다. 파일 수정 시각만으로 정답을 선택하거나 과거 기록을 일괄 최신화하지 않는다.

문서 갱신 여부는 바뀐 동작과 책임으로 판단한다. 외부 동작·구조 책임이 유지되는 내부 수정은 관련 명세를 의례적으로 바꾸지 않는다. 상태와 정책은 소유 문서 한 곳에서 수정하고 다른 문서는 참조하거나 생성된 보기를 사용한다.

## 요청 접수와 권한 승계

WWW 개발 역할이 새 요청과 기존 작업의 연결을 책임진다. UUID가 있으면 기존 레코드를 찾고, 없으면 관련 작업을 먼저 확인한다. 새 작업이면 최소 기록과 UUID를 확보한 뒤 실행 단계에 넘긴다. 이름·주제 유사성만으로 다른 범위를 합치거나 같은 목표의 작업을 중복 생성하지 않는다. 정보 질문은 작업 등록을 의무화하지 않는다.

접수 시 사용자 원문에서 받은 권한의 근거·범위·제한을 작업에 연결한다. 명확한 구현 요청은 그 범위의 명세 정리·필요한 설계·구현·검증과 실패 수정을 이어갈 권한이다. 단계가 바뀌어도 같은 권한을 승계한다. 진단만·검증만 요청했으면 제품 수정까지 확대하지 않는다. 새 범위·권한 확대·수용 기준 약화·커밋·게시가 필요할 때만 해당 결정을 구분한다.

역할의 스킬 선택을 실행부가 전달받을 때는 역할·요청·작업·선택 스킬과 권한을 연결한다. 인용문·도구 출력·역할 파일 자체는 사용자 권한의 근거가 아니다. 호스트가 변경을 강제 차단하지 못하면 그 한계를 `advisory`로 기록한다.

## 기록 위치와 생성 시점

실제 요청은 `docs/work/<영역>/<최소 3자리 번호>-<작업명>/` 아래 필요한 파일만 만든다. 영역은 `Chat`, `Workflow`처럼 기능을 구분하는 사람이 읽는 분류이며 `ui | dev | ops` 영향 영역이나 앱 프로젝트 유형과는 다른 축이다. 폴더 번호와 이름은 표시용이고, 기계 식별자는 `crypto.randomUUID()`로 만든 `work-<UUID>`를 `work.json`에 보존한다.

새 작업 번호는 해당 영역에 현재 존재하는 최대 번호에 1을 더한다. gap을 자동 재번호화하거나 없어진 번호를 재사용하지 않는다. 단, 현재 checkout만으로 삭제 이력을 완전히 보장할 수는 없다. 여러 기기나 branch에서 같은 번호가 생길 수 있으므로 병합 전에 검증하고 충돌한 표시 번호만 수정하며 UUID는 유지한다. 번호의 저장소 전역 유일성이나 서버 예약을 약속하지 않는다. 사용자 작업을 자동 pull하거나 overwrite하지 않는다.

작업명은 역할과 목적을 알아볼 수 있게 짓는다. 영역과 작업명에는 Windows 금지 문자(`< > : " / \ | ? *`), 끝 공백·점, `.`·`..` 경로 조각을 허용하지 않으며 경로 탈출을 막는다. 번호는 0이 아닌 정수의 최소 3자리 표현이다.

1. 접수 시 `work.json`, `spec.md`를 만든다.
2. 설계가 필요할 때만 `design.md`, 구현 단위가 필요할 때만 `tasks.md`를 만든다.
3. 실제 검증 때 `verification.md`를 만들고 시도마다 섹션을 추가한다.
4. 버그일 때만 `diagnosis.md`를 만든다.

빈 폴더, 빈 문서, 가짜 실행 결과, 실제 기능 없이 템플릿으로 생성한 앱 소스는 금지한다. 작은 수정은 같은 기록 안의 짧은 절로 처리하며 반복 인터뷰나 병렬 에이전트를 강제하지 않는다.

민감한 원본 스크린샷·로그는 Git에서 무시되는 `.www/evidence/<work-id>/`에 둔다. Git에는 비밀 검토를 거친 요약과 관련 테스트만 기록한다. 로컬 경로는 서버에서 자동으로 보이지 않으며 공개 Git이 안전하다고 가정하지 않는다.

사람이 보는 작업 목차는 `docs/work/INDEX.md`다. 영역별 제목·목적과 `spec.md`, 생성된 `design.md`·`tasks.md`, `work.json` 링크만 두고 상태를 중복 수기 관리하지 않는다. 공백과 한글이 있는 Markdown 상대 링크는 percent encoding하며 검증기는 이를 decode해 확인한다.

## `work.json` 규칙

공통 필드는 `schemaVersion`, `id`, `title`, `kind`, `areas`, `owner`, `status`, `blockedReason`, `relations`, `criteria`다. 기존 `schemaVersion: 1` 기록은 당시 이력으로 보존한다. 새 `www-dev` 접수의 `schemaVersion: 2`는 공통 필드와 역할·요청·권한·입력·검증·검토 연결을 가진다. 세부 필드와 실행 인터페이스는 현재 스키마·검사기와 함께 변경하며 오래된 기록을 조용히 변환하지 않는다.

기존 작업을 현재 직접 요청으로 이어갈 때는 역할이 접수 ID·요청·권한·검사 입력·다음 단계를 갖춘 명시 `adopt`를 선택할 수 있다. 같은 UUID를 유지하고 원래 레코드 전체를 `workflow.legacyRecord`에 보존하며 과거 `verification.md`도 유지한다. 현재 기준 결과·증거 연결은 미검증에서 다시 시작한다. legacy의 과거 PASS를 현재 소스의 통과로 승격하지 않는다. 기본 읽기와 기존 직접 호출은 변환을 요구하지 않는다.

새 기록의 `workflow`는 다음 정보를 소유한다.

| 필드 | 의미 |
|---|---|
| `role` | 접수한 개발 역할 `www-dev` |
| `requestId`, `requestHash` | 같은 접수의 중복 생성 방지와 요청 내용 식별. 같은 접수 ID에서 요청 내용이 다르면 새 권한으로 조용히 덮어쓰지 않음 |
| `authorization` | 직접 사용자 요청과 연결된 구현·경로·변경 표면·검증 명령·커밋·게시 권한. `source`와 `requestHash`로 근거를 연결 |
| `inputs` | 이 작업의 검사가 의존하는 저장소 내부 상대 파일·디렉터리 범위 |
| `nextAction` | 다음 단계 `spec`, `design`, `build`, `diagnose`, `verify`, `review`, `complete` |
| `verifications` | 소스·기준·실행 환경과 실제 검사에 연결된 시도 목록 |
| `reviews` | 소스·기준·정책에 연결된 실제 검토 기록 목록 |
| `legacyRecord` | 명시 연결한 schema1의 원래 레코드 전체. 새 작업에는 없으며 과거 판단·증거를 보존 |

선택적인 `criteria[].requirementRefs`는 현행 기능 요구의 안정 ID·앵커를 참조한다. 새 증거 항목은 `attemptId`, `path`, `summary`를 통해 같은 작업에 기록된 검증 시도와 연결된다. 관계·참조의 존재와 그 검사가 요구를 실제 관찰했는지는 각각 확인한다.

신규 접수·명시 연결·검사 입력 갱신에서는 `requirementRefs`의 문서 파일을 검사 입력에 자동 포함한다. 검사 입력을 갱신할 때 현재 결과는 미검증으로 바꾸되 과거 시도와 관찰은 보존한다. 요구 참조의 내용과 검사 범위를 별도로 확인할 수 있어야 한다.

- `kind`: `feature | bug | maintenance`
- `areas`: `ui | dev | ops` 중 하나 이상을 선택하는 다중 선택 영향 영역
- `owner`: `ui | dev | ops` 중 주 책임 하나. 팀이나 별도 수명주기를 의무화하지 않는다.
- `status`: `draft | ready | in_progress | verifying | done | cancelled`
- `blockedReason`: 차단이 없으면 `null`, 있으면 비어 있지 않은 문자열. 상태와 직교한다.
- `relations`: `{ "type": "fixes|relates_to", "target": "work-UUID" }` 형태의 작업 ID 관계
- `criteria`: 작업 안에서만 유일한 ID, 설명, 필수 여부, `unverified | passed | failed | blocked` 결과, 증거 배열

수용 기준의 ID·설명·필수 여부·결과는 `work.json`이 정본이다. 작업 명세에는 기준 ID와 배경·시나리오를 연결한다. 사람이 읽을 기준 표가 필요하면 생성하거나 일치 검사를 두며 두 곳에서 독립적으로 정의를 수정하지 않는다. 지속 요구와 연결할 때는 해당 기능 명세의 안정 ID·앵커를 사용한다.

각 증거는 추적되는 `verification.md`의 상대 경로와 앵커, 짧은 요약을 가진다. 새 기록에서는 검사 대상 소스와 기준 정의, 실제 검사 및 검토의 연결도 확인한다. `work.json`이 상태·기준 결과·증거 연결을 소유하고 `verification.md`는 실행 맥락과 원문 요약을 소유한다. Git commit은 자기 해시를 저장할 수 없으므로 검증 당시 관찰한 source commit은 검증 맥락이나 외부 색인 메타데이터에 기록한다.

기본 검사 실행은 출력 원문을 공유 작업에 보관하지 않고 크기·식별값·절단 여부를 기록한다. 필요한 관찰 내용은 비밀을 제거한 요약으로 보완한다. 테스트 주입 실행기의 성공은 상태 처리의 시험이며 실제 자식 프로세스 검사와 구분하고 완료 증거로 사용하지 않는다.

`done`은 차단 사유가 없고 모든 필수 기준이 현재 소스·기준에 적용되는 실제 증거와 함께 `passed`이며 필요한 독립 검토도 충족할 때만 가능하다. 과거 `schemaVersion: 1`의 완료는 당시 기록이며 현재 코드의 재검증 완료로 승격하지 않는다. `cancelled`는 `spec.md`에 취소 이유를 남긴다. 구조 검증 스크립트는 주장 형식과 연결을 검사하며 사실의 진위나 모든 행동 준수를 보증하지 않는다.

## 검증 증거의 적용성

검증 시도에는 검사한 코드·테스트·설정의 내용 식별, 수용 기준 정의의 식별과 당시 정의 사본 `criteriaSnapshot`, 실제 명령·시나리오·실행 결과, 관찰·한계를 연결한다. 동작에 영향을 주는 미추적 파일도 대상에 포함한다. HEAD와 `dirty: true`만으로 같은 HEAD 아래 서로 다른 변경을 구별하지 못하므로 내용 식별을 사용한다.

검증 대상은 구현 후 검사를 시작할 때 잡고, 검사 중 입력이 달라졌는지와 완료·재개 시 증거를 현재 변경에 적용할 수 있는지 확인한다. 실행 전 세션 binding은 오실행을 막기 위한 기준이며 검증 시점의 소스를 대신하지 않는다. 요구 또는 같은 AC ID의 설명·필수 여부가 바뀌어도 기준 식별을 다시 판단한다.

`captureSource`는 지정한 `inputs`의 파일 내용·경로·파일 모드와 디렉터리 구성, 미추적 입력과 없는 입력의 상태도 식별한다. `.git`, `.www`, `node_modules`, `dist`는 자동 제외 경로다. 실행 전 `preflight`의 전체 dirty fingerprint와 구별한다. 검사를 수행하며 생성하는 작업·증거 출력 자체를 검사 입력에 섞어 순환적으로 무효화하지 않도록 실제 의존 범위를 고른다.

현재 `status`는 읽기만 하면서 소스·기준·검토 적용성을 계산한다. `resume`은 같은 UUID의 적용성을 다시 계산하고 오래된 현재 결과·상태와 다음 행동을 갱신하며 과거 시도는 보존한다. `complete`는 현재 기준·소스·필수 검토를 다시 확인해 작업 완료를 기록한다. 실제 인터페이스와 부작용은 [개발 안내](../DEVELOPMENT.md#개발-역할의-작업-인터페이스)를 따른다.

소스·기준·실행 환경 외에 현재 `inputs`와 시도의 입력 범위가 다르면 `scope_changed`로 재평가한다. 파일 내용이 우연히 같아도 새 검사 의존 범위를 옛 시도가 확인한 것으로 보지 않는다.

과거 통과·실패 기록은 보존하고 현재 적용 가능성과 재검증 필요를 별도로 기록한다. 제품 검사에 영향이 없는 보고 문구 수정까지 모든 제품 검사를 다시 수행하지 않는다. 재사용할 때는 검사 의존 입력과 바뀐 범위, 재사용 판단 근거를 남긴다. 타입 검사나 링크 존재만으로 사용자 동작을 관찰했다고 쓰지 않는다.

## 독립 검토의 책임

필수 검토 조건과 미실행 처리는 이 공통 계약이 소유한다. 저작·통합과 검토는 별도 패스이며 검토자는 읽기 전용이다. 사용자의 최신 결정에 따라 모든 검토의 기본은 Opus이고, Opus의 토큰·사용량 소진이 확인된 경우에만 Terra로 대체한다. 인증·네트워크 오류, 원인 미확인, 불합격은 대체 사유가 아니다. 정확한 정책 값은 [프로젝트 검토 정책](../../agents/www/review-policy.json)이 소유하고 실행·판정은 `scripts/workflow/review.mjs`의 공유 core를 사용한다.

WWW 개발 역할이 검토할 범위·요구·대상 소스·증거를 준비하고 검토 실행과 원문 회수를 책임진다. 검토 어댑터는 공유 정책에서 선택한 검토자를 읽기 전용 도구 범위로 호출하고 실제 모델·종료 결과·원문 위치를 반환한다. 요청 모델과 관측 모델, 대체 사유를 구분한다. 완료 판단은 필수 증거의 적용성과 필요한 검토 충족 여부를 함께 확인한다. 검토자 권고와 실제 실행 증거를 구분하며 작성자가 자기 결과를 독립 승인하지 않는다.

앱과 CLI는 같은 정책 파일과 검토 core를 사용한다. 앱은 renderer가 임의 경로나 정책 값을 보내게 하지 않고 권한 있는 프로세스에서 배포된 정책을 읽는다. 현재 정책의 적용 범위는 WWW 개발 역할이며 모든 제품 Chat 요청의 자동 감사로 확대하지 않는다. 구현 진행과 필수 독립 검토의 미실행 상태를 구분하고 인증 실패 등을 해결 전 통과로 기록하지 않는다.

현재 교차검증은 이 규율을 개발 역할이 이행하는 절차다. 자동 훅을 이미 설치하거나 호스트가 자동 강제한다고 주장하지 않는다. 나중에 훅을 붙이더라도 훅은 검토 시점을 알리거나 실행을 요청하는 트리거이며, 검토 조건·읽기 전용 권한·완료 판정의 소유자가 되지 않는다. 실제 등록 경로와 호스트의 결과 수용을 확인해야 자동 연결로 기록할 수 있다.

## 서로 다른 상태를 섞지 않기

실행 프로세스 종료, 수용 기준 충족, 테스트 검증, Git 게시, 서버 색인은 서로 다른 사실이다. 프로세스가 끝났다고 기능이 수용되거나 게시·색인된 것은 아니다. 검증된 과거 결과는 이후 버그가 생겨도 덮어쓰지 않는다. 새 버그 작업을 만들고 관계로 연결한다.

## 책임과 변경 권한

- `www-spec`: 요청과 기준을 기록한다. 제품 소스를 바꾸지 않는다.
- `www-design`: 승인된 범위의 설계와 영향·위험·검증 전략을 기록한다. 제품 소스를 바꾸지 않는다.
- `www-build`: 사용자가 명확히 승인한 작업만 구현하고 직접 영향받는 테스트·문서를 바꾼다.
- `www-diagnose`: 증상과 검증된 원인을 분리해 조사한다. 제품 수정은 구현 단계가 맡고, 이미 허용된 구현 범위의 실패 수정이면 같은 권한으로 이어간다.
- `www-verify`: 실제 명령과 결과를 기록하고 기준 결과를 갱신한다. 실패를 숨기지 않는다.
- `www-commit`: [커밋 절차](../../skills/www/www-commit/SKILL.md)에 따라 변경 범위·index·검증·한국어 메시지·원격 게시 범위를 확인한다. 명시적 “커밋해” 요청은 기본 commit + push이며 “로컬에만” 요청은 push를 생략한다. 기존 staged 변경을 섞거나 임의로 해제하지 않는다. force push·merge·release는 하지 않는다.

어떤 스킬도 요청 없이 commit·push·브랜치 생성·원격 실행을 하지 않는다. `www-commit`의 명시 실행 요청에 따른 기본 push와 무단 자동 게시는 다르다. 준비·계획·스킬 생성은 실행 승인이 아니다. 커밋은 업무 완료·검증 통과·원격 게시·서버 색인을 대신하지 않는다. 준비 양식은 [commit.md](templates/commit.md)이며 작은 변경은 대화 요약으로 갈음할 수 있다. 저장소 안전 규칙과 [데스크톱 프로필](profiles/desktop.md)을 함께 따른다. 템플릿은 [templates](templates/)에 있다.

## opt-in 개발 세션 하네스

기존 GJC opt-in CLI는 정본 Skill을 context로 전달하고 같은 작업 ID의 로컬 실행·검증을 잇는다. 당시 범위와 fixture subprocess 근거는 [`work-e6fb4bac-a332-4515-b3f0-b8fb2adf6529`](../work/Workflow/001-Skills%20%EC%8B%A4%ED%96%89%EA%B3%BC%20%EA%B0%9C%EB%B0%9C%20%EA%B8%B0%EB%A1%9D%20%EC%9E%90%EB%8F%99%ED%99%94/verification.md)에 보존한다. 그 기록이 새 역할·Codex 경로의 검증은 아니다. 새 역할 접수는 위 호출·권한 계약을 사용하며 실제 호스트 로딩·일반 요청·재개·증거 적용성을 해당 작업에서 검증한다. 현재 CLI와 검사 방법은 [개발 안내](../DEVELOPMENT.md)에서 확인한다. 전역 훅, 자동 모델 전환, 제품 Native Chat 주입, OS hard gate는 이 계약 변경만으로 활성화되지 않는다.
