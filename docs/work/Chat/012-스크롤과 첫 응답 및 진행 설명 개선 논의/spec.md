# 스크롤과 첫 응답 및 진행 설명 개선 논의

## 요청과 권한

사용자는 다음 개발을 위한 논의를 요청했다. 이번 단계는 www-dev가 www-spec을 선택하여 요구·미결정·다음 논의를 기록한다. 제품 구현·앱 재시작·커밋·게시 권한은 없다. 기존 Chat 004·009·010과 주제는 연결되지만 새 사용자 관측을 접수한 별도 논의다.

## 확인된 관측

- 01: 채팅과 사이드바의 패딩·빈 공간에서 스크롤하면 앱 전체가 내려가 기능이 화면 밖으로 밀린다. 내용 영역과 여백, 내부 스크롤의 처음·끝, 내용이 짧은 상태를 나눠 재현해야 한다. 스크롤 전파가 원인이라는 설명은 미검증 가설이다.
- 02: 실행 중 표시와 경과 시간은 보였지만 공개 설명과 명령은 첫 1분 이상 나타나지 않았다. 따라서 접수 표시 부재로 정의하지 않는다. 첫 실패 명령은 홈 폴더 /Users/jonghoPro에서 git status를 실행해 종료 코드 128을 반환했다. 첫 실패가 나타난 뒤에는 나머지 설명·명령이 한꺼번에 표시된 것이 아니라 그때부터 하나씩 쌓인 것으로 사용자가 기억한다. 이는 사용자 관측이며 이벤트 시각을 직접 측정한 결과는 아니다. Native 최초 사건과 렌더 반영 중 어디에서 지연됐는지 아직 모른다.
- 03: 미리보기와 보관된 출력 펼침의 내용 차이가 작아 기능 중복으로 느껴진다. 사용자는 같은 자리에서 Ctrl+T to expand와 같이 펼치는 방식을 선택했고, 적용 대상은 선택한 명령 출력 하나라고 확정했다. 별도 전체 보기 패널은 이번 선택에서 제외한다.
- 04: 채팅에서 작업의 실시간 판단·진행 흐름을 따라가기 어렵다. 사용자는 작업 설명과 판단 요약을 함께 보고 싶은 방향에 동의했다. Native 공개 설명의 강화뿐 아니라 앱도 실제 실행 사건을 연결해 진행 설명을 추가하는 방향을 확인했다.

## 목표와 수용 기준 연결

기준 정의·필수 여부·결과는 work.json.criteria가 정본이며 현재 모두 미검증이다.

- AC-1: 여백과 내부 경계에서 스크롤해도 앱 프레임·입력 접근을 유지하는 시나리오다.
- AC-2: 실행 중 표시가 유지되는 동안 첫 의미 있는 설명·명령이 나타나지 않는 공백을 관측하고 개선하는 시나리오다. 늦은 Native 생성과 늦은 렌더링은 별도로 측정한다.
- AC-3: 같은 자리의 한 출력 영역에서 미리보기↔전체 출력을 전환한다. 키보드로도 선택한 명령 출력 하나만 펼치고 접으며 다른 출력의 상태는 유지한다.
- AC-4: Native가 제공하는 공개 설명·판단 요약과 앱이 실제 사건을 연결한 진행 설명을 채팅에서 읽는다. 앱 설명은 출처를 구분하며 실제 관측 범위를 지킨다. 조사 시작·발견·실패 후 방향 전환·검증 등 의미 있는 변화에서 설명하는 빈도·표현은 후속 설계에서 구체화한다.

## 현재 사실과 조사 범위

기존 기능 요구에는 대화 독립 스크롤과 실시간 공개 사건 반영이 있다. 실제 사용에서 충족되지 않는다는 새 관측을 받았다. CSS에는 내부 overflow 설정이 있고 Native 턴은 detailed 공개 요약을 요청하지만, 이 정적 사실만으로 실사용 스크롤 차단이나 설명 제공 시점을 검증했다고 보지 않는다. 새 실행 재현·로그 측정은 하지 않았다.

## 확정된 방향과 개발 인계

사용자는 초기 공백의 원인 확인 후 실제 행동 흐름을 채팅에 표시하는 방향에 동의했다. 대기 카드 선택 질문은 철회했고 후속 개발의 선행 조건으로 삼지 않는다. 현재 추가 사용자 선택을 요구하는 핵심 미결정은 없다. 원인 미확정은 진단할 사실이며 사용자 선호 미결정과 구분한다.

- 01: 채팅·사이드바의 패딩·빈 공간 및 내부 스크롤 경계에서도 앱 프레임·입력 접근을 유지한다.
- 02·04: 초기 준비·요청·사건 수신·화면 반영의 시간을 먼저 비교하고, 실제로 관측한 작업 흐름을 Native의 공개 설명과 함께 채팅에 연결한다. 단순한 대기 안내 추가를 해결로 판정하지 않는다.
- 03: 선택한 출력 하나를 같은 자리에서 펼치고 접는다. 다른 출력 상태는 유지하며 이미 모두 보이는 짧은 출력에는 불필요한 펼침을 두지 않는다.

다음 개발의 첫 진입점은 diagnosis.md의 경계별 계측이다. 연결·스레드 준비·턴 요청·수신·채팅 반영을 나누어 원인을 확인한 뒤, 그 결과를 같은 UUID의 설계·구현으로 인계한다. 정확한 단축키 조합과 포커스 표현은 이 요구를 유지하는 후속 설계에서 정한다. 이번 요청은 논의와 읽기 전용 원인 조사이며 제품 구현 권한은 아직 없다.

## 제안과 제외 범위

짧은 출력에 이미 전체 내용이 보이면 별도 확장을 두지 않는 것을 동일 영역 전환의 수용 기준으로 정리한다. 구현 순서 01→02→04→03은 제안이며 확정 우선순위로 기록하지 않는다. 홈 폴더에서의 Git 실패는 작업 폴더 전달·선택을 확인할 관련 관측이며, 폴더 자동 변경으로 요구를 확대하지 않는다. 실행 코드·스킬·역할 정본 수정과 설계 완료 판정은 이번 논의에 포함하지 않는다.

## 논의 진행 규칙

사용자 답변을 확인된 사실·결정으로 반영한 뒤 다음 중요한 미결정 한 가지로 이동한다. 정리 문장만 반복하며 다음 단계를 생략하지 않는다. 명세가 ready가 되는 조건은 구현을 바꾸는 주요 미결정 해소이며, 구현 시작은 별도 요청 범위로 판단한다.

## 진단 착수

사용자가 원인 확인을 우선 요청하여 읽기 전용 소스·기존 원장 조사를 시작했다. 제품 소스 수정이나 구현 승인은 없다. 원인 가설과 초기 근거는 diagnosis.md에 기록하며 최종 원인 확정과 구분한다.
