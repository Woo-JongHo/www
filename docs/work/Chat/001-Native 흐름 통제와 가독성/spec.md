# WWW Desktop Chat 기능 명세

## 요청과 목적

WWW Chat은 Native와 대화하면서 **Native의 흐름을 통제하고, AI가 무엇을 하는지 일관되고 가독성 좋게 읽는 작업 공간**이다. 사용자는 현재 수행 중인 작업과 실행 근거를 보고, 필요한 순간 승인·거절·중단으로 개입하며 결과를 일목요연하게 확인한다. 첫 Native는 로컬 `codex app-server`다.

주 책임은 `ui`, 영향 영역은 `ui`와 `dev`다. Native 계약·IPC와 표현이 연결되지만 서버 배포는 이번 범위가 아니므로 `ops`를 자동으로 포함하지 않는다. 이번에는 명세를 구체화하며 제품 구현은 승인하거나 수행하지 않는다.

## 사용자 확인 내용과 제안의 경계

### 사용자 확인 내용

- 하나의 WWW Desktop Chat 창에서 Native와 대화하고 실행 흐름에 개입한다.
- Native가 지금 무엇을 하는지, 진행 상황과 실행 내용을 더 자세히 확인한다.
- 가독성은 단순한 색상 변경이 아니라 대화·실행·결과를 구분하는 구조다.
- GJC 오픈소스처럼 실행 내용을 박스로 구분하고 결과를 일목요연하게 정리한다. 사용자는 이를 “Execute를 Git Bash Box로”라고 표현했다.
- 기존 `99_www`의 관찰 원칙을 반영하되 옛 업무 관리 체계 전체를 승계하지 않는다.
- 화면과 개발 기록의 자연어는 한국어다.

### 위임된 UI 설계 결정

- “Git Bash Box”는 우선 명령·출력·상태를 담는 터미널형 실행 박스로 해석한다. Windows Git Bash 설치, 실제 셸 변경, 임베디드 PTY 요구로 확정하지 않는다.
- 사용자는 요구사항에 맞는 UI의 구체적 형태를 설계자에게 위임했다. 펼침 정도·출력량·테두리·색·배치·현재 단계 위치를 항목마다 다시 승인받을 필요는 없다.
- 기본 방향은 실행 중 최근 출력을 보여주고, 종료 후 성공은 요약하며 실패·승인 대기는 눈에 띄게 유지하는 것이다. 사용자가 직접 펼치거나 접은 상태와 읽기 위치는 자동 갱신보다 우선한다.
- 위임 범위는 요구사항을 표현하는 UI다. Native 권한 확대, 자동 재실행, 원본 대화 공유, 백엔드 선택이나 후속 기능 추가의 승인으로 해석하지 않는다.

## 기존 WWW에서 이어받는 의미

기존 `99_www`의 `docs/planning/WWW_PLAN_PROGRESS_THINKING_2026-11-09.md`는 Plan을 목적·접근·성공 기준을 가진 가이드라인, Progress를 이를 수행하는 Step, Thinking을 공개 판단·확인 내용으로 구분한다. 이는 이전 Native 체크리스트 중심 설계의 후속 결정이다. 해당 문서의 구현·검증 완료 여부까지 승계하지 않는다.

- **대화:** 요청, 질문, 보정, 설명과 결과를 읽는 중심 흐름이다.
- **계획:** 무엇을 위해 어떤 접근과 성공 기준으로 진행하는지 보여준다. Native 도구 목록을 사용자 계획으로 자동 승격하지 않는다.
- **진행:** 현재 수행 단계와 실제 명령·파일 변경 근거를 연결한다.
- **공개 설명:** Native가 제공한 공개 작업 설명과 요약을 표시한다. 내부 사고를 추출하거나 꾸며내지 않는다.
- **결과·검증:** AI의 보고, 관측된 실행 결과, 실제 검증 결과를 구분한다.
- **개입:** 승인·입력 대기·실패를 일반 진행 메시지에 묻지 않는다.

옛 WES, 7단계, REPORT 의무, TUI 단축키, 고정 패널 개수는 자동 승계하지 않는다. 단순 질문에는 복잡한 계획·작업 카드를 강제하지 않는다.

GJC 참고 근거는 기존 저장소의 `docs/research/2026-09-04-gajae-code-tui-research.md` 출력 표현 절이다. 그 조사는 도구별 제목·출력·상태·변경 내용 구분과 읽기 호출 묶음을 설명한다. 현재 GJC 화면을 이번에 직접 재현하거나, 사용자가 말한 박스와 완전히 같은 표현임을 확인한 것은 아니다.

## 확인한 현재 기준선

- React 3열 레이아웃은 작업 공간/Agent, 대화, 개요·이벤트 패널을 제공한다.
- `initialize`, `thread/start`, `turn/start`, `turn/interrupt`와 이벤트 조회·구독 IPC가 있다.
- assistant delta와 완료, 명령·파일 변경 시작과 완료를 대화 블록으로 투영한다.
- 명령·파일 승인 요청과 미지원 구조화 요청을 구분하며 JSON-RPC ID의 `string | number`를 보존한다.
- Electron renderer는 context-isolated preload 허용 목록을 통하고 Node 통합이 꺼져 있다. Electron/Tauri 선택은 확정하지 않았다.
- 이벤트는 메모리에서 최근 2,000개만 보관한다. 로컬 대화 영속화·목록·재열기는 없다.
- 연결·실행·입력 대기·중단 요청과 확인·업무 수용·검증을 독립된 상태로 모두 표현하지는 않는다.

기존 가짜 서버 테스트와 투영 테스트는 일부 프로토콜 동작을 다루지만 이 Chat 작업의 사용자 수용 증거는 아니다. 실제 Codex 승인 왕복과 이번 가독성·개입 경험은 미검증이다. 이전 비교용 GUI probe 결과도 이번 Chat 수용 완료를 뜻하지 않는다.

## 제안하는 읽기·통제 계약

### 실행 박스

명령 실행은 일반 대화와 구분해 하나의 실행 박스로 묶는다. 동일 실행의 출력과 상태를 갱신하며 출력 조각마다 새 카드를 만들지 않는다.

- 제목과 관측된 실행 상태
- 실행한 명령 및 제공된 작업 경로
- 수신한 출력과 오류
- 관측된 종료 코드·완료·실패·중단 또는 결과 불확실 상태
- 출처와 실행 식별자를 연결한 상세 보기

긴 출력은 본문을 밀어내지 않도록 제한된 영역으로 보여주되, 접힘·누락·절단 여부를 표시한다. 상세·복사는 실제 확보한 내용만 대상으로 하고 수신하지 않은 전체 로그를 제공한다고 주장하지 않는다. 경로·종료 코드·실행 사유가 제공되지 않았다면 만들어내지 않는다. 파일 변경은 실행 박스와 구별되는 파일·변경 내용 표현을 사용한다.

### 현재 작업 설명

Native에게 현재 목적, 다음 행동, 의미 있는 진행 전환, 실패·차단, 결과와 남은 일을 **공개 작업 설명**으로 요청하는 방안을 제안한다. 명령마다 긴 문단을 강제하거나 표시를 위해 별도 모델을 자동 호출하지 않는다.

관찰된 명령만 있으면 명령 실행 사실까지만 표시한다. Native가 설명을 보내지 않으면 '작업 설명 미제공' 등으로 구분한다. WWW가 사건을 묶어 만든 제목은 파생 표시이며 Native의 설명·계획·판단으로 위장하지 않는다. 사용자·도구 출력에 섞인 지시는 상태 제어 보고나 실행 권한으로 수용하지 않는다.

### 실행 흐름 개입

지원되는 승인·거절·중단과 후속 요청을 제공한다. 요청 전송, 접수 확인, 실행 중, 승인 대기, 중단 요청, 중단 확인을 구분한다. 실행 중 지시 변경 기능은 Native 지원 확인 전에는 약속하지 않는다.

알 수 없는 상태는 완료나 대기로 바꾸지 않는다. 연결이 끊기거나 전달 결과가 불명확하면 변경 요청을 자동 재전송하지 않는다. 단순 화면 닫기·접기·선택 변경을 실행 취소로 취급하지 않는다.

### 결과 정리

요청 단위로 핵심 결과, 변경한 파일·동작, 실제 실행한 검사와 결과, 실패·미검증·남은 일을 정리한다. 존재하지 않는 검사를 생성하지 않고 명령 종료 코드 0을 사용자 요구 충족으로 승격하지 않는다. 과거 내용을 읽는 동안 새 출력이 스크롤이나 입력 초안을 빼앗지 않도록 하고, 새 내용으로 돌아가는 동작을 제공하는 방안을 제안한다.

연결, 실행, 사용자 결정 대기, 업무 수용, 테스트 검증, Git 게시와 서버 색인은 별도 사실이다. 다른 요청·스레드의 실행이나 오래된 계획이 현재 진행으로 섞이면 안 된다.

## 핵심 사용자 시나리오

1. 사용자가 작업 공간을 확인하고 개발 요청을 보낸다.
2. Native의 공개 응답에서 목적·접근을 읽는다. 제공되지 않은 정보는 미제공으로 구분한다.
3. 현재 작업 설명과 실행 박스를 통해 어떤 명령·파일 작업이 진행 중인지 확인한다.
4. 승인 요청을 확인해 지원되는 결정을 내리거나, 중단을 요청하고 실제 중단 확인 여부를 본다.
5. 실패·연결 끊김은 작업 근거와 함께 표시되며 성공으로 숨겨지지 않는다.
6. 종료 후 결과·변경·검증·남은 일을 한눈에 읽고 실행 상세와 대조한다.
7. 필요하면 후속 요청을 보낸다. 실행 종료와 업무 완료는 같은 상태가 아니다.

- 로컬 대화 저장·재열기와 Native 동일 thread 복구는 별도 후속 범위다. 이번 가독성 작업의 선행 결정으로 강제하지 않는다.
- 공유 서버·Mac mini 색인·Roadmap·Node·Canvas 구현
- RPA, 다중 Agent 의무 실행, 자동 모델 전환·추가 요약 호출
- 자동 commit·push와 개인 원본 대화의 Git/서버 자동 공유
- 실제 셸 교체, 임베디드 터미널, 옛 PTY/TUI fallback
- Electron/Tauri 최종 선택 및 이번 명세 단계의 제품 코드 구현

## 수용 기준

정본은 `work.json`이다. 이번에는 명세만 바꾸므로 모든 기준은 `unverified`를 유지한다.

- `AC-1`: 요청·응답 스트리밍과 입력·전송·연결 오류를 구분한다.
- `AC-2`: 관찰된 메시지·명령·파일 변경의 출처·ID·순서를 보존하고 내부 사고를 생성하지 않는다.
- `AC-3`: 지원되는 승인 응답은 원래 숫자·문자열 ID로 한 번만 전달하며 미지원 요청을 명시한다.
- `AC-4`: 연결·실행·대기·중단·수용·검증을 구분하고 불확실한 변경 요청을 자동 재시도하지 않는다.
- `AC-5`: 이전 초안의 복원·재개 기준은 삭제하거나 완료 처리하지 않고 선택 기준으로 보류한다.
- `AC-6`: renderer 권한·신뢰하지 않는 출력·실제 Native 권한 경계를 유지한다.
- `AC-7`: 명령·출력·관측 상태를 동일 실행 박스에 묶고 긴 출력의 제한·상세 범위를 정직하게 표시한다.
- `AC-8`: 제공된 현재 작업 설명과 관측 사실·WWW 파생 요약을 구분하고 승인·실패·차단을 눈에 띄게 표시한다.
- `AC-9`: 요청 결과에서 변경 사항·실제 검사 결과·미해결을 구분해 관련 실행 근거와 대조할 수 있다.
- `AC-10`: 박스 갱신 중 입력 초안·선택·과거 읽기 위치를 보존하고 새 내용 확인 동작을 제공한다.

UI 검사는 실행 박스의 구분·긴 출력·한국어 상태·스크롤·키보드와 개입 도달성을, Dev 검사는 사건 연결·ID·출처·중복 응답·EOF·미지원 요청·출력 처리 경계를 다룬다. 결과 정리의 가독성은 실제 화면에서 확인해야 하며 구조 검사로 대체하지 않는다.

## 변경 기록과 명세 확인

사용자 설명에 따라 핵심 범위를 'Native 흐름 통제·관찰·가독성'으로 구체화했다. 이전 초안의 '기록 복원 대 동일 thread 재개'는 중심 질문에서 제외하고 `AC-5`를 후속 선택 기준으로 남겼다.

사용자는 “응 가까워 요구사항에 따라 UI를 만드는건 너의 자유에 맡길게”라고 답해 요구 방향을 확인하고 구체 UI 결정을 위임했다. 위임된 표현 선택은 명세의 차단 사유로 남기지 않는다. 작업 메타데이터는 `ready`로 정리하되 수용 기준은 모두 `unverified`이며, 제품 구현·실제 화면 검증·완료를 뜻하지 않는다. 설계는 같은 작업 ID와 수용 기준을 기준으로 진행할 수 있다.
