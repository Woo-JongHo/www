# 첫 Chat 실사용까지의 통합 실행 계획

## 목표

**WWW Desktop에서 Native에게 작업을 맡기고, 공개 설명·명령 실행·파일 변경·승인·중단·결과를 한 흐름으로 이해하고 통제할 수 있는 첫 Chat을 실제로 사용 가능하게 만든다.**

BoxBox와 개발 하네스는 이 목표를 구현·검증·기록하기 위한 수단이다. 하네스 구축 자체를 최종 제품 성과로 바꾸거나 기존 WWW 전체 이관을 목표로 삼지 않는다. 이 문서가 해당 목표의 실행 순서를 소유하며 경쟁하는 별도 종합 계획을 만들지 않는다. 각 연결 작업의 명세와 세부 작업은 원래 폴더에서 유지한다.

## 이번 문서와 실행 권한

이번 요청은 목표·계획 문서와 합의한 기본 commit + push 정책 정리다. 제품 구현, 현재 dirty 전체의 일괄 stage·commit·push, 전역 플러그인 설치를 실행하지 않는다. 사용자가 이 계획의 구현·검증·게시 범위를 승인하면 범위 내 작업을 단계마다 의례적으로 재승인받지 않고 진행한다. 대상·권한을 바꾸는 실제 결정과 사용자만 수행할 수 있는 인증·승인 단계는 예외다.

## 범위와 완료 판정

- 기준 제품은 현재 동작하는 Electron·React 구현이다. Electron/Tauri 비교를 폐기하지 않되 이번에 셸 마이그레이션을 하지 않는다.
- 첫 실사용 증거는 현재 접근 가능한 macOS 환경에서 확보한다. 이는 Windows 출시 검증 완료를 뜻하지 않는다. Windows·한국어 IME처럼 실행하지 못한 항목은 별도 한계로 남긴다.
- Chat의 필수 기준 `AC-1~4`, `AC-6~10`을 실제 근거로 검증한다. 선택 기준 `AC-5`의 대화 영속화·재개는 이번에 포함하지 않는다.
- 승인 응답은 클라이언트 중복 전송을 방지하는 것이며 원격 효과의 정확히 한 번 보장이 아니다. EOF·중단 요청·중단 확인·불명확 상태를 구분한다.
- fake fixture 통과와 실제 Native 동작을 분리한다. 실제 Native 실행에는 호스트·로그인·사용 가능량 확인이 필요하다. 실행하지 못하면 실사용 검증은 차단/미검증으로 남기고 전체 완료라고 하지 않는다.
- 개발 하네스·BoxBox 준비 상태는 각각 별도 사실로 기록한다. GUI가 동작한다는 이유로 해당 도구의 통합도 검증됐다고 하지 않는다.
- 게시까지 승인된 실행에서는 승인된 커밋과 원격 브랜치 반영까지 확인한다. 서버 색인·자동 앱 업데이트는 이번 완료 조건이 아니다.

## 순서와 단계별 증거

| 순서 | 작업 | 다음 단계로 넘길 근거 |
|---|---|---|
| 0 | 기존 변경·요구·권한 기준선 확정 | 새 `www`의 기존 dirty를 작업별로 분류. 포함/제외 파일, 현재 HEAD·브랜치와 검사 범위 기록. 옛 `99_www`는 변경하지 않음 |
| 1 | BoxBox 개발 준비 | 실제 설치 호스트·로컬 엔진·버전·parser·쓰기 승인 범위를 확인. 지원 언어는 작성 전 guide와 기존 check, 작성 후 check 수행 가능. 전역 설치나 align 모드는 별도 명시 선택 필요 |
| 2 | 프로젝트 opt-in 개발 하네스 | [Workflow 작업](../../Workflow/001-Skills%20실행과%20개발%20기록%20자동화/tasks.md)의 요청→Skill 로드→같은 UUID 인계→검증·기록 흐름을 최소 단위로 실제 실행. 중복·실패·승인 부족·불명확 결과의 테스트 확보 |
| 3 | Chat 사건·상태 계약 | 아래 단위 1 구현과 fixture 검증. 다른 turn 혼합·숫자/문자열 ID·중복 승인·EOF·중단 구분 확인 |
| 4 | Chat 설명·실행 박스·결과·읽기 상태 | 아래 단위 2·3 구현. 실제 화면의 실패·승인·긴 출력·입력/선택/스크롤 보존 확인 |
| 5 | 실제 UI·Native 검증과 기록 | 집중 테스트·타입·빌드, 실제 Electron GUI, 허용된 최소 Native 시나리오의 증거. 기준별 통과·실패·차단·미검증을 분리 |
| 6 | 선택 변경 commit + push | `www-commit`으로 승인 범위·미게시 이력·공개 안전성을 검토. 로컬 커밋과 원격 ref 확인 결과를 구분 |

이 순서는 하나의 수직 흐름을 완성하기 위한 기본 순서다. BoxBox 호스트 인증처럼 외부 의존이 막히면 영향 없는 문서·fixture 준비는 진행할 수 있지만 필수 검증을 생략해 통과로 바꾸지 않는다. 하네스가 지원하지 않는 호스트에서는 `unsupported`나 advisory 한계를 기록하며 GJC를 Codex/Claude 플러그인 호스트와 같은 것으로 가정하지 않는다.

## BoxBox와 하네스의 경계

BoxBox는 [공식 코드 가독성 플러그인](https://github.com/Woo-JongHo/boxbox)이다. WWW의 실행 박스 UI나 업무 라우터가 아니며 제품 실행에 배포할 필수 라이브러리로 넣지 않는다. TypeScript·Python·strict JSON·YAML 지원과 Markdown·`.mjs`·Rust 등 미지원 범위를 구분한다. `misaligned=0` 또는 감지 그룹 없음은 전체 가독성·기능 검증을 뜻하지 않는다. 기본 check는 읽기 전용이며 자동 정렬은 기본값으로 켜지 않는다.

BoxBox 적용은 문서 구조 정리 뒤의 후속 요구였고 이 계획에 그 순서를 연결했다. 현재 설치·훅 연결이 완료된 것으로 표시하지 않는다. 하네스는 전역 훅부터 설치하지 않고 프로젝트별 명시 진입점과 로컬 기록부터 만든다. Skill 경로·hash·로드 방식·실제 성공과 모델 요청값/관측값을 구분한다. 같은 작업 UUID를 유지하며 요구·수용 기준은 자동 재작성하지 않는다. 이 하네스를 Chat 제품의 Native에 강제 주입하지 않는다.

## 단위 1: 사건과 상태 계약 분리

- 변경: `src/shared.ts`, `src/main.ts`, `src/preload.ts`, `src/projection.ts`에서 turn별 상관관계와 transport/turn/interrupt/approval 상태를 분리하고 원본 ID를 보존한다. 동일 승인에 최대 한 번 전송을 시도하며 전송 결과 불명확 시 자동 재시도하지 않는다.
- 관련 기준: `AC-1`, `AC-2`, `AC-3`, `AC-4`, `AC-6`
- 확인: projection/RPC fixture에서 문자열·숫자 ID, 다른 turn 혼합, 중복 승인, EOF, 중단 요청과 확인, `exitCode: null`/`0`을 검사한다.

## 단위 2: 실행·설명·결과 표현

- 변경: `src/renderer.tsx`, `src/index.html`에서 실행 중 최근 출력, 성공 접힘, 실패·승인 강조, Native 공개 설명/관측 사실/파생 요약, 검사와 미해결을 구분한다.
- 관련 기준: `AC-7`, `AC-8`, `AC-9`
- 확인: 합성 fixture 화면과 실제 Electron GUI에서 긴 출력·한국어 상태·실패·승인·미제공 설명을 확인하며 live Codex 여부를 별도 기록한다.

## 단위 3: 사용자 읽기 상태 보존

- 변경: 자동 갱신 중 실행 박스 접힘, 입력 초안, 선택, 과거 스크롤을 보존하고 새 내용 확인 동작을 추가한다.
- 관련 기준: `AC-10`
- 확인: 키보드/포커스/스크롤 GUI 시나리오와 컴포넌트 상태 회귀 검사를 수행한다.

## 직접 영향받는 후속 변경

- `test/projection.test.ts`, `test/rpc.test.ts`, `test/rpc.fixture.test.ts`, `test/fixtures/fake-app-server.mjs`를 계약 변경과 함께 수정한다.
- `AC-5`의 기록 복원은 후속 선택 기준이며 이 구현 작업에 포함하지 않는다.
- 제품 구현 승인 이후에만 위 단위를 수행하고, 검증은 별도 `verification.md`와 `work.json` 기준 결과에 기록한다. 현재 Chat의 `ready`와 모든 기준의 `unverified`를 구현 완료 상태로 바꾸지 않는다.

## 범위 밖과 중단 조건

서버/DB/Canvas·Roadmap, RPA, 다중 에이전트 의무화, 모델 자동 전환, PTY 셸 대체, 기존 WWW 전체 이관, 자동 동기화, 자동 업데이트, force push·merge·release는 제외한다.

승인 범위 밖 변경, 예상하지 못한 기존 staged 내용, 미검증 BoxBox/호스트, 라이브 실행 자격 부족, 원격 이력 충돌, 실패한 필수 검사에서는 해당 단계의 구체적 차단 사유를 기록한다. 사용자 변경 삭제·자동 재시도·scope 확대로 해소하지 않는다. 승인된 범위 안에서 해결 가능한 실패는 재현→원인 확인→수정→재검증하고, 사용자만 해결 가능한 차단은 정직하게 남긴다.
