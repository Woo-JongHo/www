# 표시 창의 입력·휠·명령 카드 측정

2026-11-24 macOS에서 Electron 39.8.10의 표시 창을 열고 1,440×868 뷰포트에서 측정했다. 검사기는 BrowserWindow의 표시 상태와 문서 가시성을 확인하고, 40개 입력 표본마다 입력창이 DOM 포커스를 유지하는지 검사한다. 이전 숨김 창에서 얻은 값은 실제 표시 창의 근거에서 제외했다.

기준 커밋은 `0169e47`이다. 동일한 호스트 앱과 fixture에서 renderer 번들만 바꾸고 기준→후보, 후보→기준, 기준→후보 순서로 실행했다. 입력 지연은 합성 input 사건에서 다음 requestAnimationFrame까지의 시간이다. 운영체제 한글 조합·키보드 지연과 React commit 시각은 측정 범위 밖이다.

| 관측값(ms) | 기준 1 / 2 / 3 | 후보 1 / 2 / 3 |
| --- | --- | --- |
| 짧은 이력 입력 p95 | 7.2 / 7.8 / 7.2 | 7.7 / 7.1 / 7.6 |
| 명령 카드 65개 대기 입력 p95 | 7.9 / 8.4 / 8.0 | 8.8 / 11.2 / 9.1 |
| 같은 이력에 출력 스트리밍 중 입력 p95 | 52.7 / 48.4 / 52.8 | 47.7 / 47.4 / 43.1 |
| 같은 이력 휠 스크롤 최대 프레임 간격 | 7.7 / 8.0 / 8.5 | 13.8 / 7.6 / 8.7 |

스트리밍 중 입력 p95의 세 번 중앙값은 52.7ms에서 47.4ms로 줄었고 후보 세 번 모두 명세의 제안 목표인 50ms 안에 들었다. 긴 이력 대기 입력의 중앙값은 8.0ms에서 9.1ms로 늘었다. 대기 입력·스크롤 개선은 확인하지 못했다. 별도로 앞서 표시 창에서 시험한 CSS `content-visibility` 후보는 휠 프레임의 최대 간격이 667~681ms까지 늘어 이번 변경에서 제외했다.

입력 표본 수집 후 동일한 스트림이 계속 흐르는 350ms 동안 명령 블록의 JSON 직렬화 호출을 계측했다. 기준에서는 각 2,244 / 2,112 / 2,112회, 출력 문자열로 4,433만~4,711만 UTF-16 코드 단위를 반복 처리했다. 후보에서는 세 번 모두 0회였고 그동안 transcript DOM 변경이 각각 34회 관찰됐다. 후보는 명령의 스칼라 필드를 React가 직접 비교하게 하고, 대화·턴·콜백 등 입력이 같은 경우 행 목록을 재사용한다. 대기 입력 때 명령 카드 DOM 변경은 기준과 후보 모두 0회다. DOM 변화만으로 컴포넌트 함수 호출 횟수를 판정할 수 없다.

[실행 순서·번들 지문·각 표본의 요약](visible-input-performance.json)에 원문 SHA-256을 남겼다. 같은 검사 경로는 `npm run build` 뒤 `node scripts/verify-chat.ts --performance-only`로 실행한다. 이 측정은 AC-5의 성능 근거다. 실제 IME, 연속 추가 지시 및 탭·대화 격리는 각각의 수용 근거로 판단한다.
