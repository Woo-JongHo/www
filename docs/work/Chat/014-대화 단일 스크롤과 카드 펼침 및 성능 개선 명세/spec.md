# 대화 단일 스크롤과 카드 펼침 및 성능 개선 명세

## 요청과 권한

사용자는 카드별 스크롤로 인한 버벅임을 줄이고, 기본적으로 대화 전체를 내리는 스크롤만 사용하며 `Control+T`를 `^T`로 표시해 한도 내 출력을 펼치는 동작을 요청했다. 이어 “개발명세서만 세워놔”라고 범위를 제한했으며, “특히 Input이부분 엄청나게 랙걸리네”라고 입력창 지연을 강조했다. 추가로 Working 상태의 가시성, 흰색 위주 텍스트의 의미별 색상 구분, `99_www` 매트릭스 테마 색상을 기본으로 사용하는 방향을 요청했다. 이어 작업 중 추가 전송이 막히는 문제를 해결할 `Steer` 기능도 요청했다. 명세 전용 범위를 유지하며 이번 산출물은 개발명세와 접수 기록이다. 구현·앱 재시작·커밋·push는 수행하지 않는다.

관련 Chat 012는 첫 응답 지연·진행 설명까지 포함한 기존 작업이다. 이번 작업은 카드 내부 스크롤 제거와 입력 반응성에 초점을 둔 후속 명세이며 기존 작업의 이력·기준·판정을 바꾸지 않는다. 현행 제품 명세도 구현 전에는 바꾸지 않는다.

## 목표와 우선순위

1. **P0 입력 반응성**: 대화가 길거나 출력이 실시간으로 들어와도 타이핑·한글 조합·커서 이동·붙여넣기가 즉시 반영된다.
2. **P1 스크롤 구조**: 채팅 본문을 대화 전체의 단일 세로 스크롤로 읽는다. 카드 내부에서 휠이 따로 잡히는 동작을 없앤다.
3. **P1 펼침**: 긴 명령 출력은 기본 미리보기에서 선택한 카드만 같은 자리에 펼치고 접는다. 표시 단축키는 `^T`, 실제 키 조합은 `Control+T`다.
4. **P1 상태·색상 가독성**: 현재 작업 여부가 항상 보이고 `99_www`의 매트릭스 계열 팔레트로 텍스트 역할과 상태를 구분한다.
5. **P1 Steer**: 작업을 중단하지 않고 현재 실행 중인 턴에 추가 지시를 보낸다.
6. **P2 전체 반응성**: 스트리밍·경과 시간 갱신·카드 전환·대화 전환에서 불필요한 렌더와 계산을 줄인다.

## 관측과 아직 확인하지 않은 원인

- 사용자 관측: 카드별 스크롤과 전반적인 버벅임이 있으며, 특히 Input 지연이 심하다. 발생 빈도·대화 크기·입력 지연 시간은 아직 실측하지 않았다.
- 소스 확인: `src/command-card.tsx`는 펼친 출력에 `maxHeight: 360`을 부여하고, `src/chat.css`는 출력·명령줄에 `overflow: auto`를 사용한다. 긴 출력은 카드 내부 스크롤이 생길 수 있는 구조다.
- 소스 확인: 명령 출력은 실행 중 최근 10줄, 종료 후 앞 10줄을 미리보기로 사용한다. 포커스된 카드의 Control+T 전환과 대화별 수동 선택 기억은 이미 있다.
- 소스 확인: `src/projection.ts`의 원문 보관 한도는 32,768 UTF-16 코드 단위다. JSON 정렬 표시에는 별도의 최대 131,072 단위 제한이 있다.
- 조사 후보: 입력 상태 변경에 따른 상위 화면 및 명령 카드 재렌더, 카드별 경과 시간 갱신, 미리보기·구문 강조 반복 계산, 이벤트 수신과 스크롤 관찰 처리. 이들은 코드 조사 후보이며 Input 지연의 입증된 원인으로 단정하지 않는다.

## 입력창 요구

수용 기준 연결: AC-5, AC-6, AC-7.

- 입력 초안의 갱신이 대화 전체 투영·완료 카드·변하지 않은 Markdown의 불필요한 처리로 이어지지 않게 한다. 초안 상태 분리·컴포넌트 경계·메모화는 계측 결과로 선택한다.
- 입력 중 실시간 출력과 경과 시간 갱신이 있어도 글자가 누락·중복·역전되지 않는다. 한글 조합 중 Enter가 전송으로 처리되지 않으며 기존 Enter 전송·Shift+Enter 줄바꿈과 입력 한도를 유지한다.
- 커서 중간 삽입·선택 영역 교체·긴 붙여넣기·빠른 연속 입력을 포함한다. 실패 원문 복원·인용 삽입·대화별 초안 격리는 유지한다.
- 입력 지연을 숨기기 위해 표시를 debounce하거나 전송 원문을 지연·누락하는 방식은 사용하지 않는다.

## 단일 스크롤과 펼침 요구

수용 기준 연결: AC-1, AC-2, AC-3, AC-4.

- 입력창과 앱 프레임은 화면 안에 유지하고 대화 본문만 세로로 스크롤한다. 명령 출력·명령줄·코드·diff 카드에 높이 제한에 의한 독립 세로 스크롤을 두지 않는다.
- 긴 명령·출력·코드·diff의 줄은 카드 폭에 맞춰 줄바꿈하는 방향을 기본안으로 한다. 공백·들여쓰기·탭의 의미를 유지한다. 가로 표는 데이터 가독성 때문에 별도 가로 이동을 허용할 수 있지만 세로 휠은 대화가 처리해야 한다.
- 기본 미리보기는 기존 10개 논리 줄 정책을 유지한다. 미리보기와 전체 출력을 중복 렌더하지 않는다. 숨긴 내용이 없으면 펼침 조작을 표시하지 않는다.
- 버튼은 `출력 펼치기 · ^T` / `출력 접기 · ^T`로 표시하고 접근성 단축키 정보에는 `Control+T`를 제공한다. 카드 안에 포커스가 있을 때 그 카드만 전환한다. 입력창·다른 카드·다른 대화에 키를 전파해 뜻하지 않은 전환을 일으키지 않는다.
- 펼치면 카드 자체가 대화 안에서 늘어나며 같은 대화 스크롤로 내용을 읽는다. 실패 기본 펼침과 수동 선택 우선 정책은 유지한다.
- 펼침 상한은 별도 무제한 로딩 없이 현재 보관 원문 최대 32,768 UTF-16 코드 단위로 정한다. 정렬 표시도 이 표시 상한을 넘기면 보관 원문 보기로 전환하고 이유를 안내하는 기본안을 사용한다. 원문 복사는 보관된 원문을 복사하며 버려진 내용을 복구했다고 표시하지 않는다.
- 최신을 따라가던 사용자는 새 출력을 계속 따라가고 과거를 읽던 사용자는 강제로 끝으로 이동하지 않는다. 펼침·접힘 전후에는 조작한 카드 또는 읽던 문장의 위치를 기준으로 예상 가능한 읽기 위치를 유지한다. 대화 전환 후 초안·읽기 위치·카드 선택을 복원한다.

## Working 상태의 가시성

수용 기준 연결: AC-8, AC-10.

- 사용자 관측은 “Working 같은 표시가 보이지 않는다”다. 소스에는 작업 흐름 카드와 진행 상태 문구가 있으므로 상태 로직 자체의 부재로 단정하지 않는다. 현재 요청 카드의 위치·가시성·색상 때문에 놓치는지 실제 화면에서 확인한다.
- 입력창 바로 위의 고정 상태 줄에서 `Working · 작업 중`을 명시한다. 대화 과거 위치로 스크롤하거나 세션 모니터를 접어도 현재 활성 대화의 작업 여부를 확인할 수 있어야 한다. 상세 작업 흐름은 본문에 유지하고 고정 줄에는 요약만 둔다.
- 전송 중은 `전송 중`, 실제 시작 대기는 `시작 대기`, 실행·응답 진행은 `Working · 작업 중`, 승인 대기는 `승인 대기`, 중단 요청 뒤는 `중단 확인 중`으로 구분한다. 종료·실패·연결 미확인에서는 계속 Working으로 보이지 않도록 실제 상태를 우선한다.
- `응답 종료`와 업무 완료를 구분한다. 새 출력이 한동안 없어도 실행 중이면 Working을 유지하되 `새 활동 대기`를 보조로 표시한다. 연결을 확인할 수 없을 때 실행 중이라고 확정하거나 임의의 진행률을 만들지 않는다.
- 작고 분명한 상태 아이콘·상태 문구·색을 함께 사용한다. 경과 시간은 실제 시작 시각이 있을 때만 표시한다. 초 단위 갱신과 작은 진행 표시는 입력창·대화 전체 렌더를 유발하지 않으며 모션 축소 설정에서도 텍스트로 상태가 전달된다.
- 활성 대화 전환 시 해당 대화의 실제 상태로 바뀌어야 한다. 직전 대화의 Working·오류·승인 상태를 새 대화에 남기지 않는다.

## 매트릭스 계열 기본 테마와 텍스트 색상

- 색상은 공통 CSS 의미 토큰으로 관리한다. 형제 저장소를 런타임에서 읽거나 Chalk/TUI 실행 코드를 앱에 도입하지 않는다. 테마 전환 효과·지속 발광·무거운 애니메이션으로 입력 렉을 늘리지 않는다.

## 작업 중 추가 지시: Steer

수용 기준 연결: AC-11, AC-12, AC-13, AC-14.

### 목적과 현재 확인한 사실

사용자는 “지금 작업하고 있으면 추가 보내기가 안 된다”고 관찰했다. 목표는 실행을 중단하거나 응답이 끝날 때까지 기다리지 않고 현재 작업의 방향·조건·우선순위를 추가 지시로 조정하는 것이다.

현재 `src/renderer.tsx`의 전송 경로는 `api.startTurn`을 호출하며, `src/native-session.ts`의 `turn:start`는 `assertConversationIdle()`에서 활성 턴이 있으면 거부한다. renderer의 버튼 비활성 여부와 별개로 현재 backend에는 같은 턴에 추가 입력을 전달하는 경로가 없다. 현재 `WwwApi`와 preload에도 Steer 메서드가 없다.

설치된 `codex-cli 0.169.0`에서 `codex app-server generate-json-schema --out <임시 디렉터리>`를 직접 실행해 `turn/steer`, `v2/TurnSteerParams.json`, `v2/TurnSteerResponse.json`을 확인했다. 필수 입력은 `threadId`, `expectedTurnId`, `input`이며 선택 필드는 `clientUserMessageId`다. `expectedTurnId`가 실제 활성 턴과 다르면 실패하는 사전조건이며 응답에는 `turnId`가 있다. 이 확인은 프로토콜의 존재·형식에 관한 근거다. 실제 모델이 추가 지시를 언제 읽고 행동에 반영하는지는 이번에 실행하지 않았다.

### 사용자 동작과 상태

- 대기 중 전송은 기존 `보내기`로 새 턴을 시작한다. 활성 턴이 확인된 작업 중에는 같은 입력창의 주 동작을 `Steer · 추가 지시`로 전환한다. 현재 작업을 중단·재시작하거나 별도 대화를 열지 않는다. `중단` 버튼은 별도 동작으로 유지한다.
- Enter는 현재 표시된 전송 동작을 실행하고 Shift+Enter는 줄바꿈한다. 한글 조합·입력 한도·커서·붙여넣기 규칙은 동일하다. 작업 중에도 추가 지시를 계속 작성할 수 있다.
- 전송 전에는 `현재 작업에 추가 지시`임을 짧게 안내한다. 사용자 추가 메시지는 대화의 실제 전송 순서에 표시하며 원래 요청을 덮어쓰지 않는다.
- 각 추가 지시는 `전송 중` → `접수됨` 또는 `전송 실패` / `접수 여부 미확인`으로 표시한다. 접수는 API의 정상 응답을 뜻하며 모델의 이해·반영 완료라고 표시하지 않는다. 실제 반영 여부는 후속 공개 응답·도구 행동으로 확인한다.
- Steer 전송 중에도 입력 편집은 허용한다. 같은 요청의 중복 클릭·Enter는 잠그고 별도의 추가 지시는 직전 요청의 접수 결과를 받은 뒤 보낸다. 사용자가 작성 중인 다음 초안을 전송 완료 콜백으로 지우지 않는다.
- 턴 시작이 아직 확인되지 않아 `expectedTurnId`가 없으면 입력 초안은 유지하며 `시작 확인 후 추가 지시 가능`을 표시한다. 중단 확인 중·연결 끊김·세션 전환·미결 승인에서는 이유를 표시하고 Steer 전송을 보류한다. 승인 대기에서는 기존 승인·거절을 처리한 뒤 활성 턴을 다시 확인한다. 준비·승인 대기 중 자동 전송 큐는 이번 범위에 넣지 않는다.
- 추가 지시를 보내도 Working은 같은 활성 턴을 유지한다. 접수 알림이 원래 작업의 종료·실패나 새 턴 시작으로 오인되지 않아야 한다.

### 전송 경계와 원문 보존

- renderer → 세션에 묶인 API → preload IPC 허용 경로 → main의 Native 세션 → `turn/steer`로 연결한다. main이 실제 `sessionId`·선택 세대·`threadId`·활성 턴을 검사하고 현재 `expectedTurnId`를 검증한다. renderer가 보낸 임의 대화·다른 탭의 턴으로 전달하지 않는다.
- 안정적인 클라이언트 메시지 ID를 추가 지시마다 부여해 pending·API 응답·Native 사용자 메시지 사건을 연결한다. 동일 내용이라도 사용자가 별도로 보낸 추가 지시는 서로 다른 메시지로 보존하며, optimistic 표시와 Native 사건은 같은 ID일 때만 합쳐 중복을 방지한다. ID 제공·반환 범위는 구현 시 실제 Native 사건으로 확인한다.
- 전송 경로를 선택한 시점의 턴에 고정한다. 전송 직전·도중 턴 종료 또는 턴 불일치가 발생하면 새 턴·다른 턴에 자동 재전송하지 않는다. 실패 원문을 남기고 `새 요청으로 보내기` 같은 명시적 재전송 동작을 제공하는 기본안으로 한다.
- 오류·거절·미지원 응답에서는 원문을 복원하거나 별도의 실패 원문으로 보관한다. 그 사이 새 초안이 있으면 덮어쓰지 않는다. 응답 유실·시간 초과·연결 끊김은 접수 여부 미확인으로 구분하고 자동 재시도하지 않는다.
- 성공 응답의 `turnId`가 예상 턴과 다른 경우 정상 접수로 표시하지 않고 불일치를 드러낸다. 프로토콜이 지원되지 않으면 기능 미지원 이유를 표시하고 중단 후 재시작으로 몰래 대체하지 않는다.
- 추가 지시 수신·접수·실패가 기존 사용자 요청 상태·대화 읽기 위치·원문·리소스 관측을 잘못 초기화하지 않게 한다. 대화 재개 후의 Steer 메시지 복원은 실제 Native 저장 이력의 식별자·순서를 확인하고 중복 없이 표시한다.

### 구현 시 검증

- 작업이 계속 실행 중인 fixture에서 추가 지시를 보내 `turn/steer`의 thread·expected turn·text·메시지 ID, 정상 접수와 같은 턴 유지, 중단 호출 없음 및 새 `turn/start` 없음까지 확인한다.
- 짧은 시간에 연속 입력, 같은 내용 두 번의 의도적 전송, 중복 클릭, 전송 중 새 초안 편집, 한글 조합 Enter를 각각 확인한다.
- 시작 대기·종료 직전·종료 직후·승인 대기·중단 확인·시간 초과·연결 끊김·미지원·응답 턴 불일치·다른 탭/선택 세대의 지연 응답을 확인하고 원문·현재 초안이 보존되는지 검사한다.
- 실제 Electron에서 Working·입력·접수 문구·오류·포커스·읽기 위치·테마 색을 확인하고, 실제 Native 실행에서는 추가 지시 이후 공개 행동이 바뀌는 시나리오를 관찰한다. API 접수 성공만으로 모델이 지시를 반영했다고 판정하지 않는다. Input P0 계측에도 Steer 전송 및 스트리밍 중 입력을 포함한다.

## 개발 순서와 검증 방법

기준의 정의·필수 여부·결과는 `work.json.criteria`가 정본이며 현재 모두 미검증이다.

1. Input부터 동일 환경의 변경 전 기준선을 확보한다. 짧은 대화, 완료 카드가 누적된 긴 대화, 실시간 출력이 들어오는 긴 대화를 비교한다. fixture에는 최대 보관 길이 출력·JSON·코드·diff와 원본 사건 최대 2,000개 경계를 포함한다.
2. 입력 이벤트부터 입력값 표시 frame까지의 지연 p50/p95/최댓값, React commit 횟수·시간, 완료 카드 렌더 횟수, 50ms 초과 main-thread 작업, 스크롤 frame 간격을 측정한다. 고정 fixture·창 크기·빌드 방식·기기·측정 반복 횟수를 함께 기록한다. 합성 이벤트 지표와 실제 키보드·한글 조합 관측을 구분한다.
3. 가장 비싼 입력 경로를 최소 수정한다. 입력만 바뀔 때 변하지 않은 완료 카드와 Markdown이 다시 처리되지 않는지 확인한다. 이후 스트리밍·타이머 경로를 개선한다.
4. 카드 내부 스크롤 제거와 ^T 표시를 적용하고 읽기 위치·원문·한도·실패·대화 복원을 검증한다.
5. 같은 fixture로 변경 전후를 다시 측정한다. 제안 성능 목표는 입력 표시 지연 p95 50ms 이하, 입력으로 인한 100ms 초과 정지 없음이다. 기기 의존 수치이므로 기준선 확보 후 목표 적용 가능성과 실제 결과를 명시하며, 낮춘 목표로 자동 통과시키지 않는다. 입력 지연이 줄지 않으면 원인이 해결됐다고 판정하지 않는다.
6. Working 고정 표시의 전송·시작 대기·실행·무출력 대기·승인·중단·종료·실패·연결 끊김과 대화 전환을 확인한다. 과거 스크롤 위치·모니터 접힘·좁은 창에서도 표시와 입력이 가려지지 않아야 한다. 테마 토큰 대응·상태별 색·실제 대비를 검증하고 스타일 변경 전후의 입력 성능을 다시 비교한다.
7. Steer의 같은 턴 전달·접수·실패·종료 경합·원문 복원·연속 입력·다른 세션 격리를 검증한다.
8. 실제 Electron에서 휠·트랙패드·키보드·한글 조합·카드 포커스·^T를 확인한다. 관련 집중 테스트와 소스 정책·타입 검사·빌드를 수행한다. 합성 fixture 통과를 사용자의 실제 장시간 세션 성능 해결로 승격하지 않는다.

## 제외 범위와 남은 판단

Native 모델의 첫 답변 생성 시간, 서버 지연, 자동 모델 배분, 사이드바 전면 개편, 보관 한도 확대는 이번 범위에 포함하지 않는다. 별도 전체 보기 패널을 만들지 않는다. 카드 내부 스크롤 제거만으로 모든 렉이 해결됐다고 가정하지 않는다.

사용자 방향은 확정됐으며 추가 선호 질문 없이 명세를 보존한다. 10줄 미리보기·보관 한도 재사용·긴 줄 줄바꿈·JSON 상한 처리·수치 목표는 구현을 시작할 때 검증할 개발 기본안이다. 성능 원인과 최적화 수단은 기준선 계측 후 정한다. Working 배치와 역할별 색 배분은 이번 추가 요구를 구체화한 기본안이다. 사용자의 매트릭스 명칭과 원본 테마 ID mint의 차이를 보존한다. Steer는 작업 중 같은 턴 추가 지시가 목표이며 자동 큐·자동 재시도·자동 중단 후 재시작은 제외한다. 이번에는 제품 구현·실제 화면 재현·성능 검사·색상 대비 검사·실제 Native Steer 요청을 실행하지 않았다.
