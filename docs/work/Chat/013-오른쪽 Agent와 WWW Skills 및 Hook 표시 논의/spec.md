# 오른쪽 Agent와 WWW Skills 및 Hook 표시 논의

## 요청과 권한

사용자는 다음 개발 스펙·요구사항 논의를 요청했다. www-dev가 www-spec을 선택해 기록하며 제품 코드·스킬 정본 수정·앱 재시작·커밋·게시 권한은 없다. Chat 012의 네 요구와 구분하는 오른쪽 바 표시 작업이다.

## 확인된 사용자 결정

사용자는 전체 목록을 항상 보여주고 현재 항목을 강조하는 방식을 선택했다. Agent 아래 다섯 스킬의 트리는 앞서 제시한 구조 그대로다.

- WWW 개발 Agent
  - spec — 명세
  - design — 설계
  - build — 구현
  - diagnose — 진단
  - verify — 검증

범용 스킬 113개를 이 영역에 표시하지 않는다. 현재 저장소에는 commit·report 스킬도 있지만 이번에 사용자가 선택한 고정 트리는 위 다섯 항목이다. 스킬 파일이나 설치를 삭제하는 요청은 아니다. 현재 항목의 강조는 실제 선택·진행을 보여주는 요구이며 정확한 근거 연결과 미확인 상태는 후속 설계에서 정한다.

## 역할과 발견 경로의 사실

agents/www/AGENT.md는 www-dev의 역할·단계 선택 계약이다. skills/www에는 스킬 절차 정본이 있으며 .agents/skills는 해당 정본을 가리키는 심볼릭 링크다. 역할 문서의 존재가 독립 Agent 프로세스 실행을 뜻하지 않으며 스킬 파일 읽기를 실제 적용 완료로 승격하지 않는다.

## Hook 조사 이력

현재 WWW 저장소 cwd로 실제 codex app-server의 hooks/list를 조회했다. complete=true, 오류 없음, 등록 처리기 8개로 응답했다. BoxBox 플러그인 3개(sessionStart/postToolUse/stop), Vercel 플러그인 5개(sessionStart 3개/postToolUse 1개/sessionEnd 1개)다. 이벤트 종류는 네 종류이고 프로젝트 전용 등록은 0개다. 이는 조회 시점의 등록 상태이며 실행 횟수·실행 성공·항상 같은 수량을 보장하지 않는다. BoxBox 모드 off와 처리기 등록 여부도 다른 상태다.

후속 논의에서 사용자는 Hook 보기를 이번 오른쪽 바에서 제외하기로 결정했다. 아래 등록 수는 조사 당시 이력이며 현재 화면 요구의 표시 항목이 아니다. 내부 검증·보고서 수명주기 동작을 등록된 Native Hook과 혼동하지 않는다.

## 수용 기준 연결

기준의 정의·필수 여부·결과는 work.json.criteria가 정본이며 모두 미검증이다.

- AC-1: 사용하지 않은 스킬도 고정 트리에서 볼 수 있고 범용 목록이 섞이지 않는 시나리오다.
- AC-2: 현재 항목 강조와 실제 근거·미확인 경계를 다루는 시나리오다.
- AC-3: 이번 오른쪽 바에서 Hook 보기를 제외하고 실행 설정과 표시 범위를 구분하는 시나리오다.
- AC-4: 실제 Subagent가 호출되면 표시하고 완료가 확인되면 같은 항목에 완료 표시등을 켜는 시나리오다.
- AC-5: 요구사항 처리 계획의 항목·상태와 현재 활성 항목의 산문형 진행 요약을 연결해 추적하는 시나리오다.

## 다음 논의

사용자는 Plan을 Plan.md 또는 Native가 요구사항을 처리하는 계획으로, Progress를 현재 활성 Plan 항목의 산문형 진행 요약으로 설명했다. 따라서 Plan과 Progress를 서로 독립된 로그로 다루지 않고 요구사항·활성 항목으로 연결한다. Subagent는 작업 완료 후 같은 항목에 완료 표시등을 켜는 것으로 사용자가 선택했다. Hook 보기는 이번 오른쪽 바 범위에서 제외하는 것으로 사용자가 선택했다. 현재 추가 사용자 선택을 요구하는 핵심 미결정은 없다. 다음 개발에서는 현재 항목·Subagent·계획·진행 설명을 실제 사건과 연결하는 데이터 출처와 상태 수명부터 설계한다. 이미 확정된 고정 트리와 현재 항목 강조 여부는 다시 묻지 않는다. 원인 재현과 제품 구현은 이 명세 작성으로 승인되지 않는다.

## Vercel Hook 조사

사용자는 Vercel 플러그인이 필요 없다고 밝히고 등록·실행 경로 조사를 요청했다. 전역 Codex 설정의 enabled=true와 설치본 Hook 5개를 확인했으며 상세 근거·실행 미확인 범위는 diagnosis.md에 기록했다. 비활성화·삭제는 수행하지 않았고 초기 응답 지연의 원인으로 확정하지 않았다.

## Vercel 전역 비활성화 반영

사용자의 후속 직접 실행 요청으로 Vercel 플러그인을 전역 비활성화했다. 새 Native 프로세스에서 Vercel 스킬·Hook은 모두 0개이며, 등록 Hook은 BoxBox 3개로 줄었다. 앞선 8개는 비활성화 전 관측 이력으로 보존한다. 오른쪽 바 제품 UI의 고정 목록·강조 구현은 아직 수행하지 않았다.

## Agent와 Plan·Progress 개요

사용자는 WWW Agent가 보이고 실제 Subagent가 호출되면 Subagent도 보이기를 요청했다. Agent 표시 다음에는 개요로 Plan과 Progress를 두어 계획과 현재 작업을 추적하는 시스템을 원한다. 이 요청을 위해 실제 Subagent를 새로 호출하는 것은 아니다.

WWW Agent 아래 다섯 Skills를 고정 표시하는 기존 결정은 유지한다. Subagent의 부모·자식 관계와 역할·실행 상태는 실제 제공되는 식별 근거로 연결한다. Subagent 완료가 확인되면 기존 항목을 유지하고 완료 표시등을 켠다. Subagent별 별도 Skills 목록이나 임의 진행률을 추가하는 요구는 없다.

Plan은 Plan.md 등 계획 문서 또는 Native가 요구사항을 처리하며 제공하는 계획의 작업 항목과 상태다. Progress는 현재 진행 중인 Plan 항목에 대해 Thinking의 산문을 요약하듯 작업 상황을 설명한다는 사용자 정의를 따른다. 구현 입력으로는 Native가 제공한 공개 판단 요약·진행 설명 및 실제 실행 사건을 사용하고, 제공되지 않은 내부 추론이나 판단 이유를 생성하지 않는다. 계획 목록과 산문 요약은 같은 요구사항·활성 항목으로 연결한다. 정확한 계획 파일 경로, 문서·Native 계획이 함께 있을 때의 정합성, 저장·복원 방식은 후속 설계에서 확인한다.

정적 코드에서는 turn/plan/updated 처리와 collabAgentToolCall의 일반 도구 처리 경로가 확인된다. 이것만으로 요청한 Agent 트리나 작업 전체 추적 시스템이 구현됐다고 판정하지 않는다. 실제 Subagent 사건·식별자와 계획의 원본·갱신 방식은 후속 조사·설계에서 확인한다.

## Plan·Progress 사용자 예시

요구사항이 “로그인 기능 구현”이면 Plan에는 “개발 문서 확인”, “로그인 로직 개발” 같은 작업 항목이 있다. 로그인 로직 개발이 활성 상태인 동안 Progress는 그 항목에서 수행하는 확인·변경·판단의 공개 설명을 산문으로 요약한다. 이 예시는 요구의 뜻을 설명하기 위한 것이며 현재 실제 로그인 작업을 수행했다는 기록이 아니다. Progress는 전체 계획을 다시 나열하는 목록이나 원시 명령 로그가 아니다.

## Subagent 완료 표시 결정

사용자는 Subagent가 완료되면 “그냥 완료 불이 들어오면 된다”고 선택했다. 실행 항목을 유지하며 실제 완료 사건에 따라 완료 표시등으로 전환한다. 등록이나 도구 호출 종료만으로 Subagent 작업 완료를 추정하지 않는다. 색상 외의 상태 식별과 실패·중단·미확인 표시는 후속 설계에서 기존 실제 상태 구분을 유지하도록 정한다.

## 최종 표시 범위와 개발 인계

사용자는 Hook 보기를 제외하기로 결정했다. 이 결정은 표시 범위에 관한 것이며 남은 BoxBox Hook을 끄거나 삭제하는 요청이 아니다. Vercel은 앞선 별도 직접 요청으로 이미 전역 비활성화된 상태다. 기존 상세 모니터 전체의 삭제나 Hook 실행 기능 변경으로 범위를 확대하지 않는다.

기본 오른쪽 바는 Agent 영역과 개요 영역으로 구성한다. Agent 영역에는 WWW Agent, spec/design/build/diagnose/verify 고정 목록과 현재 항목 강조, 실제 호출된 Subagent와 완료 표시등이 있다. 개요는 Plan의 요구사항별 작업 항목·상태와 활성 항목에 연결된 산문형 Progress다.

제품 구현은 아직 승인받거나 수행하지 않았다. 명세는 사용자 결정이 정리된 ready 상태이며 수용 기준 결과는 모두 미검증이다. 후속 설계에서 실제 Agent·스킬 선택·Subagent 수명·계획 사건과 공개 진행 설명의 연결 가능성을 확인한다. 준비 문서의 존재나 이름 언급을 실제 실행으로 표시하지 않는다. 정확한 레이아웃·상태 표현·계획 파일 경로와 Native 계획의 정합성은 이 합의를 유지하는 설계 범위다.

## 2026-11-16 구현 착수

사용자가 앞선 1·2 범위 전체와 작업 내부 모델 배분의 스킬·하네스 반영을 요청하고 작업 시작을 지시했다. 기존 문서 전용 권한은 당시 이력으로 보존하며 현재 구현·검증·같은 범위 실패 수정을 허용한다. 커밋·push는 하지 않는다. Sol이 통합을 소유하고 Luna 수집·Terra의 경계가 분명한 구현을 분담한다. 실제 검증·독립 검토 전에는 완료로 기록하지 않는다.
