# 참조 HTML 기반 한 페이지 보고서 양식 변경 명세

## 요청과 권한

사용자는 “보고서 양식 변경있어. 이것도 문서화해놓자”라며 다운로드 폴더의 `www-report.html`을 지정했다. 해당 파일을 보고서의 읽기 순서·정보 구조·시각 양식의 참조로 삼아 개발명세만 작성한다. 제품 소스·보고서 생성기·현행 보고서 계약·기존 보고서 이력은 이번에 수정하지 않는다. 앱 재시작·커밋·push도 하지 않는다.

기존 Reports 002의 독자 중심 내용 요구를 유지하면서 새 참조 HTML의 구조와 표현을 구체화하는 후속 명세다. Chat 014의 Input·Working·테마·Steer 요구와는 별도 작업으로 관리한다. 수용 기준의 정의·필수 여부·결과는 `work.json.criteria`가 정본이며 현재 AC-1~AC-7 모두 미검증이다.

## 내용과 상태의 의미

연결 기준: AC-2, AC-3, AC-6.

- 독자는 첫 화면에서 무엇이 달라졌고 어디까지 확인했으며 무엇이 남았는지 파악해야 한다. 첫 문단은 자연스러운 짧은 결론으로 작성하고 기술 식별자·명령·해시를 앞세우지 않는다.
- 당시 업무 상태, 발행 시각, 현재 소스에 대한 근거 적용성, 필수 완료 감사 상태를 별도 정보로 표시한다. 과거 통과를 현재 통과로 보이게 하거나 오래된 근거를 새 실패로 바꾸지 않는다. 부분 완료·차단·감사 미실행·미확인은 상단과 해당 절에서 확인할 수 있어야 한다.
- 결과 표는 변경 파일 나열보다 사용자 행동의 전후 차이를 설명한다. 실패·미구현·미해결 항목도 같은 표에 남긴다. 요구와 결과·근거의 연결이 기존 reader 정보보다 약해지지 않게 한다.
- 검사 수는 명령 수·시도 수·조건 수·시나리오 수를 구분하고 집계 관계를 설명한다. 출처가 없는 검사 수·통과 수를 만들지 않는다. 숫자만 크게 표시해 사용자 행동 검증을 대신하지 않는다.
- 검증 설명은 방법·기대·관측·환경·한계가 연결돼야 한다. 합성 Native와 실제 Native, Electron과 실제 OS 입력, 실행 종료와 사용자 요구 충족을 구분한다. 없는 설명은 미기록으로 알린다.
- 실제로 중요한 대안 선택이 있었으면 선택·근거·대안·불리함을 문제와 접근에 포함하거나 상세로 연결한다. 새 여섯 절 구조 때문에 기존의 중요한 선택 정보를 삭제하지 않는다.
- 남은 일은 행동과 관찰 가능한 완료 조건을 쓴다. 담당자가 확인되지 않았으면 미정으로 두고 지어내지 않는다. 완료된 작업이면 남은 일 없음으로 명시하며 가짜 후속 할 일을 만들지 않는다.
- 감사 모델·정책은 작업에 연결된 실제 기록과 현행 정책에서 읽는다. 시안의 Opus 고정 문구를 일반 보고서 정책으로 복제하지 않는다.

## 상세 근거와 기존 이력 보존

연결 기준: AC-4, AC-6.

- 기본 본문에서 결론·문제·변경·검증 한계·다음 행동을 읽고 상세를 열면 AC 요약, 실행·검토 이력, 소스/기준 식별, 원문 경로와 측정 한계를 확인한다. 중요한 실패나 차단을 접힌 상세에만 숨기지 않는다.
- 타임라인은 실제 저장된 각 발행 entry의 시각과 변경 요약을 사용한다. 당시의 기록임을 표시하고 같은 제목의 모든 이력과 각 과거 UUID 조회를 유지한다. 원문에 없는 이력 요약은 사실처럼 생성하지 않는다.
- 기존 WorkReport JSON·work UUID·entry UUID·narrative·semanticHash·판정·증거의 의미를 보존한다. 양식 변경은 읽기/렌더링 변경을 우선하며 기존 JSON을 새 템플릿에 맞춰 재저작하거나 과거 내용을 덮어쓰지 않는다.
- `narrative.reader`가 없는 구형 보고서와 자동 기록도 읽을 수 있어야 한다. 기존 필드로 표현할 수 없는 부분은 미기록 안내를 두고 없는 항목을 사실처럼 채우지 않는다.
- 앱 보고서와 내보낸 독립 HTML은 같은 선택 entry의 결론·상태·한계·근거·누락 안내를 제공한다. 독립 HTML의 저장 당시 현재성과 앱에서 새로 계산한 현재 적용성은 시점 차이를 밝혀 구분한다.

## 구현 전 매핑과 검증 계획

연결 기준: AC-1~AC-7.

1. 참조 원본의 내용 식별값을 대조하고 실제 화면을 열어 글자·폭·색·반응형을 확인한다. 이번 정적 분석에서 관측하지 못한 렌더링과 동작은 이 단계에서 확인한다.
2. 기존 `ReportNarrative`·`ReportReader`·work snapshot·검증/검토 정보·보고서 entries를 여섯 절에 매핑한다. 기본안은 summary/story → 결론과 문제, before/after 및 reader.requirements → 접근과 결과, reader.decisions → 중요한 선택, reader.checks 및 저장 판정 → 검증, reader.nextActions → 남은 일, entries/references/source → 이력·상세다. 의미가 부족하면 미기록으로 표시하고 필드 확장이 필요한지 별도 설계한다.
3. `scripts/workflow/report-view.ts`, `scripts/workflow/reports.ts`, `src/reports-view.tsx`, `src/reports.css`의 실제 책임과 공유 렌더링 경로를 확인한다. 기존 writer·조회·중복 억제·상한을 유지한다. 양식만 바꾸는 데 schema 변경이나 과거 JSON 이전을 기본으로 하지 않는다.
4. 완료·부분 완료·실패·차단·감사 미실행·오래된 근거, legacy/자동 기록, 내용 없는 절, 긴 한글·URL·코드·큰 이력의 fixture를 비교한다. JSON 의미 보존·HTML 이스케이프·같은 entry의 앱/내보내기 내용·목차 링크·접힘·과거 UUID 읽기를 검사한다.
5. 실제 Electron과 일반 브라우저에서 넓은 폭·790px/540px 경계·좁은 폭, 키보드 목차 이동·상세 펼침·포커스·모션 축소를 확인한다. 라벨·아이콘과 색의 의미 및 일반 본문 대비 4.5:1 목표를 검사한다.
6. 원본 visualization wrapper·외부 CDN·범용 스크립트를 제품에 그대로 넣지 않는다. 보고서는 기존 계약대로 외부 네트워크·스크립트 실행 없이 기본 본문·목차·펼침을 읽을 수 있어야 한다. 독립 HTML 오프라인 열기와 인쇄에서 본문·완료 차단·검증 한계가 누락되지 않게 한다. 인쇄 시 목차·접힌 상세의 포함 여부를 명시적으로 검증하며 필수 정보가 상세에만 남지 않게 한다.
7. 제품 구현 시 관련 집중 테스트·소스 정책·타입 검사·빌드 및 필수 독립 검토를 실행한다. 통과한 범위와 브라우저·OS·인쇄 미실행 범위를 구분한다. 현재 문서 작성은 양식 적용 완료가 아니다.

## 범위와 남은 판단

포함은 보고서 내부 구조·스타일·읽기 동작·앱/HTML 표시 일관성과 기존 의미 보존이다. Chat 스크롤·Working·Steer 구현, 보고서 자동 작성 판단기 변경, 기존 파일명 일괄 이전, 보고서 원문 재저작은 제외한다.
