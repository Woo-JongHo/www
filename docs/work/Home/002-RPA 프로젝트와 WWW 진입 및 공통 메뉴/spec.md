## 현재 검증 회수와 과거 관측의 구분 — 2026-11-17

현재 재개는 기존 UUID의 기능 근거·문서·독립 감사·보고서 및 완료 판정을 회수하는 단계다. 과거 시도·권한 원문·보고서를 보존하며 아래의 날짜 없는 “현재”, “최신”, “fresh”가 과거 로그나 시도를 가리키면 당시 기록으로 읽는다. 최신 소스의 실제 관측은 work.json과 verification.md의 새 시도 및 적용성으로 판단한다.

이번 Terra 검토는 현재 직접 사용자 승인 원문과 요청 해시 `76e671ded65c0d349b239afa9626aa1727d62fc562bfdd1482849993117a171c`, 해당 작업 요청 해시·현재 source/criteria/policy·review 단계에 묶인 공식 직접 경로를 사용한다. 일반 검토 정책이나 과거 실패를 변경하지 않고 실제 관측 모델·별도 process receipt를 확인한다. 검토 실행 전 상태를 통과로 표시하지 않는다.


## 현행 범위와 초기 기록의 구분

2026-11-16 사용자는 이번 세션 전체 구현과 작업 시작을 요청했고, 여러 터미널의 종류는 **독립 Codex 대화 탭 여러 개와 동시 실행**으로 확정했다. 현재 범위는 View Page·기존 로컬 폴더 등록·별도 WWW·대상별 공통 메뉴·작업 기록 기반 읽기 칸반·독립 대화 탭이다. 개발용 스킬·하네스의 내부 모델 배분과 제품 Chat의 자동 모델 라우터를 구분하고 토큰 절감은 실측 전 미확인으로 둔다. 커밋·push는 승인 범위에 포함하지 않는다.

아래 초기 제안·열린 질문·문서 전용 권한은 결정 과정의 이력이다. 당시의 ‘아직 미정’, ‘개발하지 않음’을 현재 권한·구현 범위로 읽지 않는다. 현행 수용 기준의 정의·필수 여부·결과는 같은 UUID의 `work.json`이고, 현재 동작의 정본은 [대시보드 명세](../../../specs/dashboard.md), [Chat 명세](../../../specs/chat.md#chat-sessions-01)다. 소스 존재·구현과 실제 검증·독립 검토 수용을 각각 구분한다.

초기 수용 기준·권한·요청 해시의 정확한 원문은 [Git 기준본에서 회수한 작업 레코드 이력](history/README.md)에 보존한다. 처음부터 schema2였으므로 schema1 adopt용 `workflow.legacyRecord`는 없다. 별도 원본 보관 누락은 독립 감사에서 발견해 회수했으며 당시 이미 보관됐다고 표현하지 않는다.

최신 검토 운영 결정: 사용자는 Opus 사용량 소진이 확인된 뒤 Claude를 사용할 수 없으면 Terra로 감사를 계속하라고 직접 지시했다. 이전의 이번 세션 Opus 고정은 이 결정으로 대체하며, 실제 읽기 전용 Terra 검토의 요청·권한·관측 모델·원문을 공유 core에 연결한다. 검토 불합격을 호출 불가로 취급하거나 작성자가 자기 결과를 승인하지 않는다.

## 초기 문서화 기록 — 구현 착수 전 이력

이 절의 제안·미결정·현재형 표현은 초기 문서화 당시의 판단이다. 위 현행 범위와 아래 구현 착수·종류 확정 기록으로 이어지며 현재 권한을 제한하거나 제품 동작을 설명하지 않는다.

### 요청과 목적

프로젝트 선택 전 전체 대시보드인 View Page를 제공하고, RPA 프로젝트 또는 단일 WWW를 선택해 대상별 공통 메뉴로 들어가는 탐색 구조를 정리한다. Chat의 여러 터미널 요청도 함께 기록한다.

사용자의 직접 요청으로 접수했다. 요청 식별값은 work.json의 workflow.requestHash에 보존한다.

### 범위

변경 경로·표면·검증 명령과 커밋·게시 권한은 work.json의 workflow.authorization을 따른다. 범위 확대는 기존 권한으로 간주하지 않는다.

초기 화면·상태·데이터 경계와 검증 전략은 [설계](design.md), 후속 단위와 수용 기준 연결은 [실행 계획](tasks.md)에 명시했다. 이 두 문서는 당시 개발 전 제안이며 현재 구현 권한은 아래 2026-11-16 직접 요청에서 이어진다.

### 수용 기준

정의와 필수 여부의 정본은 work.json이다. 관련 기준: `S1`, `S2`, `S3`, `S4`, `S5`, `S6`, `S7`, `S8`.

### 프로젝트 선택 전 — View Page

사용자 추가 결정: 앱을 처음 열었을 때 프로젝트 선택 전 메인 화면에서 전체 대시보드를 본다. 사용자는 VS Code를 처음 열어 프로젝트를 선택하는 진입 화면을 비유로 들고 이 화면을 ‘View Page’라고 불렀다. 특정 제품의 실제 동작을 검증하거나 그 UI 전체를 복제하라는 요구는 아니다.

View Page는 특정 프로젝트에 들어가지 않은 상태의 앱 전체 진입 화면이다. 왼쪽에는 RPA 프로젝트 목록과 단일 WWW 진입점을 두고 중앙에는 전체 대시보드를 표시한다. 프로젝트를 먼저 선택해야만 전체 대시보드를 볼 수 있는 흐름으로 만들지 않는다.

```text
앱 실행 → View Page
┌─ 왼쪽 사이드바 ─────┬─ 메인 화면 ───────────┐
│ RPA (+)            │ 전체 대시보드          │
│   프로젝트 A       │                       │
│   프로젝트 B       │ 프로젝트 선택 전 보기  │
│ WWW                │                       │
└────────────────────┴───────────────────────┘
          ↓ 프로젝트 또는 WWW 선택
선택 대상의 공간
  대시보드 / 대화 / 생태계 / 리포트
```

전체 대시보드와 대상별 대시보드는 서로 다른 범위의 화면이다. 전체 대시보드는 앱 전체를 보는 용도이고, 대상별 대시보드는 선택한 RPA 프로젝트 또는 WWW를 보는 용도다. 전체 화면의 구체적인 집계 대상·정보·카드와 데이터 수집 방식은 아직 정하지 않았다. 전체 대시보드를 보기 위해 특정 프로젝트의 대화나 터미널을 자동 실행하는 요구도 없다.

### 사용자에게 확인된 탐색 구조

앱을 처음 실행하면 왼쪽 사이드바에 다음 진입점을 표시한다. 아래 프로젝트 이름은 구조 설명용 예시이며 실제 등록 항목을 의미하지 않는다.

```text
RPA                         (+)
  ├─ 프로젝트 A
  ├─ 프로젝트 B
  └─ …

WWW
```

- RPA는 여러 프로젝트를 넣을 수 있는 상위 묶음이다.
- RPA 옆의 `+`는 프로젝트 추가 진입점이다. 추가 방식은 아직 정하지 않았다.
- WWW는 RPA 하위 프로젝트가 아닌 별도의 단일 진입점이다. 사용자의 표현인 ‘단일 우리 구조’를 유지한다.
- RPA 프로젝트 하나 또는 WWW를 선택하면 선택 대상 안에서 다음 메뉴를 제공한다. 메뉴 순서는 사용자 요청을 따른다.

```text
선택한 프로젝트 또는 WWW
  ├─ 대시보드
  ├─ 대화
  ├─ 생태계
  └─ 리포트
```

이는 탐색 계층을 설명하는 도식이다. 클릭 후 하위 메뉴를 제자리에서 펼칠지, 왼쪽 사이드바 전체를 대상별 메뉴로 전환할지는 아직 확정하지 않았다.

### 초기 문서화 범위와 당시 구현의 차이 — 이력

초기 범위는 위 탐색 구조를 문서화하는 것이었다. 당시 제품 코드·테스트·실행 설정은 수정하지 않았고 RPA 자동화 엔진, 프로젝트 생성 기능, 대시보드 본문 구현도 포함하지 않았다. 이번 구현에서도 새 프로젝트 생성·RPA 자동화 엔진은 추가하지 않으며 기존 폴더 등록과 작업 기록 보드를 구현한다.

현재 `src/renderer.tsx`의 왼쪽 사이드바는 작업 공간, 화면 이동(대화·생태계·리포트), 최근·즐겨찾기 프로젝트, CODEX 상태, 저장된 대화, 폴더 경로·변경 개수를 한 열에 표시한다. 대시보드는 이 화면 메뉴에 없다. 위 구조는 앞으로의 변경 목표이며 현재 앱에서 제공하는 동작으로 표현하지 않는다.

기존 Home/001은 외부 제품 패턴을 조사한 연구 제안이다. 이번 사용자 결정과 관련 작업으로 연결하되 연구 원문과 과거 검토 이력을 덮어쓰지 않는다.

### 초기 문서화의 검토 시나리오 — 이력

다음 목록은 초기 문서화 단계의 검토 시나리오다. 현행 기준의 정의와 결과는 `work.json.criteria`에만 두며 현재 구현 검증은 위 ‘현행 기준에 연결한 검증 시나리오’를 따른다.

- `S1`: 초기 진입 도식을 읽어 RPA의 추가 버튼, 복수 프로젝트, 별도 WWW가 구분되는지 대조한다. 프로젝트가 0개인 경우에도 RPA와 추가 버튼을 식별할 수 있어야 한다. 빈 상태 문구는 후속 결정이다.
- `S2`: RPA 프로젝트 선택과 WWW 선택의 두 여정에서 공통 메뉴 네 개의 이름과 순서를 대조한다. 어느 대상을 보고 있는지 식별하는 표시 방식은 후속 설계한다.
- `S3`: 프로젝트 추가 정상 완료·사용자 취소·실패, 대상 선택·대상 간 이동·앱 재실행을 후속 검증에 포함한다. 취소·실패를 추가 성공으로 표시하지 않는 것을 제안하며, 구체적인 복원 동작은 아직 합의하지 않았다.
- `S4`: 문서 변경 범위와 diff를 확인하고, 앱 실행·GUI 검증·제품 구현 완료를 주장하지 않는다.
- `S5`: 앱 실행 후 프로젝트를 선택하지 않아도 View Page의 전체 대시보드와 왼쪽 RPA·WWW 진입점을 볼 수 있는 여정을 확인한다. 프로젝트가 없을 때도 진입 화면이 성립해야 하며 구체적인 빈 상태 표현은 후속 설계한다. 대상을 선택한 뒤의 대시보드와 전체 대시보드의 범위를 구분한다.
- `S6`: Chat의 여러 터미널 요구가 기록돼 있고, 터미널 종류와 표시·실행 방식이 미결정임을 확인한다. 미정인 내용을 구현되거나 합의된 것으로 표현하지 않는다.

### 초기 결정과 열린 질문 — 이력

확정 사항은 첫 진입 View Page의 전체 대시보드, RPA의 프로젝트 추가 진입점, RPA 아래 복수 프로젝트, 별도 단일 WWW, 두 대상에서의 공통 메뉴 네 개와 그 순서다.

다음은 구현 전에 정할 사항이며 사용자 합의로 취급하지 않는다.

1. 선택 후 표시: 같은 트리 아래 메뉴를 펼치는 방식 또는 대상별 사이드바로 전환하는 방식.
2. RPA 프로젝트 추가: 기존 로컬 폴더 등록인지, 새 프로젝트 생성까지 포함하는지.
3. WWW가 가리키는 실제 경로·데이터 범위와 고정 대상 식별 방식.
4. 전체 대시보드와 대상별 대시보드 각각에 표시할 정보, 대상을 선택했을 때 처음 여는 화면. 메뉴의 첫 번째라는 사실만으로 대상별 대시보드 자동 진입을 확정하지 않는다.
5. 기존 저장된 대화 목록·검색·새 대화 버튼을 어디에 둘지, 기존 즐겨찾기를 어떻게 다룰지.

기존 실행·전송·승인 대기와 미해결 실패 요청 중의 프로젝트 전환 제한, 프로젝트별 데이터 격리는 보존하는 방향을 제안한다. 이 문서가 기존 제한을 해제하는 근거가 되지는 않는다.

- 카드에는 작업 이름, 소속 프로젝트, 관측한 상태와 질문·진행 정보를 표시하는 방향을 제안한다.

- ‘검토 필요’ 등 열 이름과 상태 매핑은 WWW에 맞춘 제안이다. 원본의 병합 준비 상태를 WWW의 검증 완료로 치환하지 않는다. Native 답변 종료만으로 업무 완료를 판정하지 않는다.
- 드래그로 카드를 이동하는 수동 업무 보드인지, 실제 세션 상태를 읽는 관찰 보드인지는 미정이다. 카드 단위가 작업·대화·터미널 중 무엇인지, 원본 데이터와 갱신 주체도 후속 결정한다.

`S7` 후속 검토에서는 전체/대상별 범위, 상태별 카드, 카드에서 Chat·터미널로 이동하는 관계를 대조한다. 자료 없음·일부 프로젝트 수집 실패·진행 중과 완료 구분을 다루고, 실제 자료가 없는 카드와 수치를 제품 데이터처럼 만들지 않는다.

수집·기계적 대조, 조사·일상 검증, 설계·구현·통합, 독립 리뷰, 최종 감사의 역할을 구분한다. 구체적 모델 ID·추론 수준은 실행 시 유효한 정책과 가용성으로 선택하고, 선택 사유·요청 모델·실제 관측 모델·실행 결과·미실행 사유를 추적하는 방향으로 설계한다.

`S8` 검증에서는 업무별 배치 사유, 실제 호출 증거, 미확인 모델 표시, 미실행·실패·대체 근거와 작성/검토 분리를 대조한다. 현재는 설계 요구이며 자동 배치 기능을 구현한 상태가 아니다.

## 2026-11-16 구현 착수

사용자의 이번 세션 전체 해결 및 작업 시작 요청으로 현재 구현·검증을 허용한다. 이전 문서 전용 권한은 당시 이력이다. 기존 폴더 등록, 대상별 사이드바와 전체 보기 복귀, 작업 기록 기반 읽기 칸반을 구현 범위로 삼는다. 실제 완료 상태는 work.json을 보존하고 Native 응답 종료로 승격하지 않는다. 이 착수 시점에는 터미널 종류 응답을 기다렸으며 이어진 결정은 다음 절에 기록한다. 커밋·push는 하지 않는다.

## 2026-11-16 터미널 종류 확정과 동시 실행

사용자는 선택 질문에 “독립 Codex 대화 탭 여러 개 + 동시 실행 (권장)”을 명시했다. 일반 셸/PTY는 이번 범위가 아니다. 각 탭의 Native 연결·thread·turn·출력·승인·중단을 격리하고 실행 중에도 다른 탭으로 전환한다. 탭 전환은 실행 종료가 아니다. 실행·승인 중 닫기는 거부하고 중단 후 닫도록 안내하며 마지막 탭은 유지한다. 초안·실패 원문이 남은 탭의 닫기는 frontend에서 막아 먼저 처리하도록 안내한다.

새 탭은 현재 프로젝트에서 시작하고 Native child는 실제 조회/요청 전까지 생성하지 않는다. 이미 다른 탭이 소유한 같은 프로젝트·thread를 중복 재개하지 않는다. 세션별 선택·프로세스 수명을 closure로 소유하고 전역값을 교체해 비동기 실행을 흉내내지 않는다. 앱 종료는 모든 child와 리소스 저장을 정리한다. 탭 목록·초안은 이번 앱 세션의 메모리이며 재시작은 기존 Native 대화 원장 재열기를 유지한다. 별도 메시지 DB나 강제 자동 재개를 추가하지 않는다.

## 현행 구현과 검증의 구분

main은 공유 프로젝트·리소스 원장과 세션 registry·IPC 라우팅을 소유하고 `native-session.ts`는 탭별 Native 연결·프로젝트·thread/turn·승인·사건을 소유한다. `SessionApiProvider`는 조회·리포트 API와 사건·리소스 구독을 탭에 묶고 SessionShell은 비활성 App도 유지한다. 실행 중 다른 탭을 선택할 수 있으며 같은 탭의 프로젝트·대화 전환 제한과 구분한다. 세부 책임은 [아키텍처](../../../ARCHITECTURE.md#독립-세션과-동시-실행)를 따른다.

개발 내부 모델 배분은 정책·스킬·하네스에 구현됐지만 제품 Chat의 요청 자동 분류·모델 선택 라우터는 구현하지 않았다. 토큰 절감은 동일 완료 조건의 비교를 측정하지 않아 미확인이다. 작성된 문서와 소스 존재만으로 수용 기준 통과나 최종 감사 완료를 주장하지 않으며 해당 실행과 한계는 같은 UUID의 검증 기록에 연결한다.
