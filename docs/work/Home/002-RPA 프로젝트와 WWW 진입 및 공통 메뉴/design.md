# View Page·프로젝트 탐색·칸반·Chat 설계

## 설계의 지위

작업 ID는 `work-4573f7d4-62eb-4e72-9985-62994c1b30a8`다. 사용자 요구는 [명세](spec.md), 수용 기준의 정의·결과는 [작업 레코드](work.json)가 소유한다. 이 문서는 개발 전 설계 초안이며 구현 권한이나 독립 검토 통과를 의미하지 않는다. 아래의 ‘제안’은 사용자 확정 사항과 구분한다.

## 기준선과 재사용

현재 앱은 Electron main → 제한된 preload/IPC → React renderer 경계를 사용한다. `src/projects.ts`의 realpath 기반 프로젝트 식별, `src/shared.ts`의 프로젝트·대화·이벤트 계약, `src/projection.ts`의 사건 투영을 재사용하는 방향이다. 화면 전환은 `src/renderer.tsx`, 활동 표시는 `src/native-activity-view.tsx`에 있다.

현재 프로젝트 전환은 기존 Native 연결과 선택 상태에 영향을 준다. 최근 프로젝트 목록이 있다는 사실만으로 여러 프로젝트의 실시간 실행 현황을 이미 수집한다고 간주하지 않는다. 다중 터미널·다중 Native 동시 실행은 현행 구현의 보장 범위가 아니다.

생태계는 현재 WWW 빌드의 구조를 보여준다. RPA 프로젝트의 소스를 자동 분석하는 기능은 별도 설계가 필요하다. 리포트의 조회 대상과 실행 중 대화 대상도 현재 별도이므로 새 탐색 대상과 연결할 계약을 명시해야 한다.

## 화면과 탐색 경계

### 확정된 계층

```text
앱 실행
└─ View Page — 프로젝트 미선택
   ├─ 왼쪽: RPA (+) → 프로젝트 목록 / 별도 WWW
   └─ 중앙: 전체 대시보드

프로젝트 또는 WWW 선택
└─ 대상 공간
   ├─ 대시보드
   ├─ 대화(Chat) — 여러 터미널 요청 포함
   ├─ 생태계
   └─ 리포트
```

### 탐색 제안

선택 후 왼쪽을 대상 이름과 공통 메뉴로 전환하고, 위에 ‘전체 보기’ 복귀 버튼을 두는 방식을 제안한다. 대상별 대시보드를 첫 진입 화면으로 제안하되 아직 사용자 확정은 아니다. 이전 프로젝트 목록은 View Page에서 다시 선택한다. 기존 대화 목록·검색·새 대화 버튼은 Chat 내부 탐색 영역으로 옮기는 방식을 제안한다.

화면 탐색과 실행 컨텍스트 선택을 분리한다. View Page로 이동하는 동작 자체가 실행 중인 요청을 중단하거나 프로세스를 종료해서는 안 된다. 반면 실제 프로젝트 실행 컨텍스트를 바꾸는 동작은 현재 실행·전송·미결 승인·실패 요청 제한을 지킨다. 이 분리로 프로젝트 간 동시 실행이 자동 허용되는 것은 아니다.

RPA는 프로젝트 묶음, WWW는 단일 고정 진입점으로 표현한다. WWW의 실제 경로 식별이 확정되기 전 이름만으로 기존 프로젝트를 WWW에 합치거나 저장 경로를 정하지 않는다.

## 칸반 대시보드 구성

참고 출처와 조회 당시 식별값은 명세의 칸반 절에 있다. WWW 적용안은 다음과 같다.

| 영역 | 전체 View Page | 대상별 대시보드 |
|---|---|---|
| 현황 요약 | 수집된 전체 대상 범위 | 선택한 대상 범위 |
| 응답 필요 강조 | 사용자 개입이 필요한 카드 | 해당 대상의 개입 카드 |
| 필터 | 전체·RPA 프로젝트·WWW | 대상 안의 필터는 후속 결정 |
| 칸반 열 | 응답 필요·진행 중·검토 필요·완료 제안 | 같은 표현과 해당 대상의 카드 |
| 카드 열기 | 소속 대상과 연결된 Chat·터미널로 이동 | 연결된 Chat·터미널로 이동 |

카드의 단위는 아직 작업·대화·터미널 중 확정되지 않았다. 설계에서는 이를 ‘보드 항목’으로 부르며 한 터미널을 항상 한 작업으로 취급하지 않는다. 카드 이름·프로젝트·연결 대상·관측 상태·질문·갱신 시점·자료 완전성을 최소 표현 후보로 둔다. 토큰·비용·커밋 수는 자료가 확보된 경우의 선택 정보다.

상태는 업무 상태와 실행 상태를 구분한다. 승인 요청은 응답 필요의 근거가 될 수 있지만, 응답 종료는 완료의 근거가 아니다. 오류·중단·연결 끊김·이력 부족을 네 열 중 하나에 억지로 넣지 않고 결과 미확인이나 경고로 보존한다. 완료·검토 필요의 정확한 판정 주체와 이벤트 매핑은 데이터 원본을 정한 뒤 확정한다.

초기 보드는 관측 상태를 읽는 방식으로 제안한다. 드래그 이동과 수동 상태 변경은 판정 원장·저장·권한 계약을 정하기 전 포함하지 않는다. 보드에서 merge·push·release하는 기능도 이번 설계에 포함하지 않는다.

## 경계와 데이터 흐름

```text
프로젝트 등록 정보 + 확정할 보드 원본
  → main에서 대상·접근 범위 검증 및 조회
  → 읽기 전용 보드 snapshot
  → renderer에서 전체/대상별 필터와 집계
  → 카드 선택
  → 대상 선택 가능 여부 확인
  → 연결된 Chat·터미널 표시
```

위 snapshot과 보드 원본은 새로 구현할 후보 계약이다. 현재 IPC에 이미 있다고 표현하지 않는다. 전체 집계를 위해 모든 프로젝트에서 Native 프로세스를 자동 시작하지 않는다. 보드 원본을 저장된 작업 기록으로 할지 세션 관측으로 할지, 양쪽을 연결할지는 열린 결정이다.

| 책임 | 소유 제안 | 경계 |
|---|---|---|
| View Page·현재 메뉴·필터·선택 카드 | renderer | 실행 성공·업무 완료 판정 원장으로 사용하지 않음 |
| 등록 프로젝트·정규 경로 | main / 프로젝트 인덱스 | 표시 이름으로 대상 식별 금지 |
| 실행·승인·프로세스 생명주기 | main | renderer에서 임의 셸·Node 호출 금지 |
| 보드 항목과 업무 상태 원본 | 미결정 | 파생 카드가 경쟁 원장이 되지 않음 |
| 대화 본문 | 기존 Native 대화 원장 | 전체 보드를 위한 별도 본문 DB를 만들지 않음 |
| 터미널 출력·복원 | 터미널 종류 결정 후 설계 | 영속 저장을 미리 약속하지 않음 |

조회 응답에는 대상 식별과 요청 세대를 연결해 이전 대상의 늦은 응답이 현재 보드를 덮어쓰지 못하게 한다. 부분 성공 시 성공한 대상은 표시하고 실패 범위·마지막 갱신 시각을 함께 보여준다. 미수집 자료를 0건으로 확정하거나 과거 snapshot을 실시간 현황으로 표시하지 않는다.

## Chat의 여러 터미널

확정된 요구는 ‘Chat에서 여러 터미널을 열 수 있음’이다. 종류는 사용자 확인이 필요하다.

| 종류 | 필요한 후속 설계 |
|---|---|
| 독립 Codex 대화 세션 | thread·연결·승인·중단·실행의 세션별 소유, 현행 단일 선택 흐름 확장 |
| 일반 셸 터미널 | PTY 생명주기·cwd·입출력·크기 조절·종료와 preload/IPC 경계 |
| 두 종류 모두 | 탭 종류 구분과 위 두 계약을 각각 유지 |

표시 방식은 상단 탭과 추가 버튼을 기본 제안으로 두며 화면 분할은 후속 후보로 둔다. 탭 전환·닫기·프로세스 종료를 별도 동작으로 정의해야 한다. 실행 중 닫기, 승인 대기 상태에서 전환, 출력 도착 중 전환, 앱 종료·재실행의 정책도 이 단계에서 정한다. 터미널의 종류가 확정되기 전 PTY 라이브러리나 병렬 Native 실행 구조를 선택하지 않는다.

카드 연결 대상은 프로젝트와 세션의 식별자를 보존해야 한다. 사라진 세션은 다른 세션으로 자동 연결하지 않고 연결 불가 상태와 가능한 대화 재열기 경로를 보여주는 방향을 제안한다.

## 실패·접근성·좁은 화면

- 프로젝트 추가 취소는 기존 선택을 유지한다. 추가 실패는 원인과 재시도 경로를 보여주는 방향을 제안한다. 등록 방식 자체는 미결정이다.
- 키보드로 프로젝트·메뉴·카드·탭을 이동할 수 있어야 한다. 현재 대상과 선택 메뉴를 접근성 이름과 상태로 전달한다.
- 상태는 색상과 글자를 함께 사용한다. 자동 갱신으로 포커스를 이동하거나 사용자가 읽는 카드 순서를 임의로 바꾸지 않는다.
- 보드 열은 각각 읽을 수 있는 스크롤 영역으로 제안한다. 좁은 화면에서는 가로 탐색 또는 세로 적층 중 후속 시각 설계로 확정하고 카드의 핵심 정보와 대상 선택 경로를 유지한다.
- 빈 보드, 조회 중, 일부 실패, 전체 실패, 오래된 자료를 구분한다. 실제 자료가 없으면 예시 카드를 실제 현황으로 표시하지 않는다.

## 모델 배치 설계의 추가 경계

사용자 목적은 모든 작업에서의 토큰 효율이다. 자동 선택을 설계 방향으로 두고, 매 요청마다 모델 선택 질문을 추가하지 않는다. 각 작업 또는 의미 있는 단계의 복잡도·실패 위험·필요 도구·가용 모델을 판단해 적합한 실행 주체와 추론 수준을 배치한다. 실제 호스트가 모델 전환을 지원하는지 확인하기 전 자동 전환된다고 표현하지 않는다.

항상 별도 LLM으로 분류하거나 대화를 통째로 여러 모델에 복사하지 않는다. 명확한 작업은 기존 규칙으로 분류하고 필요한 입력만 인계하는 방식을 우선 제안한다. 불확실하거나 실패한 경우에는 같은 낮은 수준의 반복 호출 대신 원인을 확인해 상향할지 결정한다. 상향 이유와 재시도 횟수를 기록하며 종료 조건·상한의 구체적인 값은 후속 설계한다.

사용량 평가는 작업 전체의 분류·저작·위임·입출력·검토·재시도를 포함한다. 제공되는 경우 입력·캐시 입력·출력·추론 토큰의 포함 관계를 확인해 중복 합산하지 않는다. 관측 자료가 없으면 미확인으로 둔다. 비용은 확인한 가격·과금 단위로 별도 계산하며 총 토큰 감소와 동일시하지 않는다. 비교는 같은 품질·완료 조건에서 수행하고 근거 없는 절감률을 표시하지 않는다.

업무 단계마다 ‘무엇을 틀릴 수 있는가’를 기준으로 역할을 선택한다. 다음은 역할 배치 원칙이며 고정 모델 ID를 새로 확정하는 표가 아니다.

| 역할 | 배치 기준 | 필요한 증거 |
|---|---|---|
| 수집·목록·대조 | 범위가 명확한 기계적 작업 | 수집 원본과 대조 범위 |
| 조사·일상 검증 | 근거를 읽고 되돌릴 수 있는 판단 | 관측·가설·실행 결과 |
| 설계·구현·통합 | 상태·권한·구조와 결과 책임 | 결정·변경·검증 근거 |
| 독립 리뷰 | 작성 맥락과 분리한 읽기 전용 반증 | 실제 호출·검토 대상·발견 |
| 최종 감사 | 앞선 검증의 오류 확인 | 정책에 맞는 Opus 실행 영수증 또는 미실행 blocker |

후속 실행 계약은 작업·단계·대상 입력·선택 이유와 요청 모델·effort를 연결하고, 응답에서 확인한 모델·provider·결과와 별도로 보관한다. 단순 설정값은 ‘설정’, 호출값은 ‘요청’, 응답에서 확인한 값은 ‘관측’으로 표시한다. 관측하지 못한 값은 미확인으로 남긴다. 토큰·비용은 자료와 집계 범위가 있을 때만 표시한다.

일반 업무 모델 선택과 독립 검토자 선택은 별도 정책을 적용한다. 기존 review core를 일반 수집 작업의 실행 라우터처럼 사용하지 않는다. 모델 불가·quota·시간 초과·거절 시 미실행 원인을 남기고 허용된 대체 조건이 있는지 확인한다. 새 모델로 실제 추가 호출하는 일은 현재 문서 작성과 구별한다.

현행 개발 호스트와 WWW Chat 중 어느 쪽에 먼저 적용할지, 어떤 수준에서 사용자 선택과 자동 배치를 결합할지, 모델 목록·가용성 조회와 실행 어댑터는 후속 결정이다. 칸반·터미널은 모델 배치의 표시·진입점이 될 수 있지만 터미널 하나에 모델 하나를 고정하는 구조를 선점하지 않는다.

관련 기준 S8은 실제 호출 영수증과 표시 내용의 대조로 검증한다. 같은 모델이 여러 역할을 맡더라도 그 이유를 남기며, 별도 검토가 필요한 역할을 같은 작성자가 자기 승인하는 방식으로 대체하지 않는다.

## 결정하지 않은 미래 범위

터미널 종류, 병렬 실행, 보드 항목·상태 원본, 프로젝트 등록 방식, WWW 경로, 전체 집계 지표, 데이터 영속화·복원, 카드 드래그, 집중 모드와 RPA 생태계 분석은 미결정이다. 미결정이 남은 해당 구현 단위를 진행하지 않는다. 상세 시각 토큰·폭·라이브러리·API 필드는 후속 설계에서 실측하고 확정한다.
