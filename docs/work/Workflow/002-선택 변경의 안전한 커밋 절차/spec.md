# 선택 변경의 안전한 커밋 절차

## 요청·범위

사용자는 WWW용 커밋 스킬 하나를 만들도록 요청했다. `skills/www/www-commit/SKILL.md`와 커밋 준비 양식을 추가하고 발견 링크·공통 계약·모델 정책·카탈로그·문서 검증기에 연결한다. 영향 영역과 주 책임은 `dev`다.

작은 문서·도구 변경이므로 별도 설계와 작업 목록을 중복 생성하지 않는다. 이 문서의 절차와 검증 기록으로 관리한다.

## 절차 원칙

- 준비와 실행을 분리한다. 스킬 생성·준비 요청은 stage·commit 실행 승인이 아니다.
- 관련 작업·저장소·브랜치·HEAD·index·선택한 diff와 검증 대상을 대조한다.
- 기존 사용자 변경과 staged 변경을 보존한다. 일괄 stage, 임의 index 해제, stash/reset, 실패한 훅 우회를 하지 않는다.
- 명시적 실행 승인 뒤에만 선택한 변경을 커밋하고 실제 결과를 확인한다.
- 한국어 결과 문장으로 제목을 작성하고, 원격 게시·서버 색인과 커밋을 구분한다.

## 수용 기준

- `AC-1`: 여섯 번째 스킬의 정본·발견 링크·공통 계약·양식 연결이 유효하고, 정본이나 커밋 양식 누락 시 검증기가 실패한다.
- `AC-2`: 스킬 문서가 준비·실행·push 권한, 기존 index와 비대상 변경 보존, 후보/검증 대상 비교, 실패와 동시 변경 한계를 명시한다.
- `AC-3`: 기존 문서·스킬·작업 관계가 유효하고 집중 테스트·타입 검사·테스트·빌드가 통과한다.

## 제외·검증 한계

이번에는 실제 저장소의 stage·commit·push, Git 훅 설치, 자동 커밋 실행기, 모델 전환, BoxBox 적용, 제품 Chat 기능을 수행하지 않는다. 새 스킬은 에이전트 지침이지 자동 Git 권한 차단기가 아니다. 계약 테스트는 발견·필수 파일 누락을 검증하며 실제 커밋의 성공·부분 stage·동시 writer 차단을 실행 검증한 것은 아니다. 실제 스킬 실행 시에는 그 커밋 후보에 대해 새 검증과 명시 승인이 필요하다.
