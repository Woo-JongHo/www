# 사용자 여정과 칸반 인계를 개발 스킬에 연결

## 요청과 목적

사용자는 개발 전에 Todo와 계획을 보고 기존 칸반에서 이어가기를 원했다. 그러나 계획을 대화·scratchpad에만 남기고 작업 접수를 빠뜨린 사례가 있었고, 화면이나 버튼의 존재를 실제 사용자 흐름의 완료와 혼동할 여지도 있었다. 이 공백을 기존 개발 역할·스킬·템플릿의 책임에 반영한다.

사용자의 “이번 기회에 skills도 업데이트할게 있으면 진행하자”, “내 고민까지 넣어서 남은 작업 진행…요구사항에 대해 사용성이 높게”, “오픈소스 pstack,gajaecode 참고해도 좋다” 요청에 근거한다. 사용자 여정과 구현·검증의 인계를 구체화하되 스킬 지침과 런타임 강제 검사는 구분한다.

사용자의 직접 요청으로 접수했다. 요청 식별값은 work.json의 workflow.requestHash에 보존한다.

## 범위

변경 경로·표면·검증 명령과 커밋·게시 권한은 work.json의 workflow.authorization을 따른다. 범위 확대는 기존 권한으로 간주하지 않는다.

- 포함: 네 개발 스킬, 개발 역할, 공통 작업/산출물 검토 계약, 네 템플릿과 같은 UUID의 작업 문서. 직접 요청으로 연결한 MODEL_POLICY·REPORTS·DEVELOPMENT의 권한·보고 순서·실행 인계 문구 정합화를 포함한다.
- 제외: 제품 코드, 원장 스키마·새 칸반 상태·자동 보드 배선, 모델 배분표·일반 fallback 값·필수 감사 정책 값 변경, 외부 스킬 설치·실행, 전역 설정·발견 symlink 변경, 커밋·게시.

## 수용 기준

정의와 필수 여부의 정본은 work.json이다. 관련 기준: `SKILL-JOURNEYS`, `SKILL-HANDOFF`, `SKILL-VALIDATE`.

## 사용자 여정과 확인 방법

| 여정 | 초기 상태·입력 | 행동 | 기대 결과 | 기준 ID | 확인 방법 |
|---|---|---|---|---|---|
| UC-1 계획 요청 접수·재개 | 사용자가 개발 전 Todo/계획 요청, 관련 기존 작업이 있음 | 역할이 관련 작업을 찾고 같은 UUID로 계획·다음 단계를 남긴 뒤 재개 | 계획이 원장과 연결되고 기존 권한·차단·남은 행동에서 이어감 | SKILL-HANDOFF | 독립 에이전트에 실제 역할과 최소 요청을 주고 생성/선택한 원장·계획·인계 산출물을 검사 |
| UC-2 사용자 흐름 설계·검증 | 화면 선택이 API/IPC와 저장·재조회에 영향을 주는 변경 | 명세→설계→구현→검증 스킬로 인계 | 입력·행동·기대 결과→기준→실제 호출/상태 소유→검사·관찰이 추적됨 | SKILL-JOURNEYS, SKILL-HANDOFF | 독립 행동검사에서 여정·인계·검증 표의 내용과 미실행 구간 구분 확인 |
| UC-3 작은 수정과 미실행 처리 | 문구 등 작은 수정 또는 실행 환경 없음 | 필요한 만큼 기록하고 형식 검사만 실행 | 짧은 기록으로도 기준·검사가 연결되며 실제 사용자 동작 통과로 승격하지 않음 | SKILL-JOURNEYS, SKILL-VALIDATE | 작은 요청/GUI 미실행 상황의 독립 적용과 quick_validate·workflow 검사 결과를 대조 |

UC-2에서는 빈 자료·호출 실패·중단 후 재시도와 선택/응답 순서 경합을 작업에 해당할 때 고르도록 한다. 이번 변경 자체는 문서이므로 실제 제품 GUI·저장 동작을 구현하거나 검증했다고 주장하지 않는다. 기존 명확한 구현 권한의 승계와 작은 작업의 간소화는 유지할 비교 사례다.

## 결정과 열린 질문

작업 접수는 구현 완료가 아니다. 재개 시 같은 UUID와 현재 증거를 확인한다.

공통 추적 규칙은 WORKFLOW 한 곳에서 소유하고 각 스킬과 산출물 검토는 이를 참조한다. 추가 인터뷰·승인·의무 게이트는 만들지 않는다. 초기 모의 분석, A/B 수동 fixture·사후 보강, C2 주입, C3 개발 안내 누락, C4 실제 CLI 한 줄 변경과 필수 Opus 실패를 verification.md에서 구분한다. A/B의 사후 단계 교정과 여정 행 작성은 스킬이 산출물을 이끌어 낸 독립 행동 근거가 아니다. 새 독립 실행에는 최소 요청과 원시 자료만 주고 명세·설계·구현·검증 산출물을 직접 생성하게 하며, 실행자가 사후 보강하기 전 결과를 보존해 평가한다. 제품 GUI나 실제 저장 성공을 이 문서 작업의 결과로 승격하지 않는다.

## 계획과 다음 행동

[설계](design.md)와 [구현 단위](tasks.md), [검증 기록](verification.md)을 같은 UUID로 연결한다. 원장의 다음 단계·상태·기준 결과를 갱신하는 책임은 통합 담당에게 있으며, 문서 저작자가 실행하지 않은 검증을 먼저 완료 처리하지 않는다.


## 직접 요청과 문서 범위의 연결 보완

사용자의 “이번 기회에 skills도 업데이트할게 있으면 진행하자”와 누적 작업의 사용성 개선 요청에 따라 스킬이 참조하는 MODEL_POLICY·REPORTS·DEVELOPMENT의 관련 문구도 검토·정합화했다. 이를 workflow.authorization의 정확 경로에 추가했다. 모델 배분표·일반 fallback 값·필수 감사 정책 자체를 바꾼 것은 아니며, 과거 예외가 새 승인으로 승계되지 않는 점과 미실행 감사의 부분 보고 순서·실행 인계를 명확히 한 범위다. 변경 전 원장은 history/before-second-opus-correction-20261116.json에 보존한다.
