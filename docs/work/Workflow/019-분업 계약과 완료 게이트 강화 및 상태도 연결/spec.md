# 분업 계약과 완료 게이트 강화 및 상태도 연결

## 요청과 목적

사용자가 WWW와 pstack의 흐름·제약·검증을 비교한 뒤 “다음번 개발은 이걸로” 진행할 개발 스펙 작성과 기존 배치도에 statechart를 넣는 방안 검토를 요청했다.

목표는 분업 전에 책임과 의존 관계를 확인하고, 실행 종료를 업무 수용과 구별하며, 현재 코드에 유효한 근거가 있을 때만 완료되도록 만드는 것이다. 기존 하네스를 확장하고 작은 인터페이스 뒤에 검사를 모은다. 비교 대화의 8점·7점은 주관적 설계 평가이며 성능 기준이나 개선 실측이 아니다.

이번 세션은 명세 정리·연결 방안 검토·다음 구현 계획 작성만 한다. 아래의 구현 내용은 다음 개발의 목표이며 현재 제공 기능으로 읽지 않는다.

## 현재 근거와 재개 조건

- WWW는 이미 작업별 권한·모델 배분·소스와 기준에 연결된 검증·독립 검토·보고서·완료 판정을 가진다. 먼저 재사용하고 중복 게이트를 만들지 않는다.
- `scripts/workflow/model-allocation.ts`, `run.ts`, `work.ts`, `evidence.ts`, `report-lifecycle.ts`가 조사 출발점이다. dependency의 호스트 정상 종료는 업무 수용과 다르다.
- 기존 배치도는 `docs/architecture/structure.json`의 책임 구조와 정적 import를 구별한다. 구조 ID와 요구 연결 계약은 `docs/specs/architecture.md`가 소유한다. 현재 선언 연결은 실행 결과나 실제 호출 추적의 증명이 아니다.
- 현재 작업 트리에는 다른 세션의 변경이 많다. 다음 착수 때 경로·브랜치·dirty 상태, 관련 작업 018 및 Ecosystem 004/005의 최신 구현을 다시 읽고 설계 차이를 판단한다.
- 이 문서는 작업 목표다. 현행 정책과 구조 문서는 실제 구현에 맞춰 그때 갱신한다.

## 용어와 프로젝트 지도

Feature map은 이 작업에서 프로젝트 전체의 기능·책임과 관련 근거를 찾아가는 프로젝트 지도를 뜻한다. 별도 제품이나 제2의 지도를 신설하지 않는다. 기존 배치도의 책임 계층과 코드 의존 보기를 유지하면서 같은 구조 ID에 상태도와 검증 근거를 연결한다.

| 보기 | 확인할 내용 |
|---|---|
| 기존 배치도 | 책임·구성·담당 코드·정적 import |
| 상태도 | 상태·사건·전이 조건·효과·불변식 |
| 검증 근거 | 요구와 검사 연결, 실제 결과, 소스 적용성, 반례·스크린샷 |

지도와 상태도는 탐색 표현이다. 연결선이나 시각화가 검증 실행·증명·실시간 추적을 대신하지 않는다. 새 메뉴 명칭 변경이나 모든 기능의 증거 이관을 의무화하지 않고 첫 개발 작업 흐름부터 연결한다.

## 범위

포함:

1. 위임 전 분해 계획의 최소 계약과 실행 전 검사.
2. 실행 결과·업무 수용·통합 가능 여부의 구분.
3. 기존 완료 경로의 결함 주입 검사와 발견된 우회 경로 수정.
4. 개발 작업의 검증·수용·완료 상태도를 기존 배치도에 연결하는 첫 기능.
5. 해당 규칙을 역할·스킬·하네스·문서에서 참조하는 배선과 실제 검증.
6. 속성·모델 기반 테스트로 분업 계획과 완료 사건 순서 검사 확대.
7. 기존 배치도에서 요구·담당 코드·상태도·검증 근거를 탐색하는 첫 연결.

제외:

- 범용 멀티에이전트 스케줄러, 제품 Chat 자동 모델 라우터, OS 샌드박스 도입.
- pstack 전체 이식, 전역 훅 설치, BoxBox 규칙 복제, 플러그인 캐시 수정.
- 모든 모듈의 상태도 작성, 실시간 실행 추적, 시각 편집기와 코드 자동 생성.
- 이번 범위를 넘어선 Runtime verification 상시 모니터, Lean 증명 체계, 자동 배포·공개·운영 실험. 아래 도입 조건과 후속 계획만 기록한다.
- 무조건적인 TLA+/TLC 설치·상시 실행. 첫 단계는 기존 도구의 행동 검사와 명시적 전이 계약으로 검증한다.
- no-comments의 일괄 주석 삭제. 아키텍처 선언과 외부 계약 설명은 보존한다.
- 근거 없는 비용·시간·신뢰도 개선율 약속.

## 목표 흐름과 책임

직접 요청 → 수용 기준 → 분해 계획 → 범위/의존 검사 → 위임·실행 → 산출물과 행동 검증 → 통합 → 독립 검토 → 현재성 확인 → 완료.

- Sol은 공통 계약·위험한 경계·통합을 담당한다. 단위의 위험에 따라 모델을 배분하며 지원 모델은 실행 시 확인한다.
- 소유 경로가 독립적인 단위만 병렬 저작한다. 공통 파일은 담당자 하나가 통합하고 선행 수용을 요구하는 단위는 기다린다.
- 같은 UUID 공식 CLI 호출의 기존 직렬 실행 계약을 유지한다. 새 스케줄러가 있는 것처럼 설명하지 않는다.
- 각 단위에는 목표, 입력, 소유/제외 경로, 선행 작업, 산출물, 수용 기준 ID, 검증 방법, 결과 위치가 필요하다. 작은 작업은 동일 계약의 단일 단위로 처리한다.
- 실행 성공, 업무 수용, 검증 통과, 게시 여부는 별개 사실로 보존한다. 범위·기준을 약화시키거나 미확인을 성공으로 바꾸지 않는다.

## 수용 기준과 시나리오

기준의 정의·필수 여부·결과는 [work.json](work.json)의 `criteria`가 정본이다. 모든 구현 기준은 현재 미검증이다. 이번 작업에만 해당하는 기준이며 지속 요구 ID는 구현 시 실제 소유 문서와 연결한다.

- `FLOW-PLAN`: 독립 두 단위는 허용하고, 겹치는 파일·부모/자식 경로·같은 실제 대상을 가리키는 경로는 기존 경로 정책으로 검사한다. 제외 경로를 단순 문자열 기재만으로 충돌 해소로 보지 않는다.
- `FLOW-ACCEPT`: 프로세스가 0으로 종료돼도 필수 산출물·검사가 없으면 통합 준비로 올리지 않는다. 실패 결과를 보존하고 같은 가정의 무근거 재시도를 막는 기존 정책에 연결한다.
- `FLOW-COMPLETE`, `FLOW-FAULTS`: 아래 행렬에서 잘못된 완료를 거부하고, 정상 흐름도 통과시켜 무조건 거부하는 구현을 배제한다.
- `STATE-LINK`, `STATE-VIEW`, `STATE-CHECK`: 책임 노드 → 상태도 → 전이 조건·코드·검사 → 반례 → 원래 지도로 돌아가는 사용자 경로를 확인한다.
- `FLOW-REGRESSION`: 구형 기록은 보존해서 읽고 기존 정상 동작과 새 실패 경로를 함께 검증한다.
- `FLOW-PROPERTY`: 다양한 소유 경로와 의존 그래프, 검증·변경·검토·완료의 사건 열을 생성하고 실패를 재현한다. 생성기가 핵심 오류를 실제로 만들 수 있는지 확인한다.
- `MAP-EVIDENCE`: 같은 노드에서 요구와 검증 근거로 이동하되 선언만 있는 경우, 실행 성공이나 현재성 정보가 없는 경우, 과거 결과가 오래된 경우를 구별한다.

## 결함 주입 행렬

| 번호 | 입력 또는 사건 | 기대 관찰 |
|---|---|---|
| F01 | 파일 또는 부모/자식 쓰기 소유가 겹침 | 위임 실행 전 거부와 충돌 경로 표시 |
| F02 | 미정의 선행 단위 또는 의존 순환 | 실행 전 거부와 해당 단위 표시 |
| F03 | 호스트 정상 종료, 필수 산출물 누락 | 실행 종료 기록 유지, 수용/통합 거부 |
| F04 | 검증 실패 또는 검증 미실행 | 업무 완료 거부, 실패/미실행 구별 |
| F05 | 검증 후 대상 소스 변경 | 과거 통과 보존, 현재 완료 거부 |
| F06 | 같은 기준 ID의 설명 또는 필수 여부 변경 | 과거 기준 증거를 재사용하지 않음 |
| F07 | 입력 범위 변경, 기존 파일 내용은 같음 | 범위 변경을 감지해 현재성 재판정 |
| F08 | 필수 검토 누락 또는 오래된 검토 | 완료 거부와 재검토 이유 표시 |
| F09 | 현재 저작 보고서 누락 또는 오래됨 | 적용 대상 작업의 완료 거부 |
| F10 | 주입 실행기를 실제 프로세스 증거로 제출 | 실제 검증 통과로 수용하지 않음 |
| F11 | CLI와 앱에서 같은 부정 조건으로 완료 시도 | 동일 core 판정과 이유 사용 |
| F12 | 미정의 상태·중복 ID·없는 구조 ID | 상태도 계약 검사 실패 |
| F13 | 상태 모델 또는 연결 소스 변경 | 이전 검사 결과를 현행 통과로 표시하지 않음 |
| F14 | 오래된 증거로 완료하는 전이를 허용한 변형 | 검사 실패와 사건 순서의 반례 제공 |
| C01 | 정상 단일 단위, 현재 증거와 검토/보고서 충족 | 완료 허용 |
| C02 | 독립 단위 분업 후 정상 통합 | 기존 소유권·직렬 경계 안에서 수용 허용 |
| C03 | 모델 없는 책임 노드 선택 | 없음 안내, 지도 탐색 정상 유지 |

검증 대상은 격리된 fixture 작업과 임시 저장소다. 사용자 진행 작업에 결함을 주입하지 않는다. 부정 사례 차단률과 정상 사례 통과 수는 이 고정 행렬에 한정해 보고하고 실사용 오류 확률로 일반화하지 않는다. 테스트 이름·명령·실행 종류·기대/관측·증거 경로를 각 행에 연결한다.

## 검증 방법과 시점의 적용 범위

| 항목 | 다음 구현에서의 취급 | 산출물과 보장 한계 |
|---|---|---|
| 예제·결함 주입 | 필수: F01–F14와 C01–C03을 요구·공개 진입점에 연결 | 실제 기대/관측, 명령, 실행 결과. 고정 사례 밖의 보장은 하지 않음 |
| 속성·모델 기반 테스트 | 필수: 소유/의존 및 완료 불변식의 생성 검사 | seed, 횟수, 생성 범위, 반례, 실제 실행과 모델의 대응 |
| 상태도 계약 검사 | 필수: 모델 구조·참조·규칙·현재성 | 검사 결과와 코드 연결. 그림만으로 형식 증명을 주장하지 않음 |
| Runtime verification | 후속 후보: 저장한 사건 열을 규칙과 대조하는 읽기 전용 재생부터 검토 | 관찰한 실행에서의 위반/관측 부족. 기존 실행·완료 게이트와 별도이며 차단/복구 자동화를 전제하지 않음 |
| TLA+/TLC | 순서·동시성 문제가 남을 때 선택 도입 | 모델·설정·탐색 범위·반례·코드 재현. 구현 전체의 정확성으로 확대하지 않음 |
| Lean | 작고 명확한 핵심 규칙의 증명 이득이 확인될 때 별도 작업 | 명제·가정·증명·구현 대응. 별도 모델 증명을 TypeScript 증명으로 부르지 않음 |
| Pre-production | 패키징한 앱의 격리 검증을 계획. 실제 패키징 실행은 구현 세션 권한·환경에 따라 수행/미실행 기록 | 빌드 식별·OS·핵심 여정·스크린샷·복원 결과. 개발 서버 검사와 구분 |
| Deploy / Release | 설치·배치와 사용자 공개를 구별하는 인계 계획 작성 | 배포 대상·버전·중단/복구 조건. 이번 문서 작성은 배포 승인이 아님 |
| Post-release / Testing in production | 공개 후 전용 테스트 작업으로 확인할 절차를 계획. 실제 수행은 별도 범위 | 실제 설치 버전·환경·관측 기간·실패/복구 기록. 실사용자 자료에 결함 주입하지 않음 |

검증 방법, 실행 시점, 실행 환경은 별도 필드/표시로 표현한다. 테스트 결과나 모델 검사 결과를 단일 강도 순위로 합산하지 않는다. 배포 전 통과를 공개 후 정상으로, 로컬 캡처를 사용자 환경 확인으로 승격하지 않는다. 단계별 실행 계획은 [tasks.md](tasks.md)를 따른다.

## 검증 산출물: 보고서와 스크린샷

`STATE-VIEW`의 UI 검증은 실제 앱에서 조작한 뒤 스크린샷을 남긴다. 보고서는 기대·관측·판정과 한계를 설명하고, 스크린샷은 당시 화면을 보존하며, 행동 테스트와 실행 기록은 전이·조건·부작용을 확인한다. 스크린샷만으로 내부 완료 게이트나 키보드 동작의 성공을 증명하지 않는다.

필수 촬영 대상:

- 책임 노드에서 연 상태도와 전이를 선택한 근거 상세.
- 모델 없음(C03), 검증 미실행, 오래된 검증(F13), 위반과 반례(F14)의 화면 표시.
- 좁은 창에서 주요 조작과 정보가 보이는 화면, 지도 복귀 뒤 선택과 탐색 위치가 유지된 화면.
- 시각적 회귀를 수정한 경우 같은 시나리오·화면 크기의 수정 전후. 최초 신규 화면에는 존재하지 않는 변경 전 화면을 만들지 않는다.

촬영은 해당 상태를 실제 UI 흐름 또는 명시한 격리 fixture로 구성해 수행한다. fixture 화면과 실제 앱 화면을 구별하며, 구현한 기능을 보여주는 증거로 목업·생성 이미지를 사용하지 않는다. 촬영 후 이미지를 직접 열어 기대한 대상과 잘림·겹침·텍스트 가독성을 확인한다.

이미지는 `.www/evidence/<work-id>/<attempt-id>/screenshots/`에 보존한다. 검증 시 `verification.md`에 기준 ID·시나리오·행동·기대/관측·촬영 시각·실행 앱의 빌드/소스 식별·화면 크기·실제/fixture 구분·파일 경로·SHA256을 남긴다. 이미지 경로는 로컬 원본 위치이며 서버나 다른 머신에서 자동 열리는 것으로 표시하지 않는다. 보고서는 해당 검증 기록을 참조한다. 사용자에게 전달할 필요가 있으면 민감 내용을 확인한 사본을 별도로 제공하고 원본과의 관계를 남긴다.

필수 화면을 촬영하지 못했거나 파일이 없으면 해당 시각 검증은 미실행으로 남긴다. 소스가 바뀐 뒤 옛 화면을 재사용하려면 해당 UI 입력이 동일함을 판단하고 근거를 기록한다. 원본 이미지와 로그를 무조건 Git에 추가하지 않는다.

## statechart를 배치도에 넣는 방안 검토

### 권고: 책임 노드에 연결된 별도 상태 전이 보기

현재 구성 지도와 코드 의존 보기를 유지하고 선택 책임에서 상태 전이를 연다. 구성선·import선·상태 전이선을 한 그래프에서 섞지 않는다. 첫 대상은 개발 작업의 검증·수용·완료 책임이다. 대화·승인·프로세스 상태는 후속 후보이며 이번 필수 범위에서 제외한다.

기존 구조 ID가 연결점이다. 별도 제2의 책임 트리를 만들지 않는다. 상태 계약의 저장 위치와 생성 snapshot 경로는 다음 설계에서 현재 generator와 검사 경계를 보고 확정한다. 사람이 편집하는 정의는 한 곳에 두고 Mermaid/SVG/앱 snapshot은 파생 결과로 관리한다.

최소 정보:

- 모델: 안정 ID, 담당 구조 ID, 설명, 초기 상태, 대상 소스와 규칙, 모델 내용 식별.
- 상태: 안정 ID와 한국어 이름. 기존 work status와 다른 검증/검토 적용성은 별도 속성으로 표현해 상태 조합 폭증을 피한다.
- 전이: 안정 ID, 시작/도착 상태, 사건, 허용 조건, 효과, 실제 담당 코드 근거.
- 규칙: 완료에 필요한 현재 증거·필수 검토·보고서 등의 불변식과 검사 근거.
- 검사 기록: 수행 도구/방법, 입력 소스·모델·규칙 식별, 실행 결과, 미검사 범위, 반례 사건 열.

화면은 “설계 정의”, “검증 미실행”, “검증 통과”, “위반 발견”, “오래된 검증”, “모델 없음”을 구별한다. “검증 통과”에는 검사한 범위·시점·소스 식별을 함께 제공하며 형식 검증 여부도 명시한다. 정적 모델에서 현재 실행 중인 노드처럼 강조하지 않는다.

전이 선택 시 사건·조건·효과·코드·연결된 검사와 반례를 읽는다. 좁은 창·키보드·빈 결과를 지원하고, 상태도에서 돌아왔을 때 지도 선택·검색·배율·이동과 대화 초안이 보존돼야 한다.

### 검증 전략과 도입 순서

1. 완료 불변식과 실제 변경 함수를 대조하고 전이 계약을 작성한다.
2. 정상 경로 및 F05/F06/F08/F14 등의 잘못된 완료 경로를 기존 공개 동작 검사에 연결한다.
3. 계약 검사와 stale 표시를 만든 뒤 UI를 연결한다. 그림만 먼저 구현하고 검증 완료로 표시하지 않는다.
4. 코드와 별도 모델 사이의 중복·동기화 비용을 평가한다. 구현 전이 자료를 재사용할 수 있으면 우선 검토하고, 별도 모델이라면 코드 대응표와 변경 감지를 둔다.
5. TLA+/TLC 등 추가 모델 검사 도구는 순서·동시성 문제에서 기존 행동 검사보다 얻는 이득이 확인될 때 별도 설계로 결정한다. 첫 UI와 행동 검증의 선행 설치 조건으로 삼지 않는다.

검토한 대안: 기존 지도에 모든 상태를 겹쳐 그리면 관계 의미가 섞이고 규모가 커진다. 정적 Mermaid 문서만 두면 시작 비용은 낮지만 노드 탐색·현재성·근거 연결 요구를 충족하지 못한다. 책임에 연결된 별도 보기를 첫 구현 권고안으로 삼는다. 정확한 렌더러와 파일 배치는 다음 설계의 선택 사항이다.

## 다음 개발의 순서

[설계](design.md)와 [구현 계획](tasks.md)에 같은 UUID의 단계·입력·소유 경로·의존성·모델 역할·수용 기준·산출물·검증을 연결했다. 기본 순서는 현행 재확인 → 공통 계약 → 게이트/생성 검사와 지도/상태 계약 병렬 → UI 통합 → 실제 화면·패키지 검사 → 독립 리뷰와 최종 감사다.

관련 작업 018과 다른 진행 변경을 먼저 확인하고 이미 구현된 조건은 증거로 재사용한다. 다음 구현 요청을 받기 전에는 제품 쓰기 권한을 활성화하지 않는다.

## 결정과 열린 사항

범위와 관찰 가능한 목표는 이 명세로 준비됐다. 최소 계약과 예상 파일 경계는 design.md에 정리했다. 정확한 새 파일명·라이브러리 버전·테스트 명령은 구현 착수 때 현행 소스와 지원 환경을 확인해 확정한다. 새 프로세스나 스케줄러 도입을 전제하지 않는다. 독립 검토자는 아직 실행하지 않았으며 명세의 독립 승인이나 구현 완료를 주장하지 않는다.

## 요청에서 받은 권한

이번 직접 요청은 누적 대화에 따른 명세 재정리·statechart 연결 검토·다음 구현 계획 작성이다. 신규 작업 문서와 목차 항목만 변경하며 제품·스킬·훅·런타임은 변경하지 않는다. 다음 개발의 구현 권한과 실제 쓰기 범위는 그때의 직접 요청으로 연결한다. 현재 `workflow.authorization.implementation`은 false다.
