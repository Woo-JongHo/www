## 판정과 근거

가장 먼저 바꿀 결정은 “이전 실행이 어떤 동작을 증명했고 이번 변경이 그 동작에 영향을 주는가”다. 현재 evidence.ts는 작업 전체의 기준 정의 지문과 해당 시도의 입력 지문을 비교한다. work.ts는 기준별 최신 시도를 찾지만 시도 자체의 적용성은 넓은 범위로 판단한다. dashboard.ts는 저장된 passed 수를 센다. 원격 추적 main의 b57c102에서도 두 지문 비교와 화면 집계를 확인했다.

일시정지 전 19개 작업의 같은 기간을 재집계했다. 검증 기록 377건에서 작업·실행 파일명·인자를 묶으면 70종, 여기에 입력 지문을 더하면 365종이다. 따라서 첫 명령 이후 반복은 307건이고 그중 같은 그룹에서 처음 등장한 추가 입력 지문은 295종이다. 같은 입력 지문까지 반복한 12건도 환경·산출물·직전 실패가 다를 수 있다. 이 집계로 피할 수 있었던 실행 횟수나 시간을 확정할 수 없다. 검증과 검토 구간의 합집합은 약 3시간 26분이다. 나머지 약 14시간 6분의 원인 순위는 현재 원장만으로 알 수 없다.

Chat/003에서는 전체 검사 시간 초과가 일곱 기준의 최신 시도로 기록됐다. Chat/007에서는 두 기존 Electron 실행의 원문과 현재 적용성을 확인하고 집중 검사로 보완해 유효 기준이 2개에서 9개로 늘었다. 두 사례는 검사 범위와 결과 귀속을 바꿀 근거다. PR #16의 CI 중복 제거와 PR #19의 완료 판단 통합은 이미 병합됐다. 이 기능들을 기반으로 확장한다.

## 세션에서 최대 다섯 이슈를 통합하는 순서

1. 백로그에서 같은 사용자 여정이나 공용 변경을 공유하는 이슈를 최대 다섯 개 고른다. 세션의 이슈, PR별 소유 파일, 의존 순서와 공통 통합 시나리오를 기록한다. 공용 파일의 변경 주체는 하나로 정한다.
2. 이슈별 worktree에서 병렬 구현하고 각 PR의 집중 검사와 리뷰를 진행한다. 배치 통합을 시작하는 시점은 마지막 PR이 열리고 모든 참여 PR의 검증 대상 커밋이 정해졌을 때다.
3. 기준 main과 각 PR의 head, 적용 순서, 결합 트리를 기록하고 임시 통합 브랜치에서 최종 검사를 한 차례 실행한다. 발견한 결함은 소유 PR에서 수정하고 실패 원문은 보존한다.
4. 수정된 head로 새 후보를 만든다. 변경 전후 트리를 비교해 실패했던 검사, 수정의 소비자 검사, 관련 PR 사이의 경계 검사를 실행한다. 결과가 유효한 독립 검사는 재사용한다. 공용 빌드 등 영향 범위를 좁힐 수 없는 경우 해당 범위 전체를 다시 검사한다. 수정 사항이 최종 통합 검사 자체의 입력에 영향을 주면 그 검사도 재실행한다.
5. 최종 병합은 검사한 결합 트리와 실제 병합 결과가 일치하는 경로로 진행한다. 다섯 PR을 순차 병합하면 중간 상태도 main에 노출된다. 중간 상태까지 독립적으로 배포 가능한 경우만 순차 병합하고, 함께 들어가야 할 변경은 한 통합 PR로 병합해 원래 이슈와 PR을 연결한다. 병합 직전에 main 또는 참여 PR이 이동하면 기존 병합 예약을 해제하고 4단계로 돌아간다.
6. 같은 후보·같은 원인으로 실패가 반복되면 자동 재시도를 멈추고 원인을 진단한다. 특정 이슈가 장기 차단되면 의존성이 없는 나머지로 범위를 다시 정하고 그 조합의 후보를 검증한다.

## 변경에서 병합까지

작업자는 이슈별 worktree에서 구현한다. 각 PR은 변경 파일과 선행 PR을 제출한다. 계획기는 현재 main과 PR의 결합 후보를 기준으로 검사별 의존성을 계산하고 원장에 한 줄씩 판정을 남긴다. 독립 PR은 즉시 진행한다. 공용 파일은 한 담당자가 통합하고 그 동작을 쓰는 PR만 선행 병합을 기다린다. 기다리는 동안에도 소비자 단위 검사는 실행할 수 있다.

| 입력 사건 | 예약할 실행 | 이전 증거 처리 |
| --- | --- | --- |
| 보고서 문구만 수정 | 문서·원장 일관성 검사 | 기능 검사 실행 0회 |
| 제품 명세의 기준 하나 수정 | 해당 기준의 검증·검토 | 다른 기준은 정의와 의존성이 같으면 유지 |
| 공용 함수, fixture, 잠금 파일 또는 빌드 옵션 수정 | 바뀐 입력을 사용하는 검사 | 경로 삭제·이름 변경은 이전·새 의존 범위의 합집합으로 평가 |
| 재배치나 병합으로 커밋 ID만 변경 | 결합 후보의 입력·환경·산출물 대조 | 같은 동작을 검증한 증거를 연결 |

| 외부 입력·동적 의존성을 확정하기 어려움 | 해당 검사에 기존 전체 범위를 적용 | 불확실한 과거 결과를 현재 통과로 표시하지 않음 |

## 실행과 증거의 계약

검사 정의는 입력 코드와 전이 의존성, 요구 조항, 검사기·fixture, 실제 명령·인자, 플랫폼·도구와 관찰 환경을 소유한다. 테스트가 읽는 설정, 동적 파일, 환경 변수 등 자동 추적 바깥의 입력은 명시한다. 의존성 정의 자체도 지문에 포함한다. 하나의 실행이 여러 기준에 쓰이면 각 기준이 요구하는 관찰과 실제 assertion을 매칭한다. 다른 작업의 성공 상태만 복사해서는 이 연결을 만들 수 없다.

계획기는 기준마다 재사용·신규 실행·진행 중 실행 연결·외부 조건 대기 중 하나를 고르고 이유와 달라진 입력을 남긴다. 실행 직전과 결과 등록 직전에 입력을 확인한다. 동시 실행 소유권은 원자적으로 확보하고 소유 프로세스가 종료된 뒤에만 회수한다. 실패·미관측과 성공을 독립적으로 저장한다. 빌드·패키징은 같은 신뢰 범위의 검증된 산출물을 소비하고, 게시 직전에는 실제 병합 트리와 승인 후보를 대조한다.

## 실패가 재검사 루프로 번지는 경로 차단

- 제품 assertion 실패는 그 동작의 반례다. 원인을 수정하고 해당 기준과 소비 기준을 검사한다. 같은 입력에서 관측된 유효한 실패가 있으면 이전 성공만 골라 완료할 수 없다.
- 검사 자체의 오류는 해당 검사에 의존한 증거를 다시 연다. 실행기 시간 초과는 실제 관측 완료 지점까지만 기록한다. Chat/003처럼 통합 실행이 중단되면 필수 통합 기준은 미완료이며 이미 독립적으로 통과한 집중 기준은 별도로 판정한다.
- 동일 원인·입력에서 재시도할 때는 해소된 전제를 기록한다. 할당량 소진은 제공자가 알린 재개 조건까지 대기하고, 입력 크기 초과는 검토 입력 구성을 수정한 후 재개한다. BoxBox는 자기가 쓴 파일이나 실행 로그를 반복 검사하는지 기록하고, 실제 소스 수정이 끝난 파일 버전에 검사를 귀속한다.
- Windows·한글 입력·외부 리뷰처럼 전용 자원이 필요한 항목은 초기에 가용성을 확인한다. 조건이 확보되면 관련 기준에만 실행을 예약한다. 같은 OS 관찰을 여러 작업에서 사용할 때는 요구 시나리오와 후보가 모두 일치해야 한다.

## Opus 반박 검토 후 적용할 최종 결정

읽기 전용 설계 검토의 관측 모델은 claude-opus-5-5다. 검토자는 설계문을 읽었고 코드나 원장을 직접 검사하지 않았다. 원문은 로컬 .www/evidence/dashboard-rollforward-20261123/loop-design-opus-20261124.json에 있다. 위 표의 일반 재사용 규칙에는 다음 조건을 적용한다.

1. 계획기의 의존 목록을 같은 목록으로 채점하지 않는다. 시범 검사에서 독립적으로 관찰한 파일 접근·격리 설정과 대조하고, 빠진 공용 입력에 알려진 결함을 넣어 실제 검출 여부를 확인한다. 관찰 범위 밖의 외부 상태에 의존하는 검사는 실행 간 공유 대상에서 제외한다. 비밀 환경 값은 원장에 남기지 않는다. 관찰 비용도 실행 비용에 포함한다.
2. 두 PR을 합쳐 새로운 동작 조합이 생기면 실제 결합 트리에서 접점 통합 검사를 실행한다. 해당 트리에서 이미 통과한 동일 통합 실행은 병합 시 참조한다. 기준마다 기대 assertion 식별자와 실제 관측·완료·생략을 대조한다. 필수 관찰이 비어 있으면 미확인이다.
3. 같은 입력에서 상반된 결과가 나오면 불안정 상태로 보존한다. 제품 실패를 실행기 문제로 재분류해 완료하려면 원문 근거와 독립 검토가 필요하다. 스트림을 끝까지 관찰해야 하는 기준은 중간 성공만으로 확정하지 않는다.
4. 공유 실행에 기한과 heartbeat를 둔다. 기한을 넘기면 구독자에게 미완료를 알리고 취소·격리한다. 소유자 생존 여부가 불확실하면 새 실행이 같은 자원에 쓰지 못하게 하고, 회수 뒤 늦은 결과는 세대 식별자로 거부한다. 한 후보에 대한 판정은 묶어서 기록하고, 통합 담당 범위는 겹치는 공용 변경으로 제한한다.
5. PR 1의 실측이 후속 순서를 결정한다. 임계 경로에서 재검사보다 검토 대기나 원장 경합 비용이 크면 그 원인을 먼저 고친다. 과거 미계측 시간은 새로 복원 가능한 자료까지만 계산하고 나머지는 다음 작업에서 측정한다.

## 영향 판정의 근거와 기록 형식

판정 단위는 변경 후보 × 기준 × 관찰 항목 × 환경이다. 같은 한글 입력 기준에서도 조합 중 Enter 처리, 카드 갱신 중 포커스 유지, 글자가 보이기까지의 지연, 실제 OS 입력기 조합은 서로 다른 관찰이다. 기준 전체의 완료에는 필수 관찰이 모두 필요하다.

검사 정의에는 기대 관찰 ID, 검사 명령, 제품·검사기·fixture 입력, 공유 상태·이벤트·레이아웃·실행 스레드 등의 접점, 관찰 가능한 환경과 알려진 사각지대를 버전과 함께 등록한다. 코드 변경이나 결함 재현이 의존 목록의 누락을 드러내면 해당 정의를 갱신하고 영향을 받은 기존 재사용 결정을 역조회한다.

계획기는 양쪽 후보의 diff와 검사 정의를 비교한다. 직접 의존 변경은 재실행한다. 간접 접점이 있으면 둘을 동시에 쓰는 경계 검사를 선택한다. 예를 들어 textarea에서 조합하는 동안 fixture의 카드 출력을 갱신하고 포커스·조합 문자열·전송 횟수를 관측한다. 입력 지연에는 같은 fixture에서 프레임 지연을 별도로 측정한다. 합성 사건은 실제 OS 입력기 관찰로 인정하지 않는다. 재사용에는 이전 성공 근거와 기대 관찰, 의존 범위, 환경, 검사기 및 원문 지문의 일치가 모두 필요하다. 최초 근거가 없거나 간접 영향을 판별할 수 없으면 미확인 상태로 관련 검사를 예약한다.
