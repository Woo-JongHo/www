# 명세 검토와 개발 도구 출처 하네스

## 요청과 목적

명세를 작성했어도 사용자 여정·경계·성공 조건이 부족하거나, 설계·작업 목록과 충돌하는 상태를 구현 전에 드러낸다. 개발 도구 정본과 발견 경로, 실행에 제공한 파일과 실제 수용 여부를 구분한다. 사용자가 세 기능의 기존 하네스 통합 시나리오를 확인한 뒤 “개발진행하자”로 구현을 요청했다.

사용자의 직접 요청으로 접수했다. 요청 식별값은 work.json의 workflow.requestHash에 보존한다.

## 범위

변경 경로·표면·검증 명령과 커밋·게시 권한은 work.json의 workflow.authorization을 따른다. 범위 확대는 기존 권한으로 간주하지 않는다.

사용자의 “개발진행하자”는 논의한 하네스 구현과 직접 영향받는 테스트·문서 수정의 근거다. 접수 시 기존 출처 목록 회귀 테스트 `test/workflow-development.test.ts`를 쓰기 목록에 누락했고 첫 독립 검토가 이를 지적했다. 추가 기능이나 별도 사용자 승인을 받은 것으로 해석하지 않고 원래 요청에 필요한 테스트 경로를 레코드에 명시해 누락을 정정했다.

- 포함: 검토 준비·결과 저장·현재성 조회 CLI, 도구 출처 조회, 기존 개발 호스트 컨텍스트·영수증 연결, 스킬·계약 갱신.
- 제외: Spec Kit 설치, 새 GUI, 자동 의미 판정, 의미 검토의 자동 실행 차단, 커밋·게시.
- 정상 시나리오: 개발 역할이 명세·기준을 읽고 항목별 실제 행 근거를 기록한다. 구현 전에는 모든 기준의 작업 연결 또는 누락을 명시한다.
- 경계 시나리오: 문서·기준·누락 파일의 생성 후 이전 검토는 stale이다. 연결되지 않은 기준은 지적으로 남는다. 작은 수정은 brief로 근거를 짧게 남긴다.
- 실패 시나리오: 준비 후 문서가 바뀌거나 근거 행이 없거나 경로를 벗어나면 기록을 거부하고 기존 이력을 보존한다. 실행 출처 조회만으로 호스트 수용을 주장하지 않는다.

## 수용 기준

정의와 필수 여부의 정본은 work.json이다. 관련 기준: `AC-1`, `AC-2`, `AC-3`.

## 결정과 열린 질문

기존 WWW 하네스 확장으로 진행한다. 의미 판단은 에이전트, 형식·위치·현재성 검사는 코드가 맡는다. 수용 기준 정의는 work.json 한 곳에 유지한다. 새 검토는 기존 실제 검증과 필수 독립 검토를 대체하지 않는다. 작은 변경과 상세 기능의 차이는 brief/full로 기록한다. 추가 사용자 결정이 필요한 제품 범위는 현재 없다.
