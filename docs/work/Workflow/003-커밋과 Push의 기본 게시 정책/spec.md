# 커밋과 Push의 기본 게시 정책

## 사용자 결정

개인용 WWW 프로젝트에서는 명시적 “커밋해” 실행 요청을 commit + push의 기본 흐름으로 처리한다. “로컬에만 커밋해”는 push를 생략한다. 준비·스킬 수정·목표와 계획 작성은 실제 실행 요청이 아니다. 확인된 범위에 동일한 승인을 반복해서 요구하지 않는다.

이 결정은 이전 002 작업에서 작성한 push 제외 정책을 대체한다. 002의 명세·검증 기록은 당시 사실로 남기고 소급해 고치지 않는다.

## 이번 변경

`www-commit`, 준비 양식, 저장소 지침·공통 계약·개발 안내·카탈로그에 새 기본값을 반영한다. commit과 push를 하나의 사용자 흐름으로 잇되 로컬 이력·원격 ref·서버 색인은 다른 사실로 기록한다.

원격 URL·브랜치·공개 범위와 함께 게시될 기존 미게시 커밋을 먼저 확인한다. 다른 작업이나 미승인 이력이 섞이면 범위를 확인하고, force push·merge·release·자동 pull/rebase·ref 삭제는 포함하지 않는다. push 실패·응답 유실은 로컬 커밋과 구분하고 원격을 조회한 뒤 판단하며, 같은 변경을 다시 커밋하지 않는다.

## 연결 목표와 계획

사용자는 계획 문서도 요청했다. 제품 목표는 “WWW에서 Native에게 작업을 맡기고 실행·개입·결과를 확인하는 첫 Chat 실사용”으로 제안한다. 실행 순서는 기존 Chat 작업의 `tasks.md`에 통합하며 별도 경쟁 계획을 만들지 않는다. BoxBox 준비→opt-in 개발 하네스→Chat 구현→실제 검증→승인된 commit + push의 선후 관계와 실제 차단 조건을 명시한다.

이 계획을 작성하는 것으로 제품 구현·전역 설치·라이브 추론·현재 dirty 전체의 게시를 승인받았다고 보지 않는다. 기존 Chat의 필수 기준과 선택적 기록 복원 범위는 바꾸지 않는다.

## 수용 기준

- `AC-1`: 스킬과 연결 문서의 기본 commit + push·로컬 전용·준비 전용·원격 확인·실패 구분·금지 범위가 일관된다.
- `AC-2`: 기존 Chat 계획에 단일 목표, 단계별 증거, 연결 작업, 권한·미검증 경계를 기록하며 기존 구현 단위와 기준을 보존한다.
- `AC-3`: 문서 계약·원본 무결성·기존 테스트·타입 검사·빌드 검증이 통과하고 이번에 stage·commit·push나 제품 구현을 수행하지 않는다.

## 한계

이번 산출물은 계획과 스킬 절차다. 런타임 Git 자동화, 동시 writer 차단, 실제 원격 push 및 오류 복구를 실행 검증한 것은 아니다. BoxBox 설치·호스트 adapter·Native 실사용·Windows 검증도 완료하지 않았다.
