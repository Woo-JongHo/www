# RPA 공통 절차와 표준 하네스 및 프로젝트 공간

## 요청과 목적

사용자의 목표는 **“자동화되는 업무 설계만 다르고 모든 개발·검증·운영 절차와 방식은 같다”**이다. 같은 코드 구조와 재사용 Core로 신규 구축 비용을 줄이고, 어느 프로젝트에서도 같은 위치와 방식으로 원인을 찾으며, Case·로그·메일·빌드 결과까지 일관되게 관리한다.

2026-11-16 사용자는 누적 대화 내용을 문서화하고 실제 개발은 다른 세션에서 수행하도록 요청했다. 이번 변경은 작업 문서와 목차만이다. 역할·스킬·하네스·제품 코드·원격 RPA·설정·빌드·배포·커밋·push는 실행하지 않는다. 명세가 준비됐다는 것은 구현·운영 수락 완료가 아니다.

## 기존 작업과의 관계

- Home/002는 이미 있는 RPA/WWW 진입·공통 메뉴·작업 보드의 범위를 소유한다. 그 진행 변경과 UUID를 수정하지 않고 프로젝트 선택을 재사용한다.
- Workflow/019는 분업 계약·완료 게이트·상태도와 근거 연결의 공통 작업이다. 이 RPA 작업에서 같은 완료 엔진을 중복 구현하지 않는다.
- 이 작업은 RPA 도메인의 공통 표준과 실제 제품 연결을 소유한다. 현재 WWW 현행 기능 문서를 미래 구현 내용으로 미리 바꾸지 않는다.
- [조사 기준선](inventory.md), [설계](design.md), [다음 구현 계획](tasks.md)을 같은 UUID로 인계한다.

## 범위

포함:

1. rpa-dev 역할과 최소 RPA 스킬, 사이드바 프로젝트/대화 맥락의 실제 연결.
2. 공통 개발·변경·검증·패키징·운영 인계 절차와 단계 승격 검사.
3. 코드 배치·Core·Case·로그·결과 메일·배포물의 단일 계약과 프로젝트별 적용 검사.
4. 기존 HTML 지도를 재사용하는 업무 탐색과 Case/검증/실행 근거 연결.
5. 프로젝트 대시보드의 현재 단계·다음 행동·차단·표준·실제 실행·빌드 표시.
6. 단일 Process 시범 적용 뒤 KMpark 및 확인한 7개 프로젝트로 확대하는 검증 계획.

제외:

- 업무 알고리즘·계산·외부 입력 순서를 통일하기 위한 임의 변경.
- RPA 진입만으로 업무 실행, 메일 발송, 배포 또는 에이전트 호출.
- 범용 스케줄러·큐·상시 모니터링 플랫폼·자동 모델 라우터의 전면 신규 구축.
- pstack 전체 이식, 기본 다중 설계 경쟁, 일괄 주석 삭제, 필수 TLA+/Lean 설치.
- 원격 기존 코드/배포물 정리·삭제와 과거 draft 계약의 자동 승격.
- 절감 시간·ROI·개선율의 추정 표시. 사용자 데이터에 결함을 주입하는 운영 테스트.

## 통일의 의미

모든 프로젝트는 같은 절차·필수 질문·계약·기록·검사 방식으로 관리한다. 업무별 입력·출력·Case·기술 어댑터는 다르다. 해당하지 않는 항목은 근거를 가진 적용 제외로 판단하며 미구현을 적용 제외로 숨기지 않는다. 같은 명령·라이브러리·바이너리를 모든 프로젝트에 강제하는 것이 아니다.

표준 규칙은 한 곳이 소유하고 역할·스킬·화면은 참조한다. Python 업무 검사를 WWW TypeScript에서 다시 구현하지 않는다. 표준 버전 변경은 프로젝트별 차이·회귀·배포 상태를 추적한다.

## 사용자 동선

1. 사이드바에서 RPA 프로젝트를 연다. 원본 경로·프로젝트 ID·표준/소스 버전·현재 작업과 누락을 읽는다. 대시보드만 볼 때 Native/업무 실행을 시작하지 않는다.
2. 대화에서 신규 개발·수정·조사를 요청하면 rpa-dev가 현재 단계와 권한에 맞는 스킬을 선택한다. 이미 허용된 같은 범위는 이어가며 단계마다 의례적 승인을 반복하지 않는다.
3. 하네스가 입력·범위·필수 산출물을 검사하고 실행 결과를 현재 소스/기준에 연결한다. 빠진 검증이나 알려지지 않은 부수효과는 통과로 바꾸지 않는다.
4. 대시보드에서 막힌 Case를 선택해 업무 지도 → Task/Unit → 코드·로그·테스트·스크린샷·결과물로 이동한다.
5. 패키징 후 실제 배포물을 검사하고 배포·환경 확인·운영 수락을 별개로 기록한다. 변경이 생기면 영향 범위와 현재성에 따라 필요한 단계로 복귀한다.

## 수용 기준과 검증 시나리오

정의·필수 여부·결과의 정본은 [work.json](work.json)의 criteria다. 다음은 기준 ID를 연결한 시나리오이며 현재 모든 구현 결과는 미검증이다.

| 기준 | 확인할 시나리오 |
|---|---|
| RPA-ENTRY | A/B RPA와 WWW를 전환해 역할·경로·세션·권한·출력 격리, 누락 스킬과 오래된 context, 실제 호스트 제공/행동 관측 |
| RPA-FLOW | 필수 산출물 누락·실패·소스/기준 변경 시 승격 거부, 정상 대조 허용, 작은 수정의 영향 근거 재사용 |
| RPA-STRUCTURE | 단일/다중 Process 배치·코드 참조와 기존 주소/행동 보존 |
| RPA-CORE | Core 버전/해시 불일치·로컬 수정 감지, 덮어쓰기 차단, 선택적 기술 기능의 명시 적용 |
| RPA-CASE | 같은 Case의 여러 발생 건, 부분 실패, 재개/재실행 불가·미확인, 테스트/증거 누락 |
| RPA-LOG | 공통 사건 필드·부분 결과·프로젝트별 호환 로그·비밀 제거·관측 누락 |
| RPA-MAIL | 동일 공통 양식, 업무 성공/전달 실패, 발송 전 preview, 중복·발송 여부 불확실 |
| RPA-PACKAGE | 누락 파일·다른 버전 혼입·비밀 포함·manifest 불일치 차단, 정상 배포물 대조 |
| RPA-MAP | GMB 지도 재사용, KMpark 4 Process, 원본 변경 후 snapshot stale, 코드/Case/근거 탐색 |
| RPA-DASHBOARD | 자료 없음·부분 수집·실패·오래됨·다른 환경, 원본과 수치 일치, 상세 근거 이동 |
| RPA-EVIDENCE | 정상·경계·실패·부분 실패·재실행, 실제/모의 구분, 재현 가능한 반례·필수 화면 직접 확인 |
| RPA-ADOPTION | 서로 다른 두 프로젝트 시범 → KMpark → 7개 적용 표, 운영 미실측은 별도 미수락 |

## 프로젝트 대시보드

| 영역 | 값 | 원본/판정 원칙 |
|---|---|---|
| 현재 단계·다음 행동 | 단계·필수 미충족·차단 이유·다음 작업 | 공통 단계 결과와 현재 근거. 문서 존재만으로 승격하지 않음 |
| 표준 적용 | 구조·Core·Case·로그·메일·빌드의 적용/불일치 | 해당 표준 버전의 검사 결과와 범위 |
| 검증 | 필수 Case의 통과·실패·미실행·오래됨 | 같은 코드/기준/환경에 적용 가능한 실제 결과 |
| 최근 실제 실행 | 시각·소스/빌드·환경·처리량·부분 결과 | Run 증거. 수집하지 못한 값은 미확인 |
| 주의할 Case | 영향 Unit·원인·재개 조건·증거 | Case 정의와 실제 발생 건을 구별 |
| 빌드·배포 | 버전·manifest 검사·설치 대상·운영 수락 | 빌드/배포/공개/운영 수락을 별개로 표시 |
| 흐름 요약 | Process·Task·Unit과 작은 지도 | 실제 map snapshot, 전체 생태계 보기 연결 |

기간·분모·단위·집계 규칙을 표시한다. 실패 후 성공한 실행을 합칠 때 원본 이력을 보존한다. 없는 값은 0이 아니며 정적 지도·test 참조는 실시간 상태나 통과 증거가 아니다. 첫 범위에서는 성과 점수·추정 절감률을 추가하지 않는다.

## 작고 단단한 설계 원칙

기본은 rpa-dev 하나와 5개 스킬이다. 유지보수는 build의 요청 유형, 정합성은 verify의 모드, 배포/운영 수락은 package 이후 권한 있는 단계로 표현한다. 책임과 인터페이스가 실제로 커질 때만 분리한다.

pstack에서는 짧은 사전 점검(완료·선행·공유 상태·최소 분해), 명확한 위임, 실제 문제 경로 재검증과 증거 기반 반박을 참고한다. 별도 프레임워크나 일상적인 Arena를 추가하지 않는다. 상태도·TLA+·Lean 도입을 표준 준수의 필수 요건으로 삼지 않는다.

## 성숙도 기준선과 목표

현재 총평 6/10, 목표 9/10은 이 대화의 설계 성숙도 판단이다. 정량 벤치마크·장애율·절감률·산술 가중 평균이 아니다. 문서 작성이나 테스트 개수만으로 점수를 올리지 않는다.

| 축 | 현재 판단 | 목표 |
|---|---:|---:|
| 코드 구조·Core | 8 | 9 |
| 개발·유지보수 절차 | 6 | 9 |
| Case·검증 | 5 | 9 |
| 로그·결과 메일 | 6 | 9 |
| 빌드·배포·운영 수락 | 4 | 9 |
| 통합 관리·탐색 | 5 | 9 |

로그·메일 점수는 공통 기반 조사에 대한 잠정 판단이다. 전체 프로젝트 출력 일치와 운영 검증은 아직 확인하지 않았다. 9점 재평가는 조사 대상 7개에 동일한 단계/검사 적용, 누락 시 차단, 변경 후 현재성 재평가, Case부터 로그/메일/배포물까지 추적, 실제 환경 수락 또는 명확한 미수락 기록이 확인될 때 수행한다. 개별 운영 수락이 미완료라면 개발 표준 적용과 분리해서 보고한다.

## 결정과 인계

범위와 관찰 가능한 목표는 정리됐다. 정확한 계약 포맷·정본 위치·현재 표준과의 버전 호환·첫 두 시범 프로젝트는 다음 조사/설계에서 확정한다. 자동화 업무 자체를 바꾸는 결정을 추측하지 않는다.

별도 독립 의미 검토와 제품/원격 실행 검증은 이번 문서화에서 수행하지 않았다. 다음 세션은 같은 UUID로 작업을 찾고 현행 소스·권한·검토 정책을 확인한 뒤 시작한다. 명세가 구현 권한이나 외부 실행 승인을 만들지 않는다.
