# 다른 세션의 구현 계획과 인계

## 첫 읽기와 실행 경계

작업 ID는 `work-f5711e8a-33a0-41da-9f07-e2e956a43219`다. 먼저 [spec.md](spec.md), [design.md](design.md), [inventory.md](inventory.md), [work.json](work.json)을 읽는다. 이전 대화가 없어도 이 네 파일에서 목적·현재 근거·범위·다음 행동을 확인할 수 있어야 한다.

현재 권한은 문서 작성뿐이다. 제품·스킬·하네스·원격 RPA·운영 데이터·메일·빌드·배포·commit/push를 변경/실행하지 않았다. 다른 세션에서 직접 구현 요청을 받으면 같은 UUID에 요청·경로·대상 저장소·검증 명령·외부 행동 권한을 연결한다. 문서에 적힌 미래 범위를 기존 실행 승인으로 읽지 않는다.

이 임시 대화에서는 서브에이전트를 실행하지 않았다. 아래 모델/병렬 계획은 다음 메인 세션에서 적용할 후보다. Sol이 공통 계약·권한·통합, Luna는 목록/축자 대조, Terra는 경계가 명확한 구현/검증을 맡는다. 독립 검토는 읽기 전용 별도 패스로 실제 가용 모델·적용 정책·원문 근거를 회수한다.

- 행동: 7개 프로젝트의 원본 checkout·표준·Core·map·Case·로그·메일·빌드 현황을 같은 표로 정리한다. 이미 있는 검사와 실제 누락을 구별한다. 문서/코드 차이는 원인으로 단정하지 않고 확인한다.
- 통과: 대상별 수정 권한과 파일 소유, 필요한 실제 환경/계정·외부 변경 여부가 확인되고 spec/consistency 검토를 준비할 수 있음. 비밀은 수집 문서에 복사하지 않음.

## 점검 결과와 재개 상태

현재는 문서화만 수행했다. JSON schema·로컬 링크·기준별 설계/작업 연결은 별도 형식 점검 대상으로 두며 제품/운영 테스트와 독립 의미 검토를 대신하지 않는다. 실제 검증 결과와 verification.md는 검증 시 생성한다.

기본 순서: 0 → 1 → {2A, 2B, 2C} → 3 → 4 통합 → 5 → 6. 4의 독립 UI 저작은 읽기 계약 동결 뒤 병렬화할 수 있다. 공통 파일을 여러 워커가 동시에 수정하지 않는다. 실패 시 원인·범위·재현을 먼저 확인하고 같은 가정으로 호출을 반복하지 않는다.

다음 세션의 첫 행동은 단위 0이다. 기존 메인 세션의 dirty 파일을 되돌리거나 같은 이름의 오래된 사본으로 개발하지 않는다. 커밋·push·실운영 실행에는 별도 직접 요청 정책을 유지한다.
