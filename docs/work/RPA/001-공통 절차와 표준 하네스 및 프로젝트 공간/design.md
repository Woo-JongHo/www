# RPA 역할·스킬·하네스 설계안

## 기준선과 재사용

이 문서는 미래 설계안이다. 사실은 [inventory.md](inventory.md), 목표는 [spec.md](spec.md), 기준의 정본은 [work.json](work.json)이다. 현행 sidebar/project/session, work.json reader·검증/보고서 core를 우선 재사용한다. 이전 WWW의 RPA 계약과 Python 표준화 도구를 조사해서 겹치는 책임을 합친다.

이번 문서화에서는 `agents/rpa`나 실제 SKILL.md를 생성하지 않는다. 아래 이름·경로는 구현 후보이며 등록/발견/실행된 것으로 읽지 않는다.

## 역할과 최소 스킬

제안 역할은 rpa-dev 하나다. 예상 위치는 `agents/rpa/AGENT.md`, 스킬 정본 후보는 `skills/rpa/`다. discovery 방식은 실제 호스트 지원을 확인해 정하고 정본 문서를 복제하지 않는다.

| 최소 스킬 | 입력과 소유 결과 |
|---|---|
| rpa-intake | 요청·기존 코드/지도 → 범위·사실·미확인·작업 연결 |
| rpa-design | 요구·사실 → Process/Task/Unit·Case·재실행·검증 설계 |
| rpa-build | 승인된 범위 → 코드·설정·테스트 변경, 유지보수 수정 포함 |
| rpa-verify | 대상 revision·기준 → 정상/경계/실패/부분 실패/재실행과 정합성 근거 |
| rpa-package | 검증된 소스 → 공통 빌드 산출물 검사, 권한 있는 배포/운영 인계 |

스킬 수와 업무 단계 수는 일치할 필요가 없다. 보고·정합·유지보수·운영 수락은 공통 계약과 모드로 시작한다. 서로 다른 실패/권한/입출력이 커질 때만 독립 스킬로 나눈다. 운영 수락은 구현/패키징 완료와 다른 상태로 유지한다.

## 프로젝트 진입과 실제 실행 연결

sidebar 선택 → 프로젝트 실경로/ID·세션·표준 프로필 읽기 → 대시보드 → 대화 요청 → rpa-dev/스킬 선택 → 사전 검사 → 호스트 실행 → 산출물/근거 검사 → 다음 행동.

프로젝트 유형은 기존 등록 식별을 사용한다. 폴더 이름만 보고 RPA로 승인하지 않는다. 프로필의 최소 정보는 표준 버전·map/entry/검사/패키지 계약 위치와 기술 capability다. 비밀은 프로필에서 분리한다.

실행 binding은 프로젝트 ID/실경로, session/thread, 작업 ID, 직접 요청/권한, 소스·표준·역할·스킬 내용 식별을 연결한다. 실행/승인 중 전환 보호와 늦은 응답 격리는 기존 session 경계를 재사용한다. WWW 탭에 RPA 역할이 섞이거나 다른 RPA 결과를 현재 카드에 반영하지 않는다.

문서를 전달한 사실과 호스트의 의미상 수용은 구별한다. 먼저 제공 bytes/경로·호출·실제 행동/응답의 근거를 회수하고, 관측이 없으면 unconfirmed로 남긴다. 스킬/명령이 누락되면 이유와 복구 경로를 보여주며 조용히 일반 실행으로 우회하지 않는다.

## 하네스의 세 책임

| 부분 | 책임 |
|---|---|
| 공통 제어 | 작업·요청·권한·단계·검증 현재성·승격·보고 연결 |
| RPA 검사 어댑터 | Python 구조·Core·설정·Case·로그·메일·배포물 검사 도구를 실제로 호출 |
| 제품 투영 | 대시보드·지도·보고서에 제한된 읽기 결과를 제공 |

규칙 정본은 단일 소유다. TS 하네스가 Python 업무 규칙을 다시 쓰거나 renderer가 완료 조건을 재판정하지 않는다. 프로젝트 도구의 실행 가능한 경로/명령은 승인된 프로필과 실제 권한 범위에서 검증하며, 조회 시 스크립트를 실행하지 않는다. 저장소 쓰기 가능자가 만든 해시를 OS 격리·암호학적 신뢰 경계로 부르지 않는다.

## 코드와 Core 표준

Entry → Process → Task → Unit을 기본 실행 책임으로 유지한다. Process는 순서·반복·데이터 전달, Task는 업무 판단, Unit은 실패·재실행·계측 경계, Core는 기술 기능을 소유한다. 같은 프로세스의 임의 Task 간 실행 import와 업무 정책의 Core 유입을 검사한다.

공통 Core는 작은 인터페이스 뒤에 로깅·경로·session·SMTP 같은 기술 구현을 숨긴다. 브라우저·Excel·UI 등 capability의 적용 여부를 명시한다. 공통 버전/관리 파일·로컬 변경 감지·프로젝트별 회귀를 연결하고 원본 손실 없이 갱신한다. 모든 Core 파일의 byte 동일성을 무조건 목표로 삼지 않는다.

## Case와 실행 증거

Case 정의 ID는 설계의 조건·기대·처리·영향·재개·검증을 연결한다. 발생 ID는 실제 run/task/unit·시각·입력 식별·관측·결과·증거를 연결한다. 프로젝트 namespace를 붙여 p1/t1 같은 주소 충돌을 막는다. 입력 원문과 비밀은 그대로 로그에 넣지 않는다.

부수효과와 재실행은 읽기/로컬쓰기/외부쓰기와 별개 정책이다. 외부 쓰기라는 이유만으로 항상 불가, read라는 이유만으로 항상 안전으로 판정하지 않는다. unknown은 별도로 남긴다. 동일 Case의 여러 발생과 부분 결과, skipped/reused/uncertain을 잃지 않는다.

표준 검증은 공통 질문을 적용하되 프로젝트별 실환경/모의 테스트를 구별한다. 근거는 소스·기준·표준·환경·범위·검증 시도에 결박한다. 화면 증거는 `.www/evidence/<work-id>/<attempt-id>/screenshots/` 등 승인된 로컬 저장 위치에 두고 직접 열어 확인한다. 상태·Case·지도·메일 preview·빌드 구조의 필요한 캡처를 기록한다. 다른 머신에서 자동 접근 가능하다고 가정하지 않는다.

## 로그·메일·빌드의 공통 산출물

로그는 실행 요약·개발 사건·오류·Unit 단계·Case 발생을 공통 필드로 제공하고 기존 프로젝트별 업무 로그와의 호환을 관리한다. 한 번의 실행에서 업무 처리·파일 출력·외부 게시·메일 전달 결과를 분리한다.

메일은 실행/버전·처리량·업무/전달 결과·Case/조치·산출물·근거를 공통 template에서 생성한다. 업무별 표는 데이터로 주입한다. preview 생성과 실제 발송을 분리하고 send 결과 불명확을 성공/실패로 단정하지 않는다. 재발송에는 기존 발송 근거와 권한을 확인한다.

배포물 역할 구조 제안:

```text
배포물/
  실행기
  runtime/
  config/
  logs/
  output/
  version.json
  manifest.json
  운영안내
```

정확한 파일명과 onedir/다른 패키지 형식의 대응은 기존 release 계약을 대조해 확정한다. 바이너리/업무 설정/수정 가능 항목/생성 디렉터리/운영자 제공 비밀의 경계를 명시한다. manifest의 포함 범위·버전/소스·체크섬은 빌드된 실제 파일에서 검사한다. 패키지 검사 성공을 설치·운영 수락으로 올리지 않는다.

## 지도와 대시보드

기존 GMB `rpa-NODE-MAP`의 추출·snapshot·Task/Unit 카드와 근거 상세를 평가해 재사용한다. 외부 프로젝트의 생성 HTML/JS를 권한 있는 앱 컨텍스트에서 임의 실행하지 않는다. 데이터 정규화와 WWW 안의 안전한 렌더링을 우선 검토하며 실제 파일 복사/의존 추가는 구현 때 결정한다.

첫 동선은 프로젝트 대시보드 → 작은 흐름 요약 → 전체 지도 → Unit → Case/코드/테스트/실제 발생 → 원래 위치 복귀다. 기존 WWW 책임 지도와 RPA 업무 지도를 같은 의미로 합치지 않되 같은 탐색/근거 방식으로 연결한다. snapshot의 시점·원본 변경·없음·일부 누락을 표시한다.

## 영향 파일과 소유 계획

- Sol: 공통 타입·권한·상태·승격 core, 프로젝트 역할 binding, package/lockfile·generated snapshot 단독 소유.
- Terra: 동결된 인터페이스의 UI·Python 검사 어댑터·독립 테스트 파일을 범위별 소유. 하나의 파일에 병렬 쓰기하지 않는다.
- Luna: 원본·차이·필드 목록 축자 대조. 큰 설계 문서를 전부 읽게 하지 않고 필요한 파일과 판정 범위를 전달한다.
- 예상 WWW 영향: `src/{projects,native-session,main,preload,shared,renderer,dashboard}.ts(x)`와 지도/보고 뷰, 선택된 `scripts/workflow/` 공통 seam. 실제 파일 집합은 착수 때 현행 소스로 좁힌다.
- 예상 RPA 영향: 프로젝트 프로필·표준 계약·Python 검사·Core/Task 경계·메일/빌드 어댑터. 여러 저장소에 대한 별도 직접 권한과 백업/검증 범위를 먼저 정한다.

설계 문서 작성은 위 경로의 수정 승인이 아니다. 정확한 신규 파일명과 검사 명령은 다음 기준선 조사에서 확정한다.

## 기준별 설계 연결

| 기준 | 설계에서 확인할 지점 |
|---|---|
| RPA-ENTRY | 프로젝트/세션 binding, 제공과 수용 구분, 조회와 실행 분리 |
| RPA-FLOW | 공통 제어의 단계·산출물·현재성·승격 |
| RPA-STRUCTURE | Entry/Process/Task/Unit 배치와 기존 동작 보존 |
| RPA-CORE | 공통 인터페이스·버전·관리 파일·어댑터·회귀 |
| RPA-CASE | Case 정의/발생 ID, 부수효과·재개·근거 |
| RPA-LOG | 공통 사건과 호환 로그, 부분 결과·비밀 제거 |
| RPA-MAIL | 공통 template, preview/발송/불확실 구분 |
| RPA-PACKAGE | 실제 배포물 계약·manifest·포함 파일 검사 |
| RPA-MAP | 기존 GMB 지도와 다중 Process, 안전한 데이터 렌더 |
| RPA-DASHBOARD | 단계/표준/Case/실행/배포의 원본 기반 읽기 |
| RPA-EVIDENCE | 소스·기준·표준·환경·시도와 반례/캡처 연결 |
| RPA-ADOPTION | 단일 두 프로젝트·KMpark·7개 확대, 운영 미수락 분리 |

## 위험·검토·미결정

모델/코드/운영의 서로 다른 사실, 계약 복제, 프로필 스크립트 오실행, Core 강제 덮어쓰기, 메일 중복, 누적 DB 재반영, stale snapshot과 실제 결과의 혼합을 주요 위험으로 본다. 대응 기준은 work.json과 tasks.md에 연결한다.

독립 의미 검토·제품 검증·운영 수락은 미실행이다. 다음 세션은 적용 가능한 최신 검토 정책과 사용자 권한을 확인하고 spec/consistency 검토를 기록한다. 미래 검토 모델의 가용성을 현재 실행 사실로 쓰지 않는다.
