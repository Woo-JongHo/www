# 중앙 저장·로컬 실행과 GitHub 동기화 — 고민 기록

기록일: 2026-11-16
상태: 중앙화 개발 보류. 추후 검토를 위한 논의 기록이며 구현 승인·완료 명세가 아니다.

## 현재 결론

개인용이므로 우선 GitHub를 중심으로 운영한다. 작업한 컴퓨터에서 공유할 코드·문서를 commit·push하고, 다른 컴퓨터에서는 git pull 후 필요하면 의존성을 설치하고 npm start로 앱을 실행한다.

- 동기화는 Git push/pull이다. npm start 자체가 동기화 기능은 아니다.
- 코드와 Git 추적 대상인 작업 원장·명세·지도·보고서는 게시된 버전 기준으로 공유한다.
- Codex 대화·실시간 진행·미커밋 수정·Git에서 제외된 결과물은 자동 공유되지 않는다.
- Codex와 RPA 실행은 각 프로젝트의 실제 컴퓨터에 둔다.
- 중앙 API·DB·실행기 연결·실시간 동기화 개발과 이를 위한 원격 백그라운드 작업은 시작하지 않는다.
- 사용자 최종 요청은 “고민만 적어두자 나중에 찾아서할수잇도록”이다. 이 기록을 실행 승인으로 사용하지 않는다.

## 처음 해결하려 했던 문제

세 곳에서 같은 WWW 앱을 사용한다. Figma처럼 어디서 앱을 열어도 같은 프로젝트 공간·전체 프로세스 진행도·대시보드·설계도 맵·보고서·결과물을 보고 싶었다. 다만 로컬 Terminal Codex가 파일과 시스템을 쉽게 다루는 장점과 각 컴퓨터의 자원 활용은 유지하고 싶었다.

고객사 RPA의 대상 시스템은 Windows이므로 고정 Windows 한 대에서 실제 개발·실행이 필요하다. WWW 개발과 Windows RPA 개발의 결과를 반대 컴퓨터에서도 확인하는 것이 대표 시나리오다.

## 논의한 중앙화 대안 — 현재는 보류

```text
여러 WWW 앱
    │ 같은 프로젝트 공간 조회·작업 요청
    ▼
woojongho Mac mini 중앙 API
    ├─ DB: 프로젝트·대화·진행·승인·검증·사용자 확인
    ├─ 공유 자료: 지도·보고서·로그·결과 파일
    └─ 담당 실행기로 요청 전달
            ├─ Mac 실행기: Mac 프로젝트·Codex
            └─ Windows 실행기: RPA 프로젝트·Codex·고객사 시스템

GitHub: 코드·명세 정본과 CI/CD
```

중앙화는 모든 AI와 파일을 Mac mini로 옮기는 뜻이 아니었다. 파일은 프로젝트 담당 컴퓨터에 두고 어느 앱에서든 그 실행기에 작업을 요청하는 방향을 논의했다. 다른 컴퓨터로 미커밋 파일을 자동 이동하거나 실시간 공동 편집하는 것은 필수 요구가 아니었다.

## ‘언제 DB에 저장하는가’에 관한 정리

중앙화를 재검토한다면 개발 완료까지 기다리지 않고 데이터 종류별로 저장한다.

| 대상 | 논의한 저장·공유 시점 |
|---|---|
| 대화·진행·승인·오류 | 사건 발생 후 중앙에 전송·저장 |
| 기존 작업 원장·지도·보고서 | 유효한 로컬 변경을 수집하고 출처와 함께 저장 |
| 검증·결과 파일 | 결과 생성·전송 완료 시 등록 |
| 코드 게시 버전 | GitHub push 확인 후 작업과 커밋 연결 |
| 업무 완료 | 실행 성공과 별도로 사용자 확인 시 확정 |

공유 확정 시점은 중앙 서버가 영속 저장한 뒤 다른 앱에 알리는 시점이다. 전송 중·저장 실패를 공유 완료로 표시하지 않는다. 유효하지 않은 자료는 마지막 정상 자료를 유지하고 오류를 표시한다.

기존 work.json·명세·검증·보고서 파일을 정본으로 유지하고 DB는 공유 조회용으로 수집하는 방향을 선택했다. DB와 기존 파일을 서로 경쟁하는 원본으로 만들지 않는 것이 중요하다.

보고서의 발행 당시 판단과 현재 작업 상태를 구분하는 방안을 제안했으나 구체적인 버전·발행 정책은 확정하지 않았다.

## GitHub 방식과 중앙화의 차이

| 항목 | 우선 선택한 GitHub 방식 | 보류한 중앙화 방식 |
|---|---|---|
| 공유 시점 | commit·push 후 다른 기기에서 pull | 중앙 저장 후 다른 앱에 알림 |
| 공유 자료 | Git 추적 대상 파일 | API로 수집한 대화·진행·자료·결과 |
| 미게시 개발 상태 | 다른 기기에 자동 반영 안 됨 | 유효한 로컬 자료부터 공유 가능 |
| 다른 컴퓨터에서 실행 지시 | 별도 연결 없이는 불가 | 프로젝트 담당 실행기로 요청 전달 |
| 운영 부담 | Git·로컬 앱 관리 | 서버·인증·DB·백업·실행기·호환성 관리 |

혼자 사용하는 현재 단계에서는 GitHub 방식이 단순하다. 실시간 진행 공유·원격 작업 지시·Git 외 자료 조회의 불편이 실제로 커질 때 중앙화 필요성을 다시 판단한다.

## GitHub 방식에서도 확인할 사항

- 지도·보고서가 실제 Git 추적 대상인지, 다른 컴퓨터에서 같은 자료를 읽는지 확인한다.
- 로컬 절대경로가 다르므로 프로젝트 등록 경로·자료 조회 경로를 점검한다.
- 생성된 지도나 보고서의 재생성 명령·기준 버전을 구분한다.
- 고객사 자료·비밀키·대용량 로그를 GitHub에 무조건 추가하지 않는다. 사용자 설명상 중앙 저장 허용과 GitHub 게시 허용을 동일하게 취급하지 않는다.
- 로컬 미커밋 변경이 있는 상태에서 무조건 pull하거나 reset·stash·덮어쓰지 않는다.
- 의존성이나 빌드가 바뀌면 pull 후 설치·재시작이 필요할 수 있다.

## 중앙화를 재개한다면 유지할 조건

아래는 중앙화 대안을 논의할 때의 조건이며, 현재 구현 지시가 아니다.

- 본인 전용, 허용 기기만 사설 접속.
- 앱 UI와 실행기 수명 분리: UI를 닫아도 실행기 소유 작업은 지속. 컴퓨터 종료·절전 중 실행 지속을 보장한다는 뜻은 아님.
- 실행기 오프라인 중 새 요청은 중앙 대기 저장 후 연결 복구 시 실행.
- 중복 사건·순서 뒤바뀜·재전송 처리. 실행 여부가 불명확한 RPA를 무조건 재실행하지 않음.
- 마지막 정상 자료·동기화 시각·미게시 변경·실패 상태 구분.
- 서버는 main CI 성공 후 진행 작업 종료를 기다려 배포. 신규 작업 잠시 대기.
- 배포 실패 시 안전한 경우 이전 정상 버전 복귀. DB·결과물 보존.
- 앱은 릴리스 업데이트 다운로드 후 사용자 재시작 승인으로 설치.
- 과거 Codex 대화 이관은 후속. 기존 대화 삭제하지 않음.
- 기존 WWW를 확장하고 외부 제품은 우선 구조 참고 대상으로만 사용.
- 원격 구현은 woojongho의 별도 작업 공간·브랜치·프로세스·포트·DB·산출물 경로로 격리. 기존 개발 프로세스에 영향 금지.
- SSH 단절·노트북 종료에도 지속할 실행 소유자·로그·재접속 경로를 실제 확인.

## 참고 자료와 검토 한계

- 사용자 제공 문서: 다운로드 폴더의 `WWW_중앙저장_로컬실행_아키텍처_및_오픈소스_비교.md`.
- 보고서 구조 논의: https://chatgpt.com/share/6afaa95d-ece8-83ee-8de5-78289b08ce51
- 문서의 HAPI·Happier 비교는 중앙 Hub·로컬 Runner·백그라운드 실행·다중 클라이언트의 참고 후보다. 이 작업에서 외부 제품의 현재 구현·Windows RPA 호환성을 독립 검증하지 않았다. 채택·포크를 결정하지 않았다.
- 이전 중앙화 요구 명세는 세션 산출물 `.gjc/_session-01a1e30d-c804-75c4-a080-b10c22682e35/specs/deep-interview-www-central-storage-local-execution.md`에 저장됐다. 마지막 사용자 결정으로 구현은 보류됐으므로 이 과거 명세를 현재 실행 승인으로 읽지 않는다. 세션 산출물은 다른 컴퓨터에 Git으로 공유된다고 보장하지 않는다.
- SSH woojongho 읽기 조회만 수행했다. 원격 worktree 생성·중앙화 구현·DB 설치·서비스 배포는 하지 않았다. 기존 `www-architecture` tmux 세션은 변경하지 않았다.

## 나중에 재개할 때

1. GitHub push/pull 운영에서 실제로 불편했던 사례를 수집한다.
2. 게시 자료 공유만 필요한지, 실시간 진행·대화·원격 실행도 필요한지 다시 구분한다.
3. 기존 저장소·각 컴퓨터의 현재 변경과 프로세스를 확인한다.
4. 파일 정본과 중앙 조회 데이터의 책임·저장 시점·복구 규칙을 설계한다.
5. 별도 실행 승인 후 작은 수직 기능부터 구현·검증한다.
